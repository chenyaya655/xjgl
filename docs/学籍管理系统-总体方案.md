## 3. ★ 异动工作流（本方案的核心）

### 3.1 为什么自研「可配置审批流」而不是套 BPMN 引擎

你的核心诉求是「**同县区转学县区只审一次，同市转学市只审一次**」。这不是普通的条件分支，而是**流程实例化时按实际组织去重合并**——BPMN 要表达它得堆一堆排他网关，业务人员根本改不动。

所以设计成：**节点用「组织解析器」描述，实例化时解析出真实组织，相同组织的节点自动合并。** 业务人员看到的是「加一个节点 → 选这是哪一级（转入校/转入县/转入市/转出校/…） → 选审核角色 → 选是否必经」，不需要懂任何流程建模语言。

> 备选：Elsa Workflows 3（图形化强，但上述合并语义仍要自定义 Activity，且业务人员要学 BPMN 概念、还有在途单据的版本迁移问题）。**我推荐自研**，见第 15 章 Q1。

### 3.2 异动类型管理（独立模块）

`stu_change_type`

| 字段 | 说明 |
|---|---|
| `Code` / `Name` | 异动代码（如 `TRANSFER_IN`）/ 异动名称（如「转入」） |
| `CategoryCode` | 异动分类（转学类 / 休复类 / 退学类 / 毕业类 / 其他） |
| `BeforeStatus` → `AfterStatus` | 该异动导致的学籍状态变化（码值引用微代码「学籍状态码」） |
| **`MaxApproveLevel`** | **审核终止级别：校 / 县 / 市 / 省** —— 你的「需要哪一级审核完成就算结束」 |
| `NeedPeerSchoolConfirm` | 是否需要对方学校确认（转学 = 是，休学 = 否） |
| `AffectGrade` / `AffectClass` | 是否影响年级 / 班级 |
| `AllowCrossSchool` | 是否允许跨校 |
| **`ApplyTimeRule`** | **异动时间控制**：允许申请的起止日期、是否限定学期、是否允许跨学年、每年可申请次数上限 |
| **`GradeScope`** | **年级控制**：允许申请的年级集合（如毕业年级禁止转学）、最小/最大年级 |
| `FlowTemplateId` | 绑定的流程模板（当前启用版本） |
| `RequireAttachment` / `AttachmentTypes` | 是否必须上传证明材料及类型 |
| `Sort` / `IsEnabled` / `Remark` | — |

**模块功能：** 增删改查、启用停用、排序、**流程设计**跳转、时间与年级规则配置、导入导出、复制。

### 3.3 流程模板设计

> ⚠ **下表已按最终实现校正。** 本节写于设计阶段，字段名与实现有出入
> （设计稿里的 `NodeAction` / `LogOrgType` / `NodeSnapshot` / `AssigneeUserId` /
> `AllowDelegate` 在代码里**一个都不存在**，见下面的「三处与设计稿不同」）。
> 以 `src/Xjgl.Domain/Changes/ChangeTypeAndFlow.cs` 与 `ChangeApply.cs` 的实体为准。

| 表 | 关键字段（**实际实现**） |
|---|---|
| `stu_change_flow_template` | Id, ChangeTypeId, Name, **Version**, Status(草稿/已发布/已停用), PublishedTime, Remark |
| `stu_change_flow_node` | Id, TemplateId, **Seq**, **NodeName**（如「转入学校审核」）, **OrgResolver**, **RoleCode**, **MergeStrategy**(MergeToLast/MergeToFirst/NoMerge), AllowReject, TimeoutDays, IsEnabled, Remark |
| `stu_change_flow_task` | Id, ApplyId, **Seq**, **NodeName**, **OrgId**, **OrgName**, RoleCode, **ApproveLevel**, MergedFromSeqs, Status(待处理/已通过/已驳回/已跳过/已合并/已撤销), HandledByUserId, HandledByName, HandledTime, Opinion, DueTime |
| `stu_change_flow_log` | Id, ApplyId, TaskId, **Seq**, Action(提交/通过/驳回/退回/转办/撤销审核/催办/归档), OperatorUserId, OperatorName, OperatorOrgId, Opinion, **ActionTime**, ClientIp |

**三处与设计稿不同，都是落地时改的，理由记在这里**（免得读代码的人以为漏了什么）：

1. **任务上没有 `NodeSnapshot(JSON)` 单列**，改成把节点信息**摊平成普通列**
   （`NodeName` / `OrgId` / `OrgName` / `RoleCode` / `ApproveLevel`）。
   「在途单据不受流程改版影响」这个目的照样达到 —— 这几列本身就是快照。
   换来的是**能直接按组织 / 角色 / 审核级别筛待办**；塞进一个 JSON 列就得
   把整表读出来再在内存里过滤，而待办查询是全系统最热的查询之一。
2. **节点上没有 `NodeAction(Submit/Approve)`**：实现里"发起"是申请单自身的动作，
   流程节点只表达"谁来审"，因此这个枚举没有存在的必要。
3. **节点上没有 `RequireAttachment`**：它落在**异动类型**
   （`stu_change_type.RequireAttachment`）上，而不是逐个节点 ——
   "这种异动要不要证明材料"是业务规则，不该由流程配置顺手改写。
   （同一时期的 `AllowDelegate` 已删除，理由见 §24.2。）

**`OrgResolver` 组织解析器枚举**（节点按它解析出真实组织）：

`ApplicantSchool`（发起人所在学校）/ `StudentSchool`（学生当前学籍校）/ `TargetSchool`（目标/转入校）/ `SourceSchool`（原/转出校）/ `TargetCounty` / `TargetCity` / `SourceCounty` / `SourceCity` / `Province` / `FixedOrg`（固定组织）

**`MergeStrategy` 说明：**
- `MergeToLast`（**默认**）：解析到同一组织的节点合并到**序号最靠后**的那个，前面的标记为「已合并」并记录 `MergedFromSeqs`。→ 上级成为终审，符合实务。
- `MergeToFirst`：合并到最靠前的节点。
- `NoMerge`：不合并。

**`MaxApproveLevel` 截断**：实例化时只保留到「审核终止级别」的最后一个节点，之后的节点不生成。

**在途单据的稳定性**：任务实例把节点定义**冗余成普通列**（`NodeName` / `OrgId` /
`OrgName` / `RoleCode` / `ApproveLevel`，见上文「三处与设计稿不同」第 1 条），
而不是保存一个 JSON 快照列；模板改版只影响新单据。

### 3.4 实例化算法

```
输入：异动类型 → 流程模板(当前发布版本) → 节点定义列表；异动单据上下文
1. 可行性校验
   - 异动时间控制：ApplyWindowStart / ApplyWindowEnd（月-日）+ MaxApplyTimesPerYear
     （实现在 ChangeTypeAndFlow.cs；报错信息会带上允许窗口，见 ChangeFlowAppService）
   - GradeScope：学生当前年级是否在允许范围
   - 学籍状态是否允许该异动（BeforeStatusCode / AfterStatusCode 匹配）
2. 组织解析
   节点的 OrgResolver 解析成真实组织 → 落到任务上的 OrgId / OrgName
3. 截断
   按 MaxApproveLevel 保留到该级别的最后一个节点
4. 合并（核心）
   按解析出的组织分组（MergeKey = 组织 Id）
   组内按 MergeStrategy 决定保留哪个 Seq，其余 Status=已合并（写入 MergedFromSeqs）
   若同组节点解析出的组织不一致 → 降级为不合并 + 记告警日志
5. 生成 stu_change_flow_task（节点定义冗余成列，见 §3.3）；apply.CurrentSeq = 第一个有效节点
6. ⚠ 首个待办通知 —— **未实现**（设计稿写的是「站内信 + 短信 + 微信模板消息，按角色配置」）
```

> **为什么把第 6 步单独标出来**：这是"设计里有、代码里没有"的典型，而且**演示时看不出来** ——
> 待办只落在数据库里，教师**不会**收到任何主动提醒，必须自己打开「待办」页才看得到。
> 演示的人知道自己该看哪里，真实的学校不会：表现就是"单子躺在系统里没人审"，
> 而界面上一切正常。
> 要补的落点是 `ChangeFlowAppService` 里生成任务之后那一处（见
> [`ROADMAP.md`](../ROADMAP.md) 与 README「已知限制」）。

### 3.5 场景推演（请你验证这几条是否符合河南实际业务）

**流程模板 A —— 转学（6 个节点定义）**

| Seq | 节点名 | OrgResolver | 审核级别 |
|---|---|---|---|
| 1 | 转入学校提交 | `TargetSchool` | 校 |
| 2 | 转入县区审核 | `TargetCounty` | 县 |
| 3 | 转入地市审核 | `TargetCity` | 市 |
| 4 | 转出学校审核 | `SourceSchool` | 校 |
| 5 | 转出县区审核 | `SourceCounty` | 县 |
| 6 | 转出地市审核 | `SourceCity` | 市 |

推演结果：

| 场景 | 合并情况 | 最终实际流程 |
|---|---|---|
| **跨市转学**（6 个组织全不同） | 无合并 | ① 转入校 → ② 转入县 → ③ 转入市 → ④ 转出校 → ⑤ 转出县 → ⑥ 转出市 |
| **同市跨县转学** | ③ 与 ⑥ 同市 → 合并到 ⑥ | ① 转入校 → ② 转入县 → ④ 转出校 → ⑤ 转出县 → **⑥ 市局（合并审一次）** |
| **同县区转学** | ②⑤ 同县 → 合并到 ⑤；③⑥ 同市 → 合并到 ⑥ | ① 转入校 → ④ 转出校 → **⑤ 县区（合并审一次）** → **⑥ 市局（合并审一次）** |

**流程模板 B —— 休学（3 个节点）**：① 学校提交 → ② 县区审核 → ③ 市局审核，`MaxApproveLevel = 市`。

**模板 C —— 需省级审核的异动**：在 A 或 B 后追加 ⑦ 省厅审核，`MaxApproveLevel = 省`。

> 👉 **请确认这 4 个推演是否符合业务**。如果「同县区转学」你期望的是 `转入校 → 县区 → 转出校`（县区在中间审），那我们把该模板的 `MergeStrategy` 改成 `MergeToFirst` 即可，**不用改代码**——这正是配置化的价值。

### 3.6 业务人员如何调流程（不改程序）

- 入口：`异动管理 → 异动类型管理 → 选中类型 → 流程设计`
- 界面：**横向步骤条 + 节点配置面板**（新增/删除/拖拽排序/上下移），每节点配置：名称、组织解析器、审核角色、超时天数、是否必经、是否允许退回/转办、**合并策略**
- **流程预览（关键功能）**：选一个模拟学生 + 目标学校 → 实时推演出实际节点序列和合并结果，业务人员一眼就能看到「同县区会合并成几步」
- 版本管理：保存为新版本 → 发布 → 只对新单据生效；在途单据走快照
- 复制流程、导入/导出 JSON 模板、停用

### 3.7 审核操作与规则

| 操作 | 规则 |
|---|---|
| 通过 | 推进到下一有效节点；已是最后节点 → 执行「通过后动作」并归档 |
| 驳回 | 退回到**指定前置节点**或**退回发起人**，填写驳回原因，记录日志 |
| 退回上一节点 | 同上，仅退一格 |
| **撤销审核** | 限制：① 仅当前节点处理人（或上级管理员）② 后续节点均未处理 ③ 未归档。撤销后当前节点回「待处理」，写 `stu_change_flow_log` |
| 转办 / 加签（可选） | 转办给同组织同角色的其他人；加签插入临时节点 |
| 催办 / 超时 | 按 `TimeoutDays` 定时扫描 → 提醒次数递增 → 超时告警 |
| 撤回申请 | 发起人在首节点未处理前可撤回 |

**通过后动作（同一事务 + 领域事件）：**
1. 更新 `stu_student` 的学籍状态 / 学校 / 年级 / 班级（按异动类型的 `AffectGrade/AffectClass` 决定）
2. 写学籍变更流水 `stu_change_log`
3. 写异动台账（用于月报年报）
4. 目标学校确认（`NeedPeerSchoolConfirm`）= 是时生成对方学校节点
5. 发通知（申请人 + 相关管理员）
6. 失效统计缓存

### 3.8 异动申请 / 审核模块的功能清单

- **申请模块**：添加（草稿/提交）、修改（仅草稿或被驳回）、删除（仅草稿）、查看（含流转时间轴与全部附件）、导出、撤回、批量申请（同班级批量休学）
- **审核模块**：我的待办 / 我的已办 / 全部单据、审核（通过/驳回/退回）、**撤销审核**、转办、查看、导出、催办、超时列表、按组织与异动类型统计

## 4. 组织管理（教育局 / 学校 / 年级 / 班级）

### 4.1 ★ 两层建模（重要设计判断）

| 层 | 表 | 是否进组织树 | 变动频率 |
|---|---|---|---|
| **稳定组织** | `sys_org`：省教育厅 → 市教体局 → 县区教体局 → 学校 | ✅ 是（数据范围与权限的锚点） | 低（撤并校、区划调整） |
| **学年组织** | `sys_grade` / `sys_class`：挂在学校下，带 `AcademicYear` | ❌ 否 | 高（每年升级、分班） |

**为什么不把年级班级放进组织树**：一旦年级班级成为权限锚点，每年升级都要重构组织树和历史权限，且权限树会膨胀到几十万个节点。分开后，「升级」只是学年维度的一次数据操作。

### 4.2 教育局管理模块

- `sys_org`：`OrgType`(Province/City/County/School)、`Code`、`Name`、`ShortName`、`ParentId`、`PathCode`（物化路径，如 `410000.410100.410102`）、`Level`、`Sort`、`IsEnabled`
- `sys_edu_bureau`：局别、邮政编码、地址、联系电话、负责人
- `sys_org_jurisdiction`：**管辖关系覆盖表** —— 处理「省直管县（济源）」「市代管县」这类**非严格树形**关系
- 功能：增删改查、批量导入、排序、启用停用、**变更历史**（`sys_org_history`）、导出

### 4.3 学校管理模块

- `sys_school`：**学校标识码（10 位）**、学校名称、学校类型码、办别码（公办/民办）、城乡码、举办者、学制、校长、联系电话、地址、经纬度、启用状态、**撤并标记**与撤并去向
- `sys_school_history`：改名、变更归属县区、撤并 → 留痕（历史学籍数据不能乱）
- 功能：增删改查、批量导入（教育厅学校名录）、按区划/类型/办别筛选、启用停用、导出

### 4.4 年级班级管理模块

- `sys_grade`：学校、`AcademicYear`、年级码、年级名称、班主任、学生数（缓存）
- `sys_class`：学校、`AcademicYear`、年级、班级号、班级名称、班主任、教室、学生数
- 功能：**批量生成**（选学校 + 学年 + 年级 → 自动建 N 个班）、编辑、调班、**升级 / 毕业批次任务（预演 DryRun → 执行 → 回滚）**、导出

### 4.5 初始化策略

| 数据 | 来源 |

## 5. ★ 权限模型（回答你的问题）

### 5.1 三种方案对比

| 方案 | 做法 | 问题 |
|---|---|---|
| **1. 不区分** | 有某权限的人就能把它授予任何下级 | 全省统一部署下，**越权风险高**：一个县管理员可能给别的县、甚至给非管辖范围的人授权；无法表达「只能给下级授」 |
| **2. 拆成「操作权限」+「授权权限」两条** | 每个权限项变成 2 条 | 直观，但条目数 **×2**（约 60 模块 × 8 操作 = 480 → 960 条），授权界面爆炸、配置易错；而且实务中「能操作」和「能授权」的集合几乎总是一致——真正重要的「**授权范围上限**」这个维度反而没表达出来 |
| **3. 单条目 + 委派属性 + 双重硬约束** ⭐ | 权限项加 `CanDelegate`（可继续下放）标记；授权时强制 **① 子集约束** ② **范围约束** | 条目不膨胀；天然支持多级下放；越权在服务层被硬约束挡住 |

### 5.2 推荐：方案 3

**两条硬约束（服务层强制执行，不可绕过）：**

```
约束① 子集约束：A 能授予 B 权限集合 S  ⟺  S ⊆ A 已拥有的权限
约束② 范围约束：A 能操作 B 的账号      ⟺  B.OrgId ∈ A 的数据范围
                   （且 A 不能给自己授权、不能修改自己所属角色的权限）
```

**三个补充机制：**

1. **`IsDelegatable` 开关**（权限定义级，默认 `true`）：敏感权限（用户管理、权限分配、系统参数、审计日志、数据导出）设为 `false` → 只有被显式授予「委派权」的角色才能下放这类权限。
2. **超级管理员**：种子数据创建 `admin`（省厅超管），`IsSuperAdmin = true`，绕过全部权限校验（复用 ABP 的 always-allow 机制）。用于首次初始化与应急。
3. **授权变更全量审计** `sys_permission_grant_log`：谁、什么时间、把什么权限、授给谁、在什么范围内 —— **政务系统必备**。可选的「敏感权限授予需上级审批」先留钩子，本期不实现。

**逐级委派链路（完全符合你的描述）：**

```
admin（省厅超管，全部权限）
  └─ 创建省级用户 A，授予「省厅学籍管理员」角色
       └─ A 创建同级（其它省级用户）与下级（市级用户 B）并授权
            └─ B 创建县级用户 C 并授权   （B 只能授出自己有的，且只能给本市范围内的人）
                 └─ C 创建学校管理员 D 并授权
                      └─ D 管理本校用户
```

**数据范围**（与权限正交）：全部 / 本级及下级 / 仅本级 / 仅本人 / 自定义组织集合。授权时范围约束取「授权人的数据范围」。

### 5.3 权限码与授权界面

- 权限码：`{子系统}.{模块}.{操作}`，如 `Stu.Change.Audit.Approve`
- 授权界面：**子系统 → 模块 → 操作** 三级树（勾选），右侧同步显示「数据范围」下拉
- 附：权限模板（校级管理员 / 县级审核员 / 市级审核员 / 省厅管理员）一键套用；授权矩阵 Excel 导出；「我是谁、我能做什么」自查页

## 7. ★ 生僻字全链路方案（姓名必须正确显示）

### 7.1 问题本质

「𠮷」「𰻝」「䶮」这类字位于 **CJK 扩展 B/C/D/E/F/G 区（U+20000 以上，UTF-8 占 4 字节）**。系统默认中文字体（微软雅黑、苹方）**不含**这些字形 → 前端显示为 □；同时 C# 的 `string.Length` 会把一个生僻字算成 2，导致长度校验和截断出错。

### 7.2 存储层（基本无风险，但有两处要注意）

- ✅ **PostgreSQL 的 UTF-8 原生支持全部 Unicode**（不像 MySQL 需要折腾 utf8mb4），`varchar(n)` 的 n 按**字符**计。
- ⚠️ Npgsql 连接串显式 `Encoding=UTF8`；SqlSugar 全部参数化，不做字符串拼接。
- ⚠️ **避免在 PG 里对姓名做拼音/字典序排序**，用 `COLLATE "zh-x-icu"` 或 `C`，排序不保证符合中文习惯（见 7.5）。

### 7.3 后端 C# 处理（必须在框架层统一）

- **绝不使用 `string.Length` / `Substring` 做长度校验与截断** → 封装 `StringExtensions.RuneLength()` / `RuneTruncate()`（基于 `string.EnumerateRunes()`），DB 字段长度校验、导入截断、导出格式化全部走它。
- **姓名正则不能用 `^[\u4e00-\u9fa5]+$`**（会误杀生僻字）→ 改用 Unicode 属性：`\p{IsCJK_Unified_Ideographs}` + 补充平面范围 `U+20000–U+3FFFF`，或直接放宽为「不含数字/控制字符/emoji」。
- 姓名比较：`校` 与生僻字不做归一化；去空格用 Unicode 空白类。
- 拼音检索字段：能生成的用 `Microsoft.International.Converters.PinYinConverter`（**不支持扩展区**），生僻字拼音留空 → 检索时用「姓名 + 码位」双通道（见 7.5）。

### 7.4 前端显示（关键）

```css
@font-face {
  font-family: "Xjgl Rare Han";
  src: url("/fonts/plangothic-p0.woff2") format("woff2");
  unicode-range: U+20000-20FFF;   /* 按码点分片，一片约 256 字 */
  font-display: swap;
}
/* 按需再声明 p1、p2 … 分片，浏览器只下载实际用到的片 */
:root { --font-stack: "Noto Sans SC", "Microsoft YaHei", "Xjgl Rare Han", sans-serif; }
```

- **字体选型**：`Plangothic Project`（落霞孤鹜，覆盖扩展 B~I，SIL OFL 开源）或 `花园明朝 HanaMinB` / `BabelStone Han`。主字体仍用思源黑体/Noto Sans SC，生僻字由 fallback 兜底。
- **必须做 `unicode-range` 分片**：扩展区全量字体 20~40MB，不分片会拖死首屏；分片后浏览器只按需下载用到的片。
- **Element Plus 全局字体变量**统一覆盖（`--el-font-family`），避免局部回退到默认字体。
- **表格/表单/打印**所有展示姓名的地方都用同一字体栈（含 `el-table` 的虚拟滚动、`el-select` 下拉、打印样式表）。
- **小程序端**（主包 ≤2MB，不能内置全量字体）：
  1. 首选 `wx.loadFontFace()` 动态加载 woff2/ttf 分片（需 HTTPS + 域名白名单）；
  2. **兜底**：姓名用后端渲染的图片 —— `GET /api/render/name?text=𠮷田&size=32`（ImageSharp + 生僻字字体输出 PNG，带 Redis 缓存）。这个兜底在 H5 与 PC 端也能用于导出场景。
- **检测提示**：前端可用 Canvas `measureText` 探测某字是否落在 fallback（豆腐块宽度异常）→ 对未覆盖的字触发图片兜底。可作为增强项。

### 7.5 检索、排序与统计

| 场景 | 方案 |
|---|---|
| 按姓名精确/模糊查 | `LIKE` + `pg_trgm` 索引；生僻字原样匹配没问题 |
| 按拼音查 | 只对常用字生效；生僻字退化为按码位/部首（要在 UI 明示） |
| 排序 | 按 `学校 + 年级班级 + 学籍辅号` 排，**不按姓名排**；必须按姓名时用码位序 |
| 重复学籍检测 | 用身份证号 + 出生日期 + 性别，**不用姓名**做唯一键 |

### 7.6 导入导出与打印（真实痛点，必须提前告知用户）

- ✅ xlsx 本身是 UTF-8，**数据不会丢**。
- ⚠️ 但 **Excel 客户端显示的字体由客户端决定** → 用户机器没装生僻字字体时，单元格里仍显示 □。应对：
  1. 导出说明中提示安装字体（随系统提供字体包）；
  2. 提供「导出 PDF」选项，**由后端渲染并嵌入字体**（SkiaSharp/QuestPDF）→ 显示一定正确；
  3. 打印/报表（学籍卡、花名册）走 PDF 嵌入字体路线，不走"导出 Excel 再打印"。
- 导入时对超长/异常字符给出**逐行错误报告**，不要整批失败。

## 8. 学籍号规则

### 8.1 两类号，别混淆

| 号 | 谁生成 | 说明 |
|---|---|---|
| **全国学籍号** | 全国中小学生学籍信息管理系统 | 19 位，`G + 身份证号`（正式）或 `L + 规则`（临时）。**本系统只存储、不生成**，留字段与校验 |
| **学籍辅号**（省级/校级） | **本系统生成** | 见下 |

### 8.2 推荐方案：`学校标识码(10) + 流水号(6)` = **16 位**

- **学校标识码为 10 位，前 6 位即行政区划码** → 天然满足你说的「行政区划码 + 学校代码」，不用额外维护学校自编码。
- 流水号 6 位按**学校维度永久自增**（不按学年复位，避免历史撞号），单校容量 100 万。
- 唯一性：学校标识码全国唯一 × 校内流水唯一 → **全局唯一** ✔
- 例：`4141010001` + `000123` → `4141010001000123`

**为什么不推荐 14 位：** `区划码(6) + 学校自编码(2) + 流水(6)` 需要全省统一人工维护「学校自编码」，一旦分配失误就撞号；若用「学校标识码后 2 位」则同区划内必然重复，**不可行**。所以 16 位是既满足你的思路又保证唯一的最短方案。

> 若你坚持 14 位，可用 `区划码(6) + 流水号(8)`，但流水号就得按区划维度全局自增（跨校共用一个号段池，取号并发压力大、且无法从号看出学校）。**不推荐**。见 Q3。

### 8.3 实现要点

- **可配置**：`sys_code_rule` 存学籍号规则（分段模板 + 每段取值来源），`IStudentNumberGenerator` 按规则拼装 → 换规则不改代码。
- **取号并发**：`sys_sequence` 表 `UPDATE ... SET cur = cur + 1 WHERE name = 'STU_NO:{schoolId}' RETURNING cur`（原子）；Redis `INCR` 做前置缓冲，Redis 挂了回落 DB。
- **取号与建籍同一事务**；**允许跳号**（不追求连续，追求唯一与性能）。
- 唯一索引 `uk_student_no` 兜底；不加校验位（保持简单）。
- 建籍查重：身份证号哈希 + 姓名 + 性别 + 出生日期，跨校/跨区查。

```
  ├ q.photo.process     prefetch=2，消费者可横向扩
  ├ q.photo.compensate  （NAS 降级回放）
  ├ q.import.student    ├ q.export.task
  ├ q.change.notify     （异动待办/结果通知）
  ├ q.notify.sms        ├ q.notify.wechat     └ q.audit.log
Exchange xjgl.fanout(fanout,durable)   # 缓存失效广播，每节点独占队列
Exchange xjgl.dlx(direct,durable)      # → q.{name}.dlq，重试3次(指数退避)后入 DLQ + 告警
```
生产者 `mandatory` + Confirms，**关键业务走 ABP 的 Outbox 模式**（与业务事务一起提交）；消费者手动 ACK + 幂等（`msg.consumed:{id}`）；队列积压阈值告警。

### 11.5 照片存储与上传韧性

```
IPhotoStorage
 ├ NasPhotoStorage           # 主：SMB/NFS 挂载目录
 ├ LocalFallbackPhotoStorage # 降级：本机 SSD 临时目录
 └ MinioPhotoStorage         # 可选
 装饰器 ResilientPhotoStorage：Timeout(5s) → Retry(3, 指数退避) → CircuitBreaker(失败率>50%且样本≥20 → 熔断30s) → Bulkhead(并发8)
```

目录规范：`{nas}/photo/{学校标识码}/{学籍辅号}.jpg`、`{nas}/thumb/..._s.jpg`、`{nas}/export/{yyyyMM}/{taskId}.zip`、`{nas}/attach/{学校标识码}/{yyyyMM}/{uuid}.{ext}`。
`stu_photo` 只存相对路径 + SHA256 + 大小 + 宽高 + 状态。

**上传链路：** 前端压缩（长边 480px、≤200KB）→ 并发闸门 3 → Redis 令牌桶限流（单用户 5 req/s、单批 ≤500 张）→ 校验（格式白名单/数据范围/幂等 uploadId）→ **SHA256 秒传** → 落临时目录 + 建 `stu_photo(待处理)` → RabbitMQ 削峰 → 消费者生成缩略图 + 写 NAS → 成功回写状态/失败入补偿队列 → 前端轮询进度。

**熔断降级矩阵：**

| 故障 | 检测 | 动作 | 恢复 |
|---|---|---|---|
| NAS 写延迟高 | Timeout 5s | 记失败 | 重试 |
| NAS 连续失败 | 失败率>50% 且样本≥20 | **熔断 30s**（半开试探） | 半开放量 |
| 熔断打开 | — | **降级写本地盘 + 入补偿队列**，接口返回「已接收(排队中)」 | `PhotoCompensationWorker` 每 30s 回放 |
| NAS 空间不足 | 定时探针 | 告警 + 停止接收 | 人工扩容 |
| Redis 挂 | 连接异常 | 本地内存进度 + 直连 DB 查重 | 自动重连 |
| MQ 挂 | 连接异常 | 消息落 Outbox，后台重发 | 自动重连 |
| 上传洪峰 | 令牌桶 + 舱壁 | 429 + `Retry-After`，前端排队重试 | 自然回落 |

#### 11.5.1 已实现（第一版，含测试）

| 能力 | 落地方式 | 测试 |
|---|---|---|
| 主/降级双存储 | `FileSystemPhotoStorage` 同一实现按根目录参数化，派生 `NasPhotoStorage` / `LocalFallbackPhotoStorage`（DI 可分辨） | `FileSystemPhotoStorageTests` |

| 健康度 | `GET /api/app/photo/storage-health`：真实写探针文件 + 熔断器快照 + 待补偿/失败条数 | 同上 |
| 上传接口 | `POST /api/photos/upload`（multipart，流式接收，**不用 base64 DTO**） | — |

**与上表的差异（第一版未做，已在 P4 余量中列出）：** 缩略图生成（宽高暂记 0）、RabbitMQ 削峰（当前同步写，靠舱壁 + 熔断保护）、Redis 令牌桶限流、幂等 `uploadId`、`stu_photo` 之外的附件/导出存储。

**路径规范修正：** 实际落地为 `photo/{学校组织Id:N}/{学生Id:N}.{ext}`，而不是 `photo/{学校标识码}/{学籍辅号}.jpg`。原因是文件名里带学籍号会把学生身份信息暴露在 NAS 目录上，运维一浏览就泄露；用 Id 还能完全避开生僻字文件名编码问题。代价是需要查库才能由路径反推学生，这对运维场景可以接受。

**配置项：** `Xjgl:Photo:{NasRoot, FallbackRoot, FailureRateThreshold, MinimumSamples, OpenSeconds, BulkheadSize, TimeoutSeconds, CompensationEnabled, CompensationIntervalSeconds}`。


### 12.2 关键机制

- 登录后取 `/api/system/my-profile` → 用户 + 组织 + 角色 + **权限码集合** + **可见模块树** + **数据范围**
- 路由：`router.addRoute()` 动态挂载（组件路径来自模块元数据，`import.meta.glob` 解析）
- 按钮：`v-permission="['Stu.Student.Create']"`
- 码表：`<CodeSelect code="SEX" />`，按类别批量拉取 + 内存/localStorage 缓存（带版本号）
- 大列表：`el-table-v2` 虚拟滚动 + 服务端分页 + 列配置持久化 + 查询方案
- 下拉：**凡是"选学校"这类可能上万条的集合，一律用虚拟滚动下拉**（`components/SchoolSelect.vue` → `el-select-v2`）。
  普通 `el-select` 会为每一条渲染一个真实 DOM 节点：全省 6,789 所学校时，只打开一次"批量上传照片"对话框就把主线程卡死 100 秒以上（实测节点从 1,231 涨到 29,867），详见 16.13
- 字体：统一 `--el-font-family` + 生僻字 fallback（见第 7 章）

### 16.3 端到端验证记录（第四轮：P2 导入导出）——抓出两个「动词不匹配」的 405

这一轮验证的是学生批量导入导出。**导入一次就通，导出则暴露了一个进程内测试永远发现不了的缺陷**：

| 缺陷 | 现象 | 根因 | 教训 |
|---|---|---|---|
| **导出接口 405** | `GET /api/app/student-import-export/export` 返回 **405 Method Not Allowed**（响应体为空，连报文都没有）；而进程内集成测试全绿 | ABP 自动 API 按**方法名前缀**决定 HTTP 动词：`ExportAsync` 不以 `Get` 开头 → 被注册成 **POST**。前端是"带查询串 GET 下载"，两边对不上 | 单元/集成测试**直接调方法**，压根不经过路由层 —— 路由与动词这类"契约"问题必须用真实 HTTP 请求（或比对真实路由表）来守。改名 `GetExportAsync` 后路由即变为 `GET .../export`（已从 `swagger.json` 确认，含全部查询参数） |
| **照片批量删除 405** | 前端 `photoApi.deleteMany` 发的是 `POST /api/app/photo/many`，后端只接受 **DELETE**（集合参数走请求体） | 同上：`DeleteManyAsync` → `DELETE /many`。这是同一个坑的**第二处**，说明属于一类问题而非偶发 | 修完导出后立刻做了一次**全量核对**（下面第 3 点），才把它找出来 —— 修一个"同类问题"时应当顺手把这一类全查一遍 |

**假绿灯比没有检查更危险**，所以必须对"检查本身有没有真的执行"做断言。

### 16.4 端到端验证记录（第五轮：学生档案子表）——先验证"路由长什么样"，再写前端

| 实测路由 | 动词 |
|---|---|
| `/api/app/student-profile/guardians/{studentId}` | GET |
| `/api/app/student-profile/guardian/{studentId}` | POST |
| `/api/app/student-profile/{id}/guardian` | PUT / DELETE |

规律：**查/增把动作名放前面（复数/单数两种），改/删把 id 放前面**。
其余五张子表同构（resumes/data、rewards、punishments、subsidies、physicals）。
之所以要先看再写：这个形状"看着别扭"，凭直觉写出来的会是 `{studentId}/guardians`，
两种写法都"合理"，但只有一种是真的。

同轮 26 条端到端断言全部通过，其中几条是**专门验证设计意图**的：

| 验证项 | 结果 |
|---|---|
| 监护人身份证：入库加密、接口只回掩码 | 返回 `410102********4311`，**响应体里搜不到明文** |
| 修改监护人时**不回传**身份证号 | 原号保留（`hasIdCard=true`），不会把掩码当新号写进去 |
| 第二个监护人设为"第一监护人" | 前一个自动降级（列表复查通过） |
| 同一学年重复录体检 | 被拒，且原因可读："该学生 2025-2026 学年的体检记录已存在，请直接修改原记录" |
| 处分"撤销" | 记录仍保留（不删行），`isRevoked=true` 且撤销日期被自动补上 |
| 资助金额 625.5 | 原样返回（decimal 不是浮点） |
| 对不存在的学生取子表 | **404**，证明子表接口真的加载并校验了主档（数据范围守卫生效） |
| 码值翻译 | `relationName=父亲`、`healthName=健康`、`punishTypeName=警告` |

**一处被自己的错误认知绊住**：断言"重复体检应返回 HTTP 400"，实际是 **403**。
ABP 把业务异常统一映射成 403（与"没权限"同码），只能靠 `error.code`（`Xjgl:00004`）区分。
**接口是对的，断言是错的** —— 所以探针脚本里也把这条认知写进了注释，免得下次又"修错地方"。

### 16.5 端到端验证记录（第六轮：学生详情页）——抓出一处「静默空结果」和一处「写坏数据」

做学生详情页（6 张子表的标签页）时，顺手核对了列表页的几个下拉框，抓出两个同源缺陷：
**前端把"码值的英文名"当成了码值**。

| 缺陷 | 现象 | 根因 | 教训 |
|---|---|---|---|
| **学籍状态过滤永远返回空** | 学生列表按"在读"过滤 → 列表为空，**HTTP 200、无任何报错**；表格里的状态标签也全是灰色 | 前端写的是 `{ value: 'Studying', label: '在读' }`，而后端的学籍状态是码值（01/02/…），`GetListAsync` 直接拿 `'Studying'` 去比对。实测：`StudentStatusCode=Studying` → `totalCount=0`，`=01` → `1520` 条 | "界面能点、接口 200、结果为空"是最容易被当成"没数据"的一类缺陷。**码值类的下拉框一律从码表取**，不要在前端手写 |
| **异动类型会写入非法学籍状态** | 异动类型的"异动前/后状态"存成了 `Studying`，而审批通过时会执行 `student.StudentStatusCode = apply.TargetStatusCode` —— **等于把码表里不存在的值写进学生的学籍状态** | 同一个硬编码选项，但这次不只是"查不到"，而是"把脏数据写进主档" | 同一个错误的两种后果，**写比读严重得多**。因此除了改前端，后端也加了码值校验（`EnsureStudentStatusCodesAsync`）：配置阶段就拦住，而不是等哪天发现学生状态不对再回头找原因 |

修复方式（两层）：
1. **前端**：新增 `codeApi.getItemsByCode(categoryCode)`（实测 `GET /api/app/code/items-by-code?categoryCode=STUDENT_STATUS` → 200；
   注意 `categoryCode` 是**查询串**而不是路径段），学生列表与异动类型页的状态项都改为从码表取；
   列表显示也改成用码表翻译（原来直接显示 `01`）。
2. **后端**：`ChangeTypeAppService` 在新增/修改异动类型时校验 `BeforeStatusCode`/`AfterStatusCode` 必须是
   `STUDENT_STATUS` 里的码值（码表尚未导入时跳过校验，**不能因为字典没准备好就让业务存不下去**）。
   实测：PUT 传 `Studying` → 403 + `reason`："学籍状态码不合法：Studying。应填码表 STUDENT_STATUS 中的码值（如 01=在读、02=休学），而不是英文名称。"

**顺手记一个排查坑**：写测试时用 `"Transferred"`（11 个字符）验证"英文名会被拒"，
结果抛的是 `AbpValidationException`（HTTP 400）而不是业务异常 ——
因为它先被 DTO 的 `[StringLength(8)]` 挡下了，**根本没走到业务校验**。
而 `"Studying"` 恰好 8 个字符，才能进到码表校验里。
"长度规则先于业务规则生效"会让"校验没生效"的假象出现，测试数据要按这个顺序挑。

**学生详情页本身**（`StudentProfileDrawer.vue`）：抽屉 + 6 个标签页，与 `ChangeApplyDetail.vue` 一致
**做成组件而不是独立路由** —— 本系统路由完全由后端元数据驱动，把"学生详情"做成独立路由
就得在模块管理里给它建一条菜单记录，而它显然不是一个可独立授权的功能菜单。
表单用"字段描述 + 一套模板"驱动六张子表（手写六遍必然漏改），身份证号在编辑时只回填掩码、
留空即"不修改"。

### 16.6 端到端验证记录（第七轮：学籍变更留痕）——两处"看起来在工作"的缺陷

学籍变更流水（`stu_change_log`）本身实现得很直白：**改之前取快照，改完做前后比对，只写真正变化的字段**。
但这一轮抓到两个"看起来在工作、其实没工作/漏工作"的问题，恰好都不是业务逻辑写错：

| 缺陷 | 现象 | 根因 | 教训 |
|---|---|---|---|
| **删档之后查不到自己的留痕** | "删除学生后仍能追溯"的用例直接报 `EntityNotFoundException` | `GetStudentLogsAsync` 先调 `StudentAccessGuard.GetInScopeAsync(studentId)`，而它按 Id 加载学生 —— 学生被软删后查不到，于是**留痕最该发挥作用的场景（删档追溯）反而 404** | 复用现成的守卫很自然，但"守卫的前提是对象存在"与"留痕的前提是对象可能不存在"直接冲突。**写完功能要按"这个功能被发明出来的那个场景"验一遍**，而不是验"常规路径能跑通" |
| **路由核对脚本漏了 20 次调用** | 脚本报告"核对 81 项、0 项不匹配"，看着一切正常 | 提取调用的正则是 `http\.(get\|post\|put\|delete)<[^>]*>\(`，`[^>]*` 遇到嵌套泛型（`http.get<PagedResult<StudentChangeLog>>(...)`）就匹配不上，这类调用被**静默跳过** | 这是本项目**第二次**在"核对工具"上踩到假绿灯（第一次是脚本因 ENDPOINTS 解析失败跳过一半调用）。修法有两层：正则改成 `<[^(]*>`，并新增**交叉校验**——文件里出现多少次 `http.<verb>` 就必须解析出多少条，对不上直接失败。修好后核对数从 81 涨到 **101** |

修正后的行为：
- 学生**还在**时按当前数据范围校验（历史记录可能属于已转出的学校，不影响查看完整履历）；
- 学生**已被删除**时退回按流水上冗余的学校路径校验（写入时特意存下来的 `SchoolPathCode`），
  且只要有一条在范围内就放行；
- 一条流水都没有时抛 `EntityNotFoundException`，调用方才能区分"没有变更"与"没有这个人"。

留痕的设计要点（都写进了实体注释）：
- **字段级**：只记"某人某时改过这条记录"没有审计价值，要能回答改了哪个字段、从什么变成什么；
- **码值翻译**：`在读（01）` 这种形式，既给人看也保留可追溯性；
- **身份证号只存摘要前缀**：审计要的是"被谁改过"，而不是把全校身份证号再抄一份进日志表；
- **删除也留痕**：档案的"消失"本身就是一次需要留痕的变更，因此删除前先写流水（否则拿不到姓名与辅号）；
- **一次操作一个 BatchId**：改两个字段产生两行但属同一次操作，界面才能合并显示；
- **`Source` 字段区分来源**：异动审批写入的行会带上申请单号（`异动申请 YCxxxx 审核通过`），
  可以从档案反查是哪一单引起的；这部分与异动自己的 `stu_change_flow_log`（记审批动作）互补。

### 16.7 端到端验证记录（第八轮：学籍卡与花名册打印）——PDF 与字体

方案里早就写明"打印/报表走 PDF 嵌入字体路线，不走导出 Excel 再打印"，本轮把它落地：
新增 `src/Xjgl.Reporting`（QuestPDF），应用层通过 `IStudentCardPdfRenderer` / `IStudentRosterPdfRenderer`
两个接口调用，**Host 才装配实现** —— 业务层不依赖任何渲染库。

真实 HTTP 验证（主机运行中直接请求）：

| 调用 | 结果 |
|---|---|
| `GET /api/print/student-card/{id}` | 200，**66,264 字节**，魔数 `%PDF-`，`Content-Type: application/pdf`，`Content-Disposition` 里的中文文件名正确（`学籍卡_异动测试学生_1001560001000001.pdf`） |
| `GET /api/print/student-roster?SchoolOrgId=…` | 200，53,812 字节，`%PDF-`，文件名 `花名册_测试第一小学.pdf` |

本轮踩到并解决的三个"看起来能用、其实会出事"的点：

| 问题 | 现象 | 根因与处理 |
|---|---|---|
| **QuestPDF 许可证未声明** | 9 个渲染用例全挂，报 `Please configure the QuestPDF license` | 我原本把 `Settings.License` 放在 ABP 模块的 `ConfigureServices` 里 —— 这只覆盖"通过 ABP 装配"的路径，**单元测试直接 new 渲染器就漏了**。移到渲染必经的初始化点（`PrintFontRegistry.EnsureInitialized`）后两条路径都覆盖 |
| **默认字体不含中文，且默认不使用系统字体** | 报 `The text "河南省中小学生学籍卡" uses font families that are not available: 'Microsoft YaHei'`，并列出 `System fonts (Settings.UseSystemFonts): disabled` | QuestPDF 2026 默认**只认随应用部署的字体**（为了容器/云环境输出稳定）。本系统的部署形态是教育系统的 Windows 服务器，中文字体必然存在，因此默认 `UseSystemFonts = true` 保证开箱可用；容器化部署可关掉并指定字体目录。**关键取舍**：同时打开 `ThrowOnMissingTextGlyphs` —— 画不出字形就报错，绝不出"满是方块的学籍卡"（纸质件上出现方块是绝对不能接受的），并把该异常翻译成"服务器缺少中文字体"的运维提示 |
| **表头 API 与直觉不同** | 编译报"无法从 TableDescriptor 转换为 TableCellDescriptor"，来回改了两次才对 | QuestPDF 2026 是 `TableDescriptor.Header(Action<TableCellDescriptor>)` —— 传进来的是**格子游标**，每次 `header.Cell()` 前进一格。**这次没靠猜**：直接读包里的 `QuestPDF.xml` 成员签名确认（反射在 PowerShell 里因依赖加载失败，XML 文档更可靠） |

版面即业务规则，几处刻意的取舍（都写进了渲染器注释）：
- **身份证号打掩码**：纸质件会被拍照、传阅、归档，明文收不回来；
- **缺照片时明确写"未采集照片"**：留白看起来像排版省略，写清楚才能让经办人知道要去补；
- **姓名含生僻字时用备用字体并标注"请核对原件"**；
- **花名册不打印家庭住址与联系电话**（列表项本来就没有，这里也不去补）：花名册是"点名/核对"用途，把全校家长电话印在纸上属于过度收集；
- **表头每页重复 + 页脚"第 X 页 / 共 Y 页"**：散页后必须能拼回去；
- **花名册沿用当前筛选条件**：否则"筛出二班来打印"会印出全校，而这类错误要到校对时才发现——纸已经印出来了。

### 16.8 端到端验证记录（第九轮：照片缩略图与二进制接口）——两次"改了没生效"

补齐 P4 的缩略图：新增 `src/Xjgl.Imaging`（ImageSharp），上传时探测尺寸并生成缩略图
（长边 480、JPEG 质量 82、先按 EXIF 摆正再缩放、比上限小则不放大），
并补上**照片的二进制读取接口**（此前系统里根本没有"取照片"的接口，缩略图生成出来也没人用）。

真实 HTTP 验证（主机运行中）：

| 调用 | 结果 |
|---|---|
| `POST /api/photos/upload-one`（1000×750、22,246 字节的真实 JPEG） | 200，`宽高=1000x750`，返回缩略图路径 `photo/{学校Id:N}/thumb/{学生Id:N}.jpg` |
| `GET /api/photos/{studentId}/thumbnail` | 200，**6,526 字节（原图的 29.3%）**，实际像素 **480×360**（等比：1000:750 → 480:360） |
| `GET /api/photos/{studentId}/content` | 200，22,246 字节，**与上传字节完全一致** |
| ETag / 缓存 | 首次 200 带 `ETag`（内容哈希）与 `Cache-Control: private,max-age=86400`；带 `If-None-Match` 再取 → **304** |
| 无令牌访问 | **401** |

这一轮抓到两个"代码写了但没生效"的问题，都不是逻辑写错：

| 问题 | 现象 | 根因与处理 |
|---|---|---|
| **尺寸探测结果没带到落库对象上** | 接口返回 `宽高=0x0`，缩略图字段为空；但**同一个逻辑在集成测试里是绿的** | 上传流水线里 `PreparedItem` 会被复制成另一个 `writeItem` 对象（校验阶段的字段只留在前者）。我把 `Size` 赋给了 `prepared`，落库阶段读的却是 `writeItem.Size` —— 于是静默丢失。集成测试先于真实请求发现了它（`result.Width` 一直是 0），修法是显式把 `Size` 带过去并在代码里写明"这个对象是复制出来的，别只给 prepared 赋值" |
| **只重建了测试项目，没重建 Host** | 改完代码重新验证，接口仍返回旧行为（`宽高=0x0`） | `dotnet build` 只编译测试项目时，新的 `Xjgl.Application.dll` 只会被复制进**测试的 bin**，Host 的 bin 里还是旧 DLL；表现就是"代码明明改了、行为没变"。**这类假象最容易让人怀疑自己改错了地方**，所以验证前先 `dotnet build Xjgl.sln`（或直接重建要启动的那个项目） |

同一轮还被 `tools/audit-routes.mjs` 当场拦下一次真错误：
前端把照片二进制接口写成了 `/api/app/photo/{id}/thumbnail`，
而手写控制器的路由是 **`/api/photos`（没有 `/app`）** ——
照片模块有两套入口（`/api/app/photo` 是约定式应用服务返回 JSON，`/api/photos` 是手写控制器收发二进制），
路径不同不是笔误。若没有这道核对，运行期会是 404，而前端的 `catch` 会把它变成"缩略图全是空的"，很难查。

另外顺手修掉一个**自己写的脆断言**：原本用"两份 PDF 长度不同"来验证"内容确实变了"，
而 PDF 是压缩流，长度偶然相同并不罕见（跑测试时就翻过一次车，表现为偶发失败）。
已改为比较**整份字节是否相同**（`SequenceEqual`）。

### 16.9 端到端验证记录（第十轮：照片打包导出）——"少一张照片"是最不能接受的失败

### 16.10 端到端验证记录（第十一轮：令牌桶限流）——以及一个被"容错"藏起来的配置问题

给昂贵接口加上限流：**照片上传（单用户 5 次/秒）、照片导出（每 5 秒 1 次）、打印（每 2 秒 1 次）**。

设计取舍（都写在 `DistributedTokenBucketRateLimiter` 注释里）：
- **令牌桶而不是固定窗口计数**：固定窗口在边界会放过双倍流量；
  而令牌桶允许"攒一会儿再突发" —— 教师一次选几十张照片并发上传本来就是正常用法；
- **桶状态放 `IDistributedCache`，不直连 Redis**：本系统的分布式缓存已经是
  「Redis 主 + 内存兜底」的容错装饰器，复用它就自动继承了那套降级策略，
  业务层也不必依赖 StackExchange.Redis；
- **失败放行**：缓存抖动时限流精度下降，但绝不能反过来变成"Redis 一抖，全校传不了照片"；
- **限流维度是"用户"而不是 IP**：一所学校往往整栋楼共用一个出口 IP。

真实 HTTP 验证（主机接本地 Redis）：

| 场景 | 结果 |
|---|---|
| 连续打印学籍卡（容量 3、0.5/s） | 前 3 次 200，之后 **429 + `Retry-After: 2`**，响应体 `{"message":"操作过于频繁，请 2 秒后再试。","policy":"print","retryAfterSeconds":2}` |
| **并发 8 次上传**（容量 5、5/s） | **正好 5 次 200 + 3 次 429** —— 桶在并发下也没被击穿 |
| Redis 里的桶状态 | `KEYS ratelimit*` 直接查到 `ratelimit:print:{userId}`、`ratelimit:photo-upload:{userId}` |
| 顺序 8 次上传（未触发限流） | 全部 200 —— 顺序请求约 2~3 次/秒，低于 5/s 的补充速率，**这是符合预期的**（限流不是"每次都拦"） |

**顺带发现一个被"容错"藏起来的问题**：验证时我在 Redis 上直接 `AUTH`，
发现 `appsettings.json` 里配的密码（`Xjgl@Dev2026`）**与本机实际运行的 Redis 不一致**，
主机日志里是：

```
[WRN] 分布式缓存主实现不可用，接下来 30 秒内直接使用内存缓存（累计失败 1 次…）
StackExchange.Redis.RedisConnectionException: AuthenticationFailure … Error: NOAUTH Authentication required.
```

也就是说**这套开发环境其实一直在用内存缓存**（登录、权限缓存都正常，因为降级是设计好的），
只是没有任何界面会提示这件事 —— 容错架构的代价就在这里：**配置错了不会报错，只会静默降级**。
因此验证限流时必须换个思路：临时起一个密码已知的 Redis（`127.0.0.1:56379`）并让主机连它，
再直接查 Redis 键名，才能确认真的是 Redis 在存桶状态（同时也验证了"Redis 正常时无降级告警"）。

这条已经写进 README 的已知限制：**部署后请检查日志里有没有"缓存主实现不可用"，
它意味着你的 Redis 配置没生效，而系统会安静地退回单机缓存**。

### 16.11 端到端验证记录（第十二轮：生产部署编排）——探针必须挂在管道最前面

P6 的第一块：**Linux + Docker 的生产编排**（`deploy/docker-compose.prod.yml` + 两个多阶段 Dockerfile + nginx 配置）。

产物与关键取舍：

| 文件 | 关键点 |
|---|---|
| `deploy/api.Dockerfile` | 多阶段；**装 `fonts-noto-cjk`**（PDF 画中文靠它，本项目刻意不做"缺字体画方块"的降级）与 `curl`（healthcheck 用）；**同一个镜像里同时发布 Host 与 DbMigrator**，生产初始化数据库只要 `docker compose run --rm migrate`；`ENTRYPOINT ["dotnet"]` + `CMD [...]`，这样 migrate 能用 `command` 覆盖启动参数 |
| `deploy/web.Dockerfile` | Node 构建（`--frozen-lockfile`）→ nginx 托管静态资源；前端调用同源相对路径，因此不需要注入任何 `VITE_*` |
| `deploy/nginx.conf` | ① history 路由回落（否则刷新深链 404）；② `client_max_body_size 210m`（与接口的 200MB 对齐，否则大文件在 nginx 层被 413，接口层限制成了摆设）；③ `proxy_read_timeout 300s`（导出/打印是同步生成）；④ `index.html` 禁缓存（否则发版后加载旧壳子、引用已删除的 chunk） |
| `deploy/docker-compose.prod.yml` | 口令全部 `${VAR:?提示}` 注入（缺失即报错退出，而不是空值启动）；降级照片目录挂**命名卷**（NAS 熔断期间暂存的照片不能因重建容器而丢）；NAS 以**同路径**绑入；MQ 与 Seq 走 profile |
| `deploy/.env.example` / `README.md` | 逐步部署手册（含 NAS 挂载、生僻字字体、HTTPS、备份、第三方许可证、排错清单） |

**本轮抓到的问题：健康检查写在 ABP 管道后面 = 探针永远看不到数据库故障。**

先写的版本是把 `/health` 用 `MapGet` 挂在 `UseConfiguredEndpoints()`（管道末尾）。实测数据库不可达时：

```
GET /health  →  HTTP 500（一页 Npgsql 异常堆栈）
```

堆栈显示失败发生在**到达我的端点之前**：ABP 的请求本地化中间件要读"租户设置"（`TenantSettingValueProvider` → EF 查询），数据库不可用它就抛了。
一个只会返回 200/500 的探针是没有意义的 —— 容器与负载均衡都据此判断"要不要放流量"。
改法是把健康检查做成**管道最前面的终止式中间件**，并对数据库探测 `try/catch`（连不上就是"不健康"，不需要把异常抛出去）。

修复后实测：

| 场景 | `/health` | 同一时刻其它接口 |
|---|---|---|
| 数据库正常 | **200** `{"status":"ok","database":"up"}` | `swagger.json` 200（确认中间件没打断正常路由） |
| 数据库不可达（连接串指向空端口） | **503** `{"status":"degraded","database":"down"}` | `/api/app/my-profile` → 500（正好反证了探针确实提前拦截） |

**部署文件的自动核对**：手写编排最容易出的问题是"变量名写错一个字母" —— 容器照样起来，功能上线才炸。
因此新增 `tools/verify-deploy.mjs`，以 `src/Xjgl.HttpApi.Host/appsettings.json` 为**唯一事实来源**，
反推 compose 必须提供的环境变量（`A:B` → `A__B`）逐个核对，并检查字体安装、healthcheck、数据卷、
nginx 的深链回落与上传体积、`.env.example` 是否覆盖所有变量、生产文件里是否混入开发口令。
CI 另有一道 `docker compose config -q` 做语法与插值校验（本机没有 docker，这道只能在 CI 跑）。

**脚本自己也被自己抓了一次**：第一版用 `POSTGRES_PASSWORD:\s*[^$\s]` 判断"口令是字面量"，
结果误命中了 `${POSTGRES_PASSWORD:?提示}` 里的 `POSTGRES_PASSWORD:` + `?`；
变量提取也把**注释里**的 `${VAR:?提示}` 当成了真变量。已改为"先去掉注释行 + 只认行首键与字面量值"。

### 16.12 照片模块的故障演练方式（值得记住的做法）


集成测试**不搭真实 NAS**，而是把「NAS 主存储」的根目录指向测试输出目录下的一个本地目录；
需要模拟故障时，把这个目录换成一个**同名文件** —— 目录创建必然失败，
于是「写入失败 → 熔断 → 降级 → 待补偿」的完整链路真实发生；修复只需把文件删掉。

好处：与生产走**同一套 DI 装配和同一个熔断器**（不是 mock），
毫秒级完成，且能反复演练「NAS 恢复后自动补传」。

### 16.13 端到端验证记录（第十三轮：在真浏览器里点一遍）——三个"只有浏览器能看见"的缺陷

补上 P5 的最后一块：**Playwright 端到端测试**（`web/e2e`，4 个规格文件 / 27 个用例 ——
这是**当时**的规模；后续已扩到 **10 个规格文件 / 50 个用例**，含独立的 H5 项目，见 §24）。
它不是"把接口再测一遍"，而是守住集成测试与类型检查都看不见的那一层：
前端到底有没有按真实的路径与动词调接口、按钮在权限与路由下是否真的可点、一条完整流程能不能走完。

| 规格 | 覆盖 |
|---|---|
| `01-login.spec.ts` | 未登录访问业务页被重定向、密码错误不跳转、登录后能看到菜单、**刷新页面后会话仍有效**（令牌持久化 + 静默恢复）、激活页是公开页 |
| `02-student.spec.ts` | 按辅号查询 + 掩码身份证、详情抽屉新增监护人并留下变更记录、**打印学籍卡并校验下载到的确实是 PDF**（查 `%PDF-` 魔数）、导出当前筛选结果（CSV 含表头与掩码身份证）、导入对话框的模板与列说明 |
| `03-photo.spec.ts` | 台账两个页签与导出/上传入口、**批量上传对话框 + 学校下拉能选中**、**上传后台账能显示缩略图**（`<img src>` 带不上令牌，只能走 Blob）、打包导出对话框 |
| `04-modules.spec.ts` | 11 个业务模块逐个打开并渲染出内容（守住"白屏"这类整体性故障）+ 左侧菜单与后端元数据一致 |

**这一轮抓到的三个缺陷，集成测试（405 个用例）与 `vue-tsc` 类型检查全都是绿的：**

| 缺陷 | 现象 | 根因 | 教训 |
|---|---|---|---|
| **深链 / 刷新 404** | 直接访问或刷新 `/student/list` 这类业务页，显示"页面不存在或您没有访问权限" | 两处"看起来等价"的写法叠加：① 路由守卫用 `to.meta.anonymous` 判断公开页，而**兜底路由（catch-all）也带这个标记**，于是被误判成受保护页；② 恢复会话后 `return { ...to, replace: true }` 把解析结果里的 `name: 'not-found'` 一起带上了 —— vue-router 里 **`name` 的优先级高于 `path`**，于是重定向到了不存在的路由 | 改成显式 `PUBLIC_PATHS` 白名单 + `return { path: to.fullPath, replace: true }`。教训：**路由守卫要用"点菜单"“刷新”“直接粘贴地址”三种方式各验一遍**，只点菜单永远发现不了 |
| **导出按钮是死的** | 学生列表点"导出"毫无反应（控制台 400） | 导出复用了列表的查询参数，其中带着 `maxResultCount: 5000`；**ABP 把单次 `MaxResultCount` 硬性限制在 1000**，DTO 验证直接 400 | 集成测试直接调应用服务、**绕过了 ABP 的 DTO 验证**，所以 405 个用例全绿。教训：**"上限类"契约规则（分页上限、体积上限、超时）只在 HTTP 层生效**，必须在端到端或契约层验证 |
| **打开批量上传对话框 = 页面假死 100 秒** | 点"批量上传"后对话框迟迟不出现，后续断言全部超时；连 `getByRole('button')` 这类查询也一起卡住 | **学校下拉把全省 6,789 所学校全部渲染成了真实 DOM**：普通 `el-select` 的每个 `el-option` 都是一个节点，实测 `.el-select-dropdown__item` 有 6,799 个、页面节点从 1,231 涨到 29,867，浏览器主线程被样式与布局算到卡死（一次 `page.evaluate` 要 **103 秒**才返回） | 这是**只在真实数据规模 + 真实浏览器下才会出现**的缺陷（集成测试不渲染 DOM，类型检查更看不见）。修法：新增 `components/SchoolSelect.vue`，用**虚拟滚动**的 `el-select-v2` 只渲染可见的十几项，把 6 处"选学校"全部换掉；E2E 里加了一条**与学校总数无关**的守卫断言（`.el-select-dropdown__item` 少于 200 个），并顺带验证"选中学校后『选择照片文件』按钮由灰变亮"（虚拟列表 + 过滤写错时的表现就是"选不中、按钮永远是灰的"） |

**为了让这套端到端测试在 CI 上真的能跑，又抓到两个缺陷 —— 都属于"配置根本没生效"这一类：**

| 缺陷 | 现象 | 根因 | 修法 |
|---|---|---|---|
| **迁移器在 CI 里一启动就崩** | 用 CI/部署脚本的方式调用（`dotnet run --project src/Xjgl.DbMigrator`，当前目录是仓库根）直接报 `The configuration file 'appsettings.json' was not found and is not optional. The expected physical path was '<当前目录>\appsettings.json'` | `Host.CreateDefaultBuilder` 的**内容根就是"当前工作目录"**，而 appsettings.json 是随生成复制到**输出目录**的（`CopyToOutputDirectory=Always`）。也就是说：这个工具只有在"从它自己的输出目录启动"时才可用 | `UseContentRoot(AppContext.BaseDirectory)`。命令行工具不该依赖"从哪个目录被调起来" |
| **容器与 CI 里 appsettings.json 根本没被读到，而且是静默的** | 容器是 `WORKDIR /app` + `dotnet /app/api/Xjgl.HttpApi.Host.dll`（appsettings.json 在 `/app/api`）；CI/脚本是 `dotnet run --project src/...`（当前目录是仓库根）—— 两种情况下内容根都不是配置文件所在目录。而 ASP.NET Core 默认把 appsettings.json 当**可选**文件，**读不到也不报错**：照片存储路径、打印字体、Redis 连接、学籍号规则一起悄悄退回代码默认值 | 与上一条同源：内容根取的是"当前工作目录"。因为默认值恰好都能跑，所以现象是"什么都没发生"—— 这正是最难发现的一类问题 | `WebApplication.CreateBuilder(new WebApplicationOptions { Args = args, ContentRootPath = AppContext.BaseDirectory })`；另外在内容根下**没有** appsettings.json 时打一条 WARNING，并把内容根写进启动日志（宁可吵，也不要静默降级） |
| **端到端测试在"全新装出来的库"上必挂** | 本地全绿，CI 上第一个用例就断言失败："测试库里没有学校组织，无法造数据" | 迁移器只建表 + 码表/权限/账号种子，**不建组织树**；而 E2E 假定"库里至少有一所学校" —— 本地库是长期累积出来的（已有 6,789 所），所以这个假设一直没被戳破 | E2E 自己造数据：没有学校时按**固定编码**现建"省 → 市 → 县 → 校"（先按编码查、查不到才建，所以可重复跑；学校标识码取 10 位，因为学籍辅号 = 学校标识码(10) + 流水号(6)） |

这两个"内容根"缺陷的验证方式很具体：**把后端按 CI/容器的调用方式启动一次**，
日志里应当出现 `内容根：...\bin\Debug\net10.0\` 且没有"没有 appsettings.json"的告警；
`/health` 返回 200 且能查到业务表。修完后再把整套 E2E 打到一个**全新迁移出来的库**上跑，
成绩与在长期库上完全一致（26 通过 / 1 跳过 / 51 秒），并确认测试自己建出了组织树
（`410000 → 410100 → 410102 → 4101020001`，物化路径完整）。

修复前后（同一套用例、同一套数据）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 单个学生 / 照片用例耗时 | 60~130 秒，且偶发超时失败 | 1.4~3.6 秒 |
| 整套 E2E | 9 分 42 秒，22 通过 / 4 失败 | **51 秒，26 通过 / 1 跳过** |
| 学生列表 / 照片页 DOM 节点 | 14,761（打开对话框 29,867） | 2,674（打开对话框 2,746） |

**排查过程本身也值得记下来：判据是"连不需要等待的调用也卡住了"。**
最初的报错是 `expect(locator).toBeVisible() failed / Received: undefined`，
看起来像"选择器写错了"。但 `locator.count()` 这种**根本不会等待元素**的调用同样卡了 90 秒，
这一条就把"选择器写错"整个方向排除掉了。接着打开 Playwright 的 trace，
看到最后一个未完成的操作停在 `expect`，再用 `page.evaluate` 逐秒探测主线程，
才看到"节点数从 1,231 爆炸到 29,867、单次 evaluate 耗时 103 秒"。
**"卡住"与"找不到元素"是两种病，报错文案却很像** —— 区分它们的方法就是问一句：
"这个调用本来就该立即返回吗？"

E2E 的几条工程约定（都写进了 `web/e2e/playwright.config.ts` 与 `specs/support/auth.ts` 注释）：

- **不用 `globalSetup` 预热**：Playwright 的 `globalSetup` 在 `webServer` **之前**执行，
  此时 dev server 还没起来，`page.goto` 必然超时（本项目实测踩过）；
  冷启动的代价改由放宽的断言超时吸收（expect 30 秒 / 用例 90 秒）；
- **不用 `networkidle`**：Vite 的 HMR websocket 让网络永远不"静默"，等它必然超时；
  改为 `waitForLoadState('load')`，需要"数据到位"时用针对元素的断言；
- **`fullyParallel: false` + `workers: 1`**：用例共用一套数据库与一个后端进程，
  并行会互相踩（都在改同一所学校的学生）；测试项目本身也已关掉程序集/集合级并行；
- **数据用接口造、界面只验界面**：学生建档目前走导入或接口，
  E2E 不假装去点一个尚不存在的对话框；唯一性靠系统生成的学籍辅号而不是姓名里的时间戳
  （第一版用了 `E2E学生123456`，被后端校验直接拒掉：**"姓名包含非法字符『2』"**）；
- **选择器按 Element Plus 2.x 的真实 DOM 写**：`el-select` 的占位符是 `<span>`（`getByPlaceholder` 找不到）、
  对话框右上角的 X 与页脚按钮的可访问名都是"关闭"（不加范围会命中两个元素）、
  表格里的图标会污染 `img` 选择器（缩略图要用 `img.el-image__inner`）。

## 17. SSO 多客户端共享会话与 Front-Channel 全局登出

对应原始目标里的「支持学分系统 SSO 免登」。本节记录**骨架已落地**的部分、
**必须由真实接入方补齐**的占位参数，以及一条容易被忽略的事实边界。

> 状态：服务端骨架完成并编译通过（`dotnet build`）。**未做**前端页面改造、
> **未**接入真实学分系统、**未**连库验证种子落库。E2E 层面无覆盖。

### 17.1 先核对事实：哪些能力是现成的，哪些必须自己写

动手前用程序集元数据核对了 OpenIddict 7.5.0 与 ABP 10.6 的真实能力边界
（不是靠记忆，也不是靠文档），结论直接决定实现方式：

| 能力 | 谁提供 | 证据 |
|---|---|---|
| `FrontChannelLogoutUri` 字段与持久化 | **ABP 10.6** | `AbpApplicationDescriptor.FrontChannelLogoutUri`（`Uri`）、`IAbpApplicationManager.GetFrontChannelLogoutUriAsync`、实体列 `OpenIddictApplications.FrontChannelLogoutUri` |
| 该列已在数据库里 | **本仓库早已具备** | `20260916185322_Initial.cs` 第 474 行 —— 不需要新迁移 |
| 授权端点 / 会话结束端点的 passthrough | **ABP 10.6** | `AbpOpenIddictAspNetCoreModule` 调用 `EnableAuthorizationEndpointPassthrough()` / `EnableEndSessionEndpointPassthrough()` |
| 授权端点的**控制器** | **ABP 10.6 已提供** | `Volo.Abp.OpenIddict.Controllers.AuthorizeController`，路由 `connect/authorize` |
| 会话结束端点的**控制器** | **ABP 10.6 已提供** | `Volo.Abp.OpenIddict.Controllers.LogoutController`（文件名为 `EndSessionController.cs`），路由 `connect/endsession`。但它**只做 SignOut，不通知任何 RP** |
| Front-Channel Logout 的**扇出逻辑** | **没有，必须自己写** | OpenIddict 程序集内无 `FrontChannelLogoutUri` 一类符号；ABP 只给存储与读取 |
| `sid`（会话标识） | 生成需自己来，**传递 ABP 已支持** | `OpenIddictConstants.Claims` 里没有 SessionId；但 ABP 的 `AuthorizeController` 会把动态主体里的 `JwtRegisteredClaimNames.Sid`（=`"sid"`）复制进令牌 |

**这解释了仓库此前"授权码流程未接线"的确切含义**：端点已声明、passthrough 已打开，
但没有任何代码承接 —— 浏览器导航到 `/connect/authorize` 只会落空。
（令牌端点不同：它没有"用户"语义，由 OpenIddict 内部处理完毕，所以密码模式一直是通的。）

### 17.2 端点的实际路径由一个"覆盖顺序"决定（易踩）

ABP 的模块把端点设成 `connect/authorize`、**`connect/endsession`**、`connect/revocat`；
而 Host 的 `PreConfigure<OpenIddictServerBuilder>` 又设成 `/connect/authorize`、
**`/connect/logout`**、`/connect/revoke`。ABP 在自己的 builder 末端调用
`ExecutePreConfiguredActions(builder)`，**预配置动作最后执行**，所以 **Host 的取值生效**。

> ⚠ 这是**承重**的：若哪天删掉 Host 里那段 `SetEndSessionEndpointUris`，
> 登出端点会**悄悄搬回** `/connect/endsession`，而前端与 `SsoConstants.EndSessionPath`
> 仍指向 `/connect/logout` —— 现象是登出 404，且没有任何编译或启动期告警。
> 修改任一处的端点路径，必须同时改另一处。

### 17.3 多客户端共享会话：当前实现状态（已按"登录先不搞复杂"精简）

> ⚠ **本节原描述的方案（自建 SSO Cookie + `POST /api/sso/session` 交换）已被删除**，
> 原因是它与 ABP 自带的授权端点不兼容，实测表现为授权端点返回裸 401，详见 §17.8 第二节。
> 下面写的是**精简后的真实状态**。

**已实现且实测可用：**

- 会话来源统一为 ABP 的 **Identity 应用 Cookie**（`IdentityConstants.ApplicationScheme`）——
  与 ABP 的 `AuthorizeController`、以及本仓库的登出扇出**同一个来源**，不再有第二套会话。
- RP 客户端注册以**配置驱动**（`OpenIddict:EducationResourcePartners`），
  含 `FrontChannelLogoutUri`，实测落库成功（`Xjgl_Credit` 显式配置、`Xjgl_EduOther` 由
  `RootUrl` 推导，两者都验证过）。
- **协议层已通**：以 `Xjgl_Credit` 向 `/connect/authorize` 发请求，
  返回 302 到它注册的回调地址并带 `error=login_required` + 原样回传的 `state`
  —— 证明 OpenIddict 接受这个新种子出来的客户端。

**刻意留白（未实现，属"登录链路的最后一公里"）：**

浏览器交互式登录**尚未接线**：授权端点在"未登录"分支调用的是**不带方案名**的
`Challenge()`，落到本 Host 的默认方案（OpenIddict 令牌校验，它没有重定向能力），
所以浏览器拿到的是 **401 而不是 302 到登录页**。打通只需三步、且**不引入第二套会话**
（代码位置与原因写在 `XjglHttpApiHostModule.ConfigureAuthentication` 的注释里）：

1. 用 `IdentityConstants.ApplicationScheme` 建立会话（把 `sid` 作为声明放进去，
   ABP 会自动把它带进令牌 —— 见 §17.1 表格最后一行，令牌那一环不用自己写）；
2. `DefaultAuthenticateScheme` 保持 OpenIddict 校验（保证 `/api` 失败仍是 401），
   只把 `DefaultChallengeScheme` 指向 Identity 应用 Cookie；
3. `ConfigureApplicationCookie(o => o.LoginPath = "/sso/login")` 把挑战指向本仓库入口。

**为什么这样定位是合理的**：本系统的日常登录走的是**已有的密码模式**（前端拿 Bearer 令牌），
它一直正常；需要浏览器会话的只有"外部 RP 发起的免登"这一条路径，而它现在缺的正是上面三步。

### 17.4 全局登出：一处登出，所有 RP 全部下线

```
浏览器 ──▶ /connect/logout
             │
             ├─ 1. 读 SSO Cookie → 取 sub（主体）与 sid（本次会话）
             ├─ 2. 【先】收集靶点：该主体"仍然有效"的授权 → 查各 RP 的 frontchannel_logout_uri
             ├─ 3. 【后】撤销该主体的全部令牌 + 授权（RP 手里的刷新令牌同步作废）
             ├─ 4. 清掉 SSO Cookie
             └─ 5. 渲染扇出页：每个 RP 一个隐藏 iframe
                    <iframe src="{uri}?iss={issuer}&sid={sid}">
                    + 宽限期 3 秒后回跳 post_logout_redirect_uri（state 原样带回）
```

**第 2 步与第 3 步的顺序是正确性的一部分，不是风格问题。**
收集靶点时会按「授权状态仍然是 valid」过滤，而撤销正好把状态改成 revoked。
若反过来先撤销，**最该被通知的那些 RP 一个都收不到**，
而现象是"登出看起来成功了"、接口 200、日志无异常 —— 属于最难查的一类缺陷。

另外两点：

- **撤销令牌与撤销授权都要做**。只撤授权的话，RP 手里的刷新令牌仍可能换出新的访问令牌，
  等于"登出了但又自动登回来"。
- **返回 `Content` 而不是 `SignOut(OpenIddictServerAspNetCoreDefaults...)`**。
  后者立刻发 302，页面一卸载浏览器就可能取消那些 iframe，
  于是"部分 RP 没收到通知"会静默发生。宽限期是前通道登出固有的取舍。

### 17.5 为什么是"前通道"，以及它的可靠性边界

前通道由**浏览器**逐个 iframe 通知 RP，不需要 IdP 能反向访问 RP 的内网地址 ——
这是教育系统这种"各校各系统、网络互不相通"场景下唯一可行的方向。

代价必须说清楚，不能当成"已经解决了"：

- iframe 被浏览器拦截/取消、RP 侧响应慢于宽限期 → **该 RP 收不到通知**，且 IdP 不知道。
- 因此**真正保证下线的是第 3 步的令牌撤销**：RP 的刷新令牌已失效，
  下一次静默续期会失败并被迫重新登录。前通道通知只是让"已打开的页面"尽快跳到登录页。
- 后通道登出（IdP 直接 POST 到 RP 的 `backchannel_logout_uri`，有重试与确认）
  是更可靠的方案，**当前未实现**，见 17.7。

### 17.6 接入一个新教育系统要改什么

只改配置，不改代码 —— 这是种子代码遍历配置子节点换来的：

```jsonc
// src/Xjgl.HttpApi.Host/appsettings.json → OpenIddict:EducationResourcePartners
"Xjgl_Credit": {
  "ClientId": "Xjgl_Credit",
  "DisplayName": "学分系统",
  "ClientType": "public",                    // 后端对接则改 confidential + ClientSecret
  "RootUrl": "https://credit.example.edu.cn",
  "RedirectUri":              "https://credit.example.edu.cn/signin-oidc",
  "PostLogoutRedirectUri":    "https://credit.example.edu.cn/signout-callback-oidc",
  "FrontChannelLogoutUri":    "https://credit.example.edu.cn/signout-iframe"   // ← 登出投递地址
}
```

当前仓库里的三个占位项（`Xjgl_Credit` / `Xjgl_EduOther` / 本系统自身 `Xjgl_App`）
**地址全部是 `example.edu.cn` 占位值**。只填了 `RootUrl` 的项会按约定路径推导出另外三个地址，
但那只是"让占位配置能通过 URI 格式校验"，猜出来的地址在对方那里一定是 404
—— 表现为"登出后停在白页或 RP 侧会话仍在"，很难定位。

`FrontChannelLogoutUri` **必须校验**而不是原样存下（种子代码里做了 `Uri.TryCreate`）：
一个拼错的地址不会让任何流程报错，只会让登出通知打到不存在的站点。

### 17.8 ★ 实测推翻的三个判断（§17.1~17.3 已被本节部分修正）

本节是在**真正把应用跑起来**（`dotnet run` + 真实 PostgreSQL 55432 + 匿名 HTTP 探针）之后写的。
编译通过完全没能暴露下面任何一条 —— 它们全是运行期才现形的。

#### 一、ABP **有**授权端点控制器；我重复实现了它（我的错误）

- **真相**：`Volo.Abp.OpenIddict.Controllers.AuthorizeController`（路由 `connect/authorize`）与
  `LogoutController`（文件 `EndSessionController.cs`，路由 `connect/endsession`）都已存在。
- **我的误判**：我按 `AuthorizationController`、`OpenIddictController`、`OpenIddictEndSessionController`
  去搜程序集符号，全部零命中，于是写成"ABP 只给 passthrough、控制器必须自己写"，并实现了一个授权端点。
- **实测后果**（不是编译错）：

  ```
  AmbiguousMatchException: The request matched multiple endpoints. Matches:
    Xjgl.Sso.SsoAuthorizationController.AuthorizeAsync (Xjgl.HttpApi.Host)
    Volo.Abp.OpenIddict.Controllers.AuthorizeController.HandleAsync (Volo.Abp.OpenIddict.AspNetCore)
  ```

  `GET /connect/authorize` → **HTTP 500**，SSO 全链路不可用。
- **已修**：删除了本仓库的授权端点动作（`SsoAuthorizationController` 现在只剩登出扇出）。
- **教训（值得写进 review 清单）**：**"没搜到"不等于"不存在"。** 拿猜出来的符号名去撞二进制，
  猜错时零命中是必然结果，而这个零命中被我当成了证据。要否定一个能力，
  必须用**能枚举全部成员**的手段（类型清单 / 源码），不能靠符号名试探。

#### 二、ABP 的授权端点认 Identity 应用 Cookie，我自造的 Cookie 与它不兼容

- `AuthorizeController` 用 `HttpContext.AuthenticateAsync(IdentityConstants.ApplicationScheme)`
  取用户，并要求 `UserManager.GetUserAsync(...)` 成功。
- 我为此新增了独立的 `Xjgl.Sso` Cookie 方案 —— **两条路对不上**：
  即使我的 Cookie 建立成功，ABP 的授权端点仍然判定"未登录"。
- **实测**：`GET /connect/authorize`（无任何 Cookie）→ **HTTP 401**（而不是 302 到登录页）。
  原因是 ABP 在该分支调用的是**不带方案名**的 `Challenge(...)`，落到了本 Host 的**默认方案**
  —— 而默认方案是 OpenIddict 令牌校验（为了让 `/api` 保持 401），它没有重定向能力。
  所以浏览器在 SSO 起点拿到的是一个裸 401，而不是登录页。
- **收敛方向**（尚未实施）：不要自造 Cookie，改为
  1. 用 `IdentityConstants.ApplicationScheme` 建立会话（`sid` 作为声明放进去，
     ABP 会自动把它带进令牌 —— 见 §17.1 表格最后一行）；
  2. `AddAuthentication` 里把 **`DefaultAuthenticateScheme` 保持 OpenIddict 校验**
     （`/api` 失败仍 401），但把 **`DefaultChallengeScheme` 设为 Identity 应用 Cookie**，
     这样 ABP 那条 `Challenge()` 才会重定向；
  3. `ConfigureApplicationCookie(o => o.LoginPath = SsoConstants.LoginPath)` 把挑战指向 `/sso/login`。

#### 三、`/connect/endsession` 是一个**坏的孤儿入口**（本次之前就存在）

- 本 Host 的 `PreConfigure` 把 OpenIddict 会话结束端点覆盖为 `/connect/logout`
  （ABP 自己设的是 `connect/endsession`），而 ABP 的登出控制器**硬编码**在 `connect/endsession`
  —— 它的路由不来自 OpenIddict 选项，因此不会被一起改掉。
- **实测**：`GET /connect/endsession` → **HTTP 500**

  ```
  InvalidOperationException: A sign-out response cannot be returned from this endpoint.
    at OpenIddict.Server.OpenIddictServerHandlers.ValidateSignOutDemand.HandleAsync(...)
  ```

  即该地址仍是可达的 MVC 路由，但 OpenIddict 已不把它当作会话结束端点，`SignOut` 直接被拒。
- 这解释了 §17.2 那条"承重"警告为什么会咬人，也说明**在这次改动之前，本系统根本没有任何可用的登出端点**:
  `/connect/logout` 无人处理、`connect/endsession` 一调就 500。
- **两个可选收敛方案**（需决策）：
  - **(a) 向 ABP 对齐**：删掉 Host 的 `SetEndSessionEndpointUris` 覆盖，改用 `connect/endsession`；
    扇出逻辑改为挂 OpenIddict 会话事件处理器，或替换 ABP 的登出控制器。
    好处：与 ABP 默认一致、孤儿消失；代价：要处理控制器替换 / 事件钩子，改动更深。
  - **(b) 保持覆盖**：继续用 `/connect/logout` + 本仓库控制器；代价是 `connect/endsession`
    这个孤儿入口仍在（要么屏蔽该 MVC 路由，要么接受它 500）。
- **在决策之前不要在登出链路上继续叠加功能**：现在 `/connect/logout` 会渲染扇出页且 200，
  `prompt=none` 场景也已验证能正确回 `error=login_required`，但**交互式登录链路仍是断的**（见第二条）。

#### 四、顺带修正的两条环境事实（§2 与快照）

本机同时存在**两套 PostgreSQL**，先前的混淆来自此：

| 实例 | 端口 | 归属 | 库 |

### 17.9 数据库已切到 Docker 实例（2026-09，环境变更记录）

**决定**：本项目改用 **Docker 里的 `postgres-dev`（Windows `localhost:5432`）**，
弃用 `.tools/pgsql-extract` 那套原生 PG（55432）。

**为什么这次切换几乎没有配置改动**：仓库 `appsettings.json` /
`DbMigrator/appsettings.json` 里写的本来就是 **`Port=5432`**、`User ID=xjgl`、
口令 `Xjgl@Dev2026`。所以只要在 Docker 实例上**建出同名角色与同名库**，
两个被跟踪的配置文件**一行都不用改**，也就不必把口令写进仓库。

**实际做了什么**（可复核）：

| 步骤 | 命令要点 | 结果 |
|---|---|---|
| 建角色 | `CREATE ROLE xjgl LOGIN CREATEDB PASSWORD 'Xjgl@Dev2026'` | OK |
| 建库 | `CREATE DATABASE xjgl OWNER xjgl` / `CREATE DATABASE xjgl_test OWNER xjgl` | OK |

**踩到并值得记住的一点**：Docker 实例的 `pg_hba.conf` 里

因此在**容器内**用任意口令都能连上——我一开始就是被这个假象骗了，
以为口令有两种读法都成立；换成走容器桥接 IP（走 scram 分支）才验出
`pgpw.txt` 里的口令是唯一正确的那个。**验证认证策略必须在与被验证客户端相同的网络路径上做。**

### 17.10 ★ RP 种子配置放错文件会**静默什么都不种**（实测抓到的缺陷）

我在把 Host 的 appsettings 加好 RP 配置、信心满满地跑完 DbMigrator 之后，
日志一切正常（迁移完成、模块元数据 4 子系统 / 11 模块 / 54 操作、码表 33 类 / 188 条），
**但库里只有 `Xjgl_App` 与 `Xjgl_Swagger` 两个客户端，`FrontChannelLogoutUri` 全为 NULL。**

根因：**种子代码在 `Xjgl.DbMigrator` 进程里执行，读的是 `Xjgl.DbMigrator/appsettings.json`**，
而我把 `OpenIddict:EducationResourcePartners` 写进了 **Host** 的 appsettings。
Host 根本不跑种子，那段配置**永远不会被读到**。

- **失败方式**：DbMigrator 退出码 0、日志无任何异常、什么都不种。属于本方案反复在防的"静默降级"。
- **讽刺之处**：这个坑我事先在 `SsoPartnerConsts` 的类注释里写过
  （"改了配置节名，种子静默地什么都不种"），然后自己踩了进去 ——
  **说明"知道"不等于"防住"，只有可执行的检查才算**。
- **修法**：配置移到 `src/Xjgl.DbMigrator/appsettings.json`；Host 的 appsettings 里
  只留一条指路注释（Host 运行时是从**数据库**读 `FrontChannelLogoutUri`，不需要这段配置）。
- **验证**：重跑 DbMigrator 后 `Xjgl_Credit` / `Xjgl_EduOther` 两条落库，
  后者（只配了 `RootUrl`）的 `FrontChannelLogoutUri` 由约定路径**推导**得出，
  证明"新增接入方只改配置"这句承诺成立。
- **待补的可执行检查**（避免同类问题复发）：`tools/verify-deploy.mjs` 已有"配置一致性核对"的先例，
  可以加一条 —— **若 Host 的 appsettings 出现 `EducationResourcePartners`，或
  DbMigrator 的缺失，直接在 CI 里报错**。目前只是靠注释提醒，靠不住。

两种 PDF→`Stu.Student.Print`；zip→`Pho.Photo.Export` **且** `Pho.Photo.Query`。

### 18.2 三处安全决定（做错都不报错）

1. **后台线程里必须冒充发起人**。数据范围由 `ICurrentUser` 推出，而后台线程里它全空 →
   `UserDataScope` 会解析成 `Empty`，导出安静地变成**空文件**；若"图省事"以超管跑，
   则所有人的导出都绕过数据范围，变成"界面看不到、导出拿得到"的越权。
   实现：`ICurrentPrincipalAccessor.Change(principal)`，principal **同时带 `sub` 与角色**——
   角色不能省，因为 `UserDataScopeProvider` 靠 `Roles.Contains("admin")` 做超管旁路，
   只带 sub 会让 **admin 自己的导出变成空的**。
   解不出发起人时**让任务失败**，绝不降级为不受限。
2. **每个任务单独开一个 DI 作用域**。`UserDataScopeProvider` 是 Scoped 且**带缓存**，
   同一作用域里连跑多个任务会让上一个人的数据范围泄漏给下一个人 ——
   只在"一轮里有多个任务"时出现。**实测证据**：县级花名册任务 `total=10`、省厅 `total=40`。
3. **下载仅限发起人，且非本人返回 404 而不是 403**。403 等于确认"这个任务存在"，
   而任务 Id 会出现在日志、聊天记录、工单截图里。另加一道"当前是否仍具备该种类权限"
   （只认发起人等于把权限冻结在入队那一刻）。

### 18.3 抢占与时间

- 抢占用**带条件的 UPDATE**（`WHERE id=? AND status='Pending'`）而不是"先读后写"：
  多实例下两个实例会读到同一条 Pending 各跑一遍，产物互相覆盖。
- 时间**一律走 `IClock`**，不混用 `DateTime.UtcNow`：`ExpiresTime` 是入队时用
  `IClock.Now`（本地时间）写的，混用会让过期清理整整偏一个时区，开始/结束时间也对不上。

### 19.2 ★ 缺陷一：`IncludeDescendantOrgs` 被应用层整个丢掉

```csharp
// 修复前（StatisticsAppService.ResolveScopeAsync）
requestedPath = includeDescendants ? org.PathCode : org.PathCode;
```

三元运算符**两个分支写成一样** —— 参数收下了、注释也写了"只看本级时收缩为自身"，
实际是什么都没做。于是界面上关掉"含下级"后，返回的仍然是整棵子树的人数。

这类写法的危害在于它**看起来像实现过了**：有参数、有注释、有分支。
排查时读代码会直接跳过它。教训：**三元两边一样就是"没实现"的信号**；
真正的取舍被挪到了 SQL 层（前缀匹配 vs 等值匹配），那么这里就不该出现这个参数。

修复：`ResolveScopeAsync` 只负责算出路径，**是否含下级交给过滤器**，并在
`ScopeDescription` 里如实写出"；仅本级（不含下级组织）"——两种口径的数字不同，
不写出来用户无法解释。

### 19.3 ★ 缺陷二：叶子路径的 `like '路径.%'` 永远不匹配（最严重，静默全 0）

物化路径是 `省.市.县.校` 的形式，**叶子（学校）后面没有点**。所以：

```sql
-- psql 实测（xjgl_test）
select count(*) ... where school_path_code =  '422033.423661.424267.4250645634';  -- 3
select count(*) ... where school_path_code like '422033.423661.424267.4250645634.%'; -- 0
```

而**校级账号的默认数据范围恰好就是本校**（`scope.OrgPathCode` = 学校路径），
于是：**学校管理员打开统计页永远是 0**，接口 200、无异常、无日志。
界面选了具体某所学校时同样恒为 0。

这解释了为什么"按学校统计"在省厅账号下看着是对的（省厅路径有下级，`like` 能命中），
只有范围收到学校一级时才暴露 —— 而这一级正是最常用的使用者。

修复：范围条件显式包含路径本身：

```sql
school_path_code = @scopePath                        -- 自己
or (not @仅本级 and school_path_code like @scopeLike) -- 下级
```

（这正是 `StudentAppService.BuildPredicateAsync` 里 `exactSchoolId` 那套语义；
统计当初没有对齐它。新增用例 `学生统计_校级账号_不传学校也要能看到本校学生` 钉死。）

### 19.4 ★ 缺陷三：按转出/转入学校统计直接 500

```csharp
// 修复前：按维度只 join 其中一个 org 表
var scopeJoin = dimension is SourceSchool or TargetSchool ? joinExpr : "两个都 join";
```

但**范围条件里同时引用了 `so` 与 `to2`**。查"按转出学校"时 `to2` 不在 FROM 里：

```
42P01: missing FROM-clause entry for table "to2"
```

也就是说 —— **恰恰在"按转出学校 / 按转入学校"这两个维度上，统计接口是 500**。
修复为无条件带上两个 `left join`（都是 LEFT JOIN，多带一个不影响任何维度的计数）。

### 19.5 ★ 缺陷四（照片模块）：队列会被"原图读不到"的记录永久堵死

不属于统计，但同一轮测试暴露的。`IPhotoThumbnailService.EnsureThumbnailsAsync`
按 `UploadedTime ASC` 取前 N（默认 200）条"缺缩略图"的照片。
而**原图读不到的记录状态不变，每轮都会被重新扫到**：

| 指标 | 本机 `xjgl_test` 实测 |
|---|---|
| 缺缩略图且状态正常 | **415 条**（单轮上限 200） |
| 其中原图文件实际存在 | 7 个（`App_Data/photo-tests/nas` 下只有 7 个文件） |

于是 415 条读不到原图的陈年记录**永久占据队列前 200 位**，
比它们新的照片永远轮不上 —— 台账里表现为"新上传的照片一直没有缩略图"，
而后台任务每轮都在跑、日志里也不报错。

修复：`EnsureThumbnailsAsync` 增加可选参数 `Guid? schoolOrgId`（只补某校），

> **未根治**：真正的修法是给"已确认原图缺失"的记录打标记并移出队列。

### 19.7 顺手修掉的一处"魔法数字"断言（照片模块）

跑到全量测试时 `PhotoAppServiceTests.上传照片_写入主存储并登记台账` 稳定失败：

```
photo.FileSize  should be  512L  but was  616L
```

排查过程本身值得记一笔：这条用例**单独跑会"通过"**，一开始被误判成"测试顺序依赖"。
真实原因是 `--filter-namespace Xjgl.Photos` 根本没有选中它
（该类的命名空间是 `Xjgl.Application.Tests.Photos`，不是 `Xjgl.Photos`），
于是"过滤后通过"其实是"压根没跑"。**"过滤后绿了"必须先确认过滤真的选中了它。**

真实原因是断言写死了 `ShouldBe(512)` —— 而 JPEG 的具体字节数由 ImageSharp 的
编码器决定、随版本变化（当前 `JpegBytes(seed: 1)` = 616 字节）。
改成与**自己上传的字节数**比较：

```csharp
photo.FileSize.ShouldBe(content.Length, "台账里的文件大小必须等于实际写入的字节数");
```

这既保留了用例的价值（台账大小必须等于实际写入字节数），
又不会因为图像库升级而变红 —— 而它变红时的报错信息看起来像"业务把大小算错了"，
排查方向会被完全带偏。

### 20.2 ★ 本轮抓到的三个"只能真跑才暴露"的缺陷

**缺陷 A：照片导出按 `StudentNo ASC` 排序 —— NULL 排在最前，与意图相反**

`stu_photo.student_no` 在上传事务里稍后才回填，因此**新建行一开始是 NULL**；
而 PostgreSQL 的 `ORDER BY … ASC` 默认把 NULL 排在最前面。结果是"还没有学生号的
中间态记录"把可导出的照片挤到后面，与"优先导出能用的照片"正好相反。
改为 `UploadedTime ASC`（非空、稳定、语义就是"先来先导"）。

**缺陷 B：缩略图补齐队列会被"原图读不到"的记录永久堵死**

`EnsureThumbnailsAsync` 按 `UploadedTime ASC` 取前 N（默认 200）条。
而原图读不到的记录**状态不变、每轮都会被重新扫到**：

| 指标 | 本机 `xjgl_test` 实测 |
|---|---|
| 缺缩略图且状态正常 | 415 条（单轮上限 200） |
| 其中原图文件实际存在 | 7 个 |

于是陈年坏数据永久占据队列前 200 位，**新上传的照片永远轮不上**，
而后台任务每轮都在跑、日志里也不报错。两处修复：
1. **扫描方向改为"新的优先"**（`UploadedTime DESC`）—— 刚上传的下一轮就拿到缩略图，
   坏数据只是永远排在队尾（它们本来也生成不出来）；
2. 新增可选参数 `Guid? schoolOrgId`（只补某校），给运维一个"就修这一所"的入口，
   同时让依赖它的 4 个测试**确定**。
> **未根治**：真正的修法是给"已确认原图缺失"的记录打标记并移出队列，
> 那需要先与业务确认能否自动标记。

**缺陷 C：路由名跨子系统冲突 —— 一个菜单项永远 404**

`toRoute` 用模块的 `code` 当路由名。而 `code` 只在**子系统内**唯一
（后端是 `(subsystem_id, code)` 唯一索引），跨子系统重名完全正常：

```
Stu 子系统有模块 code=Student → /student/list
Rpt 子系统也有模块 code=Student → /report/student   ← 同一个路由名
```

`registerDynamicRoutes` 的去重集合按路由名判断，于是**第二个被静默跳过**。
表现：菜单里有「学生统计」，点进去是 404；而接口、类型检查、`audit-routes`
**全都是绿的** —— 因为问题不在接口，在路由注册。

抓它的过程本身值得记：我先怀疑"视图文件不存在""glob 没收集到""菜单没返回"，
逐一排除后才在 `registerDynamicRoutes` 里加了一行日志，立刻看到
`item=Student path=/report/student already=true`。
**"我以为的根因"被证伪了五次，最后一次是对的** —— 这个过程比结论更有价值。
修法：路由名前缀子系统 code（`Stu:Student` / `Rpt:Student`）。

> 这个缺陷还有一个"只有它才抓得到"的旁证：它**只影响跨子系统同 code 的那一个模块**，
> 同一子系统内完全看不出来 —— 所以 27 条既有用例全绿也拦不住它。

### 20.3 ★ 一处"级联删除"差点删错东西（审计数据）

实现债 17 时，我一开始把**变更留痕**也一起级联软删了（理由听起来很顺：
"学生都没了还留着流水干嘛"）。结果立刻打红了既有用例：

```
删除学生_记录删除流水并保留姓名与辅号
```

那条用例原本就明确写着"学生删掉之后，流水里仍要能看出这是谁"——
**留痕是这次删除唯一的凭证**：主档已经查不到，姓名与学籍辅号只存在于流水里。
把留痕跟着删掉，等于删完什么都不剩。

教训：**审计数据与业务数据的生命周期必须分开考虑**，
不能因为"都是子表"就一起处理。现在 `CascadeSoftDeleteAsync` 的注释里写明了
为什么留痕**不**在这里处理，并有用例同时钉住两个方向
（子表必须清空 + 留痕必须留下且**变多**）。

### 20.5 ★ SSO 交互式登录：修好了一半，另一半**明确未完成**

**已修好的一处（真实缺陷）**：授权端点在"未登录"分支调的是不带方案名的 `Challenge()`，
而 `DefaultChallengeScheme` 是 OpenIddict 令牌校验（**没有重定向能力**），
于是浏览器拿到**裸 401**。修法是把 `DefaultChallengeScheme` 指向 Identity 应用 Cookie。
实测：`GET /connect/authorize`（未登录）现在 **302 → 登录入口**，不再是 401。

**过程中还修掉一个双重编码缺陷**：`SsoSessionController` 自己
`Uri.EscapeDataString(returnUrl)`，而 `returnUrl` **已经被 Cookie 挑战编码过一次**
（`scope=openid profile` 到达时是 `openid%20profile`），再编码一次变成 `%2520` ——
服务端认不出参数、直接 400，而地址栏里"参数看起来都在"。
改用 `QueryHelpers.AddQueryString`（先解码再编码，幂等）。

**明确未完成的部分**：**前端密码模式登录不建立 Identity 应用 Cookie**，
它只签出 Bearer 令牌；而授权端点认的是 Cookie。
所以"登录成功 → 回授权端点 → 又被送回来"——一段走不通的路。
我一度把 `LoginPath` 也指到前端登录页，跑起来才发现那只会把 401 换成一个
**看起来在跳转、实际永远进不去**的状态（比裸 401 更难查），已撤回并写进注释。

下一步的三步做法（已在 `XjglHttpApiHostModule.ConfigureAuthentication` 注释里写清）：
加 `POST /api/sso/session` 用 `SignInManager.PasswordSignInAsync` 建 Cookie 会话、
前端在**带 returnUrl 时**改调该端点、再补 `LoginPath`。
注意 Cookie 必须落在**前端同源**域上，本机 5173→44300 是跨源的，需要一并确认。

E2E 里有一条**刻意断言"当前是坏的"**的用例（`07-sso.spec.ts` 第三条），
它的作用是：把"未打通"变成可执行的记录，并在真打通后**变红**提醒改断言。

### 21.2 ★ 债 1 的真问题不是"没有事务"，而是"能力放在够不着的地方"

`ISqlSugarTransactionScope` 原本定义在 **`Xjgl.SqlSugarCore`**，
而应用层**不引用那个项目**（分层约定：Application 只依赖 Domain/Contracts）。
后果：审批要写 4 张表却只能各自 `autoSave` 提交 ——
"申请单已通过、学生学籍没改"这种半成品状态成为可能。

**修法**：接口上提到 `Xjgl.Domain.Data.IXjglTransactionScope`，实现留在 SqlSugarCore。

> **一句话教训**：**能力放在调用方够不着的地方，等于没有这个能力。**
> 这条比"忘了加事务"更隐蔽 —— 因为**接口看起来是存在的**（在另一个项目里）。

### 21.3 ★ 一个 ABP 约定式注册的坑：类能解析 ≠ 接口能解析

把接口上提到 Domain 之后，**所有 ChangeFlow 用例全红**：

```
Cannot resolve parameter 'Xjgl.Data.IXjglTransactionScope tx'
```

容器探针给出的答案很明确：

| 解析目标 | 结果 |
|---|---|
| `SqlSugarTransactionScope`（**实现类**） | ✅ OK |
| `IXjglTransactionScope`（**接口**） | ❌ "has not been registered" |

原因：ABP 的约定式注册对"实现了 `ITransientDependency` 的类"
**只把它注册成它自己**，不会顺带注册它实现的**自定义接口**。

修法是显式声明暴露哪个服务：

```csharp
[ExposeServices(typeof(IXjglTransactionScope))]
public class SqlSugarTransactionScope : IXjglTransactionScope, ITransientDependency
```

> **这个坑的通用教训**：**"类能被解析"不等于"接口能被解析"** ——
> 只探实现类会得出"注册没问题"的错误结论。探针必须两条都试。
> （我在接口上继承 `ITransientDependency` 也无效，实测确认。）

### 21.4 ★ 事务"包了"必须用会失败的用例证明

"包了事务"从代码上看不出来，所以三条用例构成完整证据链：

| 用例 | 守住什么 |
|---|---|
| 中途抛异常 → 全部回滚 | 回滚生效 |
| 正常结束 → 数据确实落库 | 不是"永远不提交" |
| **嵌套时内层不提交** | 外层回滚能覆盖内层 |

其中第一条有一个**不可省的中间断言**：

```csharp
await guardians.InsertAsync(NewGuardian(marker), autoSave: true);
// ★ 事务内确实能查到自己刚写入的数据 ——
//   没有它，"回滚后查不到"无法区分"被回滚了"与"压根没写进去"
(await guardians.GetCountAsync(g => g.Name == marker)).ShouldBe(1);
throw new InvalidOperationException("故意失败");
```

**选表也有讲究**：我用 `stu_guardian`（必填列只有三列）。
最初用 `sys_org`，结果红在"插入失败"上 —— `path_code` 是必须由服务层计算的物化路径。
**用例红在"插不进去"上，等于没测到事务语义。**

### 21.5 ★ 债 4：Outbox 的真正价值是"broker 不可达不再影响业务写入"

背景（第 20 章已记录）：不开 Outbox 时，`PublishAsync` 是**在工作单元提交阶段
直接发 broker**；broker 不可达 → 提交失败 → 回滚 —— 而 **HTTP 响应早已写出**，
客户端只看到"成功"。实测：`POST /api/identity/users` 返回 200 带完整用户对象，
但 `AbpUsers` 计数没变。

本轮把前置条件补齐（写在**共享的 EF 模块**里，这样集成测试也能走到它）：

```csharp
// XjglEntityFrameworkCoreModule.ConfigureServices
Configure<AbpDistributedEventBusOptions>(options =>
{
    options.Outboxes.Configure(box => box.UseDbContext<XjglDbContext>());
    options.Inboxes.Configure(box => box.UseDbContext<XjglDbContext>());
});
```

**验证方式（必须有，因为漏配任何一步都不报错）**：直接查 `AbpEventOutbox` 表。

```csharp
var rows = await db.OutgoingEvents
    .Where(e => e.EventName == "Xjgl.Tests.OutboxProbe")
    .Select(e => e.EventData)      // ⚠ 是 byte[]，不是 string
    .ToListAsync();

rows.ShouldContain(p => Encoding.UTF8.GetString(p).Contains(marker));
```

**变异验证**：注释掉 `options.Outboxes.Configure(...)`，
"事件落进发件箱"那条立刻变红（回滚那条仍绿）
→ 证明用例真的盯着这件事，而不是"碰巧绿"。

### 21.7 H5 端到端（债 28）：为什么必须是独立项目

H5 是**另一个 Vite 应用**（端口 5174、hash 路由、移动端布局），
所以 Playwright 配置里两个项目**互相 `testIgnore`**，并**多起一个 webServer**：

```typescript
{ name: 'chromium', testIgnore: /h5-.*\.spec\.ts$/, use: { ...devices['Desktop Chrome'], baseURL: WEB_URL } },
{ name: 'h5',       testMatch:   /h5-.*\.spec\.ts$/, use: { ...devices['Pixel 5'],     baseURL: H5_URL  } }
```

让 PC 的 spec "顺便跑一下"H5 只会制造噪音（登录页字段都不同：
PC 是"请输入用户名"，H5 是"用户名 / 手机号"）。

4 条用例里最有价值的是**横向溢出探针**：

```typescript
const overflow = await page.evaluate(
  () => document.documentElement.scrollWidth - document.documentElement.clientWidth
)
expect(overflow, `「${label}」页在 ${page.viewportSize()?.width}px 宽下有横向溢出`).toBeLessThanOrEqual(1)
```

移动端最典型的布局缺陷就是"某个元素比屏幕宽"，而**桌面宽度下永远不会出现**。

### 21.8 k6 压测：首次实跑的结果与两个坑

**结果（60 VU / 3 分钟 / 3000+ 学生的测试库）**：

| 指标 | 数值 |
|---|---|
| 请求总数 | 8,284（约 44 req/s） |
| `http_req_failed` | **0.00%** |
| `p(95)` / `p(99)` | **461.64 ms** / **933.59 ms** |
| `avg` / `med` | 275.62 / 157.84 ms |
| **`max`** | **23.74 s** ← 只看均值会漏掉 |
| 业务校验通过率 | 100%（13,805/13,805） |
| 429 比例 | **0.00%**（限流未误伤） |

**坑一：k6 里 `BASE` 不能写 `localhost`。** 有些 WSL 的 `/etc/hosts` 里有
`127.0.1.1 localhost.localdomain localhost`，Go 的解析器可能先取到它，
于是报 `dial tcp 127.0.1.1:44300: connect: connection refused` ——
而同一时刻 `curl http://localhost:...` **是通的**（解析顺序不同）。用 IP 即可。

**坑二：演示账号口令各层不同（此结论已被 §22 推翻，保留原文以见排查过程）。**
当时实测 `admin` 用 `1q2w3E*`、`demo-school-9901010001` 用 `Demo@Xjgl2026`，
而 `demo-province-990000` **不可用**。所以脚本的 `setup()` 登录失败时
**直接抛错**，避免"跑完 3 分钟才发现全程 0 请求"。

> **§22 复核更正**：该结论有**两层错误** ——
> 一是用户名抄错一个字母（实际是 `demo-prov-990000`），
> 二是**改了 `Xjgl:DemoData:Password` 后旧库已存在账号的口令不会变**
> （`EnsureUserAsync` 对已存在用户幂等返回）。显式开
> `Xjgl:DemoData:ResetPassword=true` 重跑后可确认：
> `admin` / 省 / 市 / 县 / 校 **五个账号全部 200**。
> 所以"账号不可用"从来不是权限或数据问题，**是文档与种子的口令脱节**。

**这份基线的边界（必须说明）**：数据量只有 3000+ 学生，
**远小于生产的几十万**；它证明的是"当前实现没有明显的并发缺陷"，
**不能**用来推断生产容量。

> 本轮的两个缺陷都发生在**测试与真实使用之间那条缝**上 ——
> 一个是"测试用的账号恰好权限最全"，一个是"测试脚本自己的数据构造方式"。

### 22.2 ★ 缺陷一：菜单为空 —— 权限是两级的，菜单却只认了上一级

**现象**：演示账号登录成功、工作台正常，但左侧菜单**只有写死的「工作台」**，
四个子系统一个都不出现 —— 每个业务页面都进不去。

**根因**（在 `MyProfileAppService.BuildMenus`）：

权限树是**两级** —— 模块权限 `Stu.Student` + 操作子权限 `Stu.Student.Query`。
菜单判定原本只写 `permissionSet.Contains(m.PermissionName)`，即
**必须显式授予"模块"这一级**。而它长期没暴露，是因为：

| 账号 | 被授予的权限 | 结果 |
|---|---|---|
| `admin` | 种子里"当时定义的全部权限"：**模块级 13 条 + 操作级 56 条** | 5 个菜单组全部正常 |
| `DemoOperator`（演示账号） | 按最小权限手工列出：**只有 13 条操作级** | permissions 有 13 条，**menus 是空数组** |

这一点值得单独记住：**admin 之所以看起来正常，纯属"权限给得最全"**，
缺陷只对"按最小权限建的角色"生效。实测数字：
`admin` → permissions 69 / menus 5 组；`demo-prov-990000` → permissions 13 / menus **0 组**。

**修法**：模块**或它的任一操作**被授予，模块即可见（`IsModuleVisible`）。

**这算不算放宽鉴权？不算**，而且方向不能反：
- 菜单可见只是"显示入口"，能不能看数据仍由各接口上的 `[Authorize]` 按操作级权限判定；
- 反过来才是荒谬的 —— **一个能查学生的账号看不到「学生管理」菜单**，等于把功能藏起来。

**回归测试**（`ModuleMetadataTests`，+2 条）：一条**只授操作权限**（复现演示账号情形）
断言模块菜单出现；一条**只授模块权限**断言同样可见。
两条都刻意用**独立角色**而不是 admin —— 复用 admin 的话，它本来就有全部权限，
无论过滤逻辑是否生效断言都通过，用例会退化成**永远绿的装饰**。

### 22.3 ★ 缺陷二：走查脚本自己的两个坑（都不是产品缺陷，但会误导）

**(1) 截图路径写成了相对路径。**
Playwright 解析 `screenshot({ path })` 的基准是**配置文件所在目录**（`web/e2e/`），
不是仓库根目录。写成 `e2e/demo-shots` 后实际落点是 `web/e2e/e2e/demo-shots/` ——
凭空多一层，而 `.gitignore` 忽略的是 `web/e2e/demo-shots/`，
于是**截图会全部混进 git 状态**，同时"按文档去找图"什么也找不到。已改为绝对路径。

**(2) 演示账号的用户名抄错了一个字母**（`demo-province-990000` vs 实际 `demo-prov-990000`），
表现为浏览器里"用户名或密码错误，或账号已被停用"。
但**同一个口令用 curl 打令牌端点是 200** —— 这组对照直接把排查方向从
"账号/口令/权限"收敛到了"脚本里那行字面量"，省掉了整条错误路径的排查。
**遇到"接口能过、界面不能过"时，先做这个对照实验。**

### 22.4 ★ 顺带修掉一个偶发失败的测试（它比看起来严重）

全量跑时 `StatisticsAppServiceTests.异动统计_按异动类型_申请提交后即有真实行` 偶发失败一次，
重跑又绿。**没有当作噪音放过**，追下去发现是测试脚手架的设计缺陷：

```csharp
// 旧实现：撞号就"整棵树重来"
for (var attempt = 0; attempt < 10; attempt++)
    try { return await BuildTreeOnceAsync(); } catch (BusinessException) { }
```

两个致命问题：

1. **重试反而加剧撞号**：撞号只可能发生在某一个编码上，但重试把已经落库的
   省/市/县**再建一遍** —— 库里组织越多，下次越容易撞，是**自我加剧**的循环，
   最终把 10 次额度耗光。测试库实测已累积 **4164 个「统计测试」组织、13342 所学校**。
2. **失败信息指不到原因**：报错是「多次尝试后仍无法生成唯一的组织编码」，
   堆栈指向 `BuildTreeAsync`，看不出哪个编码、撞了什么，很容易被当成统计功能回归。

而且概率根本不小 —— `NewDivisionCode()` 只有 `"42" + 4 位 = 9000` 种，
库里 4164 个组织 ⇒ **单次撞号约 1/10000，而建一棵树要生成 6 个编码**。

**修法**：改为**按单编码定向重试**（`CreateOrgAsync` / `CreateSchoolAsync`，各 20 次），
不再重建整棵树、不再产生垃圾行。

> **在本轮里还踩了一次自己的修改**：为了"降低撞号"把学校码后 4 位放宽成 6 位，
> 结果 6+6=12 位**超过 `StudentNumberRule` 里 `SchoolCode` 段的宽度 10**，
> 18 条用例里 **16 条立刻全红**，报错还指向学号生成，与"改了测试的组织编码"看不出关系。
> 教训：**这个项目里"学校标识码 10 位"是硬约束**（学号 = 学校标识码(10)+流水号(6)），
> 撞号要靠重试解决，不能靠加长号段。

### 22.5 另一种"测试陷阱"：授权写进库 ≠ 权限检查器看得见

写回归测试时踩到两个只有测试里才会遇到的问题，都记进了注释：

| 陷阱 | 表现 | 原因 |
|---|---|---|
| 主体缺 `role` claim | 明明授了权，`permissions` 却是**空数组** | 角色授权靠主体里的 `AbpClaimTypes.Role` 解析；真实 JWT 带 `role` claim，测试替身 `SetUser(id, name)` 默认不带 |
| `IPermissionDataSeeder` 不失效缓存 | 同上，报"应该包含 X 但实际是 []" | 它只写授权表；`IPermissionChecker` 读的是缓存。改用 `IPermissionManager.SetAsync`（会失效缓存） |

两者都会把排查带向"权限解析/菜单逻辑坏了"，实际是测试自己没准备好上下文。

## 23. 第五轮：角色管理补齐，以及三个"权限形状不对"的缺陷（2026-09-19，已实测）

用户看着「权限管理」页的截图问：**"没看到怎么添加修改删除角色，也没见到怎么给角色分配权限"**。
这一问暴露的不是"少写一个页面"，而是**三处彼此独立的权限问题** ——
它们共同的形态是：**失败的样子不像权限问题**，所以每次都把人带到错误的方向。

### 23.1 先分清：哪些"没有"是真没有

| 用户说"没看到" | 实际情况 |
|---|---|
| 怎么给角色分配权限 | **已经有了**，就在那一页：选「角色」→ 选具体角色 → 展开分组勾权限 → 保存。分组默认折叠，所以第一眼看不到 |
| 怎么增删改角色 | **真的没有**。后端（ABP 自带 `/api/identity/roles`）完整支持，前端零入口 |

**补的东西**：新增元数据模块 `Sys.Role` + 页面
`web/apps/pc/src/views/system/role/index.vue`，列表每行带「分配权限」直达
（跳 `/system/permission?role=xxx`，权限页据此预选角色）。

### 23.2 ★ 缺陷一：未授权时返回的是 302，而不是 403 —— 于是错误"消失"了

演示账号读角色列表**读不到**，而且**没有任何提示**。实测：

| 接口 | admin | demo-prov-990000 |
|---|---|---|
| `GET /api/identity/roles` | 200 | **302** |
| `GET /api/identity/roles/all` | 200 | **302** |
| `GET /api/identity/users` | 200 | **302** |

根因是**两个权限层次**：ABP 自带的身份接口判的是 `AbpIdentity.Roles` / `AbpIdentity.Users`，
**不是**我们的业务权限；演示角色只有业务权限，所以被拒。
而它拒的方式是 **302 重定向到登录页**，浏览器 XHR 会静默跟随，于是前端拿到 **200 + 登录页 HTML**。

**接着是最关键的一点（我一开始也判断错了）**：
我原以为错误被 `catch { roles.value = [] }` 吞掉了，于是在页面上加了提示。
但提示**没有出现** —— 单独探针测出来真相是：

```
axios 收到（200 + text/html）→ NO THROW | typeof data = string | value = "<!DOCTYPE html>..."
```

**axios 对"解析失败"是静默降级的**：不抛异常，把原始字符串当 data 返回。
于是 `r.items` 是 undefined、`totalCount` 是 undefined，页面**从容地**渲染出一个空表格 ——
**连 catch 都没进**。这不是"错误被吞"，是"错误根本没被当成错误"。

**修法**（在 `web/packages/api/src/http.ts` 的响应拦截器里，**全站生效**）：
拿到 `content-type: text/html` 就主动抛一个可识别的 `SyntaxError`，
由页面翻译成"服务端返回的不是 JSON —— 未授权时接口会重定向到登录页，
请确认拥有框架权限 `AbpIdentity.Roles`"。同时给演示角色补上
`AbpIdentity.Roles*` 与 `AbpIdentity.Users*`（只读 + 增删改，**刻意不给**
`*.ManagePermissions`，也不给任何 `AbpTenantManagement.*` / `FeatureManagement.*`）。

> **一句话教训**：**HTTP 层"成功"不等于业务层成功。**
> 302 → 跟到登录页 → 200 + HTML，在 axios 眼里是一次成功的 GET。
> 这类失败不会出现在任何异常日志里，只能靠"检查响应的形状"发现。

### 23.3 ★ 缺陷二：「分配权限」点了掉进 404

角色管理按 `Sys.Role.*` 放开，而权限页（`/system/permission`）这个**路由**由
`Sys.Permission` 决定 —— 两者可以独立授权。演示账号有前者、没有后者，
于是"分配权限"按钮点下去直接是 **404 页面**。

**修法**：按权限显隐这个按钮（与用户管理、学生管理等页面同一约定）。
**不是**"把权限补上就完事" —— 因为"能管角色、不能配权限"是一个合理的授权组合，
系统必须能正确表达它。

### 23.4 ★ 缺陷三：测试用例自己踩的三个坑（都不是产品缺陷，但很费时间）

| 现象 | 真实原因 |
|---|---|
| 建角色报 403「角色名已存在」，而表面症状是"弹窗关不掉" | 前置清理**偶发失效**：`settle()` 等的是 loading 蒙层消失，而蒙层可能**还没出现**就被判为已消失 → 读到尚未加载的**空表格** → 判"无残留"。准备/收尾改成**走接口**（确定性），界面删除另立断言保留覆盖 |
| `page.request` 调接口拿到未授权 | `page.request` **共享 Cookie 但不共享 localStorage**，而令牌在 localStorage 里。改用独立 `APIRequestContext` 自己走一次令牌登录 |
| `.perm__header` 定位不到 | Vue **scoped 样式**把类名编译成 `perm__header[data-v-xxx]`，`.perm__header` 选择器不匹配 → 用 `[class*="perm__header"]` |

## 25. 第七轮：把剩下的做完（2026-09-29，已实测）

### 25.1 这一轮最重要的变化：**集成测试真的跑起来了**

前几轮所有"已实测"都成立，但本轮的验证条件本身先被卡了一次：

```
FATAL: could not signal for checkpoint: Operation not permitted
```

绕开的办法不是"再试一次"，而是**换一个干净关闭的集群**：
崩溃恢复才需要那个 checkpoint，`initdb` 出来的新实例不需要。

> **诚实标注**：这台临时集群是 `--locale=C`（PG 在 Windows 上没有 `C.UTF-8`），

### 25.2 组织层级校验补齐（ROADMAP 20）

四级树（省 → 市 → 县 → 校）是硬规则，但**新增与移动两条路都没有校验**。
本轮补上，并且**两条路共用同一条规则**：

- 指定了父节点 → 父节点类型必须是 `SysOrg.ExpectedParentOf` 要求的那一级；
- **没有父节点 → 允许任意类型作为根**（刻意保留）；
- 错误码 **`Xjgl:00104`**（`OrgHierarchyInvalid`）。

保留"允许作为根"的理由是可验证的：界面上"新增下级"会按当前节点自动推断类型，
用户没有机会凭空建一所"没有上级的学校"；而导入与测试会直接造单点数据，
把它当错误挡掉只会逼出一堆纯为满足校验的脚手架数据。
这条决定由一个专门的用例（`不指定父节点时允许作为根节点`）**固定下来**，
免得以后有人"顺手"改成必须给父节点。

### 25.3 按角色配置数据范围（ROADMAP 9）——顺带揪出两个"比配置更宽"的缺陷

新增业务表 `sys_role_data_scope`（一个角色一行；**没有配置行 = 沿用按组织层级推导**，
所以升级后现有角色行为完全不变）。解析顺序：admin 旁路 → 角色配置（取**最宽**）→ 层级推导。

"取最宽"是刻意的，理由写在 `DataScopes.ResolveEffective`：权限是**加法**的，
若数据范围反过来取最窄，就会出现"给某人加一个全省角色，他反而看得更少"——
没有人能理解、也没有人能排查。

**真正有价值的不是这个功能本身，而是对照式用例抓出来的两个缺陷**：

| 缺陷 | 为什么危险 |
|---|---|
| **预置名单查询完全无视 `OrgOnly`** | 它没有像学生/照片/留痕那样把"后代"那一半换成哨兵前缀，于是配了「仅本级」照样能看到下属县的人。**方向是放宽**（管理员以为收紧了） |
| **`IncludeDescendantOrgs = true` 排除了该组织自身** | "整棵子树"显然含根自己。表现是"刚建完就查不到"，而代码里另有一处注释正好警告过这个症状 —— 说明当时只修了一半 |

两条都在**学生 / 预置名单**两处统一为"本级 **或** 后代"。
顺带把哨兵前缀 `DataScopes.ImpossiblePathPrefix` 上提共享：它原本在 3 个服务里各写一份
`private const`，而**漏掉的那一处**（预置名单）就是上面第一个缺陷。
"复制四份、漏掉一份"这类缺陷，靠 code review 是抓不住的。

> **一句话教训**：**"看不到"必须能被归因，才叫验证。**
> 所以每条用例都做"同一用户、同一份数据、**只改配置**"的对照：
> 先断言未配置时**看得到**，再断言配置后**看不到**。
> 只断言后半句的话，"看不到"完全可能是数据没建出来或权限不对造成的。

### 25.4 H5「缺照片名单 → 上传」（ROADMAP 10）

`#/photo/missing` 子页面：关键字查询 + 每次 20 条的"加载更多" + 点学生卡片直接进入
**确认姓名 → 拍照 → 上传**，全程不用输学籍辅号。确认姓名那一步保留 ——
照片装错人是很难在事后发现的错误。

做的过程中有两个判断值得记下：
1. **做成子页面，而不是第 4 个页签**：名单只是"把照片补齐"这一个任务的队列，
   4 个页签在 320px 下会把「拍照上传」挤成两行；而且名单与取景区都需要整屏高度。
2. **秒传（skipped）不能从名单里移除**：名单是按 `StuStudent.PhotoPath` 为空筛的，
   只有"上传成功"与"降级暂存"两条路径会写它。把秒传也算成功移除，
   会让"名单清空了但照片还是缺"——一个查不出来的状态。

H5 **发起**异动申请仍未做：它需要先定"移动端怎么选目标学校"
（`orgApi.getTree()` 自述"上万所学校时不要用"）与入口归属两个产品决策，
而 300~400 行且起不了 dev server 的移动端交互，交付出去就是猜。

### 25.6 本轮**未做**：权限委派（ROADMAP 19）——它需要一个设计决定

不变更结论：**没有实现，也不该在没有决定的情况下实现**。

§5.2 的方案要求"委派出去的权限必须是授予者权限的子集，**并且受同一套数据范围约束**"。
前半句（子集约束）在授权时就能校验；**后半句落不下去**：
现在的 `IUserDataScopeProvider.GetAsync()` **不接收"正在行使哪个权限"**，
因此无法表达"同一个人的 A 权限限制在甲县、B 权限限制在乙县"。

若把范围约束省掉、只落子集约束，那就得到一个**提权通道**：
被委派人拿到权限后，可凭自己的数据范围看到委派人本来看不到的数据 ——
正是 ROADMAP 里那句"否则委派就成了提权通道"。

两条可选路径（需要产品/架构决定，不是实现细节）：
- **(a) 权限感知的数据范围**：把 `GetAsync(permissionName)` 化，
  数据范围取"自身范围 ∩ 委派范围"，各查询再按权限名解析 —— 影响面是所有列表查询；
- **(b) 委派即授权 + 组织收敛**：委派时直接把权限授给被委派人（走 ABP 原生授权，
  `[Authorize]` 立刻生效），代价是**放弃按权限分范围**，
  改为"一次委派一个组织子树"的粗粒度模型。

### 26.2 ★ 一个"永远空着的列"（本轮最值得记的缺陷）

写"申请单导出"的用例时断言 `当前节点` 应等于"转入学校审核"，结果是**空字符串**。追下去：

（只有"待办"页签有值）。界面不报错、也不缺列，**只是一个空格子** ——

### 26.3 权限委派（ROADMAP 19）——以及"把安全边界说清楚"的价值

方案文档 §5.2 要求"委派出去的权限必须是授予者权限的子集，**并且受同一套数据范围约束**"。
前半句（子集）实现起来直接；**后半句落不下去** ——
现在的 `IUserDataScopeProvider.GetAsync()` **不接收"正在行使哪个权限"**，
无法表达"同一个人的 A 权限限甲县、B 权限限乙县"。

本轮的做法是把**安全边界想清楚之后**再落：

- 委派**只授予"能不能调这个接口"，不改动"能看哪些数据"**；
- 数据范围层与权限**无关**（按被委派人自己的组织算）→
  被委派人**看不到一件他自己本来看不到的数据**，因此**不存在提权通道**；
- 代价如实写进 ROADMAP：委托给范围更小的人，他仍只能在自己范围内办事；
  **"代我审我这一片"这种按权限限定范围的委派做不到**。

> 这一步比"照着 §5.2 硬做"更重要：**只做子集约束、不做范围约束**看起来是"完成了一半"，
> 实际是**造了一条提权通道**（被委派人凭自己的范围去看委派人看不到的数据）。
> 想清楚"哪一半不做、为什么不做、代价是什么"，比硬凑一个看起来完整的实现安全得多。

另外两个决定：

1. **允许委派的判定用"允许清单"**：默认不可委派，只有业务办理类可以；
   导出类（把数据带走）、`Sys.*`（系统管理）、运维动作都不可委派。
   方案文档设想的是给每条权限挂一个 `CanDelegate` 属性 ——
   但权限是元数据驱动的，加一个字段意味着"新权限默认能不能委派取决于写代码的人记不记得设"，
   而**记错的代价是把系统管理权限借出去了**，界面上还看不出来。
2. **到期必须真的回收**：授权在 ABP 的授权存储里，而 `[Authorize]` 不认台账表 ——
   只在查询时过滤台账等于一条到期委派**永远生效**。因此加了
   `PermissionDelegationExpiryWorker`。

### 26.5 收尾：一个"后端做完、前端没有入口"的漂移，与 H5 的最后一条路径

#### (1) 不变式检查抓出来的东西，比人眼可靠

给 `tools/check-permissions-sync.mjs` 加了一条不变式：**导出任务种类前后端一致**
（`ExportTaskConsts.cs` ↔ `types.ts` 的 `ExportTaskKinds`）。第一次跑就报红：
后端 8 种、前端 6 种 —— 缺的正是 `ChangeApplyCsv` / `ChangeAuditCsv`。

这意味着**后端把异动导出做完了，而界面上根本没有入口**。它不会报错、不会 404，
只是"这个功能永远点不到"，而集成测试从服务层直接调用，绕过了前端，所以全绿。

> **教训与 26.2 同源**：**"后端有、前端没有"与"字段有、值为空"是同一类缺陷** ——
> 都需要**换一个出口读一遍**才会现形。前者换的是"调用方"（服务层 → 界面），
> 后者换的是"读取方"（待办查询 → 导出）。这类"跨层契约"最省事的探测手段不是再写一遍
> 人工检查清单，而是**写成脚本**：清单会过期，脚本每次都会跑。
> 现在这条脚本有 **6 处不变式**：权限码 / 码类别 / 元数据操作类型 / 导出种类 /
> 数据范围 / 异动与待办状态。

补齐方式：申请页「导出」（`Chg.Apply.Export`）→ 申请单清单；
审核页「导出审核流水」（`Chg.Audit.Export`）→ 审核台账。两处都**沿用当前筛选条件**
（与组织 / 微代码 / 学生导出同一口径：**看到什么就导出什么**），
且都展示 `describeTruncation` 的截断提示 —— 异动这两种**会截断**
（申请单没有天然上限，后端按 `Xjgl:Export:MaxRows` 收口），
"少了几条却只弹成功"是名单类产出最不可接受的失败方式。

#### (2) H5「发起异动申请」：两个产品决策，落地时定型

ROADMAP 10 原来把这一项挂在"等产品决策"上。本轮按**能用一句话说清理由**的原则定型：

| 决策 | 选择 | 理由 |
|---|---|---|
| 入口放哪 | 「我的」→「业务入口」，按 `Chg.Apply.Create` 显隐 | 「待办」的语义是"轮到我审"；发起是反方向。混进待办会让"今天有几件事等我"这个数字失真 |
| 怎么选目标学校 | 关键字检索（≥2 字、最多 20 条、超限明说） | `orgApi.getTree()` 自述"上万所学校时不要用"；逐级下钻 4 次点击。超限时**不静默截断**，而是提示继续输入 |

学生同样走关键字检索，并且**不自动选中**：点一行后收起列表、换成
"已选学生（请核对姓名）"块（姓名 + 学籍辅号 + 学校/年级/班级）——
与照片补采同一套理由：**选错人的代价是别人的学籍被动过**。
提交成功后停在结果卡片（申请单号 / 共 N 步）而不跳待办（自己提的单不会出现在自己的待办里）；
提交失败**不清空**已填内容，`catch` 里也不重复弹提示（拦截器已按后端 `reason` 弹过）。

为此在 `@xjgl/api` 补了 `orgApi.getList`（`GET /api/app/org`）——
原以为它存在，实际只有 `getTree/getRoots/getChildren/...`。新增调用后
`audit-routes` 的"已核对调用数" +1，而**不匹配项一条没增**。

**⚠ 未实测**：本沙箱起不了 `vite dev/build` 与 Playwright，
所以 H5 页面在 320~414px 下无横向滚动是**据样式推理**（`min-width: 0`、
`overflow-wrap: anywhere`、全宽控件，与已通过的 H5 待办页同一套写法），**没有在浏览器里跑过**。

#### (3) 异动附件（ROADMAP 18）：一个"勾了等于没勾"的开关，变成真的拦审批

异动类型上一直有个「必须上传证明材料」开关，但**没有任何读取方** ——
上一轮因此把它删了（"勾了不影响任何行为"的开关比没有更坏）。本轮把附件能力
连同**行为**一起补回来，关键取舍有三处，都写进了代码注释：

| 取舍 | 结论 | 理由 |
|---|---|---|
| 校验点 | **批准前**，不是提交时 | 提交那一刻申请单还不存在（`applyId` 是提交时生成的），客户端没有东西可挂附件；要按"提交时必须带附件"做就得先引入"草稿"阶段，那是流程改造 |
| 只查哪次批准 | **第一次批准** | 批过一次就说明材料当时是齐的；后续节点再数一遍没有价值（撤销审核退回待处理时，用"当前序号最小"判断会把已放行的单子重新卡住） |
| 存储 | **独立的本地文件存储**，不复用照片那套主/降级 | 照片的补偿回放只扫描**照片表**；附件若走同一条路，NAS 故障期间写入的附件**永远不会被回放**——"以为存住了、其实没有"的静默丢失。代价如实记下：多副本部署需要共享卷 |

#### (4) ★ 一个"真机上必然 404"的路由错误（集成测试抓不到）

`tools/audit-routes.mjs` 在重新生成 swagger 快照后只剩 **1 项**不匹配：

```
✗ POST /api/app/role-data-scope   → 后端: GET
```

真实路径是 `POST /api/app/role-data-scope/**set**` —— ABP 会把不以
`Get/Create/Update/Delete` 开头的方法按**方法名**补一段路径。前端少写了 `/set`，
于是"保存角色数据范围"在真机上必然 404/405。

**为什么一直没被发现**：集成测试**直接调应用服务**，HTTP 层根本没参与 ——
越权、数据范围、业务规则都测得出来，**唯独测不出"路径写错"**。
所以这类缺陷只有两条路能抓：真的发一次请求，或者**用后端自己生成的路由表核对**。
这也是这份仓库保留 `audit-routes.mjs` 的全部理由。

> **顺带一条维护经验**：那份 swagger 快照停在 2026-09-17，于是脚本一次报了
> **23 项**"不匹配"，其中 22 项只是"快照里没有这个新接口"。**噪声会淹没信号** ——
> 23 项里有 1 项是真的，而人看到 23 项时第一反应是"又是快照过期"。
> 正确做法是**每次改接口后重新生成快照**（起一次 Host，抓 `/swagger/v1/swagger.json`），
> 让"不匹配"永远等于"真的有问题"。

#### (5) 给已有数据的表补一个非空列，会让整个迁移失败

重新加回 `stu_change_type.require_attachment` 时，DbMigrator 直接失败：

```
23502: column "require_attachment" of relation "stu_change_type" contains null values
```

原因是 CodeFirst 补列时执行的是 `ALTER TABLE ... ADD COLUMN x boolean NOT NULL`，
而 PostgreSQL 要求**新增的 NOT NULL 列必须带默认值**（老行要被回填成什么？）。
这不是"某一张表的问题"：任何"给已上线的表补一个非空列"都会踩到。

修在**映射约定**里（`SqlSugarClientFactory`）：非空值类型列一律带上与 C# `default(T)`
一致的数据库默认值，于是 DDL 变成 `ADD COLUMN ... NOT NULL DEFAULT false`，
PG 会把存量行回填。**不修在实体上**：领域层要保持对 ORM 无感知，
所以规则和字符串长度约定一样集中在一个地方。
（顺带踩到：`Guid` / 时间类型的默认值字面量**不能自带单引号** ——
SqlSugar 会把它当参数值，PG 报 `22P02: invalid input syntax for type uuid: "'0000…'"`。）

#### (6) 审核员"有审核权限却打不开任何一条"

`GetApplyAsync` 只认 `Chg.Apply.Query`，而审核页点开待办走的正是这个接口。
只被授了 `Chg.Audit.*` 的审核员于是能看见待办列表、**点详情 403**，
权限管理页上却明明勾着审核权限 —— 这类"勾了权限却按不出功能"最难解释。

改法：**读权限 = 申请查询 或 审核查询，任一即可**（写权限不变，仍是
`Chg.Apply.Update`，审核人只读材料、不能替换材料）。
实现上有个必须注意的细节：ABP 的 `[Authorize(A, B)]` 是**全部满足**语义，
表达不了"任一"，所以接口层只要求登录，真正的判断放在应用服务里用
`IPermissionChecker` 逐条判。副作用是集成测试里凡要读申请单的操作者
**必须真的被授了权限**（测试基类放行 `[Authorize]`，但不替换 `IPermissionChecker`）——
这一点写进了 `ChangeAttachmentTests` 的注释。
