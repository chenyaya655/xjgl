## 3. ★ 异动工作流（本方案的核心）

### 3.1 为什么自研「可配置审批流」而不是套 BPMN 引擎

你的核心诉求是「**同县区转学县区只审一次，同市转学市只审一次**」。这不是普通的条件分支，而是**流程实例化时按实际组织去重合并**——BPMN 要表达它得堆一堆排他网关，业务人员根本改不动。

所以设计成：**节点用「组织解析器」描述，实例化时解析出真实组织，相同组织的节点自动合并。** 业务人员看到的是「加一个节点 → 选这是哪一级（转入校/转入县/转入市/转出校/…） → 选审核角色 → 选是否必经」，不需要懂任何流程建模语言。

> 备选：Elsa Workflows 3（图形化强，但上述合并语义仍要自定义 Activity，且业务人员要学 BPMN 概念、还有在途单据的版本迁移问题）。**我推荐自研**，见第 15 章 Q1。

### 3.2 异动类型管理（独立模块）

`stu_change_type`

| 字段 | 说明 |
|---|---|
| `Code` / `Name` | 异动代码（如 `TRANSFER_IN`）/ 异动名称（如「转入」） |
| `CategoryCode` | 异动分类（转学类 / 休复类 / 退学类 / 毕业类 / 其他） |
| `BeforeStatus` → `AfterStatus` | 该异动导致的学籍状态变化（码值引用微代码「学籍状态码」） |
| **`MaxApproveLevel`** | **审核终止级别：校 / 县 / 市 / 省** —— 你的「需要哪一级审核完成就算结束」 |
| `NeedPeerSchoolConfirm` | 是否需要对方学校确认（转学 = 是，休学 = 否） |
| `AffectGrade` / `AffectClass` | 是否影响年级 / 班级 |
| `AllowCrossSchool` | 是否允许跨校 |
| **`ApplyTimeRule`** | **异动时间控制**：允许申请的起止日期、是否限定学期、是否允许跨学年、每年可申请次数上限 |
| **`GradeScope`** | **年级控制**：允许申请的年级集合（如毕业年级禁止转学）、最小/最大年级 |
| `FlowTemplateId` | 绑定的流程模板（当前启用版本） |
| `RequireAttachment` / `AttachmentTypes` | 是否必须上传证明材料及类型 |
| `Sort` / `IsEnabled` / `Remark` | — |

**模块功能：** 增删改查、启用停用、排序、**流程设计**跳转、时间与年级规则配置、导入导出、复制。

### 3.3 流程模板设计

| 表 | 关键字段 |
|---|---|
| `stu_change_flow_template` | Id, ChangeTypeId, Name, **Version**, Status(草稿/已发布/已停用), PublishedTime, Remark |
| `stu_change_flow_node` | Id, TemplateId, **Seq**, Name（如「转入学校审核」）, **NodeAction**(Submit/Approve), **OrgResolver**, LogOrgType, **RoleCode**, TimeoutDays, AllowReject, AllowDelegate, RequireAttachment, **MergeStrategy**(MergeToLast/MergeToFirst/NoMerge), IsEnabled |
| `stu_change_flow_task` | Id, ApplyId, **NodeSnapshot(JSON)**, NodeSeq, MergedFromSeqs, ResolvedOrgId, ResolvedOrgName, RoleCode, Status(待处理/已通过/已驳回/已跳过/已合并/已撤销), AssigneeUserId, HandledBy, HandledTime, Opinion, DueTime |
| `stu_change_flow_log` | ApplyId, TaskId, Action(提交/通过/驳回/退回/转办/撤销审核/催办/归档), OperatorId, OperatorOrgId, Opinion, Time, ClientIp |

**`OrgResolver` 组织解析器枚举**（节点按它解析出真实组织）：

`ApplicantSchool`（发起人所在学校）/ `StudentSchool`（学生当前学籍校）/ `TargetSchool`（目标/转入校）/ `SourceSchool`（原/转出校）/ `TargetCounty` / `TargetCity` / `SourceCounty` / `SourceCity` / `Province` / `FixedOrg`（固定组织）

**`MergeStrategy` 说明：**
- `MergeToLast`（**默认**）：解析到同一组织的节点合并到**序号最靠后**的那个，前面的标记为「已合并」并记录 `MergedFromSeqs`。→ 上级成为终审，符合实务。
- `MergeToFirst`：合并到最靠前的节点。
- `NoMerge`：不合并。

**`MaxApproveLevel` 截断**：实例化时只保留到「审核终止级别」的最后一个节点，之后的节点不生成。

**在途单据的稳定性**：任务实例保存 `NodeSnapshot`（节点定义 JSON 快照），模板改版只影响新单据。

### 3.4 实例化算法

```
输入：异动类型 → 流程模板(当前发布版本) → 节点定义列表；异动单据上下文
1. 可行性校验
   - ApplyTimeRule：当前日期是否在允许窗口内、学期/学年限制、次数上限
   - GradeScope：学生当前年级是否在允许范围
   - 学籍状态是否允许该异动（BeforeStatus 匹配）
2. 组织解析
   node.ResolvedOrgId = OrgResolver.Resolve(上下文)   // 学生、目标校、目标年级班级、发起人组织…
3. 截断
   按 MaxApproveLevel 保留到该级别的最后一个节点
4. 合并（核心）
   按 ResolvedOrgId 分组（MergeKey = 解析出的组织Id）
   组内按 MergeStrategy 决定保留哪个 Seq，其余 Status=已合并
   若同组节点解析出的组织不一致 → 降级为不合并 + 记告警日志
5. 生成 stu_change_flow_task（含快照），apply.CurrentSeq = 第一个有效节点
6. 发首个待办通知（站内信 + 短信 + 微信模板消息，按角色配置）
```

### 3.5 场景推演（请你验证这几条是否符合河南实际业务）

**流程模板 A —— 转学（6 个节点定义）**

| Seq | 节点名 | OrgResolver | 审核级别 |
|---|---|---|---|
| 1 | 转入学校提交 | `TargetSchool` | 校 |
| 2 | 转入县区审核 | `TargetCounty` | 县 |
| 3 | 转入地市审核 | `TargetCity` | 市 |
| 4 | 转出学校审核 | `SourceSchool` | 校 |
| 5 | 转出县区审核 | `SourceCounty` | 县 |
| 6 | 转出地市审核 | `SourceCity` | 市 |

推演结果：

| 场景 | 合并情况 | 最终实际流程 |
|---|---|---|
| **跨市转学**（6 个组织全不同） | 无合并 | ① 转入校 → ② 转入县 → ③ 转入市 → ④ 转出校 → ⑤ 转出县 → ⑥ 转出市 |
| **同市跨县转学** | ③ 与 ⑥ 同市 → 合并到 ⑥ | ① 转入校 → ② 转入县 → ④ 转出校 → ⑤ 转出县 → **⑥ 市局（合并审一次）** |
| **同县区转学** | ②⑤ 同县 → 合并到 ⑤；③⑥ 同市 → 合并到 ⑥ | ① 转入校 → ④ 转出校 → **⑤ 县区（合并审一次）** → **⑥ 市局（合并审一次）** |

**流程模板 B —— 休学（3 个节点）**：① 学校提交 → ② 县区审核 → ③ 市局审核，`MaxApproveLevel = 市`。

**模板 C —— 需省级审核的异动**：在 A 或 B 后追加 ⑦ 省厅审核，`MaxApproveLevel = 省`。

> 👉 **请确认这 4 个推演是否符合业务**。如果「同县区转学」你期望的是 `转入校 → 县区 → 转出校`（县区在中间审），那我们把该模板的 `MergeStrategy` 改成 `MergeToFirst` 即可，**不用改代码**——这正是配置化的价值。

### 3.6 业务人员如何调流程（不改程序）

- 入口：`异动管理 → 异动类型管理 → 选中类型 → 流程设计`
- 界面：**横向步骤条 + 节点配置面板**（新增/删除/拖拽排序/上下移），每节点配置：名称、组织解析器、审核角色、超时天数、是否必经、是否允许退回/转办、**合并策略**
- **流程预览（关键功能）**：选一个模拟学生 + 目标学校 → 实时推演出实际节点序列和合并结果，业务人员一眼就能看到「同县区会合并成几步」
- 版本管理：保存为新版本 → 发布 → 只对新单据生效；在途单据走快照
- 复制流程、导入/导出 JSON 模板、停用

### 3.7 审核操作与规则

| 操作 | 规则 |
|---|---|
| 通过 | 推进到下一有效节点；已是最后节点 → 执行「通过后动作」并归档 |
| 驳回 | 退回到**指定前置节点**或**退回发起人**，填写驳回原因，记录日志 |
| 退回上一节点 | 同上，仅退一格 |
| **撤销审核** | 限制：① 仅当前节点处理人（或上级管理员）② 后续节点均未处理 ③ 未归档。撤销后当前节点回「待处理」，写 `stu_change_flow_log` |
| 转办 / 加签（可选） | 转办给同组织同角色的其他人；加签插入临时节点 |
| 催办 / 超时 | 按 `TimeoutDays` 定时扫描 → 提醒次数递增 → 超时告警 |
| 撤回申请 | 发起人在首节点未处理前可撤回 |

**通过后动作（同一事务 + 领域事件）：**
1. 更新 `stu_student` 的学籍状态 / 学校 / 年级 / 班级（按异动类型的 `AffectGrade/AffectClass` 决定）
2. 写学籍变更流水 `stu_change_log`
3. 写异动台账（用于月报年报）
4. 目标学校确认（`NeedPeerSchoolConfirm`）= 是时生成对方学校节点
5. 发通知（申请人 + 相关管理员）
6. 失效统计缓存

## 4. 组织管理（教育局 / 学校 / 年级 / 班级）

### 4.1 ★ 两层建模（重要设计判断）

| 层 | 表 | 是否进组织树 | 变动频率 |
|---|---|---|---|
| **稳定组织** | `sys_org`：省教育厅 → 市教体局 → 县区教体局 → 学校 | ✅ 是（数据范围与权限的锚点） | 低（撤并校、区划调整） |
| **学年组织** | `sys_grade` / `sys_class`：挂在学校下，带 `AcademicYear` | ❌ 否 | 高（每年升级、分班） |

**为什么不把年级班级放进组织树**：一旦年级班级成为权限锚点，每年升级都要重构组织树和历史权限，且权限树会膨胀到几十万个节点。分开后，「升级」只是学年维度的一次数据操作。

### 4.2 教育局管理模块

- `sys_org`：`OrgType`(Province/City/County/School)、`Code`、`Name`、`ShortName`、`ParentId`、`PathCode`（物化路径，如 `410000.410100.410102`）、`Level`、`Sort`、`IsEnabled`
- `sys_edu_bureau`：局别、邮政编码、地址、联系电话、负责人
- `sys_org_jurisdiction`：**管辖关系覆盖表** —— 处理「省直管县（济源）」「市代管县」这类**非严格树形**关系
- 功能：增删改查、批量导入、排序、启用停用、**变更历史**（`sys_org_history`）、导出

### 4.3 学校管理模块

- `sys_school`：**学校标识码（10 位）**、学校名称、学校类型码、办别码（公办/民办）、城乡码、举办者、学制、校长、联系电话、地址、经纬度、启用状态、**撤并标记**与撤并去向
- `sys_school_history`：改名、变更归属县区、撤并 → 留痕（历史学籍数据不能乱）
- 功能：增删改查、批量导入（教育厅学校名录）、按区划/类型/办别筛选、启用停用、导出

### 4.4 年级班级管理模块

- `sys_grade`：学校、`AcademicYear`、年级码、年级名称、班主任、学生数（缓存）
- `sys_class`：学校、`AcademicYear`、年级、班级号、班级名称、班主任、教室、学生数
- 功能：**批量生成**（选学校 + 学年 + 年级 → 自动建 N 个班）、编辑、调班、**升级 / 毕业批次任务（预演 DryRun → 执行 → 回滚）**、导出

## 5. ★ 权限模型（回答你的问题）

### 5.1 三种方案对比

| 方案 | 做法 | 问题 |
|---|---|---|
| **1. 不区分** | 有某权限的人就能把它授予任何下级 | 全省统一部署下，**越权风险高**：一个县管理员可能给别的县、甚至给非管辖范围的人授权；无法表达「只能给下级授」 |
| **2. 拆成「操作权限」+「授权权限」两条** | 每个权限项变成 2 条 | 直观，但条目数 **×2**（约 60 模块 × 8 操作 = 480 → 960 条），授权界面爆炸、配置易错；而且实务中「能操作」和「能授权」的集合几乎总是一致——真正重要的「**授权范围上限**」这个维度反而没表达出来 |
| **3. 单条目 + 委派属性 + 双重硬约束** ⭐ | 权限项加 `CanDelegate`（可继续下放）标记；授权时强制 **① 子集约束** ② **范围约束** | 条目不膨胀；天然支持多级下放；越权在服务层被硬约束挡住 |

### 5.2 推荐：方案 3

**两条硬约束（服务层强制执行，不可绕过）：**

```
约束① 子集约束：A 能授予 B 权限集合 S  ⟺  S ⊆ A 已拥有的权限
约束② 范围约束：A 能操作 B 的账号      ⟺  B.OrgId ∈ A 的数据范围
                   （且 A 不能给自己授权、不能修改自己所属角色的权限）
```

**三个补充机制：**

1. **`IsDelegatable` 开关**（权限定义级，默认 `true`）：敏感权限（用户管理、权限分配、系统参数、审计日志、数据导出）设为 `false` → 只有被显式授予「委派权」的角色才能下放这类权限。
2. **超级管理员**：种子数据创建 `admin`（省厅超管），`IsSuperAdmin = true`，绕过全部权限校验（复用 ABP 的 always-allow 机制）。用于首次初始化与应急。
3. **授权变更全量审计** `sys_permission_grant_log`：谁、什么时间、把什么权限、授给谁、在什么范围内 —— **政务系统必备**。可选的「敏感权限授予需上级审批」先留钩子，本期不实现。

**逐级委派链路（完全符合你的描述）：**

```
admin（省厅超管，全部权限）
  └─ 创建省级用户 A，授予「省厅学籍管理员」角色
       └─ A 创建同级（其它省级用户）与下级（市级用户 B）并授权
            └─ B 创建县级用户 C 并授权   （B 只能授出自己有的，且只能给本市范围内的人）
                 └─ C 创建学校管理员 D 并授权
                      └─ D 管理本校用户
```

**数据范围**（与权限正交）：全部 / 本级及下级 / 仅本级 / 仅本人 / 自定义组织集合。授权时范围约束取「授权人的数据范围」。

### 5.3 权限码与授权界面

- 权限码：`{子系统}.{模块}.{操作}`，如 `Stu.Change.Audit.Approve`
- 授权界面：**子系统 → 模块 → 操作** 三级树（勾选），右侧同步显示「数据范围」下拉
- 附：权限模板（校级管理员 / 县级审核员 / 市级审核员 / 省厅管理员）一键套用；授权矩阵 Excel 导出；「我是谁、我能做什么」自查页

## 7. ★ 生僻字全链路方案（姓名必须正确显示）

### 7.1 问题本质

「𠮷」「𰻝」「䶮」这类字位于 **CJK 扩展 B/C/D/E/F/G 区（U+20000 以上，UTF-8 占 4 字节）**。系统默认中文字体（微软雅黑、苹方）**不含**这些字形 → 前端显示为 □；同时 C# 的 `string.Length` 会把一个生僻字算成 2，导致长度校验和截断出错。

### 7.2 存储层（基本无风险，但有两处要注意）

- ✅ **PostgreSQL 的 UTF-8 原生支持全部 Unicode**（不像 MySQL 需要折腾 utf8mb4），`varchar(n)` 的 n 按**字符**计。
- ⚠️ Npgsql 连接串显式 `Encoding=UTF8`；SqlSugar 全部参数化，不做字符串拼接。
- ⚠️ **避免在 PG 里对姓名做拼音/字典序排序**，用 `COLLATE "zh-x-icu"` 或 `C`，排序不保证符合中文习惯（见 7.5）。

### 7.3 后端 C# 处理（必须在框架层统一）

- **绝不使用 `string.Length` / `Substring` 做长度校验与截断** → 封装 `StringExtensions.RuneLength()` / `RuneTruncate()`（基于 `string.EnumerateRunes()`），DB 字段长度校验、导入截断、导出格式化全部走它。
- **姓名正则不能用 `^[\u4e00-\u9fa5]+$`**（会误杀生僻字）→ 改用 Unicode 属性：`\p{IsCJK_Unified_Ideographs}` + 补充平面范围 `U+20000–U+3FFFF`，或直接放宽为「不含数字/控制字符/emoji」。
- 姓名比较：`校` 与生僻字不做归一化；去空格用 Unicode 空白类。
- 拼音检索字段：能生成的用 `Microsoft.International.Converters.PinYinConverter`（**不支持扩展区**），生僻字拼音留空 → 检索时用「姓名 + 码位」双通道（见 7.5）。

### 7.4 前端显示（关键）

```css
@font-face {
  font-family: "Xjgl Rare Han";
  src: url("/fonts/plangothic-p0.woff2") format("woff2");
  unicode-range: U+20000-20FFF;   /* 按码点分片，一片约 256 字 */
  font-display: swap;
}
/* 按需再声明 p1、p2 … 分片，浏览器只下载实际用到的片 */
:root { --font-stack: "Noto Sans SC", "Microsoft YaHei", "Xjgl Rare Han", sans-serif; }
```

- **字体选型**：`Plangothic Project`（落霞孤鹜，覆盖扩展 B~I，SIL OFL 开源）或 `花园明朝 HanaMinB` / `BabelStone Han`。主字体仍用思源黑体/Noto Sans SC，生僻字由 fallback 兜底。
- **必须做 `unicode-range` 分片**：扩展区全量字体 20~40MB，不分片会拖死首屏；分片后浏览器只按需下载用到的片。
- **Element Plus 全局字体变量**统一覆盖（`--el-font-family`），避免局部回退到默认字体。
- **表格/表单/打印**所有展示姓名的地方都用同一字体栈（含 `el-table` 的虚拟滚动、`el-select` 下拉、打印样式表）。
- **小程序端**（主包 ≤2MB，不能内置全量字体）：
  1. 首选 `wx.loadFontFace()` 动态加载 woff2/ttf 分片（需 HTTPS + 域名白名单）；
  2. **兜底**：姓名用后端渲染的图片 —— `GET /api/render/name?text=𠮷田&size=32`（ImageSharp + 生僻字字体输出 PNG，带 Redis 缓存）。这个兜底在 H5 与 PC 端也能用于导出场景。
- **检测提示**：前端可用 Canvas `measureText` 探测某字是否落在 fallback（豆腐块宽度异常）→ 对未覆盖的字触发图片兜底。可作为增强项。

### 7.5 检索、排序与统计

| 场景 | 方案 |
|---|---|
| 按姓名精确/模糊查 | `LIKE` + `pg_trgm` 索引；生僻字原样匹配没问题 |
| 按拼音查 | 只对常用字生效；生僻字退化为按码位/部首（要在 UI 明示） |
| 排序 | 按 `学校 + 年级班级 + 学籍辅号` 排，**不按姓名排**；必须按姓名时用码位序 |
| 重复学籍检测 | 用身份证号 + 出生日期 + 性别，**不用姓名**做唯一键 |

### 7.6 导入导出与打印（真实痛点，必须提前告知用户）

- ✅ xlsx 本身是 UTF-8，**数据不会丢**。
- ⚠️ 但 **Excel 客户端显示的字体由客户端决定** → 用户机器没装生僻字字体时，单元格里仍显示 □。应对：
  1. 导出说明中提示安装字体（随系统提供字体包）；
  2. 提供「导出 PDF」选项，**由后端渲染并嵌入字体**（SkiaSharp/QuestPDF）→ 显示一定正确；
  3. 打印/报表（学籍卡、花名册）走 PDF 嵌入字体路线，不走"导出 Excel 再打印"。
- 导入时对超长/异常字符给出**逐行错误报告**，不要整批失败。

## 8. 学籍号规则

### 8.1 两类号，别混淆

| 号 | 谁生成 | 说明 |
|---|---|---|
| **全国学籍号** | 全国中小学生学籍信息管理系统 | 19 位，`G + 身份证号`（正式）或 `L + 规则`（临时）。**本系统只存储、不生成**，留字段与校验 |
| **学籍辅号**（省级/校级） | **本系统生成** | 见下 |

### 8.2 推荐方案：`学校标识码(10) + 流水号(6)` = **16 位**

- **学校标识码为 10 位，前 6 位即行政区划码** → 天然满足你说的「行政区划码 + 学校代码」，不用额外维护学校自编码。
- 流水号 6 位按**学校维度永久自增**（不按学年复位，避免历史撞号），单校容量 100 万。
- 唯一性：学校标识码全国唯一 × 校内流水唯一 → **全局唯一** ✔
- 例：`4141010001` + `000123` → `4141010001000123`

**为什么不推荐 14 位：** `区划码(6) + 学校自编码(2) + 流水(6)` 需要全省统一人工维护「学校自编码」，一旦分配失误就撞号；若用「学校标识码后 2 位」则同区划内必然重复，**不可行**。所以 16 位是既满足你的思路又保证唯一的最短方案。

> 若你坚持 14 位，可用 `区划码(6) + 流水号(8)`，但流水号就得按区划维度全局自增（跨校共用一个号段池，取号并发压力大、且无法从号看出学校）。**不推荐**。见 Q3。

### 8.3 实现要点

- **可配置**：`sys_code_rule` 存学籍号规则（分段模板 + 每段取值来源），`IStudentNumberGenerator` 按规则拼装 → 换规则不改代码。
- **取号并发**：`sys_sequence` 表 `UPDATE ... SET cur = cur + 1 WHERE name = 'STU_NO:{schoolId}' RETURNING cur`（原子）；Redis `INCR` 做前置缓冲，Redis 挂了回落 DB。
- **取号与建籍同一事务**；**允许跳号**（不追求连续，追求唯一与性能）。
- 唯一索引 `uk_student_no` 兜底；不加校验位（保持简单）。
- 建籍查重：身份证号哈希 + 姓名 + 性别 + 出生日期，跨校/跨区查。

### 11.5 照片存储与上传韧性

```
IPhotoStorage
 ├ NasPhotoStorage           # 主：SMB/NFS 挂载目录
 ├ LocalFallbackPhotoStorage # 降级：本机 SSD 临时目录
 └ MinioPhotoStorage         # 可选
 装饰器 ResilientPhotoStorage：Timeout(5s) → Retry(3, 指数退避) → CircuitBreaker(失败率>50%且样本≥20 → 熔断30s) → Bulkhead(并发8)
```

目录规范：`{nas}/photo/{学校标识码}/{学籍辅号}.jpg`、`{nas}/thumb/..._s.jpg`、`{nas}/export/{yyyyMM}/{taskId}.zip`、`{nas}/attach/{学校标识码}/{yyyyMM}/{uuid}.{ext}`。
`stu_photo` 只存相对路径 + SHA256 + 大小 + 宽高 + 状态。

**上传链路：** 前端压缩（长边 480px、≤200KB）→ 并发闸门 3 → Redis 令牌桶限流（单用户 5 req/s、单批 ≤500 张）→ 校验（格式白名单/数据范围/幂等 uploadId）→ **SHA256 秒传** → 落临时目录 + 建 `stu_photo(待处理)` → RabbitMQ 削峰 → 消费者生成缩略图 + 写 NAS → 成功回写状态/失败入补偿队列 → 前端轮询进度。

**熔断降级矩阵：**

| 故障 | 检测 | 动作 | 恢复 |
|---|---|---|---|
| NAS 写延迟高 | Timeout 5s | 记失败 | 重试 |
| NAS 连续失败 | 失败率>50% 且样本≥20 | **熔断 30s**（半开试探） | 半开放量 |
| 熔断打开 | — | **降级写本地盘 + 入补偿队列**，接口返回「已接收(排队中)」 | `PhotoCompensationWorker` 每 30s 回放 |
| NAS 空间不足 | 定时探针 | 告警 + 停止接收 | 人工扩容 |
| Redis 挂 | 连接异常 | 本地内存进度 + 直连 DB 查重 | 自动重连 |
| MQ 挂 | 连接异常 | 消息落 Outbox，后台重发 | 自动重连 |
| 上传洪峰 | 令牌桶 + 舱壁 | 429 + `Retry-After`，前端排队重试 | 自然回落 |

#### 11.5.1 已实现（第一版，含测试）

| 能力 | 落地方式 | 测试 |
|---|---|---|
| 主/降级双存储 | `FileSystemPhotoStorage` 同一实现按根目录参数化，派生 `NasPhotoStorage` / `LocalFallbackPhotoStorage`（DI 可分辨） | `FileSystemPhotoStorageTests` |
| 熔断 | 手写状态机 `PhotoCircuitBreaker`（失败率阈值 + 最小样本 + 半开试探），**未引入 Polly** | `PhotoCircuitBreakerTests` 12 例 |
| 超时 + 舱壁 + 降级 | `ResilientPhotoStorage` 装饰器，任何失败都转写本地并返回「成功但降级」 | `ResilientPhotoStorageTests` 10 例 |
| 批量上传 | `PhotoUploadService`：**先并发写存储（慢、纯 IO）+ 再串行落库**（SqlSugar 客户端非线程安全），单批 ≤100 张、并发度 4 | `PhotoAppServiceTests` |
| 秒传 | 同一学生 + 内容 SHA256 一致且上次状态正常 → 不重复写存储 | 同上 |
| 台账 | `stu_photo`（相对路径 / SHA256 / 大小 / 状态 / 批次 / 上传人）；重新上传**覆盖同一路径**，天然幂等 | 同上 |
| 缺照片名单 | 判据是学生主表 `PhotoPath` 为空（而非 `stu_photo` 无行）—— 只有这样总数与分页才正确 | 同上 |
| 补偿回放 | `PhotoCompensationService` 先探活再回放，连续 3 次失败即中止；Host 侧 `PhotoCompensationWorker` 周期执行 | 同上 |
| 健康度 | `GET /api/app/photo/storage-health`：真实写探针文件 + 熔断器快照 + 待补偿/失败条数 | 同上 |
| 上传接口 | `POST /api/photos/upload`（multipart，流式接收，**不用 base64 DTO**） | — |

**与上表的差异（第一版未做，已在 P4 余量中列出）：** 缩略图生成（宽高暂记 0）、RabbitMQ 削峰（当前同步写，靠舱壁 + 熔断保护）、Redis 令牌桶限流、幂等 `uploadId`、`stu_photo` 之外的附件/导出存储。

**路径规范修正：** 实际落地为 `photo/{学校组织Id:N}/{学生Id:N}.{ext}`，而不是 `photo/{学校标识码}/{学籍辅号}.jpg`。原因是文件名里带学籍号会把学生身份信息暴露在 NAS 目录上，运维一浏览就泄露；用 Id 还能完全避开生僻字文件名编码问题。代价是需要查库才能由路径反推学生，这对运维场景可以接受。

**配置项：** `Xjgl:Photo:{NasRoot, FallbackRoot, FailureRateThreshold, MinimumSamples, OpenSeconds, BulkheadSize, TimeoutSeconds, CompensationEnabled, CompensationIntervalSeconds}`。

### 16.5 端到端验证记录（第六轮：学生详情页）——抓出一处「静默空结果」和一处「写坏数据」

做学生详情页（6 张子表的标签页）时，顺手核对了列表页的几个下拉框，抓出两个同源缺陷：
**前端把"码值的英文名"当成了码值**。

| 缺陷 | 现象 | 根因 | 教训 |
|---|---|---|---|
| **学籍状态过滤永远返回空** | 学生列表按"在读"过滤 → 列表为空，**HTTP 200、无任何报错**；表格里的状态标签也全是灰色 | 前端写的是 `{ value: 'Studying', label: '在读' }`，而后端的学籍状态是码值（01/02/…），`GetListAsync` 直接拿 `'Studying'` 去比对。实测：`StudentStatusCode=Studying` → `totalCount=0`，`=01` → `1520` 条 | "界面能点、接口 200、结果为空"是最容易被当成"没数据"的一类缺陷。**码值类的下拉框一律从码表取**，不要在前端手写 |
| **异动类型会写入非法学籍状态** | 异动类型的"异动前/后状态"存成了 `Studying`，而审批通过时会执行 `student.StudentStatusCode = apply.TargetStatusCode` —— **等于把码表里不存在的值写进学生的学籍状态** | 同一个硬编码选项，但这次不只是"查不到"，而是"把脏数据写进主档" | 同一个错误的两种后果，**写比读严重得多**。因此除了改前端，后端也加了码值校验（`EnsureStudentStatusCodesAsync`）：配置阶段就拦住，而不是等哪天发现学生状态不对再回头找原因 |

修复方式（两层）：
1. **前端**：新增 `codeApi.getItemsByCode(categoryCode)`（实测 `GET /api/app/code/items-by-code?categoryCode=STUDENT_STATUS` → 200；
   注意 `categoryCode` 是**查询串**而不是路径段），学生列表与异动类型页的状态项都改为从码表取；
   列表显示也改成用码表翻译（原来直接显示 `01`）。
2. **后端**：`ChangeTypeAppService` 在新增/修改异动类型时校验 `BeforeStatusCode`/`AfterStatusCode` 必须是
   `STUDENT_STATUS` 里的码值（码表尚未导入时跳过校验，**不能因为字典没准备好就让业务存不下去**）。
   实测：PUT 传 `Studying` → 403 + `reason`："学籍状态码不合法：Studying。应填码表 STUDENT_STATUS 中的码值（如 01=在读、02=休学），而不是英文名称。"

**顺手记一个排查坑**：写测试时用 `"Transferred"`（11 个字符）验证"英文名会被拒"，
结果抛的是 `AbpValidationException`（HTTP 400）而不是业务异常 ——
因为它先被 DTO 的 `[StringLength(8)]` 挡下了，**根本没走到业务校验**。
而 `"Studying"` 恰好 8 个字符，才能进到码表校验里。
"长度规则先于业务规则生效"会让"校验没生效"的假象出现，测试数据要按这个顺序挑。

**学生详情页本身**（`StudentProfileDrawer.vue`）：抽屉 + 6 个标签页，与 `ChangeApplyDetail.vue` 一致
**做成组件而不是独立路由** —— 本系统路由完全由后端元数据驱动，把"学生详情"做成独立路由
就得在模块管理里给它建一条菜单记录，而它显然不是一个可独立授权的功能菜单。
表单用"字段描述 + 一套模板"驱动六张子表（手写六遍必然漏改），身份证号在编辑时只回填掩码、
留空即"不修改"。

### 16.6 端到端验证记录（第七轮：学籍变更留痕）——两处"看起来在工作"的缺陷

学籍变更流水（`stu_change_log`）本身实现得很直白：**改之前取快照，改完做前后比对，只写真正变化的字段**。
但这一轮抓到两个"看起来在工作、其实没工作/漏工作"的问题，恰好都不是业务逻辑写错：

| 缺陷 | 现象 | 根因 | 教训 |
|---|---|---|---|
| **删档之后查不到自己的留痕** | "删除学生后仍能追溯"的用例直接报 `EntityNotFoundException` | `GetStudentLogsAsync` 先调 `StudentAccessGuard.GetInScopeAsync(studentId)`，而它按 Id 加载学生 —— 学生被软删后查不到，于是**留痕最该发挥作用的场景（删档追溯）反而 404** | 复用现成的守卫很自然，但"守卫的前提是对象存在"与"留痕的前提是对象可能不存在"直接冲突。**写完功能要按"这个功能被发明出来的那个场景"验一遍**，而不是验"常规路径能跑通" |
| **路由核对脚本漏了 20 次调用** | 脚本报告"核对 81 项、0 项不匹配"，看着一切正常 | 提取调用的正则是 `http\.(get\|post\|put\|delete)<[^>]*>\(`，`[^>]*` 遇到嵌套泛型（`http.get<PagedResult<StudentChangeLog>>(...)`）就匹配不上，这类调用被**静默跳过** | 这是本项目**第二次**在"核对工具"上踩到假绿灯（第一次是脚本因 ENDPOINTS 解析失败跳过一半调用）。修法有两层：正则改成 `<[^(]*>`，并新增**交叉校验**——文件里出现多少次 `http.<verb>` 就必须解析出多少条，对不上直接失败。修好后核对数从 81 涨到 **101** |

修正后的行为：
- 学生**还在**时按当前数据范围校验（历史记录可能属于已转出的学校，不影响查看完整履历）；
- 学生**已被删除**时退回按流水上冗余的学校路径校验（写入时特意存下来的 `SchoolPathCode`），
  且只要有一条在范围内就放行；
- 一条流水都没有时抛 `EntityNotFoundException`，调用方才能区分"没有变更"与"没有这个人"。

留痕的设计要点（都写进了实体注释）：
- **字段级**：只记"某人某时改过这条记录"没有审计价值，要能回答改了哪个字段、从什么变成什么；
- **码值翻译**：`在读（01）` 这种形式，既给人看也保留可追溯性；
- **身份证号只存摘要前缀**：审计要的是"被谁改过"，而不是把全校身份证号再抄一份进日志表；
- **删除也留痕**：档案的"消失"本身就是一次需要留痕的变更，因此删除前先写流水（否则拿不到姓名与辅号）；
- **一次操作一个 BatchId**：改两个字段产生两行但属同一次操作，界面才能合并显示；
- **`Source` 字段区分来源**：异动审批写入的行会带上申请单号（`异动申请 YCxxxx 审核通过`），
  可以从档案反查是哪一单引起的；这部分与异动自己的 `stu_change_flow_log`（记审批动作）互补。

### 16.7 端到端验证记录（第八轮：学籍卡与花名册打印）——PDF 与字体

方案里早就写明"打印/报表走 PDF 嵌入字体路线，不走导出 Excel 再打印"，本轮把它落地：
新增 `src/Xjgl.Reporting`（QuestPDF），应用层通过 `IStudentCardPdfRenderer` / `IStudentRosterPdfRenderer`
两个接口调用，**Host 才装配实现** —— 业务层不依赖任何渲染库。

真实 HTTP 验证（主机运行中直接请求）：

| 调用 | 结果 |
|---|---|
| `GET /api/print/student-card/{id}` | 200，**66,264 字节**，魔数 `%PDF-`，`Content-Type: application/pdf`，`Content-Disposition` 里的中文文件名正确（`学籍卡_异动测试学生_1001560001000001.pdf`） |

本轮踩到并解决的三个"看起来能用、其实会出事"的点：

| 问题 | 现象 | 根因与处理 |
|---|---|---|
| **QuestPDF 许可证未声明** | 9 个渲染用例全挂，报 `Please configure the QuestPDF license` | 我原本把 `Settings.License` 放在 ABP 模块的 `ConfigureServices` 里 —— 这只覆盖"通过 ABP 装配"的路径，**单元测试直接 new 渲染器就漏了**。移到渲染必经的初始化点（`PrintFontRegistry.EnsureInitialized`）后两条路径都覆盖 |
| **默认字体不含中文，且默认不使用系统字体** | 报 `The text "河南省中小学生学籍卡" uses font families that are not available: 'Microsoft YaHei'`，并列出 `System fonts (Settings.UseSystemFonts): disabled` | QuestPDF 2026 默认**只认随应用部署的字体**（为了容器/云环境输出稳定）。本系统的部署形态是教育系统的 Windows 服务器，中文字体必然存在，因此默认 `UseSystemFonts = true` 保证开箱可用；容器化部署可关掉并指定字体目录。**关键取舍**：同时打开 `ThrowOnMissingTextGlyphs` —— 画不出字形就报错，绝不出"满是方块的学籍卡"（纸质件上出现方块是绝对不能接受的），并把该异常翻译成"服务器缺少中文字体"的运维提示 |
| **表头 API 与直觉不同** | 编译报"无法从 TableDescriptor 转换为 TableCellDescriptor"，来回改了两次才对 | QuestPDF 2026 是 `TableDescriptor.Header(Action<TableCellDescriptor>)` —— 传进来的是**格子游标**，每次 `header.Cell()` 前进一格。**这次没靠猜**：直接读包里的 `QuestPDF.xml` 成员签名确认（反射在 PowerShell 里因依赖加载失败，XML 文档更可靠） |

版面即业务规则，几处刻意的取舍（都写进了渲染器注释）：
- **身份证号打掩码**：纸质件会被拍照、传阅、归档，明文收不回来；
- **缺照片时明确写"未采集照片"**：留白看起来像排版省略，写清楚才能让经办人知道要去补；
- **姓名含生僻字时用备用字体并标注"请核对原件"**；
- **花名册不打印家庭住址与联系电话**（列表项本来就没有，这里也不去补）：花名册是"点名/核对"用途，把全校家长电话印在纸上属于过度收集；
- **表头每页重复 + 页脚"第 X 页 / 共 Y 页"**：散页后必须能拼回去；
- **花名册沿用当前筛选条件**：否则"筛出二班来打印"会印出全校，而这类错误要到校对时才发现——纸已经印出来了。

### 16.8 端到端验证记录（第九轮：照片缩略图与二进制接口）——两次"改了没生效"

补齐 P4 的缩略图：新增 `src/Xjgl.Imaging`（ImageSharp），上传时探测尺寸并生成缩略图
（长边 480、JPEG 质量 82、先按 EXIF 摆正再缩放、比上限小则不放大），
并补上**照片的二进制读取接口**（此前系统里根本没有"取照片"的接口，缩略图生成出来也没人用）。

真实 HTTP 验证（主机运行中）：

| 调用 | 结果 |
|---|---|
| `POST /api/photos/upload-one`（1000×750、22,246 字节的真实 JPEG） | 200，`宽高=1000x750`，返回缩略图路径 `photo/{学校Id:N}/thumb/{学生Id:N}.jpg` |
| `GET /api/photos/{studentId}/thumbnail` | 200，**6,526 字节（原图的 29.3%）**，实际像素 **480×360**（等比：1000:750 → 480:360） |
| `GET /api/photos/{studentId}/content` | 200，22,246 字节，**与上传字节完全一致** |
| ETag / 缓存 | 首次 200 带 `ETag`（内容哈希）与 `Cache-Control: private,max-age=86400`；带 `If-None-Match` 再取 → **304** |
| 无令牌访问 | **401** |

这一轮抓到两个"代码写了但没生效"的问题，都不是逻辑写错：

| 问题 | 现象 | 根因与处理 |
|---|---|---|
| **尺寸探测结果没带到落库对象上** | 接口返回 `宽高=0x0`，缩略图字段为空；但**同一个逻辑在集成测试里是绿的** | 上传流水线里 `PreparedItem` 会被复制成另一个 `writeItem` 对象（校验阶段的字段只留在前者）。我把 `Size` 赋给了 `prepared`，落库阶段读的却是 `writeItem.Size` —— 于是静默丢失。集成测试先于真实请求发现了它（`result.Width` 一直是 0），修法是显式把 `Size` 带过去并在代码里写明"这个对象是复制出来的，别只给 prepared 赋值" |
| **只重建了测试项目，没重建 Host** | 改完代码重新验证，接口仍返回旧行为（`宽高=0x0`） | `dotnet build` 只编译测试项目时，新的 `Xjgl.Application.dll` 只会被复制进**测试的 bin**，Host 的 bin 里还是旧 DLL；表现就是"代码明明改了、行为没变"。**这类假象最容易让人怀疑自己改错了地方**，所以验证前先 `dotnet build Xjgl.sln`（或直接重建要启动的那个项目） |

同一轮还被 `tools/audit-routes.mjs` 当场拦下一次真错误：
前端把照片二进制接口写成了 `/api/app/photo/{id}/thumbnail`，
而手写控制器的路由是 **`/api/photos`（没有 `/app`）** ——
照片模块有两套入口（`/api/app/photo` 是约定式应用服务返回 JSON，`/api/photos` 是手写控制器收发二进制），
路径不同不是笔误。若没有这道核对，运行期会是 404，而前端的 `catch` 会把它变成"缩略图全是空的"，很难查。

另外顺手修掉一个**自己写的脆断言**：原本用"两份 PDF 长度不同"来验证"内容确实变了"，
而 PDF 是压缩流，长度偶然相同并不罕见（跑测试时就翻过一次车，表现为偶发失败）。
已改为比较**整份字节是否相同**（`SequenceEqual`）。

### 16.9 端到端验证记录（第十轮：照片打包导出）——"少一张照片"是最不能接受的失败

### 16.10 端到端验证记录（第十一轮：令牌桶限流）——以及一个被"容错"藏起来的配置问题

给昂贵接口加上限流：**照片上传（单用户 5 次/秒）、照片导出（每 5 秒 1 次）、打印（每 2 秒 1 次）**。

设计取舍（都写在 `DistributedTokenBucketRateLimiter` 注释里）：
- **令牌桶而不是固定窗口计数**：固定窗口在边界会放过双倍流量；
  而令牌桶允许"攒一会儿再突发" —— 教师一次选几十张照片并发上传本来就是正常用法；
- **桶状态放 `IDistributedCache`，不直连 Redis**：本系统的分布式缓存已经是
  「Redis 主 + 内存兜底」的容错装饰器，复用它就自动继承了那套降级策略，
  业务层也不必依赖 StackExchange.Redis；
- **失败放行**：缓存抖动时限流精度下降，但绝不能反过来变成"Redis 一抖，全校传不了照片"；
- **限流维度是"用户"而不是 IP**：一所学校往往整栋楼共用一个出口 IP。

真实 HTTP 验证（主机接本地 Redis）：

| 场景 | 结果 |
|---|---|
| 连续打印学籍卡（容量 3、0.5/s） | 前 3 次 200，之后 **429 + `Retry-After: 2`**，响应体 `{"message":"操作过于频繁，请 2 秒后再试。","policy":"print","retryAfterSeconds":2}` |
| **并发 8 次上传**（容量 5、5/s） | **正好 5 次 200 + 3 次 429** —— 桶在并发下也没被击穿 |
| Redis 里的桶状态 | `KEYS ratelimit*` 直接查到 `ratelimit:print:{userId}`、`ratelimit:photo-upload:{userId}` |
| 顺序 8 次上传（未触发限流） | 全部 200 —— 顺序请求约 2~3 次/秒，低于 5/s 的补充速率，**这是符合预期的**（限流不是"每次都拦"） |

**顺带发现一个被"容错"藏起来的问题**：验证时我在 Redis 上直接 `AUTH`，
发现 `appsettings.json` 里配的密码（`Xjgl@Dev2026`）**与本机实际运行的 Redis 不一致**，
主机日志里是：

```
[WRN] 分布式缓存主实现不可用，接下来 30 秒内直接使用内存缓存（累计失败 1 次…）
StackExchange.Redis.RedisConnectionException: AuthenticationFailure … Error: NOAUTH Authentication required.
```

也就是说**这套开发环境其实一直在用内存缓存**（登录、权限缓存都正常，因为降级是设计好的），
只是没有任何界面会提示这件事 —— 容错架构的代价就在这里：**配置错了不会报错，只会静默降级**。
因此验证限流时必须换个思路：临时起一个密码已知的 Redis（`127.0.0.1:56379`）并让主机连它，
再直接查 Redis 键名，才能确认真的是 Redis 在存桶状态（同时也验证了"Redis 正常时无降级告警"）。

这条已经写进 README 的已知限制：**部署后请检查日志里有没有"缓存主实现不可用"，
它意味着你的 Redis 配置没生效，而系统会安静地退回单机缓存**。

### 16.11 端到端验证记录（第十二轮：生产部署编排）——探针必须挂在管道最前面

P6 的第一块：**Linux + Docker 的生产编排**（`deploy/docker-compose.prod.yml` + 两个多阶段 Dockerfile + nginx 配置）。

产物与关键取舍：

| 文件 | 关键点 |
|---|---|
| `deploy/api.Dockerfile` | 多阶段；**装 `fonts-noto-cjk`**（PDF 画中文靠它，本项目刻意不做"缺字体画方块"的降级）与 `curl`（healthcheck 用）；**同一个镜像里同时发布 Host 与 DbMigrator**，生产初始化数据库只要 `docker compose run --rm migrate`；`ENTRYPOINT ["dotnet"]` + `CMD [...]`，这样 migrate 能用 `command` 覆盖启动参数 |
| `deploy/web.Dockerfile` | Node 构建（`--frozen-lockfile`）→ nginx 托管静态资源；前端调用同源相对路径，因此不需要注入任何 `VITE_*` |
| `deploy/nginx.conf` | ① history 路由回落（否则刷新深链 404）；② `client_max_body_size 210m`（与接口的 200MB 对齐，否则大文件在 nginx 层被 413，接口层限制成了摆设）；③ `proxy_read_timeout 300s`（导出/打印是同步生成）；④ `index.html` 禁缓存（否则发版后加载旧壳子、引用已删除的 chunk） |
| `deploy/docker-compose.prod.yml` | 口令全部 `${VAR:?提示}` 注入（缺失即报错退出，而不是空值启动）；降级照片目录挂**命名卷**（NAS 熔断期间暂存的照片不能因重建容器而丢）；NAS 以**同路径**绑入；MQ 与 Seq 走 profile |
| `deploy/.env.example` / `README.md` | 逐步部署手册（含 NAS 挂载、生僻字字体、HTTPS、备份、第三方许可证、排错清单） |

**本轮抓到的问题：健康检查写在 ABP 管道后面 = 探针永远看不到数据库故障。**

先写的版本是把 `/health` 用 `MapGet` 挂在 `UseConfiguredEndpoints()`（管道末尾）。实测数据库不可达时：

```
GET /health  →  HTTP 500（一页 Npgsql 异常堆栈）
```

堆栈显示失败发生在**到达我的端点之前**：ABP 的请求本地化中间件要读"租户设置"（`TenantSettingValueProvider` → EF 查询），数据库不可用它就抛了。
一个只会返回 200/500 的探针是没有意义的 —— 容器与负载均衡都据此判断"要不要放流量"。
改法是把健康检查做成**管道最前面的终止式中间件**，并对数据库探测 `try/catch`（连不上就是"不健康"，不需要把异常抛出去）。

修复后实测：

| 场景 | `/health` | 同一时刻其它接口 |
|---|---|---|
| 数据库正常 | **200** `{"status":"ok","database":"up"}` | `swagger.json` 200（确认中间件没打断正常路由） |
| 数据库不可达（连接串指向空端口） | **503** `{"status":"degraded","database":"down"}` | `/api/app/my-profile` → 500（正好反证了探针确实提前拦截） |

**部署文件的自动核对**：手写编排最容易出的问题是"变量名写错一个字母" —— 容器照样起来，功能上线才炸。
因此新增 `tools/verify-deploy.mjs`，以 `src/Xjgl.HttpApi.Host/appsettings.json` 为**唯一事实来源**，
反推 compose 必须提供的环境变量（`A:B` → `A__B`）逐个核对，并检查字体安装、healthcheck、数据卷、
nginx 的深链回落与上传体积、`.env.example` 是否覆盖所有变量、生产文件里是否混入开发口令。
CI 另有一道 `docker compose config -q` 做语法与插值校验（本机没有 docker，这道只能在 CI 跑）。

**脚本自己也被自己抓了一次**：第一版用 `POSTGRES_PASSWORD:\s*[^$\s]` 判断"口令是字面量"，
结果误命中了 `${POSTGRES_PASSWORD:?提示}` 里的 `POSTGRES_PASSWORD:` + `?`；
变量提取也把**注释里**的 `${VAR:?提示}` 当成了真变量。已改为"先去掉注释行 + 只认行首键与字面量值"。

### 16.12 照片模块的故障演练方式（值得记住的做法）


集成测试**不搭真实 NAS**，而是把「NAS 主存储」的根目录指向测试输出目录下的一个本地目录；
需要模拟故障时，把这个目录换成一个**同名文件** —— 目录创建必然失败，
于是「写入失败 → 熔断 → 降级 → 待补偿」的完整链路真实发生；修复只需把文件删掉。

好处：与生产走**同一套 DI 装配和同一个熔断器**（不是 mock），
毫秒级完成，且能反复演练「NAS 恢复后自动补传」。

|---|---|---|---|
| 1 | 跨 ORM 的共享事务尚未实现（`ISqlSugarTransactionScope` 在 SqlSugarCore，Application 层用不到） | 异动审批里「改学籍 + 写审批状态」不是原子的 | 把事务抽象上提到 Domain，或引入 ABP `IUnitOfWork` 适配器 |

| 9 | 导入导出是**同步**实现：导出上限 5000 行（超限只取前 5000）、导入逐行串行调用 `CreateAsync` | 上千人的花名册导入耗时较长，浏览器请求可能超时；导出超过 5000 行会静默截断 | 导出改为「后台任务 + 生成文件 + 下载链接」，导入改为「分批 + 进度轮询」；导出截断时应在响应头/末尾明确提示 |

| 14 | **花名册不打印住址与联系电话**（刻意的最小化） | 需要这两列的场景（如家访名单）眼下拿不到 | 需要时以「显式勾选 + 记入审计」的方式开启，而不是默认打印 |
| 15 | **生僻字字体仍未随仓库分发**（Plangothic 分片体积大、授权各异） | 姓名含生僻字时打印件可能出现方块（卡片上会标注"请核对原件"提示） | 部署时把字体放入 `Xjgl:Print:RareCharacterFontDirectory`；或按需生成"生僻字图片"兜底 |
