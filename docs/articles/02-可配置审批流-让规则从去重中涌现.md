# 可配置审批流：让"同县区转学只审一次"从算法里自然涌现

> 本文是河南省学籍管理系统的对外技术文章之一。
> 算法实现在 `src/Xjgl.Domain/Changes/ChangeFlowPlanner.cs`（**纯函数、可单测**），
> 逐章教程见 [`docs/learning/29~34`](../learning/README.md)。

## 一、业务侧的真实困境

学籍异动（转学、休学、复学、退学…）的审批流程，**每个地方都不一样**：

- 本市内转学：可能只要转出校 + 转入校两方点头；
- 跨县转学：两边县区教育局都要盖章；
- 跨市转学：还要两个市局；
- 而某个省可能规定"跨市转学只需市级，不必惊动省厅"。

如果把这些规则写进代码，你会得到一个 `if/else` 森林，而且**每换一个省就要改程序、
重新测试、重新发版**。政务系统的现实是：业务人员拿着红头文件来找你，
说"从这个月起跨市转学不用省厅了"——你不可能每次都发一版。

所以目标很明确：**让业务人员在界面上配置流程，程序不为具体规则写特例。**

---

## 二、关键抽象：节点不写"哪个组织"，而写"哪一级的哪个位置"

这是整套设计的转折点。

**错误做法**（把组织写死）：

```json
{ "seq": 1, "orgId": "3a23...甲县教育局", "name": "县区审核" }
```

一旦写死，同一个流程模板就不能被别的县用 —— 模板失去了复用价值，
"每个县配一遍"又回到人力堆砌。

**我们的做法**：节点只描述**相对位置**，实例化时结合"这个学生、这次异动的具体目标校"再解析：

```csharp
public static class ChangeOrgResolvers
{
    public const string TargetSchool = "TargetSchool"; // 转入学校
    public const string SourceSchool = "SourceSchool"; // 转出学校
    public const string TargetCounty = "TargetCounty"; // 转入学校所在县区
    public const string TargetCity   = "TargetCity";   // 转入学校所在地市
    public const string SourceCounty = "SourceCounty";
    public const string SourceCity   = "SourceCity";
    public const string Province     = "Province";
    // …
}
```

于是"跨市转学的标准流程"可以描述成：

| 序号 | 节点名 | 审哪一级 |
|---|---|---|
| 1 | 转入学校提交 | `TargetSchool` |
| 2 | 转出学校审核 | `SourceSchool` |
| 3 | 转入县区审核 | `TargetCounty` |
| 4 | 转出县区审核 | `SourceCounty` |
| 5 | 转入地市审核 | `TargetCity` |
| 6 | 转出地市审核 | `SourceCity` |

**同一份模板，全省所有县都能用。** 这是"可配置"真正成立的前提。

## 三、算法只有三步：解析 → 截断 → 合并

核心算法刻意做成**纯函数**（输入节点定义 + 组织解析函数 + 终止级别，输出任务序列），
不依赖数据库、不依赖 ABP，因此可以用单元测试把各种场景钉死：

```csharp
public FlowPlanResult Plan(
    IEnumerable<FlowNodeDefinition> nodes,
    Func<string, ResolvedOrg?> resolveOrg,   // 组织解析由调用方注入
    string maxApproveLevel);
```

### 第 1 步：解析

逐个节点调用 `resolveOrg` 得到真实组织。解析不出来就**记一条警告并跳过**，
而不是抛异常 —— 因为"某个节点的组织解析不了"不应该让整个申请提交失败
（配置错一个节点，不该让全省今天的转学都办不了）。

### 第 2 步：截断

```csharp
if (ApproveLevels.GetOrder(level) > maxLevelOrder)
{
    result.Warnings.Add($"…超出审核终止级别「{…}」，已截断。");
    continue;
}
```

`maxApproveLevel` 是**异动类型**上的配置（如"转学最高审到市级"）。
超出终止级别的节点被丢弃 —— 这就是"跨市转学不必惊动省厅"的实现方式：
**模板里可以留着省级节点，但类型上把终止级别设成市级即可。**

这一点很重要：模板保持完整（表达"完整的理想流程"），
终止级别负责"本次实际审到哪"。两者正交，业务人员容易理解。

### 第 3 步：合并 —— "只审一次"是怎么来的

```csharp
// 按解析出的组织 Id 分组；同一组织只保留一个待办
var groups = resolved.GroupBy(x => x.Org.Id);
```

**就这一行，实现了所有"只审一次"的规则。** 举例：

| 场景 | 第 3/4 节点解析结果 | 合并后 |
|---|---|---|
| 甲县 → 乙县（跨县） | 甲县教育局 / 乙县教育局 | 两个待办，各审一次 ✔ |
| 甲县一中 → 甲县二中（**同县**） | **同一个**甲县教育局 | **合并成一个待办** ✔ |
| 同校内部调整 | 同一个学校 | 合并 ✔ |

所以"同县区转学，县区只审一次"**不是特判**，而是"按组织去重"的自然结果。
这正是我们想要的性质：规则从数据里涌现，而不是从代码里硬编码。

组内保留谁、以及合并策略：

```csharp
// MergeToLast（默认）：保留序号最大的节点，上级成为终审
// MergeToFirst：保留序号最小的节点
var survivor = strategy == ChangeMergeStrategies.MergeToFirst
    ? members.First()
    : members.Last();
```

被合并掉的节点序号会记录在 `MergedFromSeqs` 里，**在界面上显示"本节点合并了第 3、4 步"**——
这一点不能省：否则业务人员看到"我配了 6 步，怎么只生成了 4 个待办"会以为系统坏了。

### 输出按序号排序

```csharp
result.Tasks = tasks.OrderBy(t => t.Seq).ToList();
```

顺序即审批顺序，简单直接，不引入图或拓扑排序 —— 政务审批流是**线性的**，
没必要为了通用性把复杂度提上去。

## 四、这个设计带来的三个好处

### 1. 模板可复用，配置量骤降

一份"跨市转学"模板，两个县的模板都指向它；差异只在异动类型上的终止级别。
实测中，配置 6 个节点即可覆盖某省的全部转学场景。

### 2. 可以用单元测试穷尽合并场景

因为 `Plan` 是纯函数，测试不需要数据库：

```csharp
[Fact]
public void 同县转学_县区节点被合并成一个()
{
    var plan = planner.Plan(nodes, resolveOrg, ApproveLevels.City);
    plan.Tasks.ShouldHaveSingleItem();   // 3、4 步合并
    plan.Tasks[0].MergedFromSeqs.ShouldContain(4);
}
```

项目里这类用例覆盖了**跨市 / 同市 / 同县 / 本校 / 含省级**五种组合，
跑一次只要几毫秒。**验证方法**：把数据库容器停掉，这组用例仍然全绿 ——
说明它们真的没碰数据库。

### 3. 配置错误是"可见的降级"，不是崩溃

解析失败的节点、被截断的节点、非法终止级别，统统进 `Warnings` 并回传给界面。
"某个节点配错了"表现为一条醒目提示 + 流程少一步，
而不是"提交申请报 500" —— 后者会让业务人员彻底不敢动配置。

---

## 五、这套设计**不**解决什么

诚实列出边界，避免误用：

1. **不支持并行分支 / 会签 / 条件跳转**。政务审批绝大多数是线性的，
   引入 BPMN 引擎的代价（学习、部署、调试、版本迁移）远大于收益。
   真需要复杂编排时，应该换 BPMN 引擎而不是在这套上加特性。
2. **不支持"动态加签"**：审批过程中临时加一个部门。当前流程在提交时一次性实例化。
3. **节点上的组织解析器是**编译期枚举**（9 个），不是可扩展表达式。
   够用且安全（不存在表达式注入），但业务人员不能自己写新解析器 ——
   加一个需要改代码 + 加测试。
4. **实例化后流程不可改**：已提交的申请不会因为模板改了而变化。
   这是刻意的（审批依据必须稳定），但意味着"改流程只对新申请生效"要写在操作手册里。
