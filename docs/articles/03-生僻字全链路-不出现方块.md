# 生僻字全链路：从 PostgreSQL 到 PDF，一个方块都不许出现

> 本文是河南省学籍管理系统的对外技术文章之一。
> 相关代码：`src/Xjgl.Domain.Shared/Text/RareCharacterText.cs`、
> `src/Xjgl.Reporting/`、`web/apps/pc/public/fonts/`，
> 逐章教程见 [`docs/learning/24~25`](../learning/README.md)。

## 一、为什么这件事躲不过去

做人口、户籍、学籍、医疗这类系统，一定会遇到生僻字。真实姓名里有：

| 字 | 码位 | 所在区 |
|---|---|---|
| 䶮 | U+4DAE | CJK 扩展 A（BMP 内，1 个 `char`） |
| 𠮷 | U+20BB7 | CJK 扩展 B（**代理对**，2 个 `char`） |
| 𰻞 | U+30EDE | CJK 扩展 G（代理对） |

注意第二、三个：它们在 UTF-16 里是**代理对**（surrogate pair），
`"𠮷".Length == 2` 而它只是**一个字**。所有按 `string.Length` / `Substring` /
`[index]` 处理姓名的代码，在它们身上全错。

而这类错误的后果不是"显示不好看"，而是：

- **长度校验误判**：3 个字的姓名被判成 4 个字，超长拒绝 → 学生建不了档；
- **截断把字劈开**：`Substring(0, 3)` 可能切在代理对中间 → 产生非法字符串，
  存进数据库报错或变成 `?`；
- **打印成方块**：PDF 里字体缺字形 → 学籍卡上名字是 `□□□`，而**档案不能用**。

政务系统里，这类问题会被家长直接投诉到窗口。所以它必须全链路解决。

## 二、原则：全系统按 **Unicode 码位（Rune）** 处理

.NET 从 Core 3.0 起提供了 `Rune` 与 `EnumerateRunes()`，这是解决问题的正确工具。
我们把它收敛到一个类里，**禁止业务代码直接用 `string.Length` 处理姓名**：

```csharp
public static class RareCharacterText
{
    /// <summary>按码点计数（不是按 char）。</summary>
    public static int RuneLength(string? value)
        => string.IsNullOrEmpty(value) ? 0 : value.EnumerateRunes().Count();

    /// <summary>按码点截断，绝不劈开代理对。</summary>
    public static string TruncateByRune(string? value, int maxRunes)
    {
        if (string.IsNullOrEmpty(value) || maxRunes <= 0) return string.Empty;

        var builder = new StringBuilder();
        var count = 0;

        foreach (var rune in value.EnumerateRunes())
        {
            if (count >= maxRunes) break;
            builder.Append(rune);
            count++;
        }

        return builder.ToString();
    }
}
```

`StringBuilder.Append(Rune)` 是安全的：它按码位追加，不会产生半个代理对。

### 姓名校验也要按码位

```csharp
public static bool IsValidPersonName(string? value, out string? error)
{
    // 1) 长度按码点
    var length = RuneLength(value);

    // 2) 逐码点判断"是不是汉字/允许的字符"
    foreach (var rune in value.EnumerateRunes())
    {
        if (IsCjkIdeograph(rune)) continue;
        // 少数民族姓名的间隔号「·」等白名单字符
        if (rune.Value == 0x00B7) continue;

        // 拉丁字母（< 0x0250）一律拒绝：政务姓名不该出现英文
        if (Rune.IsLetter(rune) && rune.Value < 0x0250)
        {
            error = $"姓名包含非法字符「{rune}」";
            return false;
        }

        error = $"姓名包含非法字符「{rune}」";
        return false;
    }

    return true;
}
```

**为什么必须用码点遍历**：如果改成 `foreach (var ch in value)`，
一个代理对会被拆成两个 `char`，两个都不在高新区范围内，
于是 `𠮷` 会被判成"非法字符"—— 一个合法姓名被系统拒绝。

## 三、数据库：PostgreSQL 的 C.UTF-8 排序规则

数据库这一层要注意的是**排序规则（collation）**，不是编码。

- **编码**：PostgreSQL 的 UTF-8 原生支持全部 Unicode 平面，存 `𠮷` 没问题；
- **排序规则**：如果建库时用了默认的 `en_US.UTF-8` 或某些 `C` 变体，
  生僻字的排序、`LIKE`、大小写处理可能不符合预期。

我们的做法是在 `docker-compose` 里显式指定：

```yaml
POSTGRES_INITDB_ARGS: "--encoding=UTF8 --locale=C.UTF-8"
```

`C.UTF-8` 的语义是"按码位比较"，行为可预测，不依赖操作系统 locale 数据。
对一个需要在 Linux 容器里稳定运行的政务系统来说，**可预测比"符合语言学直觉"更重要**。

> ⚠️ 建库之后再改 collation 是很麻烦的（要 `pg_dump` + 重建）。
> 所以在**第一次 `docker compose up` 之前**就要把 `POSTGRES_INITDB_ARGS` 定下来。
> 这也是第 01 章就讲基础设施的原因。

**验证方法**（一条命令确认排序规则）：

```sql
SELECT datcollate, datctype FROM pg_database WHERE datname = 'xjgl';
-- 期望：C.UTF-8 / C.UTF-8
```

## 四、前端：字体必须分片，而且必须验证真的生效

生僻字的字形**不在**常见中文字体里。微软雅黑、思源黑体都不含扩展 B 区。
你需要一个覆盖扩展区的字体（本项目用 Plangothic，按 `unicode-range` 分片）。

### 为什么必须分片

完整的扩展区字体动辄几十 MB。整包加载会让首屏慢到不可用。
`@font-face` 的 `unicode-range` 让浏览器**只下载用得上的分片**：

```css
/* 只在页面里真的出现扩展 B 区字符时，浏览器才去取这个分片 */
@font-face {
  font-family: 'RareCJK';
  src: url('/fonts/plangothic-ext-b-1.woff2') format('woff2');
  unicode-range: U+20000-2003F;
  font-display: swap;
}
```

```css
body {
  /* 回落到系统字体，只有生僻字才落到 RareCJK */
  font-family: system-ui, 'Microsoft YaHei', 'RareCJK', sans-serif;
}
```

关键顺序：**系统字体在前、生僻字字体在后**。常用字走系统字体（好看、快），
只有系统字体没有的字形才回落到 RareCJK。

### 字体文件不进仓库

分片字体体积大（本项目约几十 MB），且授权需要确认，因此**不进 Git**。
缺失时的行为是**回落到系统字体** —— 生僻字显示为方块，但功能不受影响。
这一点写进了 README 的「已知限制」，避免部署时以为"坏了"。

## 五、PDF：这才是最容易翻车的地方

浏览器里显示对了，**不代表打印出来是对的**。PDF 渲染是完全不同的一条链路。

### 依赖服务器字体，且必须内嵌

我们用 QuestPDF 渲染学籍卡。它的行为是：

- **渲染时**从服务器上找字体 → 找不到就报错（或画出方块）；
- **生成时**把用到的字形**内嵌**进 PDF（`FontFile2`）。

所以：

| 环境 | 需要做的事 |
|---|---|
| Windows 服务器 | 默认能拿到"微软雅黑"，一般可用 |
| Linux / 容器 | 必须 `apt-get install fonts-noto-cjk`，并把配置改成 `Noto Sans CJK SC` |
| 生僻字 | 还要另放 Plangothic 分片，并配置 `Xjgl:Print:RareCharacterFontDirectory` |

配置项（`appsettings.json`）：

```json
{
  "Xjgl": {
    "Print": {
      "DefaultFontFamily": "Noto Sans CJK SC",
      "RareCharacterFontDirectory": "/app/fonts/rare"
    }
  }
}
```

### 刻意不做的"降级"

如果找不到中文字体，一个"贴心"的做法是回落到默认西文字体，
让 PDF 至少能生成出来 —— 出来的是一张**满是方块的学籍卡**。

**我们刻意选择直接报错。** 理由：一张能生成但不可用的学籍卡，
会被当成"系统能用"发到学校，然后几百张废卡被打印出来才发现。
宁可在接口上返回明确错误，也不要产出静默损坏的正式文档。

### 怎么验证"真的对了"

不要只看生成的 PDF 能不能打开。我们的端到端测试是：

1. 在浏览器里点击「打印学籍卡」；
2. **下载到 PDF 字节**；
3. 校验字节流：
   - 开头是 `%PDF-`；
   - 文件里包含 `FontFile2`（说明字体**真的内嵌了**，而不是依赖阅读器本地字体）；
   - 用含生僻字的测试学生建档，确保渲染链路走到扩展区字形。

CI 里专门装了 `fonts-noto-cjk`，因为**缺字体时 CI 会红** ——
这恰恰反映了"部署环境缺字体就打不出学籍卡"这个真实约束。

## 六、一份自查清单

如果你也在做类似系统，按这个顺序逐层验证，**不要跳步**：

| # | 检查项 | 验证方法 |
|---|---|---|
| 1 | 建库时 collation 对不对 | `SELECT datcollate FROM pg_database WHERE datname='…'` |
| 2 | 数据库能存能查 | 插入 `𠮷` 后 `SELECT length(name)` → 期望 **1** |
| 3 | 后端长度/截断按码点 | 单测：`RuneLength("𠮷") == 1`；`TruncateByRune("𠮷𠮷", 1)` 是完整一个字符 |
| 4 | 姓名校验不误杀 | 单测：`𠮷` 被判为**合法**（这一步最容易被 `foreach (char)` 写坏） |
| 5 | JSON 传输不变形 | 接口返回里生僻字是原字符，不是 `\uXXXX` 乱码或 `?` |
| 6 | 浏览器显示 | 页面里该字**不是方块**（看图，别只看 HTML 源码） |
| 7 | PDF 内嵌字体 | 生成的 PDF 里存在 `FontFile2`，且在**没装该字体的机器**上打开仍正常 |
| 8 | 导出 CSV 编码 | 用 Excel 直接打开不乱码（我们为此写了专门的 CSV 编码处理） |

第 3、4 两条必须写成单元测试。**它们是纯函数，没有理由只靠手工点一遍**。

## 七、这套方案的成本

诚实说明代价：

1. **代码里多了个"必须用 Rune"的约定**，靠 review 与单测守，编译器帮不了你；
2. **字体分片要自己切**（我们用的是现成分片），并且要测"分片是否真的按需加载"；
3. **PDF 打印强依赖服务器字体**，容器镜像因此变大（`fonts-noto-cjk` 约 200MB+）；
4. **生僻字字体授权要确认**（Plangothic 是 OFL，但企业分发仍建议法务过一眼）。

但这些代价换来的是：**档案上的名字是对的**。对一个学籍系统来说，
这属于"不做就不合格"的那一类需求。
