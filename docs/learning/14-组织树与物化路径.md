# 14 组织树：省 / 市 / 县 / 校与物化路径

> **对应阶段**：P1 ｜ **预计耗时**：2.5 小时 ｜ **产出**：一棵可逐层加载、能按子树查询、且删不坏的组织树

---

## 14.1 要解决的问题

组织树是整个系统的地基，它同时承担四个职责：

| 职责 | 说明 |
|---|---|
| **数据范围的锚点** | "县区管理员能看本县所有学校" —— 靠的是组织树的父子关系 |
| **权限的归属** | 审核任务派给某个组织，而不是某个具体的人（人员会调动，组织不会） |
| **学生的归属** | 每个学生挂在一个学校上 |
| **统计的口径** | 按市/县汇总上报 |

这四个职责决定了它必须满足三个技术要求：

1. **能按子树查询**："本县所有学校的学生" 不能靠递归查 N 次；
2. **能承受上万节点**：河南一个省有上万所学校，一次性把整棵树发给前端会卡；
3. **删不坏**：删掉一个还有下级的节点会产生孤儿数据。

## 14.2 核心设计：物化路径（materialized path）

```csharp
public class SysOrg : FullAuditedAggregateRoot<Guid>, IXjglBusinessEntity
{
    public Guid? ParentId { get; set; }
    public string OrgType { get; set; } = default!;   // Province / City / County / School
    public string Code { get; set; } = default!;      // 学校是 10 位标识码
    public string Name { get; set; } = default!;

    /// <summary>物化路径：从根到本节点的编码用 "." 连接，例如 410000.410100.410102.4101020001</summary>
    public string PathCode { get; set; } = default!;

    public int TreeLevel { get; set; }                // 1=省 2=市 3=县 4=校
    public int Sort { get; set; }
    public bool IsEnabled { get; set; }
}
```

**`PathCode` 是这棵树的关键**。有了它，两个最常用的查询都变成一条 SQL：

```sql
-- 某县下所有学校（子树查询）—— 不需要递归
SELECT * FROM sys_org WHERE path_code LIKE '410000.410100.410102.%';

-- 某个学生是否在我的数据范围内 —— 一次前缀比较
SELECT ... WHERE :myPathCode LIKE path_code || '%';
```

实测（真实环境建的县区与学校）：

```
省厅   101733
 └ 市局 101733.141565
    └ 县局 101733.141565.TX4530
       └ 学校 101733.141565.TX4530.4145300000
```

**为什么不用递归 CTE**：PostgreSQL 支持 `WITH RECURSIVE`，写起来也优雅，
但每次查询都要展开；而物化路径是**普通的前缀索引查询**，
在组织树这种"读多写极少"的场景下更划算。代价是移动节点时要级联重写子树 —— 见 14.4。

## 14.3 动手步骤

### 步骤 1：实体与仓储（第 07 章那套约定自动生效）

给实体加 `IXjglBusinessEntity`，DbMigrator 就会建表；
表名 `sys_org`、列名 `path_code` 由第 07 章的映射约定自动得到。

### 步骤 2：应用服务（`OrgAppService`）

```csharp
public interface IOrgAppService : IApplicationService
{
    /// <summary>获取组织列表（可按类型 / 父节点 / 关键字过滤，可选返回子树）。</summary>
    Task<List<OrgDto>> GetListAsync(OrgQueryDto input);

    /// <summary>获取整棵组织树（节点数量大时不建议使用）。</summary>
    Task<List<OrgDto>> GetTreeAsync(string? rootPathCode = null);

    /// <summary>逐层加载：获取某个节点下的直接子节点。</summary>
    Task<List<OrgTreeNodeDto>> GetChildrenAsync(Guid? parentId, bool onlyEnabled = true);

    Task<OrgDto> CreateAsync(CreateUpdateOrgDto input);
    Task<OrgDto> UpdateAsync(Guid id, CreateUpdateOrgDto input);
    Task DeleteAsync(Guid id);

    /// <summary>移动节点到新的父节点下（会级联重写整棵子树的物化路径）。</summary>
    Task MoveAsync(Guid id, MoveOrgDto input);
}
```

**`GetChildrenAsync` 是给大组织树准备的口子**：一次只取一层，
前端用懒加载展开 —— 上万所学校也只需要用户展开的那几层数据。

### 步骤 3：新增时算好 `PathCode`

```csharp
private async Task<string> BuildPathCodeAsync(Guid? parentId, string code)
{
    if (parentId == null)
    {
        return code;                       // 根节点：路径就是自己的编码
    }

    var parent = await _orgs.GetAsync(parentId.Value);

    return $"{parent.PathCode}.{code}";    // 子节点：父路径 + "." + 自己的编码
}
```

`TreeLevel` 同理取 `parent.TreeLevel + 1`。

### 步骤 4：删除守卫

```csharp
public async Task DeleteAsync(Guid id)
{
    var org = await _orgs.GetAsync(id);

    // 有下级就拒绝：删掉中间节点会让整棵子树失去路径语义
    if (await _orgs.AnyAsync(o => o.ParentId == id))
    {
        throw new BusinessException(XjglDomainErrorCodes.OrgHasChildren)
            .WithData("reason", "该组织下还有下级组织，请先删除下级");
    }

    // 还有学生挂着也不能删（学生主表引用学校）
    if (await _students.AnyAsync(s => s.SchoolOrgId == id))
    {
        throw new BusinessException(XjglDomainErrorCodes.DataInUse)
            .WithData("reason", "该组织下还有学生，不能删除");
    }

    await _orgs.DeleteAsync(org, autoSave: true);
}
```

### 步骤 5：移动节点要级联重写路径

```csharp
public async Task MoveAsync(Guid id, MoveOrgDto input)
{
    var org = await _orgs.GetAsync(id);
    var oldPath = org.PathCode;
    var newPath = await BuildPathCodeAsync(input.NewParentId, org.Code);

    org.ParentId = input.NewParentId;
    org.PathCode = newPath;
    org.TreeLevel = ...;

    // 子树里每个节点的路径前缀都要换掉，否则整棵子树的"子树查询"全部失效
    var descendants = await _orgs.GetListAsync(o => o.PathCode.StartsWith(oldPath + "."));
    foreach (var child in descendants)
    {
        child.PathCode = newPath + child.PathCode[oldPath.Length..];
    }

    await _orgs.UpdateManyAsync(new[] { org }.Concat(descendants), autoSave: true);
}
```

> **真实系统里移动组织是极少发生但影响面极大的操作**（撤县设区、学校合并）。
> 建议生产环境把它限制在"仅省厅管理员可操作"，并且操作前先备份。

## 14.4 前端：懒加载的组织树

`web/apps/pc/src/views/system/org/index.vue` 用的是 Element Plus 的
`el-tree` + `lazy` + `:load`：

```typescript
async function loadNode(node, resolve) {
  if (node.level === 0) {
    // 根节点：取省厅。**不要用 /children/{parentId} 传空来取根** —— 空路由段会 404
    resolve((await orgApi.getRoots()).map((o) => ({ ...o, leaf: false })))
    return
  }

  const children = await orgApi.getChildren(node.data.id)
  resolve(children.map((c) => ({ ...c, leaf: !c.hasChildren })))
}
```

对应后端：`GetRoots()` 走列表接口按类型过滤（`GET /api/app/org?orgType=Province`），
其余层级走 `GET /api/app/org/children/{parentId}`。

**组织选择器（如下拉框）也用同一个懒加载写法**：
`views/system/user-provision/index.vue` 里的 `el-tree-select` 配 `lazy` + 同一个 `loadNode`。
上万所学校时，选一个节点只需要拉三层。

## 14.5 验证方法

**① 物化路径正确**

```powershell
# 在某个市下建县区，再在县区下建学校，然后看路径
GET /api/app/org/<学校 id>
# 期望 pathCode 形如 101733.141565.TX4530.4145300000（逐级拼接）
# 期望 treeLevel = 4
```

**② 逐层加载正常**

```powershell
GET /api/app/org/children/<县区 id>
# 期望只返回直属学校，且 hasChildren=false
```

**③ 删除守卫**

```powershell
DELETE /api/app/org/<有下级的县区 id>
# 期望 403，且 data.reason = "该组织下还有下级组织，请先删除下级"
# 先删学校再删县区 → 204
```

**④ 子树查询用的是前缀**

```powershell
GET /api/app/org?keyword=...&includeDescendants=true
```

或者直接看 SQL 日志（把 `Xjgl:SqlSugar:EnableSqlLog` 打开），
确认生成的是 `LIKE 'xxx.%'` 而不是递归查询。

## 14.6 踩坑记录

### 坑 1：用 `/children/{parentId}` 传空取根节点 → 404

路由模板是 `children/{parentId}`，`parentId` 为空时 URL 会变成
`/api/app/org/children/`，ASP.NET Core 匹配不上（**空路由段**）。

**处理**：根节点改走列表接口按类型过滤（`?orgType=Province`），语义还更清楚。
这个坑在写前端时要特别注意 —— 它表现为"树永远加载不出来"，而网络面板里是一个 404。

### 坑 2：一次性拉整棵树上万节点

最初组织下拉框直接调 `GetTreeAsync()`。开发库只有几所学校时毫无问题，
真环境灌入上万所学校后，接口返回 **1MB+ JSON**，在县区网络上要等好几秒，
而且浏览器解析这么大的 JSON 也会卡顿。

**处理**：改成懒加载（`getRoots` + `getChildren`）。
判断标准很简单：**组织选择器永远只需要用户点到的那一层**。

### 坑 3：移动节点忘了级联重写子树

只改自己的 `PathCode`，子树的路径就指向上级的旧路径 ——
表现是"移动后，原来能查到的学生查不到了"，而且**不报任何错**。

**处理**：`MoveAsync` 里按旧路径前缀捞出整棵子树，统一替换前缀。

### 坑 4：`Code`（组织编码）与 `PathCode`（路径）混用

- `Code` 是**组织自己的业务编码**（学校是 10 位标识码，教育局是行政区划码）；
- `PathCode` 是**从根到这里的编码串**，只为查询服务。

把两者混用会出现"用学校标识码去做前缀匹配"这种荒谬的查询，
而且因为学校标识码本身以行政区划码开头，**偶尔还能查对**，更难发现。

### 坑 5：组织层级不是固定的四级

本项目内置了 Province / City / County / School 四级，
但**实际中会出现"省直管县"**（县直接挂在省下）以及"九年一贯制学校下设校区"。

**处理**：树结构本身不限层级（`TreeLevel` 是算出来的，不是写死的），
但业务规则里对"审核级别"的映射是显式的（第 32 章的 `ChangeOrgResolvers`）——
组织树保持灵活，业务语义在业务代码里明确。
