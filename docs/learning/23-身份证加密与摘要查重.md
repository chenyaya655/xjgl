# 23 身份证加密存储与摘要查重：既要能查重，又要看不到明文

> 对应代码：`src/Xjgl.Domain.Shared/Validation/IdCardValidator.cs`、
> `src/Xjgl.Application/Students/IdCardProtector.cs`、
> `src/Xjgl.Application/Students/StudentAppService.cs`
> 对应测试：`test/Xjgl.Domain.Tests/Validation/IdCardValidatorTests.cs`、
> `test/Xjgl.Application.Tests/Students/StudentAppServiceTests.cs`、
> `Students/StudentProfileTests.cs`

## 23.1 要解决的问题

身份证号在学籍系统里有两副面孔：

- **它是唯一性的关键**：同一身份证号不能建两份学籍（跨校也要能查出来）；
- **它是最高级别的个人信息**：泄露一次就是无法挽回的事故。

这两个需求**互相冲突**：要按身份证号查重，就得能按它检索；而"能检索"意味着明文可被索引 ——
一旦数据库被拖库，所有学生的身份证号就是明文的。

本项目的解法是**一个号码、两种存储**：

| 字段 | 内容 | 用途 |
|---|---|---|
| `IdCardEncrypted` | AES 密文（ABP 的 `IStringEncryptionService`） | 需要看原文时解密（受权限控制），平时只给掩码 |
| `IdCardHash` | HMAC-SHA256 摘要（密钥来自配置） | **唯一索引与查重**，不可逆 |

为什么摘要用 **HMAC 而不是普通 SHA256**？因为身份证号的取值空间很小且有规律
（地区码 + 生日 + 顺序码），普通哈希可以被暴力枚举反推；加了密钥才不可逆。

## 23.2 第一步：严格的格式校验（`IdCardValidator`）

身份证号校验不是"18 位数字"这么简单，国标（GB 11643-1999）有校验位算法：

```csharp
private static readonly int[] Weights = { 7, 9, 10, 5, 8, 4, 2, 1, 6, 3, 7, 9, 10, 5, 8, 4, 2 };
private const string CheckCodes = "10X98765432";

public static bool TryNormalize(string? input, out string normalized, out string? error)
{
    // 1) 空值、长度、前 17 位必须是数字
    // 2) 15 位老号补齐为 18 位（插入 "19" 前缀 + 计算校验位）
    // 3) 出生日期段必须合法（含"2 月 30 日"这种）
    // 4) 校验位必须一致
}
```

四类错误信息都刻意做成**可读的中文**，因为它们会直接出现在界面上与导入错误明细里：

| 错误 | 提示 |
|---|---|
| 长度为 15/18 之外 | 身份证号长度必须为 18 位（或 15 位老号） |
| 前 17 位含字母 | 身份证号前 17 位必须为数字 |
| 出生日期段不合法（如 `20161301`） | 身份证号的出生日期段不合法 |
| 校验位错 | 身份证号校验位不正确 |

顺带还能从号码里解析出生日期与性别（顺序码奇数为男）：

```csharp
public static bool TryGetBirthDate(string idCardNumber, out DateOnly birthDate);
public static bool TryGetGender(string idCardNumber, out bool isMale);
```

> 实战提醒：**端到端验证导入功能时，我用随机数拼的身份证号全被拒了** ——
> 提示分别是"出生日期段不合法"和"校验位不正确"。这不是 bug，恰恰说明校验在生效。
> 写测试数据时要用"算法生成校验位"的方式（本项目测试基类里就有 `NewUniqueIdCard()`）。

## 23.3 第二步：加密、摘要、掩码

```csharp
public interface IIdCardProtector
{
    string? Encrypt(string? idCardPlain);          // 明文 → 密文
    string? Decrypt(string? idCardEncrypted);      // 密文 → 明文（解不开返回 null，不抛异常）
    string? MaskEncrypted(string? idCardEncrypted); // 密文 → 掩码
    string  MaskPlain(string idCardPlain);          // 明文 → 掩码
    string  ComputeHash(string normalizedIdCard);   // 查重摘要
}
```

### 为什么把它抽成独立服务

学生主档要用，**监护人子表也要用**（家长的身份信息同样敏感）。
如果这段逻辑留在 `StudentAppService` 的私有方法里，子表就只能复制一份 ——
而"密文入库 + 摘要查重 + 默认只给掩码"这三条规则**一旦不一致**，
迟早会出现某个界面把明文吐出去。因此它被抽成了一个共享服务。

### 解密失败不要抛异常

```csharp
public string? Decrypt(string? idCardEncrypted)
{
    try { return _encryption.Decrypt(idCardEncrypted!); }
    catch (Exception)
    {
        // 密钥轮换后老数据可能解不开 —— 返回 null 让界面显示「—」，
        // 而不是让整个列表接口 500
        return null;
    }
}
```

### 掩码规则：前 6 后 4

```csharp
return idCardPlain.Length >= 10
    ? $"{idCardPlain[..6]}********{idCardPlain[^4..]}"
    : new string('*', idCardPlain.Length);
```

保留前 6 位（地区码）与后 4 位，中间 8 位打码 —— 足够人工核对，又不足以还原。
**注意掩码是"展示形态"，绝不入库存档**。

## 23.4 第三步：写入与查重

```csharp
var idCard = NormalizeIdCard(input.IdCardNumber);   // 校验 + 规范化
var idCardHash = _idCards.ComputeHash(idCard);

// 写入前查重：同一身份证号在系统内只能有一份有效学籍
var duplicated = await _students.FindAsync(s => s.IdCardHash == idCardHash);

if (duplicated != null)
{
    throw new BusinessException(XjglDomainErrorCodes.DuplicateIdCard)
        .WithData("reason", $"身份证号已存在学籍记录：{duplicated.Name}（学籍辅号 {duplicated.StudentNo}）");
}

entity.IdCardEncrypted = _idCards.Encrypt(idCard);
entity.IdCardHash = idCardHash;
```

三个要点：

1. **查重走摘要字段**，而不是解密后比较（那要全表解密，性能不可接受，也失去索引）；
2. **错误提示要给出已有记录**（姓名 + 辅号）—— 只说"身份证号重复"会让经办人无从下手；
3. **摘要字段可以建唯一索引**（方案文档里把它列为"可做唯一约束"的字段）：
   应用层查重是"友好提示"，唯一索引是"最后一道防线"（并发下两次查重都可能通过）。

## 23.5 第四步：更新时的两个语义

### ① 只有号码变了才查重

```csharp
if (!string.Equals(entity.IdCardHash, idCardHash, StringComparison.Ordinal))
{
    var duplicated = await _students.FindAsync(s => s.IdCardHash == idCardHash && s.Id != id);
    if (duplicated != null) { ... }
}
```

### ② 子表（监护人）里"留空 = 不修改"

监护人详情页只显示掩码。用户没改就不该回传身份证号 —— 否则会把**掩码**当成新号码存进去：

```csharp
// 身份证号：留空 = 不修改（界面只显示掩码，用户没改就不该回传）
if (!input.IdCardNumber.IsNullOrWhiteSpace())
{
    if (!IdCardValidator.TryNormalize(input.IdCardNumber, out var idCard, out var error))
    {
        throw new BusinessException(XjglDomainErrorCodes.ValidationFailed)
            .WithData("reason", $"监护人身份证号不合法：{error}");
    }

    entity.IdCardEncrypted = _idCards.Encrypt(idCard);
}
```

前端也配合这条语义：编辑监护人时**故意不回填**身份证号，只给占位提示"留空表示不修改"。

## 23.6 第五步：密钥管理（这一条最容易被忽略）

```csharp
private readonly IConfiguration _configuration;

public string ComputeHash(string normalizedIdCard)
{
    var key = _configuration["Xjgl:Security:IdCardHmacKey"];

    if (key.IsNullOrWhiteSpace())
    {
        key = "xjgl-dev-idcard-hmac-key-please-change-in-production";
    }

    return IdCardValidator.ComputeIdCardHash(normalizedIdCard, Encoding.UTF8.GetBytes(key!));
}

// AES 的密钥来自 ABP：Xjgl:Security:EncryptionPassphrase
```

**开发默认值必须在生产被覆盖**（见仓库根目录 `SECURITY.md`）：

| 配置项 | 后果 |
|---|---|
| `Xjgl:Security:EncryptionPassphrase` | 用于 AES。换了它，**已存的数据解不开**（因此上线后不要随意更换，或准备好迁移脚本） |
| `Xjgl:Security:IdCardHmacKey` | 用于查重摘要。换了它，**查重会失效**（同一号码算出不同摘要 → 重复号能建进去） |

## 23.7 验证方法

### ① 单元测试穷尽非法输入（`IdCardValidatorTests`）

| 类别 | 用例 |
|---|---|
| 合法 | 18 位合法号、15 位老号（自动补齐并算校验位） |
| 长度 | 17 位 / 19 位 / 空 |
| 字符 | 前 17 位含字母、末位小写 x（应被规范化成大写 X） |
| 日期 | 月份 13、2 月 30 日、年份 1899 |
| 校验位 | 故意改坏最后一位 |
| 派生 | 出生日期解析正确、顺序码奇偶 → 性别 |

### ② 集成测试验证"存进去的是密文，出来的是掩码"

```csharp
var dto = await _students.CreateAsync(new CreateUpdateStudentDto { IdCardNumber = idCard, ... });

dto.MaskedIdCard!.ShouldContain("*");
dto.MaskedIdCard.Contains(idCard).ShouldBeFalse("响应里不能出现完整明文");

// 库里存的必须是密文与摘要
var entity = await _students.FindAsync(s => s.Id == dto.Id);
entity!.IdCardEncrypted.ShouldNotBe(idCard);
entity.IdCardHash.ShouldNotBeNullOrWhiteSpace();
```

## 23.8 踩坑记录

| 现象 | 根因 | 教训 |
|---|---|---|
| 编辑监护人后号码变成了 `410102********0011` | 前端把掩码当原值回传，后端又把它当新号码存了 | 敏感字段的编辑语义必须显式定义："留空 = 不修改"；前端不回填原值 |
| 密文比较导致留痕"改了又没改" | AES 随机 IV，同一明文每次密文都不同 | 用于**比较**的值必须是确定性的（摘要），不能是密文 |
| 导入测试数据全部被拒 | 随机拼的身份证号校验位不对 | 测试数据要用算法生成合法号；被拒恰恰证明校验有效 |
| 密钥写在代码里 | "先用默认值，上线再改" | 默认值 + `SECURITY.md` 强制清单；换密钥的后果（解不开 / 查重失效）必须写进文档 |
