# 39 批量上传：为什么"并发写存储"但要"串行落库"

> 对应代码：`src/Xjgl.Application/Photos/PhotoUploadService.cs`
> 对应测试：`test/Xjgl.Application.Tests/Photos/PhotoAppServiceTests.cs`

## 39.1 要解决的问题

一次上传可能是 500 张照片（一个年级）。而这条链路要做四件事：

```
读内容 → 校验+探测尺寸 → 哈希 → 写存储（NAS）
                              → 落库（台账行 + 学生主表标记）
```

哪些能并发、哪些不能，是本章的核心。**做错了不会报错，只会变慢或偶发失败**。

## 39.2 第一步：先纠正一个常见误解

很多人会想"500 张照片，那当然全部并发处理最快"。但这里有几个硬约束：

| 阶段 | 能并发吗 | 为什么 |
|---|---|---|
| 读上传内容 | 不能（已读进内存） | 内容本来就在 `MemoryStream` 里 |
| 解码探测尺寸 | **能，但没必要** | 已经是内存操作，CPU 密集；并发只会争 CPU |
| 写存储（NAS） | **能，而且必须** | 网络 I/O，串行会让 500 张变成 500 个往返 |
| 落库 | **不能** | 见下 |

**为什么落库不能并发**：台账行要与学生主表的 `photo_path` 标记**一致地更新**，
而"同一学生的多条记录"（重复上传）之间有先后关系。
并发落库会让"学生主表标记指向哪一张"变成不确定 —— 而它是"缺照片名单"的判据（第 41 章）。

## 39.3 第二步：分阶段的实际形状

```
UploadBatchAsync(batchId, requests)
  │
  ├─ ① 准备阶段（串行）
  │     逐个：查学生 → 校验扩展名 → 读内容 → 算哈希 → 探测尺寸
  │     ├─ 学生不存在 → 记 itemResult.ErrorMessage，计入 Failed
  │     ├─ 扩展名不允许 → 同上
  │     ├─ 内容不是图片（ProbeAsync 返回 null）→ 同上
  │     └─ 命中秒传（同学同哈希，且上次是成功态）→ 记 Skipped，跳过写存储
  │
  ├─ ② 写存储阶段（并发，受舱壁限制）
  │     WriteStorageInParallelAsync(items.Where(i => i.NeedWrite))
  │
  └─ ③ 落库阶段（串行）
        逐个：写台账行（状态由写入结果决定）→ 更新学生主表标记
```

代码里的分层非常明确：

```csharp
var prepared = await PrepareItemsAsync(batchId, requests, cancellationToken);
await WriteStorageInParallelAsync(prepared, cancellationToken);
await PersistAsync(prepared, result, cancellationToken);
```

## 39.4 第三步：逐行容错（这是产品要求，不是健壮性）

批量上传的返回结构里**每一张都有自己的结果**：

```csharp
public class PhotoUploadItemResultDto
{
    public Guid StudentId { get; set; }
    public string? StudentNo { get; set; }
    public bool Success { get; set; }
    public bool Skipped { get; set; }     // 秒传命中
    public bool Degraded { get; set; }    // 落到本地降级区
    public string? ErrorMessage { get; set; }
    // ...
}
```

为什么必须这样：50 个文件里如果有 3 个文件名写错（不是学籍辅号），
**用户需要知道是哪 3 个**。如果整批返回一个"上传失败"，用户只能自己一个个试。

前端也照着这个结构做：上传结果表里逐行显示"成功 / 秒传 / 已暂存 / 失败 + 原因"
（第 48 章）。

## 39.5 第四步：一个真实的坑 —— `prepared` 与 `writeItem` 是两个对象

这是本模块注释里明确记录的一个 bug：

```csharp
var writeItem = new PreparedItem
{
    Request = request,
    Result = itemResult,
    Student = prepared.Student,
    Existing = prepared.Existing,
    Content = content,
    Hash = hash,
    RelativePath = relativePath,

    // ★ 注意：探测结果必须**显式带过来**。
    //    writeItem 是另一个对象，只给 prepared 赋值的话，
    //    落库阶段读到的仍是 null —— 尺寸会静默丢失
    //    （这个坑被集成测试逮住：result.Width 一直是 0）
    Size = size,
    ContentLength = content.Length,
    NeedWrite = true
};
```

**教训**：多阶段流水线里，"阶段之间的数据传递"是最容易漏的地方，
而且漏了**不报错**——只是某个字段变成默认值。对策是让集成测试断言这些字段
（`result.Width` / `photo.Width`），而不是只断言"上传成功"。

## 39.6 第五步：秒传（同一张图重复上传不重复写存储）

```csharp
// 条件：同一学生 + 内容哈希一致 + 上次是「正常」或「降级待补偿」
if (prepared.Existing != null
    && prepared.Existing.FileHash == hash
    && (prepared.Existing.Status == PhotoStatuses.Normal
        || prepared.Existing.Status == PhotoStatuses.FallbackPending))
{
    itemResult.Success = true;
    itemResult.Skipped = true;          // ← 界面显示"秒传（内容未变）"
    itemResult.PhotoId = prepared.Existing.Id;
    // 不再写存储
    return prepared;
}
```

三个细节：

1. **必须限定"上次是成功态"**：如果上次是 `Pending`（写了一半）或 `Failed`，
   哈希一致也不代表存储里有文件 —— 那必须重写；
2. **`Skipped` 不是 `Success` 的同义词**：界面上要区分（老师会疑惑"我明明传了 50 张，
   怎么只写了 2 张"）；
3. **秒传仍要返回 `ThumbnailPath` 等已有信息**，否则前端会以为"这张没有缩略图"。

集成测试里有一条 `重复上传相同内容_命中秒传不重复写存储` 专门守它，
并且测试数据必须保证"同 seed 出完全相同的字节"（第 51 章会讲测试数据怎么造）。

## 39.7 怎么验证

```powershell
dotnet test test\Xjgl.Application.Tests --filter "FullyQualifiedName~PhotoAppServiceTests"
```

值得关注的用例：

| 用例 | 守什么 |
|---|---|
| `上传照片_写入主存储并登记台账` | 尺寸/哈希/路径/学生标记全部正确 |
| `重复上传相同内容_命中秒传不重复写存储` | 秒传 |
| `上传失败的文件_不影响同批其它文件` | 逐行容错 |
| `NAS 故障时_降级写入并标记待补偿` | 降级链路 |
| `上传照片的FileSize 等于实际字节数` | 见下 |

最后一条是**修掉的一个坏断言**：它原本写的是 `photo.FileSize.ShouldBe(512)` ——
而 JPEG 的具体字节数由图像库编码器决定、随版本变化（实测某版本是 616 字节）。
改成与"自己上传的字节数"比较：

```csharp
photo.FileSize.ShouldBe(content.Length, "台账里的文件大小必须等于实际写入的字节数");
```

它变红时的报错（"应为 512、实际 616"）看起来像"业务把大小算错了"，
**排查方向会被完全带偏**。这是"魔法数字断言"的典型危害。

## 39.8 本章要点

1. 职责分离：**准备（串行）→ 写存储（并发）→ 落库（串行）**。
2. 落库不能并发：台账与学生主表标记必须一致地更新。
3. 逐行容错是产品要求：每张照片有自己的结果与失败原因。
4. 多阶段流水线里"阶段间数据传递"最容易漏，而且**漏了不报错** —— 靠断言字段守住。
5. 秒传必须限定"上次是成功态"，且 `Skipped` 与 `Success` 在界面上要区分。
6. 不要写魔法数字断言（`FileSize == 512`）；断言"I/O 两端的值相等"才有意义。
