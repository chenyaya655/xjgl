# 51 集成测试：真实数据库、故障演练与"长期累积的库"

> 对应代码：`test/Xjgl.TestBase/`（基类、配置、假身份）、`test/Xjgl.Application.Tests/`（265 条）
> 相关文档：第 50 章（单元测试）、第 52 章（端到端）

## 51.1 要解决的问题

集成测试要打**真实数据库 + 真实文件系统 + 真实两套 ORM**。这带来四个必须解决的问题，
每一个处理不好都会让测试变成"偶尔红、没人信"的负担：

| 问题 | 不处理的后果 |
|---|---|
| **测试库是长期累积的** | 计数断言"应为 3、实际 32" |
| 测试之间互相污染身份 | 数据范围断言全部失效 |
| 故障场景无法复现 | 熔断/降级/补偿只能靠人工验 |
| 两套 ORM 的可见性 | 写完查不到，怀疑人生 |

本章逐条讲，重点是那些**看起来是业务 bug、实际是测试设计问题**的情况。

## 51.2 第一步：默认以超管身份运行

```csharp
public abstract class XjglIntegrationTestBase : AbpIntegratedTest<XjglTestBaseModule>
{
    protected XjglIntegrationTestBase()
    {
        GetRequiredService<FakeCurrentPrincipalAccessor>()
            .SetUser(Guid.NewGuid(), "test-admin", "admin");
    }
}
```

**为什么默认给一个身份**：绝大多数用例只关心业务行为（能不能建学生、流程走得对不对），
不关心"当前是谁"。而数据范围一开启，**没有身份的调用会解析不出组织、进而什么都看不到** ——
那会让所有与身份无关的用例一起失败，掩盖真正的回归。

需要差异身份的用例（数据范围、越权）自己在用例里覆盖。

## 51.3 第二步：换身份必须**新开 DI 作用域**（这条最容易踩）

```csharp
/// <summary>
/// 以指定用户身份执行一段操作：**换 principal 并新开 DI 作用域**。
/// </summary>
private async Task<T> InScopeAsAsync<T>(
    Guid userId, string userName, string[] roles, Func<IServiceProvider, Task<T>> action)
{
    _principal.SetUser(userId, userName, roles);
    using var scope = ServiceProvider.CreateScope();
    return await action(scope.ServiceProvider);
}
```

`ICurrentUser` 是 **Scoped** 的，并且**会缓存**用户 Id 与角色。
集成测试里整个测试类共用根作用域，如果在同一个作用域里换身份，
第二次之后 `ICurrentUser` 仍然返回**第一次**的值 ——

> 表现是"所有身份都像第一个身份"，**越权断言全部失效**。
> 本仓库的数据范围测试类最初 8 个用例全挂就是这个原因。

所以"以某个身份做某事"必须走这个辅助方法：**换 principal + 新开作用域**。

## 51.4 第三步：让测试"不依赖库里已有多少数据"

测试库是**长期累积**的（本机有 3000+ 学生、14000+ 组织）。
所以**绝对计数断言一定会红**。三条可行做法：

### 做法 A：把范围收窄到本用例自己造的数据

```csharp
private StudentStatisticsQueryDto SchoolQuery(string dimension, Guid schoolOrgId)
    => new()
    {
        Dimension = dimension,
        AcademicYear = _year,
        SchoolOrgId = schoolOrgId,        // ← 收到本用例自己建的学校
        IncludeDescendantOrgs = true
    };
```

这是**首选**：断言变成确定的，而且顺带验证了"统计能按学校过滤"这个真实功能。

### 做法 B：无法按范围过滤时，断言**增量**

```csharp
var before = await _statistics.GetStudentStatisticsAsync(StudentQuery(StudentStatDimensions.HasPhoto));
var beforeNo = CountOf(before, "no");

await CreateStudentAsync(tree.SchoolA1);
await CreateStudentAsync(tree.SchoolA1);

var after = await _statistics.GetStudentStatisticsAsync(StudentQuery(StudentStatDimensions.HasPhoto));

CountOf(after, "no").ShouldBe(beforeNo + 2);
```

### 做法 C：年份由**时间推导**，而不是写死

```csharp
private readonly string _year = $"{DateTime.UtcNow.Year}-{DateTime.UtcNow.Year + 1}";
```

写死年份（如 `"2090-2091"`）在跑过几轮之后会与历史数据撞在一起；
按年推导既保证隔离，也不会随时间推移和别的用例重名。

### 反面教材：为什么"本类专用学年"也不够

我最初用"本类专用学年 + 只按学年过滤"来隔离，结果统计出 **32** 而不是 3 ——
因为**同一个年份下，别的测试类也在造学生**。这是"看起来隔离了、实际没有"的典型。

## 51.5 第四步：造数据的两个固定套路

### 身份证号：计数器 + 撞号重试

```csharp
private static int _idCardSequence = Random.Shared.Next(0, 900_000);

protected static string NewUniqueIdCard(int birthYear = 2015, string areaCode = "410103")
{
    var n = Interlocked.Increment(ref _idCardSequence);
    var month = n / 1000 % 12 + 1;
    var day = n / 12000 % 28 + 1;
    var seq = n % 1000;
    // ... 按国标算校验位
}

protected static async Task<T> RetryOnDuplicateIdCardAsync<T>(Func<Task<T>> action, int maxAttempts = 8)
{
    for (var attempt = 1; ; attempt++)
    {
        try { return await action(); }
        catch (BusinessException ex) when (attempt < maxAttempts && ex.Code == XjglErrorCodes.DuplicateIdCard)
        { /* 换一个号再来 */ }
    }
}
```

**为什么不能"用一个固定号"**：身份证号有查重（第 23 章），
而测试库跨轮累积 —— 固定号跑第二次就撞。早期版本用"固定地区 + 3 位随机顺序码"
只有 899 种可能，跑几轮必然撞号，表现是**随机变红的用例**。

> 基类注释里写得很明确：**不要为了让用例稳定而放宽断言**，
> 也不要在偶发失败时删掉用例 —— 正确做法是把不确定性收敛在**测试数据生成**这一层。

### 姓名：只能用规范汉字

后端对姓名做**码点白名单**校验（第 24 章），所以
`E2E学生${Date.now()}` 这种"加时间戳保唯一"的写法会被直接拒收：

```
姓名包含非法字符"1"
```

需要唯一姓名时，把数字转成中文（`web/e2e/specs/support/auth.ts` 的 `chineseNumeral`）。

### 组织编码：必须**精确 10 位**

学校标识码是 `{SchoolCode:10}{Seq:6}`。写成 12 位会让**建学生**时抛
`StudentNumberGenerateFailed` —— 而报错来自学号生成，看起来与"建学校"无关。
这个坑我踩过（测试里 `Code = NewDivisionCode() + Random.Shared.Next(10000,99999)`）。

## 51.6 第五步：故障演练 —— 不 mock，把"NAS"弄坏

第 37 章讲过原理，这里给出**为什么这比 mock 好**：

```csharp
/// <summary>把「NAS」弄坏：删掉目录，在原地放一个同名文件，任何目录创建都会失败。</summary>
private void BreakNas()
{
    var root = _nasStorage.RootPath;
    if (Directory.Exists(root)) Directory.Delete(root, recursive: true);
    Directory.CreateDirectory(Path.GetDirectoryName(root)!);
    File.WriteAllText(root, "NAS 故障演练：这里故意放一个文件占位。");
}

private void RepairNas()
{
    var root = _nasStorage.RootPath;
    if (File.Exists(root)) File.Delete(root);
    Directory.CreateDirectory(root);
}
```

| | mock | BreakNas/RepairNas |
|---|---|---|
| 真实度 | 只测"我们对接口的假设" | 走**完全相同**的代码路径（同一套 DI、同一个熔断器） |
| 速度 | 快 | 毫秒级（本地目录） |
| 能测到 | 分支逻辑 | 熔断 → 降级 → 补偿回放**整条链路** |
| 维护成本 | mock 与实现漂移 | 无 |

配置里把"NAS 根目录"指向测试输出目录：

```csharp
["Xjgl:Photo:NasRoot"] = NasRoot,          // App_Data/photo-tests/nas
["Xjgl:Photo:FallbackRoot"] = FallbackRoot,
// 熔断参数调小，让测试能在几百毫秒内观察到「熔断→恢复」
["Xjgl:Photo:MinimumSamples"] = "3",
["Xjgl:Photo:FailureRateThreshold"] = "0.5",
["Xjgl:Photo:OpenSeconds"] = "1",
```

## 51.7 第六步：为"验证某件事真的生效"而写的用例

有些实现**看起来生效了但实际没有**，这类地方必须专门写用例。本项目的例子：

### 例一：事务回滚（第 33 章）

"包了事务"看不出来 → 必须断言"中途抛异常后前面的写查不到"。

### 例二：Outbox 真的落库（第 33 章）

少了 `UseDbContext` / `ConfigureEventOutbox()` / 迁移，**三者都静默退回老行为** →
必须去 `AbpEventOutbox` 表里查那一行。我做过变异验证：注释掉配置，用例立刻红。

### 例三：`IncludeDescendantOrgs` 真的生效

```csharp
// 含下级 → 两所学校都算（2 人）
withChildren.Total.ShouldBe(2);
// 同一条件改成"仅本级" → 县局本身没有直接挂学生，必须是 0
exactOnly.Total.ShouldBe(0, "「仅本级」不能把下级学校的学生算进来");
```

这条抓出过一个真缺陷：应用层把参数丢了
（`includeDescendants ? org.PathCode : org.PathCode` —— 三元两边一样）。

## 51.8 怎么跑

```powershell
# 全量（268 条，约 4 分钟；**不要用 VSTest 的 --filter**）
$app = "test\Xjgl.Application.Tests\bin\Debug\net10.0\Xjgl.Application.Tests.dll"
dotnet $app
dotnet $app --filter-class "*StatisticsAppServiceTests"
dotnet $app --filter-namespace "Xjgl.Photos"
dotnet $app --list-tests          # 先确认过滤器真的选中了范围

# 连的是哪个库？（默认原生 PG 的 xjgl_test @55432）
# 可用 XJGL_TEST_CONNECTION 覆盖
```

> ⚠ **xunit v3 + Microsoft.Testing.Platform 的过滤器与 VSTest 不同**：
> `--filter "FullyQualifiedName~X"` 会"运行 0 个测试"并返回退出码 5，
> 看起来像"测试不存在"。要用 `--filter-class` / `--filter-method` / `--filter-namespace`。
>
> 而且 **"过滤后绿了"不等于"通过"**：我遇到过一次
> `--filter-namespace Xjgl.Photos` 根本没选中 `Xjgl.Application.Tests.Photos` 下的类，
> 于是"单独跑通过"其实是"压根没跑"。**先 `--list-tests` 确认选中范围**。

## 51.9 本章要点

1. 基类默认给超管身份，否则数据范围会让所有用例一起失败。
2. **换身份必须新开 DI 作用域**（`ICurrentUser` 是 Scoped 且会缓存）。
3. 测试库长期累积 → 断言要**收窄范围**或用**增量**；年份按时间推导。
4. 造数据：身份证号用计数器 + 撞号重试；姓名只用规范汉字；学校码精确 10 位。
5. 故障演练用 `BreakNas/RepairNas`（换同名文件），比 mock 更真实、比真 NAS 可控。
6. 为"看起来生效但实际没有"的实现专门写用例（事务、Outbox、被丢掉的参数）。
7. MTP 的过滤器与 VSTest 不同；**"过滤后绿了"要先确认真的选中了**。
