# 40 照片台账与缺照片名单：判据为什么放在学生主表

> 对应代码：`src/Xjgl.Application/Photos/PhotoAppService.cs`
> 对应测试：`test/Xjgl.Application.Tests/Photos/PhotoAppServiceTests.cs`

## 40.1 要解决的问题

照片管理有两个看似对称、实际差别很大的功能：

| 功能 | 数据来源 | 分页准确吗 |
|---|---|---|
| **照片台账** | `stu_photo` 表 | 准确（直接分页） |
| **缺照片名单** | **学生主表的 `photo_path` 是否为空** | 准确 |

第二个的判据选择是本章的核心：**"缺照片"看起来应该查"`stu_photo` 里没有行"，
但本项目刻意改成读学生主表的冗余列**。

## 40.2 为什么不能"左连接后过滤"

自然的写法是：

```sql
-- ❌ 在仓储抽象里做不到，且分页会错
select s.* from stu_student s
left join stu_photo p on p.student_id = s.id and p.is_deleted = false
where p.id is null
limit 50 offset 0;
```

两个问题：

1. **本项目的 `IXjglRepository` 刻意不暴露 join**（第 08 章）。
   要在应用层实现就只能"先分页学生、再逐个查有没有照片" —— 也就是
   **先分页再过滤**；
2. "先分页再过滤"会让**总数与翻页都错**：第 1 页取 50 个学生、其中 20 个有照片，
   于是这一页只显示 30 行，而总数还是按全表学生算的。用户会觉得"少显示了"，
   却不知道少的是什么。

## 40.3 本项目的解法：冗余一个可索引、可分页的判据

在学生主表上加 `photo_path`，上传/删除照片时**同步维护**它：

```csharp
// 上传成功后：写主表标记
student.PhotoPath = relativePath;

// 删除照片后：清空标记（否则「缺照片名单」永远看不到这些学生）
student.PhotoPath = null;
```

于是缺照片名单变成一个**普通的分页查询**：

```csharp
var predicate = BuildMissingPredicate(input, scope);   // s.PhotoPath == null && 数据范围
var totalCount = await _students.GetCountAsync(predicate);
var students = await _students.GetPagedListAsync(predicate, sorting, skip, take);
```

代价与收益：

| | 说明 |
|---|---|
| **代价** | 两处写（上传、删除都要维护标记），漏一处就会不一致 |
| **收益** | 总数与分页**准确**；查询能走索引；不需要 join |

> 这个取舍的判据是：**"名单类功能"最不能接受的失败方式是"少了几个人"**。
> 分页不准会让用户看到一份"看起来完整"的名单 —— 那比报错严重得多。

删除时的清理逻辑（`PhotoAppService.RemoveAsync`）写得很明确：

```csharp
// 3) 清掉学生主表上的照片标记，否则「缺照片名单」永远看不到这些学生
var studentIds = entities.Select(e => e.StudentId).Distinct().ToList();
var students = await _students.GetListAsync(s => studentIds.Contains(s.Id));
// ... 逐个把 PhotoPath 置空
```

## 40.4 台账查询：谓词怎么拼

```csharp
private static Expression<Func<StuPhoto, bool>>? BuildPredicate(PhotoQueryDto input, UserDataScope scope)
{
    var hasStudent = input.StudentId.HasValue;
    var hasSchool = input.SchoolOrgId.HasValue;
    var hasBatch = input.BatchId.HasValue;
    var hasStatus = !string.IsNullOrWhiteSpace(input.Status);
    var hasKeyword = !string.IsNullOrWhiteSpace(input.Keyword);

    // ★ 无过滤条件时返回 null 是安全的 —— **前提是它同时考虑了数据范围**。
    //   若漏掉 hasScopePath，带数据范围时会返回 null 谓词，等于范围约束被丢掉。
    if (!hasStudent && !hasSchool && !hasBatch && !hasStatus && !hasKeyword && !hasScopePath)
    {
        return null;
    }
    // ...
}
```

注释里那句是**真实的越权入口**：`null` 谓词在仓储里表示"不加条件"。
如果"判断是否无过滤条件"时忘了把数据范围算进去，
一个只带数据范围的请求就会拿到**全库照片**。

## 40.5 三个"看起来一样"的状态必须区分

台账里 `stu_photo.status` 有四个值，而它们在界面上的意义完全不同：

| 状态 | 含义 | 界面提示 |
|---|---|---|
| `Normal` | 已写入主存储（NAS） | 正常 |
| `FallbackPending` | **写到本地降级区了，等 NAS 恢复后补传** | 降级待补偿 |
| `Pending` | 中间态（还没落盘） | 待处理 |
| `Failed` | 处理失败 | 处理失败 |

为什么不把 `FallbackPending` 显示成"成功"：**文件确实存下来了（在本地盘），
但没在 NAS 上**。如果告诉用户"成功"，那么 NAS 磁盘故障时这些照片就全丢了，
而"成功"的记录会让运维以为不需要处理。

## 40.6 缩略图：两条容易搞混的路径

台账列表要显示缩略图，而它涉及两个不同的问题：

1. **台账里有没有缩略图路径**（`thumbnail_path` 列）；
2. **存储里那个文件在不在**。

接口的返回行为是"**缩略图缺失时回落成原图**"：

```csharp
public sealed class PhotoContentResult
{
    public byte[] Content { get; init; }
    public string ContentType { get; init; }
    public string? ETag { get; init; }

    /// <summary>实际返回的是缩略图还是原图（缩略图缺失时会回落成原图）。</summary>
    public bool IsThumbnail { get; init; }
}
```

`IsThumbnail` 这个字段是**给测试用的**：断言"确实返回了缩略图"不能只看"有内容"，
要看这个标记。有专门的用例 `读取_缩略图接口返回缩小后的图` 守它。

> **前端注意**：图片请求**带不上 Authorization 头**（`<img src>` 不会带），
> 所以前端必须用 axios 取 Blob 再 `createObjectURL`（第 48 章）。
> 这条链路任何一环写错的表现都是"表格里一片空白"，而接口日志一切正常。

数据库侧抽查（"缺照片名单"的判据是否一致）：

```sql
-- 应当恒为 0：主表说有照片、但台账里没有有效记录
select count(*) from stu_student s
where s.is_deleted = false and s.photo_path is not null
  and not exists (select 1 from stu_photo p
                  where p.student_id = s.id and p.is_deleted = false);
```

## 40.8 本章要点

1. "缺照片名单"的判据放在**学生主表的 `photo_path`**，而不是"台账里有没有行" ——
   这样总数与分页才准确（代价是两处写）。
2. 删除照片**必须同时清主表标记**，否则那些学生永远从名单里消失。
3. 拼谓词时"是否无过滤条件"的短路判断**必须把数据范围算进去**，否则是越权读全库。
4. `FallbackPending` 不能显示成"成功"：文件在本地盘、不在 NAS。
5. 读缩略图接口要有 `IsThumbnail` 标记，测试才能区分"缩略图"与"回落的原图"。
6. 图片接口要 Bearer 令牌 → 前端必须走 Blob，**这是界面上唯一会表现为"空白"的链路**。
