# 54 部署、扩容与开源准备

> 对应文件：`deploy/`（compose、Dockerfile、nginx）、`deploy/README.md`、
> `tools/verify-deploy.mjs`、`.github/workflows/`
> 相关文档：`deploy/README.md`（第 11 章 K8s、第 12 章压测）

## 54.1 要解决的问题

部署这件事的难点**不在"把服务跑起来"**，而在于：

1. **配置项分散且容易漏**：容器起来了、功能上线才炸；
2. **多副本会改变行为**：单实例永远看不出问题（第 54.4 节）；
3. **开源前要过一遍**：密钥、内部信息、个人数据。

本章把这三件事按"本仓库怎么做的 + 为什么"讲清楚。

## 54.2 第一步：编排文件的"事实来源"是 appsettings

手写 compose 最容易出的问题是**变量名写错一个字母** ——
容器照样起来，功能上线才炸。所以本仓库有一道自动核对：

```bash
node tools/verify-deploy.mjs
```

它以 `src/Xjgl.HttpApi.Host/appsettings.json` 为**事实来源**，
反推 compose 必须提供的环境变量（`A:B` → `A__B`）逐个核对，并检查：

- 字体目录挂载；
- 健康检查路径与端口；
- 数据卷（数据库、降级照片、导出产物）；
- nginx 的深链回落与上传体积上限。

```bash
# CI 里再跑一次 docker 自己的解析器，校验 YAML 语法与变量插值
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env.example config -q
```

**为什么要"反推"而不是"人工对照"**：配置项会随功能增长（本项目的
`Xjgl:*` 配置节有几十项），人工对照一次就要半小时且必然漏。
把 appsettings 当事实来源，**加了新配置节之后忘记同步 compose 会被脚本拦下**。

## 54.3 第二步：三层配置来源与优先级

```
appsettings.json                 ← 默认值（进仓库，不含任何密钥）
appsettings.{Environment}.json   ← 环境相关（Development 才提交）
环境变量 Xjgl__Xxx__Yyy           ← 生产唯一来源（不进仓库）
```

生产环境**只通过环境变量注入**，`.env.example` 里是占位符：

```bash
# deploy/.env.example
POSTGRES_PASSWORD=__CHANGE_ME__
Xjgl__Redis__Password=__CHANGE_ME__
Xjgl__StringEncryption__DefaultPassPhrase=__CHANGE_ME__
```

`deploy/README.md` 里逐条说明了"为什么这个值不能写进配置文件"，最典型的是 Redis：

> 口令**必须**走独立的 `Redis:Password` 键，不能写进 `Configuration`：
> 连接串用逗号分隔参数，而 dev 环境的口令本身就含逗号（`Qq123456,`），
> 写成 `password=Qq123456,,abortConnect=false` 时会被截成 `Qq123456` → `WRONGPASS`，
> 而报错只说"认证失败"，完全看不出是逗号被当成了分隔符。

**这条值得抄下来**：任何"密码里含分隔符"的连接串都有这个问题。

## 54.4 第三步：多副本会改变什么（单实例永远看不出来）

这是本仓库最值得读的一节之一。上多副本**不是"加副本数"这么简单**：

| 能力 | 单实例 | 多副本 | 本项目的状态 |
|---|---|---|---|
| 限流精度 | 准确 | 约为 N 倍 | ✅ 已换 **Redis Lua** 原子脚本 |
| 导出任务抢占 | 单 worker 独占 | 多 worker 抢同一批 | ⚠ 靠"状态 + 乐观并发"，理论上有重复执行（产出幂等） |
| 领域事件外发 | 无 MQ | 无 MQ | ✅ Outbox 已接入（第 33 章），MQ 未接线 |
| 后台任务 | 每轮一份 | 每副本各一份 | ⚠ 都是"扫表 + 处理"，幂等；要收敛需分布式锁 |
| **DataProtection 密钥** | 进程目录 | **每副本不同** | ❌ **必须挂共享卷**，否则"在 A 登录、请求落到 B 就 401" |
| **导出产物** | 本地目录 | **每副本不同** | ❌ 下载请求必须落到生成它的副本，否则 404 |

最后两条是**上 K8s 最现实的坑**，`deploy/README.md` 第 11.2 节把它们显著标出：

> 当前实现把产物写在容器本地磁盘（相对路径存在任务行里）。
> 多副本下"任务在 A 生成、下载请求打到 B"就是 404。
> 要么给 `App_Data/exports` 挂 **ReadWriteMany**（NFS/CephFS），
> 要么把 `IExportArtifactStore` 换成对象存储实现 —— 接口是为这件事留好的。

**迁移器（DbMigrator）必须单次执行**：多副本同时启动 = 多个进程同时建表/写种子。
用 `Job`（`backoffLimit: 0`）+ `helm.sh/hook: pre-install,pre-upgrade`。

### 探针必须挂在管道最前面

`deploy/README.md` 第 16.11 节记录了一个实测教训：

> 探针挂在 nginx/Ingress 上时，**后端已经挂掉它仍然返回 200** ——
> 因为 nginx 自己活着。于是编排系统认为服务健康，不会重启故障容器。

正确做法是把 liveness/readiness 直接挂到应用容器的 `/health`。

## 54.5 第四步：部署后的验证清单（逐条可执行）

`deploy/README.md` 第 6 节给的是**可执行的验证**，而不是"打开页面看看"：

| 验证 | 命令/判据 |
|---|---|
| 健康检查 | `/health` 返回 200 **且 `database=up`** |
| 登录 | 拿一次令牌（证明 OpenIddict + 数据库 + Redis 都通） |
| **学籍卡 PDF** | 返回体以 `%PDF` 开头 —— **顺带验证中文字体装好了** |
| 分布式缓存 | 日志里**不能**出现「分布式缓存主实现不可用」 |
| 内容根 | 启动日志的内容根必须是容器里的 `/app/api`，且**不该**出现「内容根下没有 appsettings.json」告警 |

第三条特别巧妙：**打印一张学籍卡**这一个动作同时验证了
"应用能跑 + 数据库能读 + 字体文件在" —— 比分别检查三件事省事得多。

## 54.6 第五步：备份与恢复（哪些能清、哪些绝对不能）

| 对象 | 位置 | 建议 |
|---|---|---|
| 数据库 | 卷 `xjgl-pgdata` | `pg_dump` 每日定时 |
| 照片 | NAS 的 `/mnt/nas/xjgl` | 走 NAS 自身快照策略 |
| **降级照片** | 卷 `xjgl-photofallback` | **不要清理**：里面是 NAS 熔断期间暂存、等待补偿的原始照片 |
| 生僻字字体 | `deploy/fonts/rare` | 与镜像一起纳入部署资产 |

第二条的"不要清理"值得强调：那个目录看起来像临时文件，
但它是**唯一的一份副本**（NAS 上还没有）。

备份验证也要做（而不是"备份了就行"）：

```bash
# 恢复到另一个库并核对关键表的行数
createdb xjgl_restore
gunzip -c xjgl-2026-09-18.sql.gz | psql xjgl_restore
psql -d xjgl_restore -c "select count(*) from stu_student;"
psql -d xjgl_restore -c "select count(*) from sys_org;"
```

## 54.7 第六步：开源前的清理清单

本仓库的 `.gitignore` 与 `.github/` 已经处理了大部分，但要**逐条确认**：

### 必须确认"不在仓库里"的东西

| 类别 | 检查方法 |
|---|---|
| 密钥 / 口令 | `git grep -i "password\|passphrase\|secret"` 看是否只有占位符与配置键名 |
| 连接串 | 确认 `appsettings.json` 里的是 `localhost` 开发值（生产走环境变量） |
| 个人数据 | 演示数据里的姓名/身份证号必须是**造出来的**，不是真实学生 |
| 内部信息 | 内部域名、IP、工单系统链接、同事姓名 |
| 工具残留 | `.tools/`（自建 PG / NuGet 缓存 / 探针脚本）不应进仓库 |

### 必须确认"在仓库里"的东西

| 类别 | 说明 |
|---|---|
| `LICENSE` | 本仓库已有 |
| `SECURITY.md` | 漏洞上报方式（政务系统尤其需要） |
| `README.md` | 含**可复现的启动步骤**（照着敲能跑起来） |
| `docs/学籍管理系统-总体方案.md` | 设计文档：这是本仓库最值钱的部分 |
| `docs/learning/` | **49 章 + 1 篇导航 README**（共 50 个 md），**已随仓库发布** —— `.gitignore` 里刻意留了"不再忽略它"的说明，免得下一个人以为是漏写了 |
| `.editorconfig` / `Directory.Build.props` | 统一风格与版本 |

### 一个容易忽略的点：许可证合规

`deploy/README.md` 第 9 节把第三方组件的许可证逐条列出，并注明**商用前请确认**：

| 组件 | 用途 | 要点 |
|---|---|---|
| QuestPDF | 学籍卡 / 花名册 PDF | 社区版对年收入 < 100 万美元的组织免费 |
| ImageSharp | 照片缩略图 | Six Labors Split License：开源与小微组织免费，商用需评估。**必须钉在 3.1.x**（4.x 构建期强制要许可 key） |
| ABP Framework | 应用框架 | LGPL-3.0（或商业版） |
| 字体（Noto CJK / Plangothic） | 中文与生僻字渲染 | Noto 是 SIL OFL；扩展区字体请自行确认 |

**替换渲染/图像库只需改 `Xjgl.Reporting` 与 `Xjgl.Imaging`** ——
业务层依赖的是 `IStudentCardPdfRenderer` / `IImageProcessor` 接口
（这是分层带来的实际收益，不只是"好看"）。

> ### 本节踩过的坑：把 `error` 当成 `warning` 写进了 README
>
> 项目一度把 `ImageSharp` 引在 **4.1.2**。该版本起包内带了
> `build/SixLabors.ImageSharp.targets` + `SixLabors.Licensing.dll`，
> 没有商业许可 key 时 `dotnet build` 输出的是：
>
> ```
> error : No Six Labors license found. Set $(SixLaborsLicenseKey) ...
> ```
>
> 但 README 当时把它写成了"**两条 warning，正常，不是问题**"，
> 于是**任何人都克隆不下来构建**，而文档还在安慰他"这是正常的"。
>
> 两处教训，都很具体：
>
> 1. **读构建输出要连前缀一起读**。`error` 与 `warning` 只差一个词，
>    但一个是"构建失败"、一个是"构建成功但有提示"。凭印象转述给文档，
>    就把一个致命缺陷写成了使用说明。
> 2. **"许可证合规"与"能不能构建"是两件事**。3.1.12 与 4.1.2 的许可证条款
>    **完全相同**（都是 Six Labors Split License），差别只在于
>    4.x 把这套条款做成了**技术强制**。所以"我们是开源项目、条款允许我们用"
>    并不能推出"这条依赖能构建过"。
>
> 修法是钉回 **3.1.12**（Apache 时代之后的最后一个不需要 key 的版本线），
> 并顺手核对漏洞：GitHub Advisory 里 3.x 影响面最高的一条是
> `>= 3.0.0, < 3.1.11`，3.1.12 已在全部 7 条已知公告的修复版本之上 ——
> **降级不必然是安全降级**，但这件事必须去查，不能假设。

## 54.8 怎么验证部署

```bash
# 1) 本地静态核对（本机即可跑）
node tools/verify-deploy.mjs

# 2) compose 语法与插值（需要 docker）
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env.example config -q

# 3) 起依赖 + 迁移 + 起应用（见 deploy/README.md 第 4~5 节）
# 4) 按第 6 节的验证清单逐条走
```

## 54.9 本章要点

1. **以 appsettings 为事实来源**反推 compose 变量，并用脚本核对 —— 别靠人工对照。
2. 生产配置**只走环境变量**；`.env.example` 里只有占位符。
3. 连接串里的口令若含分隔符（逗号），**必须走独立配置键**，否则被静默截断。
4. 多副本会改变行为：**DataProtection 密钥与导出产物必须共享**，
   否则出现"在 A 登录、在 B 就 401"与"导出下载 404"。
5. 迁移器必须**单次执行**（Job + hook）。
6. 探针挂在**应用容器**上，不能挂在 nginx/Ingress 上。
7. 部署后用"打印一张学籍卡"这类**复合动作**验证（一次覆盖三件事）。
8. 降级照片目录**不要清理** —— 那是 NAS 上还没有的唯一副本。
9. 开源前逐类清理：密钥、连接串、个人数据、内部信息、学习文档、工具残留。
10. 第三方许可证逐条列出并注明"商用前确认"；替换只需改两个项目（分层收益）。
11. **第三方库的许可证条款 ≠ 能不能构建**：ImageSharp 4.x 起在构建期强制要 key，
    没有 key 是 `error` 不是 `warning`。选版本时**两个都查**：许可条款 + 已知漏洞公告。

## 全篇结语

这套文档从"建库建表"一路写到"部署与开源"，而贯穿全篇的其实是**同一种态度**：

> **不接受"看起来在工作"。**

- 判据要看**字节**（`octet_length`）而不是"显示正常"；
- 验证要看**回滚后查不到**，而不是"没抛异常"；
- 端到端要**断言 404 文案不存在**，因为 catch-all 也返回 200；
- 配置对了不算数，要**变异验证**（注释掉配置，用例必须变红）；
- 能力放在够不着的地方等于没有（第 33 章）；
- 少人必须**说出来**，不能只弹一个绿色提示（第 41 章）。

如果你按这套文档自己搭了一遍，希望带走的不是"这段代码怎么写的"，
而是**"我怎么知道它真的在工作"**。
