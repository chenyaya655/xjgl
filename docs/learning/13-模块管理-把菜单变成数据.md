# 13 模块管理：把菜单变成数据

> **对应阶段**：P1 ｜ **预计耗时**：2 小时 ｜ **产出**：管理员能在界面上新增模块，菜单与权限自动跟着变

---

## 13.1 要解决的问题

第 11、12 章把权限做成了三级元数据表，但还有一个问题没回答：

> **谁来往这三张表里写数据？**

如果答案是"开发者改种子代码然后发版"，那"权限是数据"这件事就只做了一半 ——
省厅临时要加一个"随迁子女统计"模块，还是得走一次发版流程。

**所以"模块管理"必须是一个功能页面**：管理员自己建子系统、模块、操作，
配好前端路由路径与组件名，保存后：

- 左侧菜单**立刻**出现新模块（下次拉 `/api/app/my-profile` 时带上）；
- "权限管理"页面**立刻**能勾选新权限；
- 前端会自动注册对应的动态路由（第 46 章）。

唯一需要重启的是 `[Authorize]` 对新权限码的识别（第 12 章坑 2 讲过的限制）。

## 13.2 数据模型回顾

```
sys_subsystem（子系统）   Sys / Stu / Chg / Pho
   └── sys_module（模块）  Sys.Module / Stu.Student / Pho.Photo
          └── sys_module_action（操作）  Query / Create / Update / Delete / Import / Export…
```

关键字段（完整定义见 `src/Xjgl.Domain/Metadata/`）：

| 实体 | 字段 | 作用 |
|---|---|---|
| `SysSubsystem` | `Code`、`Name`、`Icon`、`Sort`、`IsEnabled` | 权限码第一段；菜单分组 |
| `SysModule` | `PermissionName`（冗余 `{子系统}.{模块}`） | 权限码第二段 |
| | `Path`、`Component` | **前端路由路径与组件路径** —— 这是"菜单变成数据"的关键 |
| | `IsEnabled` / `IsHidden` / `IsExternal` | 停用 / 隐藏菜单但可按路径访问 / 外链 |
| | `OrgTypes` | 允许访问的组织层级（如 `Province,City`） |
| `SysModuleAction` | `PermissionName`（冗余 `{子系统}.{模块}.{操作}`） | 权限码第三段 |
| | `ActionType`、`IsDefaultGranted` | 按钮类型；新建角色时默认勾选 |

**注意权限码是冗余存下来的**，不是每次拼。原因：权限校验是高频操作，
读元数据快照时要立刻拿到权限名，冗余一个字符串换来"不用 join 三张表"。

## 13.3 后端：`ModuleAppService`

```csharp
[Authorize]
public class ModuleAppService : XjglAppService, IModuleAppService
{
    // 完整元数据树：子系统 → 模块 → 操作
    public async Task<List<SubsystemDto>> GetTreeAsync(bool onlyEnabled = false) { ... }

    [Authorize(MetadataPermissions.Sys.Module.Create)]
    public async Task<SubsystemDto> CreateSubsystemAsync(CreateUpdateSubsystemDto input) { ... }

    // ... CreateModule / CreateAction / Update* / Delete*
}
```

**每个写方法的最后一行都是同一句**：

```csharp
_metadataCache.Invalidate();     // 否则菜单与权限要等重启才生效
```

本项目的 `ModuleAppService` 里这句话出现了 10 次（每个写方法一次）。
**容易漏** —— 新增写方法时一定要带上，排查方法见 13.5。

### 三处业务规则

| 规则 | 为什么 |
|---|---|
| 删除子系统/模块前检查下级 | 有下级就拒绝（`Xjgl:00101`），避免产生孤儿节点（实测返回 403 + 明确原因） |
| 编码唯一 | 权限码里含编码，重码会让两个模块共用一个权限 |
| 权限码由系统拼装 | 不允许人工填写 —— 拼错的权限码会让 `[Authorize]` 永远不通过 |

## 13.4 前端：树 + 详情面板

`web/apps/pc/src/views/system/module/index.vue`，结构是"左树右详情"：

```
┌──────────────────────┬────────────────────────────────────┐
│ 元数据树（可搜索）      │ 详情：按选中节点类型切换表单           │
│  ├ 系统管理 [子系统]   │  · 子系统：编码/名称/图标/排序/启用     │
│  │   ├ 模块管理 [模块] │  · 模块：+ 路由路径/组件/组织层级/隐藏   │
│  │   │   ├ 查看 [操作] │  · 操作：+ 操作类型/默认授予            │
│  │   │   └ 添加 [操作] │                                    │
│  │   └ 权限管理 [模块] │ 权限码: Stu.Student.Create  ← 自动显示 │
│  ├ 学生管理 [子系统]   │                                    │
└──────────────────────┴────────────────────────────────────┘
```

三个刻意的设计：

1. **选中节点时把拼好的权限码显示出来**
   （`该节点对应的权限码：Stu.Student.Create（由「子系统.模块.操作」自动拼装）`）——
   避免有人以为要自己输入权限码。
2. **操作节点的编码不允许修改**，并写明原因：权限码里含它，改了历史授权立刻失效。
3. **模块表单上挂一条常驻警告**：新增/改动模块后要重启后端，
   `[Authorize]` 才会认识新的权限码。**把限制写在界面上比写在文档里有用得多。**

## 13.5 验证方法

**① 权限码拼装正确**

从接口建一条链路，逐级核对：

```powershell
# 建子系统 TX7505
POST /api/app/module/subsystem  { "code":"TX7505", "name":"验证子系统", ... }
# → 200

# 在它下面建模块 Demo
POST /api/app/module/module     { "subsystemId":"<上一步的 id>", "code":"Demo", ... }
# → permissionName 必须是 "TX7505.Demo"

# 再建操作 Query
POST /api/app/module/action     { "moduleId":"<模块 id>", "code":"Query", "actionType":"Query", ... }
# → permissionName 必须是 "TX7505.Demo.Query"
```

我在真实环境跑过这一串，得到 `TX7505` → `TX7505.Demo` → `TX7505.Demo.Query`，符合预期。

**② 删除守卫真的生效**

```powershell
DELETE /api/app/module/<子系统 id>/subsystem
# 期望：403，message = "该组织下还有下级组织，请先删除下级"（有下级时）
```

**③ 缓存失效真的生效（最重要的一条）**

```powershell
# 1) 建一个模块，path = /test/demo
# 2) 立刻重新拉当前用户上下文
GET /api/app/my-profile
# 3) 期望：menus 里**立刻**出现 /test/demo
```

如果第 3 步看不到，说明某个写方法漏了 `_metadataCache.Invalidate()`。
排查方法：在 `ModuleAppService` 里搜 `Invalidate` 的次数应当等于写方法数量。

**④ 手工刷新缓存入口可用**

```powershell
POST /api/app/module/refresh-cache     # → 204
```

## 13.6 踩坑记录

### 坑 1：新模块的权限码要重启才被 `[Authorize]` 认识

第 12 章讲过原理：权限定义在**启动时**由 `DynamicPermissionDefinitionProvider` 构建，
新增的权限码在重启前不在定义里，`[Authorize("新模块.操作")]` 会拒绝所有人（403）。

**界面上已经给出提示，但这是真实限制。** 改进方向是用 ABP 的
`IDynamicPermissionDefinitionStore`（数据落在 `AbpPermissions` 表，EF 迁移里已建好）。

### 坑 2：改了模块编码，历史授权全部失效

权限名里含编码。管理员把 `Stu` 改成 `Student` 后，
`AbpPermissionGrants` 里存的还是旧权限名 —— **所有相关授权瞬间失效**，
而系统不会报任何错，只是原本能用的按钮都点了 403。

**当前处理**：界面上给出警告、操作编码不允许改。
更彻底的做法是把编码设为创建后只读（模块编码目前仍可改，属待改进点）。

### 坑 3：`IsHidden` 与 `IsEnabled` 混淆

- `IsEnabled = false`：模块停用，菜单不显示，**权限也不再生效**；
- `IsHidden = true`：菜单不显示，但**按路径仍可访问、权限仍然有效**。

典型场景是学生详情页 `/student/detail`：不该出现在左侧菜单，但从列表点进去必须能开。

### 坑 4：`Component` 写错的表现是"白屏"还是"占位页"？

本项目约定 `component` 是 `student/list/index` 这种**不带 `.vue` 的路径**，
前端用 `import.meta.glob('../views/**/*.vue')` 解析成
`src/views/student/list/index.vue`。

解析不到时**不报错**，回落到占位页（`Placeholder.vue`）并显示
"该模块尚未实现"以及当前路径 —— 因为模块是运行期数据，
管理员完全可能先建模块、再等开发补页面。**让用户看到一句解释，远好过一个白屏。**
