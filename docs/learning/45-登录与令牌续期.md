# 45 登录与令牌自动续期：并发 401 只刷一次

> 对应代码：`web/packages/api/src/http.ts`、`web/apps/pc/src/stores/auth.ts`、
> `web/apps/pc/src/views/login/index.vue`、`web/apps/pc/src/router/index.ts`
> 对应测试：`web/e2e/specs/01-login.spec.ts`

## 45.1 要解决的问题

前端登录不算难，难的是"**用户正在用，令牌悄悄过期了**"这一刻。
要处理四件事，每一件做错的表现都不一样：

| 要处理的事 | 做错的表现 |
|---|---|
| 每个请求带上 Bearer 令牌 | 一直 401 |
| 401 时用 refresh_token 换新令牌并**重放原请求** | 用户被无故踢回登录页 |
| **并发 401 只刷新一次** | "随机掉线"（见 45.3，这是最隐蔽的一个） |
| 把 ABP 的错误信封翻成人话 | 界面上显示 `Request failed with status code 403` |

## 45.2 第一步：令牌存哪、怎么带

```typescript
const ACCESS_TOKEN_KEY = 'xjgl.access_token'
const REFRESH_TOKEN_KEY = 'xjgl.refresh_token'

export const tokenStorage = {
  get accessToken() { return localStorage.getItem(ACCESS_TOKEN_KEY) },
  get refreshToken() { return localStorage.getItem(REFRESH_TOKEN_KEY) },
  save(token: TokenResponse) {
    localStorage.setItem(ACCESS_TOKEN_KEY, token.access_token)
    if (token.refresh_token) localStorage.setItem(REFRESH_TOKEN_KEY, token.refresh_token)
  },
  clear() {
    localStorage.removeItem(ACCESS_TOKEN_KEY)
    localStorage.removeItem(REFRESH_TOKEN_KEY)
  }
}
```

用 `localStorage` 而不是 `sessionStorage`：政务系统里"关了浏览器再打开还得重新登录"
会被当成故障报上来。代价是要接受 XSS 风险 —— 本系统是内网自有系统，
且服务端对输入做了校验（第 24 章），这个取舍是明确的。

请求拦截器统一注入：

```typescript
http.interceptors.request.use((config) => {
  const token = tokenStorage.accessToken
  if (token) config.headers.Authorization = `Bearer ${token}`
  return config
})
```

**为什么登录本身用裸 axios 而不是 `http` 实例**：`http` 的拦截器会在 401 时
触发"刷新令牌 + 重放"。而登录失败（密码错）也是 401/400 ——
走那套逻辑会把"密码错了"误当成"令牌过期"，报出莫名其妙的错。
同理，激活接口（`/activate`）也走裸 axios（它本来就是匿名接口）。

## 45.3 第二步：并发 401 **只刷新一次**（本节是最重要的一节）

先看错误的写法：

```typescript
// ❌ 每个 401 都去刷新
if (status === 401) {
  const newToken = await refreshAccessToken()   // ← 5 个并发请求会调 5 次
  if (newToken) return http.request(config)
}
```

为什么这会"随机掉线"：

1. 用户打开一个有 5 个并发请求的页面，此时令牌刚好过期；
2. 5 个请求都拿到 401，**同时**发起 5 次刷新；
3. 而 refresh_token 是**一次性**的（OAuth 里叫"令牌旋转"）：
   第 1 次刷新成功并作废了旧 refresh_token；
4. 第 2~5 次刷新带着**已作废**的 refresh_token → 全部失败 → `tokenStorage.clear()`
   → 用户被踢回登录页。

**表现**：偶发、难以复现（只有"令牌恰好过期 + 多个并发请求"时才触发），
而且用户报告的是"有时候会莫名其妙退出登录"。

正确写法 —— 用**共享 Promise 去重**：

```typescript
/** 进行中的刷新，用于把并发 401 合并成一次刷新。 */
let refreshing: Promise<string | null> | null = null

// 401 分支里：
config._retried = true

// ??= 只在为 null 时赋值：第一个 401 发起刷新，其余的**复用同一个 Promise**
refreshing ??= refreshAccessToken().finally(() => { refreshing = null })

const newToken = await refreshing

if (newToken) {
  config.headers = new AxiosHeaders({ ...config.headers, Authorization: `Bearer ${newToken}` })
  return http.request(config)        // 重放原请求
}

onUnauthorized?.()                   // 刷新也失败 → 交给路由层踢回登录页
return Promise.reject(error)
```

两个配套细节：

- **`_retried` 标记**：重放后的请求如果再 401，不能再刷新（否则无限循环）。
  它是通过 axios 的**声明合并**加进类型的，而不是到处 `as never`：

```typescript
declare module 'axios' {
  export interface AxiosRequestConfig {
    silent?: boolean      // 静默请求：失败不弹提示（后台轮询用）
    _retried?: boolean
  }
}
```

- **排除令牌端点自身**：`!config.url?.includes(TOKEN_ENDPOINT)` ——
  刷新请求自己失败时不该再触发刷新。

## 45.4 第三步：错误信封翻译（别给用户看 HTTP 状态码）

ABP 的错误信封长这样：

```json
{ "error": {
    "code": "Xjgl:00101",
    "message": "服务器内部错误",
    "details": "...",
    "data": { "reason": "该组织下还有下级组织，请先删除下级" },
    "validationErrors": [{ "message": "姓名不能为空", "members": ["Name"] }]
} }
```

取值优先级**不是随便定的**，每一层都有理由：

```typescript
// 1) 校验错误 —— 用户自己能改
if (envelope?.validationErrors?.length) return envelope.validationErrors.map(v => v.message).join('；')

// 2) details —— 业务原因的详细说明
if (envelope?.details) return envelope.details

// 3) ★ data.reason —— 我们自己的业务异常用 .WithData("reason", ...) 带出的动态说明
const payload = envelope?.data
if (payload) {
  for (const key of ['reason', 'message']) {
    const value = payload[key]
    if (typeof value === 'string' && value.trim()) return value
  }
}

// 4) message —— 最后才用兜底文案
if (envelope?.message) return envelope.message
```

第 3 层**不能省**：ABP 在错误码没有本地化文案时会把 `message` 退化成
"服务器内部错误"，而真正的原因只在 `data.reason` 里。
只读 `message` 就会**给用户看一句谎话**（本项目实测踩过）。

再往下才是网络层的兜底：

```typescript
if (error.code === 'ECONNABORTED') return '请求超时，请检查网络后重试。'
if (!error.response) return '无法连接服务器，请确认后端服务已启动。'

switch (error.response.status) {
  case 403: return '您没有执行该操作的权限，请联系管理员。'
  case 429: return '操作过于频繁，请稍后再试。'
  // ...
}
```

**提示只在拦截器里弹一次**（`if (!config.silent) ElMessage.error(...)`），
页面不需要各自写一遍 —— 否则同一个错误会弹两次。
需要静默的场景（照片存储健康度轮询）显式传 `silent: true`。

## 45.5 第四步：路由守卫与"刷新页面不丢会话"

这是端到端测试抓出来的三个缺陷之一（第 52 章的记录），值得完整讲。

**问题一：不能用 `to.meta.anonymous` 判断"是不是公开页"。**
业务路由是登录后**动态注册**的，所以在"还没恢复会话"的那一刻，
`/student/list` 匹配到的是 **catch-all（404 页）**，而它也带 `anonymous: true` ——
于是守卫直接放行，用户看到"页面不存在或您没有访问权限"。

```typescript
// ✅ 用显式白名单
const PUBLIC_PATHS = ['/login', '/activate']

router.beforeEach(async (to) => {
  const auth = useAuthStore()

  // 先尝试恢复会话：动态路由注册之后，业务路径才解析得到
  if (!auth.isAuthenticated && hasToken()) {
    if (await restoreSession(auth)) {
      // 路由表变了，重新解析当前目标
      return { path: to.fullPath, replace: true }
    }
  }

  if (PUBLIC_PATHS.includes(to.path)) return true
  if (!auth.isAuthenticated) return { path: '/login', query: { redirect: to.fullPath } }
  return true
})
```

**问题二：恢复会话后必须用 `fullPath` 字符串重定向，不能写 `{ ...to, replace: true }`。**
`to` 是已解析的路由对象，里面带着 `name: 'not-found'`（此刻它匹配的是 catch-all），
而 **vue-router 里 name 优先于 path** —— 于是会被导航回 404 页。
表现就是"刷新业务页面永远停在页面不存在"。

**问题三：令牌失效回调要在路由层注册（`setUnauthorizedHandler`），
但 `http.ts` 不能 import router（循环依赖）。** 用回调注入解决。

## 45.7 本章要点

1. 登录/激活走**裸 axios**（否则"密码错"会被当成"令牌过期"）。
2. 并发 401 必须用**共享 Promise 去重**，否则 refresh_token 旋转会让用户"随机掉线"。
3. 用 `_retried` 标记防无限重放；排除令牌端点自身。
4. 错误提示的优先级：`validationErrors` > `details` > **`data.reason`** > `message`。
   `reason` 那层不能省，否则会给用户看"服务器内部错误"这句谎话。
5. 公开页用**显式白名单**，不能用 `meta.anonymous`（catch-all 也带这个标记）。
6. 恢复会话后重定向要用 `fullPath` **字符串**（name 优先于 path 的坑）。
