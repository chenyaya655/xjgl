# 24 生僻字全链路（一）：数据库与后端

> 对应代码：`src/Xjgl.Domain.Shared/Text/RareCharacterText.cs`、
> `src/Xjgl.Application/Students/StudentAppService.cs`（姓名校验与长度）、
> `src/Xjgl.Application/Students/StudentProfileAppService.cs`
> 对应测试：`test/Xjgl.Domain.Tests/Text/RareCharacterTextTests.cs`

## 24.1 要解决的问题

学籍系统里必然遇到生僻字姓名：`𠮷`（U+20BB7）、`𰻞`（biáng）、`䶮`（U+4DAE）。

它有三个**互相独立**的陷阱，任何一个没处理都会出问题，而且症状完全不同：

| 陷阱 | 症状 | 出现在哪一层 |
|---|---|---|
| 数据库字符集不是 UTF-8 / 长度按字节算 | 存进去变 `?`，或"长度超限" | 数据库 |
| C# 里 `string.Length` 按 **UTF-16 码元**计数 | `𠮷` 被算成 **2** 个字，姓名长度校验误判 | 应用层 |
| 字体缺少该码点的字形 | 打印出来是 **方块** | 渲染层（第 25 章） |

本章解决前两个。关键认识：**"字符长度"这件事在 UTF-16 世界里是有歧义的** ——
`string.Length`、`Substring`、`foreach` 全都按码元走，而不是按"人看到的字"走。

## 24.2 第一步：先把数据库这一层钉死（可验证）

PostgreSQL 的 `UTF8` 编码本身对码点无限制（不像 MySQL 的 `utf8` 只到 3 字节），
**但前提是建库时就是 UTF8**。这一步必须实测，不能假设：

```bash
# 建库时显式指定（本仓库 deploy/initdb 与 .tools 脚本都这么做）
createdb -E UTF8 --locale=C.UTF-8 -T template0 xjgl

# 验证：三件事都要对
psql -c "SHOW server_encoding;"          # 必须是 UTF8
psql -c "SHOW client_encoding;"          # 连接上应为 UTF8
psql -c "SELECT pg_column_size('𠮷'::text);"   # 应当是 4（UTF-8 字节数）
```

`pg_column_size` 那条是本仓库用来"证明代理对完整落库"的手段：

```sql
-- 实测记录：'周𠮷' 在库里是 3 + 4 = 7 字节。若只有 3+3 或出现 EF BF BD（U+FFFD），
-- 就说明链路上有一环把代理对拆坏或替换了。
SELECT octet_length('周𠮷'), encode(convert_to('周𠮷','UTF8'),'hex');
-- → 7 | e591a8f0a0aeb7
```

> ⚠ **不要试图用"数据库侧 hex 绕行"来解决编码问题。**
> 有一种从 Oracle 移植过来的做法是：把字符串逐 `char` 转 `\uXXXX`、拼成 hex、
> 再让数据库 `utl_raw.cast_to_nvarchar2(hex)` 还原。**在 PG 上照搬会恰好在那类要解决的字上翻车**：
> Oracle 的 `NVARCHAR2` 是 UTF-16，逐 `char` 取到的**代理码元**拼 hex 正好对上；
> 而 PG 的 `convert_from(decode(hex,'hex'),'UTF8')` 要的是 **UTF-8 字节** ——
> `𠮷` 在 C# 里是 2 个 `char`（`D842`/`DFB7`），当 UTF-8 字节解会错位。
> 本项目链路是 Npgsql + UTF-8，已经有字节级证据，**不需要绕，绕了只会掩盖真实缺陷**。

## 24.3 第二步：按**码点**做校验与长度（`RareCharacterText`）

这是最容易写错的一层。看两个"看起来对"的写法及其后果：

```csharp
// ❌ 长度按 UTF-16 码元：𠮷 被算成 2，三个生僻字姓名会被误判超长
if (name.Length > 30) throw ...;

// ❌ 截断用 Substring：可能把代理对**从中间切开**，产生一个孤立代理
//    写进数据库就是 U+FFFD（替换字符）或直接报错
var short = name.Substring(0, 20);
```

正确做法是**按码点枚举**：

```csharp
// src/Xjgl.Domain.Shared/Text/RareCharacterText.cs
public static int CodePointLength(string? text)
{
    if (string.IsNullOrEmpty(text)) return 0;

    var count = 0;

    // 用 EnumerateRunes()：它按**码点**迭代，代理对算一个
    foreach (var _ in text.EnumerateRunes()) count++;

    return count;
}
```

C# 提供了 `Rune`/`EnumerateRunes()`（.NET Core 3.0+），比手写代理对判断可靠得多。
手写版本长这样，容易漏掉"低位代理单独出现"的情况：

```csharp
// 仅供理解，实际用 EnumerateRunes()
for (var i = 0; i < text.Length; i++)
{
    var c = text[i];
    if (char.IsHighSurrogate(c) && i + 1 < text.Length && char.IsLowSurrogate(text[i + 1]))
    {
        i++;  // 跳过低位代理
    }
    count++;
}
```

### 姓名校验：既要拒绝非法字符，又不能误伤生僻字

`IsValidPersonName` 的难点在于**白名单怎么定**。写 `char.IsLetter(c)` 会放行所有语言的字母；
写"只允许常见汉字"会误伤生僻字。本项目用的判据是：

- 允许：**CJK 统一表意文字**（含扩展 B/C/D/E/F/G 区，即 U+3400–U+4DBF、U+4E00–U+9FFF、
  U+20000–U+2FA1F）、常见少数民族姓名分隔符 `·`、空格；
- 拒绝：数字、拉丁字母、标点、emoji。

```csharp
// 关键：按 **Rune** 判断，而不是按 char
foreach (var rune in name.EnumerateRunes())
{
    if (!IsAllowedNameRune(rune)) { error = $"姓名包含非法字符「{rune}」"; return false; }
}
```

> **实测踩过的坑**：端到端测试里我造了个"带时间戳保唯一"的姓名
> `E2E学生123456`，被后端直接拒收：`姓名包含非法字符"1"`。
> 提示很清楚，但当时的第一反应是"是不是校验太严了"。
> 其实这正是白名单在起作用 —— **造测试数据也要守业务规则**。
> 后来改成"中文数字后缀"（见 `web/e2e/specs/support/auth.ts` 的 `chineseNumeral`）。

## 24.4 第三步：截断与补位都必须按码点

打印与导出的列宽是固定字符数，超长要截断。**截断绝不能切开代理对**：

```csharp
public static string TruncateByCodePoints(string? text, int maxCodePoints, string ellipsis = "…")
{
    if (string.IsNullOrEmpty(text) || maxCodePoints <= 0) return string.Empty;

    var runes = text.EnumerateRunes().ToArray();

    if (runes.Length <= maxCodePoints) return text;

    // 留出省略号的位置，并且**按码点取前 N 个**（不是按 char 取前 2N 个）
    var take = Math.Max(0, maxCodePoints - CodePointLength(ellipsis));

    return string.Concat(runes.Take(take).Select(r => r.ToString())) + ellipsis;
}
```

同理，`PadRight` 这类补位在打印对齐时也要按码点算宽度 —— 否则含生僻字的那一列会**整体错位一格**，
而错位在只有一两个生僻字的名单里几乎看不出来。

## 24.5 怎么验证真的做对了

单测（`RareCharacterTextTests`）覆盖的是逻辑，但**逻辑对不代表链路对**。本项目的验证顺序是：

```powershell
# 1) 单测：按码点的长度/截断/校验
dotnet test test\Xjgl.Domain.Tests --filter "FullyQualifiedName~RareCharacter"

# 2) 字节级证据：真写一个生僻字进去，直接查库看字节
$env:PGPASSWORD='Xjgl@Dev2026'
@"
select name, octet_length(name) as bytes, length(name) as pg_chars
from stu_student where name like '%𠮷%';
"@ | Set-Content -Encoding UTF8 .tools/probe-rare.sql
.tools\pgsql-extract\pgsql\bin\psql.exe -h 127.0.0.1 -p 5432 -U xjgl -d xjgl `
  -v client_encoding=UTF8 -At -f .tools/probe-rare.sql
# 期望：octet_length 比 length 多 1（因为 UTF-8 下该字占 4 字节、PG 里算 1 个字符）

# 3) 接口层：建一个含生僻字的学生，再读回来逐字节比对
```

> **为什么必须有第 2、3 步**：编码问题最典型的表现是"某一层静默替换成 `?` 或 U+FFFD"，
> 而**单测里不经过数据库与驱动，永远不会暴露**。判断依据必须是 `octet_length` 这类字节级事实。

## 24.6 本章要点

1. **数据库字符集**必须是 UTF8，且要用 `octet_length` 实测，不能靠"应该没问题"。
2. C# 的 `string.Length`/`Substring`/`foreach` 都按 **UTF-16 码元**走 —— 处理姓名必须用
   `EnumerateRunes()`（`Rune`）。
3. 姓名校验用**码点白名单**；它拒掉数字/字母是**正确行为**，造测试数据时要守这条规则。
4. 别用"数据库侧 hex 绕行"来掩盖编码问题：Oracle 那套依赖 UTF-16 代理码元，
   在 PG 的 UTF-8 字节语义下会**在那类字上恰好翻车**。
5. 验证要看**字节**（`octet_length` / hex），不要只看"读回来显示正常"。
