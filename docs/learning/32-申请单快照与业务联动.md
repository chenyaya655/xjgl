# 32 申请单、前后快照与业务联动

> 对应代码：`src/Xjgl.Domain/Changes/ChangeApply.cs`、
> `src/Xjgl.Application/Changes/ChangeFlowAppService.cs`
> 对应测试：`test/Xjgl.Application.Tests/Changes/ChangeFlowAppServiceTests.cs`

## 32.1 要解决的问题

申请单是异动的核心数据。它要回答四类问题，而**其中两类与"当前状态"无关**：

| 问题 | 数据来源 |
|---|---|
| 谁在申请什么？ | 学生 Id、异动类型、目标学校/年级/班级、原因 |
| 现在走到哪一步了？ | `Status`、`CurrentSeq`、流程任务表 |
| **申请时是什么样的？** | **`Source*` 快照字段** |
| **批准后要变成什么样？** | **`Target*` 快照字段** |

后两类**必须存快照**，不能实时读学生主档。原因有两个，都是真实会出问题的：

1. **审批期间学生档案可能被别人改了**：比如转学审核到一半，
   学校把学生的班级从一班调到二班。若"变动前"是实时读的，
   撤回审核时会把学生恢复成"二班"这个**它从未属于过的状态**；
2. **审批通过后主档就变了**，"变动前"再也读不出来。撤回审核必须靠快照回滚。

## 32.2 第一步：快照字段的设计

```csharp
public class StuChangeApply : FullAuditedAggregateRoot<Guid>, IXjglBusinessEntity
{
    public string ApplyNo { get; set; } = default!;       // 业务单号 YC2026...
    public Guid StudentId { get; set; }
    public string StudentName { get; set; } = default!;   // ← 也是快照
    public string StudentNo { get; set; } = default!;     // ← 也是快照
    public Guid ChangeTypeId { get; set; }
    public string ChangeTypeName { get; set; } = default!;// ← 也是快照

    // ── 变动前快照（提交时冻结）──
    public string? SourceStatusCode { get; set; }
    public Guid? SourceSchoolOrgId { get; set; }
    public Guid? SourceGradeId { get; set; }
    public Guid? SourceClassId { get; set; }

    // ── 变动后快照（由异动类型决定，提交时冻结）──
    public string? TargetStatusCode { get; set; }
    public Guid? TargetSchoolOrgId { get; set; }
    public Guid? TargetGradeId { get; set; }
    public Guid? TargetClassId { get; set; }

    public DateTime ApplyDate { get; set; }
    public string ApplyAcademicYear { get; set; } = default!;  // 快照：用于申请次数统计
    public string Status { get; set; } = ChangeApplyStatus.Draft;
    public int? CurrentSeq { get; set; }
    public DateTime? FinalApprovedTime { get; set; }
    public string? Reason { get; set; }
}
```

**为什么 `StudentName` / `StudentNo` / `ChangeTypeName` 也要冗余存**：
申请单是**留痕单据**，要能在多年后独立读懂。学生改名、类型改名、
甚至学生被删（第 26 章：主档会软删），都不该让历史单据上的名字跟着变或变空。

`ApplyAcademicYear` 同理：它是"这次申请发生在哪个学年"的**事实**，
用于按学年统计申请次数（第 30 章）。学生转学后主档学年会变，
用实时值去数历史申请必然算错。

## 32.3 第二步：提交时冻结快照

```csharp
public async Task<ChangeApplyDto> SubmitAsync(SubmitChangeApplyDto input)
{
    var student = await _studentsForUpdate.GetAsync(input.StudentId);
    await _guard.EnsureInScopeAsync(student);        // 数据范围
    var type = await _types.GetAsync(input.ChangeTypeId);
    var template = await GetPublishedTemplateAsync(type.Id);   // 必须有已发布流程

    // 各类校验（时间窗 / 年级白名单 / 申请次数 / 是否允许跨校 …）

    var apply = new StuChangeApply(_guidGenerator.Create(), GenerateApplyNo(), student.Id)
    {
        // 姓名与辅号也一起冻结
        StudentName = student.Name,
        StudentNo = student.StudentNo,
        ChangeTypeName = type.Name,

        SourceStatusCode = student.StudentStatusCode,
        SourceSchoolOrgId = student.SchoolOrgId,
        SourceGradeId = student.GradeId,
        SourceClassId = student.ClassId,

        TargetStatusCode = type.AfterStatusCode,
        TargetSchoolOrgId = type.AllowCrossSchool ? input.TargetSchoolOrgId : student.SchoolOrgId,
        TargetGradeId = type.AffectGrade ? student.GradeId : null,
        TargetClassId = type.AffectClass ? input.TargetClassId : null,

        ApplyDate = _clock.Now,
        ApplyAcademicYear = CurrentAcademicYear(),
        Status = ChangeApplyStatus.Submitted
    };

    await _applies.InsertAsync(apply, autoSave: true);

    // 用第 31 章的纯函数把待办算出来并落库
    await InstantiateFlowAsync(apply, template);

    return await GetAsync(apply.Id);
}
```

注意 `TargetSchoolOrgId` 的三元写法：**不允许跨校的类型（如休学），
目标学校直接取"原学校"**，而不是留空。留空会让"审批通过后要不要改学校"
变成一个有歧义的判断（"空"到底是"不改"还是"改成空"？）。

## 32.4 第三步：业务联动（审批通过后改学生档案）

```csharp
private async Task ApplyStudentChangesAsync(StuChangeApply apply)
{
    var student = await _studentsForUpdate.GetAsync(apply.StudentId);

    // 先取快照：审批改的是学籍主档，同样要进变更流水
    var before = _changeLogger.Snapshot(student);

    if (!apply.TargetStatusCode.IsNullOrWhiteSpace())
        student.StudentStatusCode = apply.TargetStatusCode!;

    if (apply.TargetSchoolOrgId.HasValue && apply.TargetSchoolOrgId.Value != student.SchoolOrgId)
    {
        var school = await _orgs.FindAsync(apply.TargetSchoolOrgId.Value);
        if (school != null)
        {
            student.SchoolOrgId = school.Id;
            student.SchoolPathCode = school.PathCode;   // ← 物化路径必须一起改（第 14 章）
        }
    }

    if (apply.TargetGradeId.HasValue) student.GradeId = apply.TargetGradeId;
    if (apply.TargetClassId.HasValue) student.ClassId = apply.TargetClassId;

    await _studentsForUpdate.UpdateAsync(student, autoSave: true);

    // 留痕：来源写「学籍异动」并把申请单号带进原因，便于从档案反查是哪一单引起的
    await _changeLogger.LogUpdatedAsync(
        student, before,
        source: "学籍异动",
        reason: $"异动申请 {apply.ApplyNo} 审核通过");
}
```

**`SchoolPathCode` 是最容易漏的一个字段**：它是数据范围的判据（第 18 章）。
只改 `SchoolOrgId` 不改路径，学生就会"归属新学校但按旧学校的路径被过滤" ——
表现是转学后学生从新学校的名单里消失，而老学校的名单里还在。
有专门的用例守这一点。

## 32.5 第四步：撤回审核（回滚业务联动）

撤回是**反向的同一套逻辑**，而且正是快照真正被用上的地方：

```csharp
private async Task RevertStudentChangesAsync(StuChangeApply apply)
{
    var student = await _studentsForUpdate.GetAsync(apply.StudentId);
    var before = _changeLogger.Snapshot(student);

    student.StudentStatusCode = apply.SourceStatusCode ?? student.StudentStatusCode;
    student.GradeId = apply.SourceGradeId;
    student.ClassId = apply.SourceClassId;

    if (apply.SourceSchoolOrgId != student.SchoolOrgId) { /* 改回原学校 + 路径 */ }

    await _studentsForUpdate.UpdateAsync(student, autoSave: true);
    await _changeLogger.LogUpdatedAsync(student, before, source: "学籍异动",
        reason: $"异动申请 {apply.ApplyNo} 撤销审核，学籍回滚");
}
```

**撤回的约束**（都要显式判断，否则会破坏流程一致性）：

| 约束 | 为什么 |
|---|---|
| 只有"已通过"的申请能撤回 | 待审核的应该走"驳回"或"撤回申请" |
| **后续节点已处理时不允许撤回** | 后面已经有人基于"已通过"做了动作 |
| 撤回后流程任务状态回到"待处理" | 否则待办列表里看不到它 |
| 回滚也要留痕 | 回滚本身是重要变更，必须可追溯 |

关键用例（本仓库已有）：

| 用例 | 守什么 |
|---|---|
| `逐级审核走完_学籍状态与学校变更生效` | 业务联动真的生效（**含 `SchoolPathCode`**） |
| `驳回后申请单结束_学生学籍不变` | 驳回不该改档案 |
| `撤销已通过的审核_学籍变更被回滚` | 快照回滚正确 |
| `驳回后_后续未处理节点应标记为已跳过` | 不会留下永远"待处理"的节点 |
| `后续节点已处理时_不允许再撤销` | 撤回约束生效 |
| `事务范围_中途抛异常时前面的写全部回滚` | 多步写的原子性（见第 33 章） |

## 32.7 本章要点

1. **前后状态都存快照**：实时读主档会让"撤回审核"把学生恢复成从未存在的状态。
2. 姓名/辅号/类型名也冗余存 —— 申请单要能独立读懂，不受改名与软删影响。
3. 不允许跨校的类型，目标学校**取原学校**而不是留空（避免"空"的歧义）。
4. 改学校时必须**同时改 `SchoolPathCode`**，否则数据范围过滤会错。
5. 撤回审核是反向逻辑，且要用快照；撤回有明确约束（已通过、后续未处理）。
