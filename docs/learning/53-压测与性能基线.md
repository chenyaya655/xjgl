# 53 压测与性能基线：怎么压、看什么、什么算不合格

> 对应代码：`tools/k6-smoke.js`
> 对应文档：`deploy/README.md` 第 11 章（多副本扩容）、第 12 章（压测基线）

## 53.1 要解决的问题

"系统能扛多少人"这个问题**没有通用答案**，只有"在当前数据量、当前配置下量到的数字"。
本章给出一套可复现的压测方法，以及**本机真实量到的基线**。

先把三件事说清楚，否则压测数字没有意义：

| 项 | 本仓库的取值 |
|---|---|
| 压测工具 | k6（WSL 里装，v2.2.0） |
| 压哪套数据 | **测试库**（`xjgl_test`，本机 3000+ 学生）—— 别对演示/生产库压 |
| 压哪些接口 | 学生列表（最高频读）、按学校统计（最重读）、用户上下文（每次进页面都调） |

## 53.2 第一步：压哪些接口（按"最容易先垮"排序）

| 优先级 | 场景 | 为什么它先垮 |
|---|---|---|
| 1 | **照片批量上传** | 唯一同时吃 CPU（解码/缩放）、内存、磁盘/NAS 的写路径 |
| 2 | **按学校统计**（`dimension=school`） | `GROUP BY` + `LIMIT 200`，最重的读 |
| 3 | **花名册 PDF 导出** | 纯 CPU，且产物要落盘 |
| 4 | 学生列表 | 最高频，但都是索引命中，一般不先垮 |
| 5 | 登录 | 早高峰短时集中，OpenIddict 有自身限流 |

**`tools/k6-smoke.js` 刻意只压 1~4 中的读路径**，不压上传。原因很实际：

> 上传限流是**单用户 5 次/秒**。用同一个账号打满时，量到的不是性能而是 **429**。
> 要压上传必须**用多账号**（每个账号一套令牌），那是另一个脚本。

## 53.3 第二步：脚本的三个设计点

```javascript
export const options = {
  // 阶梯加压：目的是找拐点，而不是一上来就打满
  stages: [
    { duration: '30s', target: 10 },
    { duration: '1m',  target: 30 },
    { duration: '1m',  target: 60 },
    { duration: '30s', target: 0 }
  ],
  thresholds: {
    // 这两条是"不合格线"，不是"目标线"。超了应该去加索引/加副本/查慢查询
    http_req_failed: ['rate<0.01'],
    http_req_duration: ['p(95)<1500', 'p(99)<4000']
  }
}
```

**① 阶梯加压而不是恒定并发**：恒定并发只能告诉你"这个并发下没崩"，
而阶梯能看到**拐点在哪**（p95 开始抬升的那个并发数才是容量）。

**② 阈值是"不合格线"**：写清楚这一点很重要，否则有人会把阈值当成优化目标，
把 `p(95)<1500` 改成 `<3000` 来"通过"。

**③ 专门统计 429**：

```javascript
const rateLimited = new Rate('rate_limited')

function track429(res) { rateLimited.add(res.status === 429) }
```

出现 429 是**预期行为**（限流在工作），但如果比例很高，
说明压测方式不对（应该用多账号），而不是系统有问题。

## 53.4 第三步：跑之前必须核对账号与地址（两个真实的坑）

### 坑一：`BASE` 要写 `127.0.0.1`，不要写 `localhost`

有些 WSL 发行版的 `/etc/hosts` 里同时有：

```
127.0.0.1   localhost
127.0.1.1   localhost.localdomain   localhost      ← 元凶
```

Go 的解析器可能先取到 `127.0.1.1`，于是 k6 报：

```
dial tcp 127.0.1.1:44300: connect: connection refused
```

而同一时刻 `curl http://localhost:...` **却是通的**（curl 的解析顺序不同）。
非常容易误判成"后端没起来"。**用 IP 就完全没有这个问题。**

### 坑二：演示账号的口令各层不同

实测（本机，2026-09-19 复核）：

| 账号 | 口令 | 实测 |
|---|---|---|
| `admin` | `1q2w3E*` | ✅ 200 |
| `demo-prov-990000` | `Demo@Xjgl2026` | ✅ 200 |
| `demo-city-990100` | `Demo@Xjgl2026` | ✅ 200 |
| `demo-county-990101` | `Demo@Xjgl2026` | ✅ 200 |
| `demo-school-9901010001` | `Demo@Xjgl2026` | ✅ 200 |

> ⚠ **这一格曾经是错的，而且错法很有教育意义。**
> 早期这里记着"`demo-province-990000` 不可用（该层演示账号未创建）"。
> 实际情况是**两层错误叠在一起**：
>   1. 用户名抄错了一个字母（`demo-province-` vs 实际 `demo-prov-`）；
>   2. 更关键的：改了 `Xjgl:DemoData:Password` 之后**旧库里已存在账号的口令不会跟着变**
>      （`EnsureUserAsync` 对已存在用户直接返回，这是正确的幂等设计），
>      于是"种子日志一切正常、文档里的口令却登不上"。
> 修法是显式开 `Xjgl:DemoData:ResetPassword=true` 重跑 DbMigrator
> （破坏性操作，默认关闭）。**排查这类问题的捷径**：同一个口令用 `curl` 直接打
> `/connect/token`，与浏览器表现做对照 —— 能立刻区分"账号/口令问题"与"前端问题"。

脚本的登录是 `setup()` 阶段，**失败会直接 `throw` 并给出明确提示** ——
这是刻意的：宁可"压测一开始就报账号不可用"，也不要跑完 3 分钟才发现全程 0 请求。

```javascript
if (res.status !== 200) {
  throw new Error(
    `登录失败（HTTP ${res.status}）：${res.body}\n` +
      '压测前请确认账号可用、后端已启动，且 BASE 指向的是测试库。'
  )
}
```

## 53.5 第四步：本机实测基线（可复现）

环境：Windows + 原生 PG 16.9（`xjgl_test` @55432）+ Redis，后端单实例，
`BASE=http://127.0.0.1:44300`，账号 `admin`，在 WSL 里跑 k6 v2.2.0。

```bash
wsl -e bash -lc "cd /mnt/d/StudentManagement && k6 run \
  -e BASE=http://127.0.0.1:44300 -e USER=admin -e PASS='1q2w3E*' tools/k6-smoke.js"
```

**实测结果（阶梯到 60 VU，持续 3 分钟）**：

| 指标 | 数值 | 阈值 | 结论 |
|---|---|---|---|
| 请求总数 | **8,284** | — | 约 44 req/s |
| 迭代数 | 2,761 | — | 约 14.7 iter/s |
| `http_req_failed` | **0.00%**（0/8284） | <1% | ✅ |
| `p(95)` | **461.64 ms** | <1500 ms | ✅ |
| `p(99)` | **933.59 ms** | <4000 ms | ✅ |
| `avg` | 275.62 ms | — | — |
| `med` | 157.84 ms | — | — |
| **`max`** | **23.74 s** | — | ⚠ 见下 |
| 业务校验通过率 | **100%**（13,805/13,805） | — | ✅ |
| **429 比例** | **0.00%**（0/8283） | — | ✅ 限流未误伤 |

> ⚠ **`max = 23.74 s` 值得注意**：均值与 p99 都很好，但最大值出现过 23 秒。
> 这符合"**冷启动第一次命中某条路径**"的特征（Vite/EF 首次查询、连接池建立），
> 而 p95/p99 不受它影响。**看压测结果一定要同时看 max** ——
> 只看均值会漏掉"少数用户等半分钟"这类体验问题。

**这份基线的适用边界（必须说明）**：
数据量只有 3000+ 学生，**远小于生产的几十万**；
所以它证明的是"**当前实现没有明显的并发缺陷**"（0 失败、429 正确），
而**不能**用来推断生产容量。生产上量前必须用真实量级的数据重跑。

## 53.6 第五步：只看 k6 输出会漏掉的东西

压测时**必须同时观察**这些（k6 看不到它们）：

| 观察点 | 怎么看 | 不合格的表现 |
|---|---|---|
| 数据库连接 | `select count(*) from pg_stat_activity where datname='xjgl_test'` | 接近 `max_connections`，`idle in transaction` 堆积 |
| 慢查询 | PG 日志（`log_min_duration_statement=200`） | 统计接口的 `GROUP BY` 全表扫 |
| Redis 延迟 | `redis-cli --latency` / `INFO commandstats` | `EVALSHA`（限流 Lua）延迟随并发线性上升 |
| 进程内存 | `docker stats` / `kubectl top` | 照片上传压测时 RSS 持续上涨不回落 |
| 导出产物磁盘 | `du -sh App_Data/exports` | 压完不回收 → 保留期清理没在跑 |
| 日志 | `grep 429` | 出现 429 是预期；但要确认没误伤正常批量上传 |

## 53.7 第六步：压测一定会暴露的已知点（别当成 bug）

1. **照片导出 zip 在内存里拼**：并发导出会看到内存尖峰。这是已知项
   （第 41 章），修法是改成写临时文件后交给产物存储。
2. **缩略图队列会被"原图读不到"的记录堵住**：扫描方向已改为**新的优先**，
   但积压很多时老照片仍可能长期没有缩略图 —— 列表页会回落加载原图，
   因此"照片列表接口响应体明显变大"是**预期内**的。
3. **单人限流很紧**（照片上传 5 次/秒/用户、导出提交 1 次/10 秒/用户）：
   单账号压满会被 429 挡住 —— 那不是性能问题。
4. **统计接口分组上限 200**：`isTruncated` 为 true 时结果是**被截断的**，
   拿它做"总人数"校验会对不上。

## 53.8 怎么把压测接进日常

```bash
# 冒烟（10 秒，确认账号与地址都对）
k6 run --vus 2 --duration 10s -e BASE=http://127.0.0.1:44300 \
  -e USER=admin -e PASS='1q2w3E*' tools/k6-smoke.js

# 阶梯（3.5 分钟，出基线）
k6 run -e BASE=http://127.0.0.1:44300 -e USER=admin -e PASS='1q2w3E*' tools/k6-smoke.js

# 只压统计接口的极限
k6 run --vus 100 --duration 3m -e BASE=http://127.0.0.1:44300 \
  -e USER=admin -e PASS='1q2w3E*' tools/k6-smoke.js
```

**建议的触发时机**：每次动过查询/索引之后、每次准备扩容之前、
以及上线前对着**接近生产量级**的数据跑一次。

## 53.9 本章要点

1. 压测前先定三件事：工具、**目标库（测试库）**、接口清单。
2. 用**阶梯加压**找拐点；阈值是"不合格线"不是目标。
3. `BASE` 写 `127.0.0.1`，**不要写 `localhost`**（WSL 的 `/etc/hosts` 有 127.0.1.1 那行）。
4. 登录失败要**立刻抛错**并提示核对账号，别让 3 分钟白跑。
5. 本机基线：60 VU/3 分钟 → **8284 请求、0 失败、p95=462ms、p99=934ms、429=0%**；
   但数据量只有 3000+ 学生，**不能推断生产容量**。
6. **一定要看 `max`**：本机出现过 23.74s，而这在均值里完全看不出来。
7. 同看数据库连接、慢查询、Redis 延迟、内存与磁盘回收 —— k6 看不到这些。
8. 已知的四个"压测必然暴露但不算 bug"的点，先记住再压。
