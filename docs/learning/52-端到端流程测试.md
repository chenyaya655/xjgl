# 52 端到端流程测试：在真浏览器里把流程点一遍

> 对应代码：`web/e2e/playwright.config.ts`、`web/e2e/specs/*.spec.ts`、
> `web/e2e/specs/support/auth.ts`、`web/package.json`（根脚本）、
> `.github/workflows/ci.yml`（`e2e` job）
> 相关基础设施：`web/apps/pc/src/components/SchoolSelect.vue`（本章抓出来的缺陷的修复）

## 52.1 要解决的问题：集成测试全绿，页面却不能用

到第 51 章为止，后端已经有 **445 个测试用例**（177 领域单元 + 268 集成），而且都是"真"的：真实 PostgreSQL、真实 PDF 渲染、
真实图像缩放、真实并发取号。前端也过了 `vue-tsc` 类型检查和 `vite build` 生产构建。

**但下面这三类问题，上面这些全都测不到：**

| 问题 | 为什么集成测试看不见 |
|---|---|
| 前端调的**路径/动词**与后端不一致（404/405） | 集成测试直接调应用服务，根本不经过 HTTP 路由与前端代码 |
| DTO 上"上限类"的规则被违反（分页上限、体积上限） | 直接在服务层调用会**绕过 ABP 的 DTO 验证** |
| 页面因为**数据规模**而卡死 / 按钮点不动 / 表格空白 | 集成测试不渲染 DOM；类型检查更与运行时无关 |

本项目在写这一章之前，正好把这三类问题**各踩了一遍**（过程见 52.8），
所以这一章不是"补一个测试工具"，而是补一层**只有真浏览器能提供的证据**。

要守住的东西很具体：

1. 前端有没有按真实路径与动词调后端；
2. 权限、路由、动态菜单组合起来之后，按钮是不是真的可点；
3. 一条完整流程（登录 → 查学生 → 详情 → 打印 → 导出）能不能一次走完；
4. 页面在**真实数据量**下还活着吗（这一条第 44 章的"虚拟滚动"那条规则就是它逼出来的）。

## 52.3 动手步骤二：把"两个服务"交给 Playwright 管

端到端测试需要后端（44300）与前端 dev server（5173）都在跑。
**不要让文档去教人"先开两个终端再跑测试"** —— 那样 CI 里必然对不上。
Playwright 的 `webServer` 配置可以在测试前自动拉起它们，并且已经起着就直接复用：

```ts
webServer: [
  {
    // 后端：本地是 Debug，CI 里构建的是 Release
    command: `dotnet run --project src/Xjgl.HttpApi.Host -c ${process.env.E2E_DOTNET_CONFIG ?? 'Debug'} --no-build`,
    cwd: repoRoot,
    url: `${API_URL}/health`,          // 用健康检查当就绪探针（见第 53 章）
    timeout: 240_000,
    reuseExistingServer: true,          // 本地已经手动起了一个？直接用
    env: { ...process.env, ASPNETCORE_ENVIRONMENT: 'Development', ASPNETCORE_URLS: API_URL }
  },
  {
    command: 'pnpm --filter @xjgl/pc dev',
    cwd: webRoot,
    url: WEB_URL,
    timeout: 180_000,
    reuseExistingServer: true
  }
]
```

**为什么前端必须用 dev server 而不是 `vite preview`：**
dev server 会把 `/api`、`/connect` 代理到后端，于是浏览器里看到的是与生产一致的**同源**形态；
用 `file://` 或者直接开两个端口，会立刻掉进 CORS 与"图片请求带不上令牌"这些与生产不一致的坑。

三条关键配置（都写在 `playwright.config.ts` 的注释里）：

| 配置 | 值 | 为什么 |
|---|---|---|
| `fullyParallel` / `workers` | `false` / `1` | 所有用例共用一套数据库与一个后端进程，并行会互相踩（都在改同一所学校的学生） |
| `timeout` / `expect.timeout` | 90 秒 / 30 秒 | 首次访问某个视图时 Vite 要按需编译，可达十几秒；Vite 编译慢不该变成"功能坏了" |
| `retries` | CI 里 1，本地 0 | 本地要立刻看到失败；CI 里容忍基础设施抖动 |

### 这里有两个必须记住的坑

**坑一：`globalSetup` 在 `webServer` 之前执行。**
第一版想用 `globalSetup` 先登录一次、把令牌存下来给所有用例复用，结果 `page.goto` 直接超时 ——
因为此时 dev server **还没起来**。要么放弃预热，要么把预热做成一个 `setup` project 并声明
`dependencies`（Playwright 会保证 `webServer` 先就绪）。本项目选了前者，靠放宽的断言超时吸收冷启动。

**坑二：`waitForLoadState('networkidle')` 永远等不到。**
Vite 的 HMR 用 websocket，网络永远不会"静默 500 毫秒"，于是每次调用都等到超时。
改用 `waitForLoadState('load')`，需要"数据到位"时用**针对元素的断言**（`expect(row).toBeVisible()`），
而不是等网络。

## 52.4 动手步骤三：登录与造数据（`specs/support/auth.ts`）

所有业务用例都要"先登录"。最省事的做法是直接往 `localStorage` 里塞令牌，
**但这等于把最该测的那条链路跳过了** —— 登录、令牌持久化、刷新后静默恢复，
恰恰是用户每天都会遇到的路径。所以这里的做法是**用界面登录**：

```ts
export async function login(page: Page, userName = ADMIN.userName, password = ADMIN.password) {
  await page.goto('/login')
  await page.getByPlaceholder('请输入用户名').fill(userName)
  await page.getByPlaceholder('请输入密码').fill(password)

  // 按钮文案是「登 录」（两个字之间有排版空格）：用正则匹配，
  // 排版微调不该让测试挂掉
  await page.getByRole('button', { name: /登\s*录/ }).click()
  await page.waitForURL('**/dashboard')
}
```

**造数据走接口，不假装点界面。** 学生建档目前走"导入或接口"，界面上的"新增学生"还没有对话框；
硬去点一个不存在的按钮，只会把测试写成"永远失败"。所以 `seedStudent()` 直接调
`POST /api/app/student` 建一个学生，然后界面只验**界面该负责的那部分**：

```ts
export async function seedStudent(request, token, schoolOrgId, name) {
  const response = await request.post('/api/app/student', {
    headers: { Authorization: `Bearer ${token}` },
    data: { name, genderCode: '1', /* … */ idCardNumber: newIdCard(), schoolOrgId }
  })
  // …
}
```

这里有两个"不懂业务就会写错"的点：

- **姓名只能用中文**：后端会校验证件式的姓名（不许数字/字母/符号）。
  第一版用了 `E2E学生123456` 这种"带时间戳保证唯一"的名字，被直接拒掉：
  「姓名包含非法字符『2』」。**唯一性要靠系统生成的学籍辅号**，而不是往姓名里塞时间戳。
- **身份证号必须"校验位正确"**：后端严格校验（校验位 + 出生日期段），
  随机拼的数字会被拒。所以 `newIdCard()` 是按 GB 11643 的加权算法**算**出来的。

## 52.5 动手步骤四：先写三条"最短但最值钱"的用例

不要一上来就写几十条。先写三条覆盖"最基础的链路"，跑通了再扩：

```ts
test('未登录访问业务页面会被重定向到登录页', async ({ page }) => {
  await page.goto('/student/list')
  await expect(page).toHaveURL(/\/login/)
})

test('刷新页面后会话仍然有效（令牌持久化 + 静默恢复）', async ({ page }) => {
  await login(page)
  await page.reload()
  await expect(page).toHaveURL(/\/dashboard/)
})

test('正确账号密码可以进入工作台并看到菜单', async ({ page }) => {
  await login(page)
  await expect(page.getByText('工作台')).toBeVisible()
})
```

第二条看着平平无奇，实际上它一次性覆盖了：令牌持久化、刷新时的静默恢复（refresh token）、
以及**路由守卫**（刷新是守卫最容易写错的地方，见 52.8 的缺陷一）。

然后按模块补齐。最终的用例分布（27 条）：

| 规格 | 条数 | 覆盖 |
|---|---|---|
| `01-login` | 5 | 重定向、密码错误不跳转、登录后菜单、刷新后会话、激活页公开 |
| `02-student` | 5 | 查询 + 掩码身份证、详情抽屉加监护人并留痕、**下载并校验 PDF**、导出 CSV、导入对话框 |
| `03-photo` | 5（1 条按条件跳过） | 台账页签、批量上传对话框、**缩略图**、打包导出对话框、缺照片名单 |
| `04-modules` | 12 | 11 个业务模块逐个打开并渲染、左侧菜单与后端元数据一致 |

### 两条"看起来多余、其实最值钱"的断言

**一、下载下来的必须真的是 PDF。**"点完没报错"说明不了什么：渲染失败时接口可能返回 200
但内容是一段错误 JSON。所以要**读字节**：

```ts
const [download] = await Promise.all([page.waitForEvent('download'), printButton.click()])
const stream = await download.createReadStream()
// 读前 5 个字节，必须是 %PDF-
```

**二、DOM 规模要有上限。** 这一条是 52.8 缺陷三逼出来的：
"学校下拉"如果为每所学校渲染一个节点，全省数据量下页面就会卡死。
断言刻意**与学校总数无关**（只要求少于 200 个），因为要守的是"虚拟滚动生效"，不是"学校有多少所"：

```ts
await expect
  .poll(async () => page.evaluate(() => document.querySelectorAll('.el-select-dropdown__item').length))
  .toBeLessThan(200)

// 再顺手验一次"选得中"：选中学校后按钮才由灰变亮
await expect(pickButton).toBeDisabled()
await select.click()
await page.locator('.el-select-dropdown__item:visible').first().click()
await expect(pickButton).toBeEnabled()
```

## 52.8 踩坑记录

### 缺陷一：深链 / 刷新 404 —— 两处"看起来等价"的写法

**现象**：点菜单进"学生管理"一切正常；但**刷新页面**或**直接把地址粘进新标签页**，
显示"页面不存在或您没有访问权限"。

**根因有两处，缺一不可**：

1. 路由守卫用 `to.meta.anonymous` 判断"这是不是公开页"，而**兜底路由（catch-all）也带这个标记**，
   于是 `/student/list` 在刷新那一刻被当成"未匹配"的路由处理；
2. 恢复会话后做重定向时写的是 `return { ...to, replace: true }`，
   而 `to` 是**已经解析过的路由对象**，里面带着 `name: 'not-found'` ——
   在 vue-router 里 **`name` 的优先级高于 `path`**，于是重定向到了一个不存在的路由。

**修法**：

```ts
// 公开页写成显式白名单，而不是靠 meta 标记（兜底路由也会带 meta）
const PUBLIC_PATHS = ['/login', '/activate']

// 恢复会话要在"公开页判断"之前做
if (token && !restored) { /* 先恢复 */ }

// 重定向只带 path：不要 spread 一个已经解析过的路由对象
return { path: to.fullPath, replace: true }
```

**教训**：路由守卫必须用**三种方式各验一遍** —— 点菜单、按 F5 刷新、直接粘贴地址。
只点菜单永远发现不了这一类问题。

### 缺陷二：导出按钮是死的 —— 集成测试绕过了 DTO 验证

**现象**：学生列表点"导出"没有任何反应，控制台里是一个 400。

**根因**：导出沿用了列表的查询参数，其中带着 `maxResultCount: 5000`
（当时想"导出全部，所以把上限调大"），而 **ABP 对单次 `MaxResultCount` 有硬上限 1000**，
DTO 验证直接拒绝，请求根本没进业务代码。

**为什么 268 个集成测试一个都没发现**：集成测试是**直接调应用服务**的，
`MaxResultCount` 的校验发生在 HTTP/DTO 层，服务层调用绕过了它。
换句话说：**"上限类"的契约规则（分页上限、上传体积、超时）只在 HTTP 层生效**，
必须有端到端（或契约）层来守。

**修法**：前端拼查询参数时不再带 `maxResultCount`（导出接口有自己的 `MaxCount`，且在上限内）。

### 缺陷三：打开批量上传对话框 = 页面假死 100 秒

**现象**：点"批量上传"后对话框迟迟不出现，随后的断言全部超时。
最初的报错是：

```
Error: expect(locator).toBeVisible() failed
Locator: locator('.el-dialog').filter({ hasText: '批量上传学生照片' }).getByText(/文件名请用学籍辅号/)
Expected: visible
Received: undefined
```

看起来**像选择器写错了**。

**根因**：学校下拉是普通 `el-select` + `el-option v-for`，**每个 `el-option` 都是一个真实 DOM 节点**。
本机测试库里有 **6,789 所学校**，于是：

| 指标 | 实测 |
|---|---|
| `.el-select-dropdown__item` 节点数 | **6,799** |
| 页面总节点（打开对话框后） | 从 1,231 涨到 **29,867** |
| 浏览器主线程被卡住的时间 | 一次 `page.evaluate` 要 **103 秒**才返回 |

这是**只在"真实数据规模 + 真实浏览器"下才会出现**的缺陷。修法是新增
`components/SchoolSelect.vue`，用**虚拟滚动**的 `el-select-v2`（只渲染可见的十几项），
再把 6 处"选学校"全部换掉。修复前后：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 单个学生 / 照片用例耗时 | 60~130 秒，且偶发超时 | 1.4~3.6 秒 |
| 整套 27 条 | 9 分 42 秒，22 通过 / 4 失败 | **51 秒，26 通过 / 1 跳过** |
| 打开对话框后的节点数 | 29,867 | 2,746 |

### 怎么区分"卡住"与"找不到元素"（本章最值得带走的一条）

这两个病的报错文案**几乎一样**，但处理方向完全相反：

| | 找不到元素 | 页面/主线程卡住 |
|---|---|---|
| 表现 | 断言超时、`Received: undefined` | 断言超时，**连不需要等待的调用也卡住** |
| 快速判据 | `locator.count()` 立刻返回 0 | `locator.count()` 也卡 90 秒 |
| 怎么查 | 打印 `dialog.innerHTML()` 看选择器到底该写什么 | 打开 trace 看最后未完成的操作；用 `page.evaluate` 逐秒探测主线程与节点数 |

所以排查时**先问一句："这个调用本来就该立即返回吗？"**
本例正是 `count()` 这种不会等待的调用也卡住了，才把"选择器写错"整个方向一次性排除掉，
转而去看主线程与 DOM 规模。

### Element Plus 2.x 的选择器"现实"

写用例时会反复踩到，先记住能省很多时间：

| 界面元素 | 想当然的写法 | 实际 |
|---|---|---|
| `el-select` 的占位符 | `getByPlaceholder('请选择学校')` | 占位符是 `<span>`，不是 input 的 placeholder 属性 |
| 对话框的关闭按钮 | `getByRole('button', { name: '关闭' })` | 右上角的 X 与页脚按钮的可访问名都是"关闭"，**会命中两个**；要限定到 `.el-dialog__footer` |
| 表格里的缩略图 | `row.locator('img')` | 行内还有图标，`img` 会命中多个；用 `img.el-image__inner` 并校验 `naturalWidth > 0` |
| 隐藏下拉里的选项 | `locator('.el-select-dropdown__item').first()` | 其它已关闭的下拉也有同名节点（只是不可见），要用 `:visible` |

## 52.9 小结与检查清单

端到端测试的价值不在"多测了多少行代码"，而在于**它是唯一能看到"用户看到的东西"的一层**。
本项目的实践经验很直接：**它第一次跑起来，就抓出了三个前面 445 个后端测试全都没发现的缺陷**，
其中两个是**功能性**的（刷新 404、导出 400），一个是**性能/可用性**的（页面假死）。

写完这一章，你应该能做到：

- [ ] `pnpm test:e2e` 一条命令跑起整套（不需要手动开服务）
- [ ] 新增一个模块时，能在 `04-modules.spec.ts` 的表格里加一行就完成冒烟覆盖
- [ ] 写用例时知道"数据用接口造、界面只验界面"
- [ ] 看到断言超时时，先分清是"找不到元素"还是"页面卡住"
- [ ] 知道哪些断言最值钱：**下载物的字节**、**DOM 规模上限**、**按钮的可用状态**

## 52.10 数据隔离：为什么不是「每个 spec 用独立 schema」（技术债 29）

本章的用例全都跑在**同一个数据库**上，而且 spec 只保证"能定位到自己造的数据"，
不保证"库里只有自己的数据"。跑得越多，库越脏：组织树、学校、学生、子表行、角色
一轮比一轮多（本仓库记录过的数字：4000+ 测试组织 / 6,789 所学校 ——
52.8 缺陷三那条"虚拟滚动"的断言正是被这个规模逼出来的）。

原本的计划是"**每个 spec 用独立 schema**"。**结论：在当前架构下做不成**，
三条阻碍都是硬的（细节写在 `web/e2e/playwright.config.ts` 的文件头注释里）：

1. **一个后端进程 = 一个连接串**。`ConnectionStrings__Default` 是进程级配置，
   而 Playwright 的 `webServer` **一次运行只启动一次** —— spec 层面换不了库/schema；
2. **前端也只有一个**。spec 走同源相对路径（`/api`、`/connect`），
   由 Vite dev server 代理到**固定**的后端地址（`VITE_API_BASE_URL`，默认 44300）；
   就算给每个 spec 起一个后端，浏览器里的请求也打不到它；
3. **两套迁移都不认 schema**。框架表走 EF Core 迁移（迁移文件里没有任何 `schema:`），
   业务表走 SqlSugar CodeFirst（`XjglConsts.DbSchema = null`），都落在 `public`。
   要按 spec 分 schema，得先让这两条迁移路径 schema 可参数化（改 `src/`）。

**现实的做法（已落地为可执行步骤）**：跑之前重建测试库 ——
`tools/reset-test-db.mjs`（第 13 条 / 技术债 8）现在也挂在 e2e 包上：

```powershell
cd web
corepack pnpm@9.15.0 --filter @xjgl/e2e run db:reset        # dry-run，先看它要做什么
corepack pnpm@9.15.0 --filter @xjgl/e2e run db:reset:force  # 真的重建（会 DROP DATABASE）
```

> ⚠ **这里有一个很容易踩空的地方**：脚本默认重建的是 `127.0.0.1:55432 / xjgl_test`
> （集成测试库），而**不设 `E2E_DB_CONNECTION` 时后端连的是 appsettings.json 里的开发库 `xjgl`**。
> 也就是说"重置了 xjgl_test，却打了 xjgl"会安静地发生。
> 正确姿势是把两者用同一个连接串钉住（`ConnectionStrings__Default` 给迁移器、
> `E2E_DB_CONNECTION` 给 Playwright），命令写在 `playwright.config.ts` 的 A 方案里。
> 重建完**必须**再跑一次 `dotnet run --project src/Xjgl.DbMigrator`（建表 + 种子），
> 否则库里连表都没有 —— 而 `06-report` 那类用例还需要种子数据。

**没做、也不建议顺手做的**：按 worker 分库（`CREATE DATABASE ... TEMPLATE` + 每个 worker
一套前后端进程）。它要改进程编排与 Vite 代理目标，属于另一件工作；而且当前 `workers: 1`，
在恢复并行之前它没有任何收益。
