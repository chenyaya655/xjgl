# 29 为什么自研可配置审批流，而不是套 BPMN 引擎

> 对应代码：`src/Xjgl.Domain/Changes/ChangeFlowPlanner.cs`、
> `src/Xjgl.Domain.Shared/Changes/ChangeFlowConventions.cs`
> 对应测试：`test/Xjgl.Domain.Tests/Changes/ChangeFlowPlannerTests.cs`

## 29.1 要解决的问题

学籍异动（转学、休学、复学、退学…）要走审核。而"走几步、谁审"这件事的特点是：

- **每个省/市/县都不一样**：有的地方转学只需两校确认，有的要过县、市两级；
- **同一个县里不同异动类型也不一样**：转学要审、休学可能只要学校批；
- **它还会变**：政策一调，流程就得改，而改流程**不应该改代码、更不应该重新发布**。

所以需求是"**业务人员自己能配流程**"。剩下的是选型：套一个通用工作流引擎（BPMN / Elsa /
Workflow Core），还是自己写？

## 29.2 先看真实需求的形状

把"转学"的流程画出来，它长这样：

```
① 转入学校提交
② 转入县区审核      ③ 转入地市审核
④ 转出学校审核
⑤ 转出县区审核      ⑥ 转出地市审核
```

看起来是个串行链。但真实规则里藏着两个**用"步骤"表达不了**的东西：

**规则一：同县区转学时，县区只审一次。**
如果甲县一中转到甲县二中，② 和 ⑤ 解析出来是**同一个县区教育局**。
业务上它的意思不是"审两遍"，而是"这一级只需要审一次"。

**规则二：审核到哪一级由"异动类型"决定，而不是由流程本身决定。**
"转学"可能审到地市，"休学"只需到县区。而中止的位置是**类型**的属性。

用通用引擎表达规则一，通常要写成"排他网关 + 条件分支 + 变量比较"：

```xml
<!-- 概念示意：BPMN 里表达"同一个组织就不要两个任务" -->
<exclusiveGateway id="gw1"/>
<sequenceFlow sourceRef="gw1" targetRef="task5">
  <conditionExpression xsi:type="tFormalExpression">
    ${targetCountyId != sourceCountyId}
  </conditionExpression>
</sequenceFlow>
```

问题不在能不能表达，而在于：

1. **条件依赖"运行时解析出来的组织 Id 是否相等"**，而这个相等关系是**数据算出来的**，
   不是建模时能画出来的分支；
2. 业务人员在 BPMN 建模器里**没法维护**这种表达式 —— 而"业务人员能自己改"正是需求本身；
3. 引擎通常要求流程"要么全审、要么按画好的分支走"，
   而我们需要的是"**先按模板解析出候选节点，再按实际情况去重与截断**"。

## 29.3 本项目的做法：三阶段（解析 → 截断 → 合并）

把流程模板当成**候选节点清单**，真正的待办由三步算法算出来：

```
模板节点（与组织无关）
   │  ① 解析：把「转入县区」这种相对描述，解析成具体组织
   ▼
(节点, 组织, 级别) 三元组
   │  ② 截断：丢掉级别高于「终止级别」的（由异动类型给定）
   ▼
候选节点（已限定在允许的层级内）
   │  ③ 合并：解析到**同一组织**的节点合成一个待办
   ▼
实际待办列表
```

**规则一不是特例，而是第 ③ 步的自然结果**：② 和 ⑤ 解析到同一个县区，所以合并成一个。
同理"同市转学市只审一次"也自动成立 —— 不需要为每个场景写判断。

这正是自研的核心理由：**"同一层级只审一次"是一句去重规则，而不是一条分支判断**。

## 29.4 关键设计：节点用"相对描述"，不用具体组织

流程模板里**不允许**写"甲县教育局"这种具体组织，只能写"转入学校所在县区"：

| 解析器 | 含义 |
|---|---|
| `TargetSchool` | 申请里选的目标学校 |
| `TargetCounty` | 目标学校所属县区 |
| `TargetCity` | 目标学校所属地市 |
| `SourceSchool` | 学生当前学籍所在学校 |
| `SourceCounty` / `SourceCity` | 同上，向上取一级 |

为什么这条是硬约束：**模板是全省共用的，而组织是每个县各不相同的**。
模板里写死组织 Id，换一个县就失效；写成"相对描述"，同一套模板在全省都能用。
解析这一步在 `IChangeFlowPlanner.Plan` 里通过**回调** `Func<string, ResolvedOrg?>` 完成 ——
领域层不认识数据库，组织由应用层查好传进来。

```csharp
FlowPlanResult Plan(
    IEnumerable<FlowNodeDefinition> nodes,
    Func<string, ResolvedOrg?> resolveOrg,   // ← 由应用层提供"解析器 → 组织"的映射
    string maxApproveLevel);
```

## 29.5 自研的代价（诚实列出）

| 代价 | 本项目怎么控制 |
|---|---|
| 要自己实现实例化与合并算法（约 400 行） | 算法只有三步，且**纯函数**、可单测（`ChangeFlowPlannerTests`）；不碰数据库 |
| 没有可视化建模器 | 前端自己写了一个"步骤条"式编辑器 + **流程预览**（见第 31 章） |
| 没有引擎自带的重试/补偿/定时器 | 只有"超时天数"一个时间语义，由查询时判断，不做定时器 |
| 复杂场景（会签、并行分支、子流程）表达不了 | **明确不支持**。本系统的异动是线性 + 按组织去重，用不上那些 |

最后一条是**刻意的**：通用引擎的能力上限远高于本需求，
但"用不到的能力"会变成"要理解的复杂度、要测试的面、以及出问题时要排查的可能"。

> **判断准则**：当需求可以被压缩成"**三步纯函数 + 一张模板表 + 一次预览**"时，
> 引入一个通用引擎就是把 400 行可读代码换成十几万行不可读代码。

## 29.6 与"套引擎"方案对比的一张表

| 维度 | 自研（本项目） | 通用引擎（BPMN/Elsa） |
|---|---|---|
| 业务人员改流程 | 前端步骤条编辑器 + 预览 | 需要建模器，学习成本高 |
| "同层级只审一次" | 去重的自然结果 | 要写条件分支，或引擎扩展 |
| 流程模板全省复用 | 相对描述 + 运行时解析 | 也可行，但要避免写死组织 |
| 代码量 | 约 400 行（纯函数） | 引擎本身十几万行 |
| 可测试性 | 单测直接调 `Plan(...)` | 通常要起引擎宿主 |
| 表达复杂流程 | **不支持** | 支持（本项目用不上） |
| 出问题排查 | 三阶段读一遍就懂 | 要懂引擎的持久化与调度模型 |

## 29.7 本章要点

1. 需求的核心不是"能画流程图"，而是"**业务人员能改、改了立刻知道会发生什么**"。
2. "同一层级只审一次"是**去重规则**，不是条件分支 —— 这是自研的关键理由。
3. 模板里只写**相对描述**（"转入县区"），组织在运行时解析；否则模板无法全省复用。
4. 自研的代价要明确承认，并且**明确不支持**复杂流程（会签/并行/子流程）。
5. 算法做成**纯函数 + 回调**，领域层不碰数据库 —— 这让它可以被彻底单测。
