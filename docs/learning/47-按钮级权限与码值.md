> 对应代码：`web/apps/pc/src/stores/auth.ts`、`web/apps/pc/src/views/student/list/index.vue`、
> `web/apps/pc/src/composables/useCodeOptions.ts`、
> `web/apps/pc/src/components/SchoolSelect.vue`、`GradeClassSelect.vue`
> 对应测试：`web/apps/pc/src/utils/csvEncoding.test.ts`、
> `web/e2e/specs/02-student.spec.ts`、`05-subtable-forms.spec.ts`

## 47.1 要解决的问题

一个业务页面的骨架其实只有四块：

```
筛选区（查询条件）
  ↓
工具栏（导出 / 导入 / 新增 …）
  ↓
表格（分页）
  ↓
对话框（新增 / 编辑 / 导入）
```

而**每一块都有两类固定的坑**：

| 坑 | 表现 |
|---|---|
| 权限控制写错 | 按钮看得见、点了 403；或者明明有权限却不显示 |
| **手写码值** | 下拉框选出来的值后端不认识 → 静默返回空列表 / 写坏主档 |

第二类是本章的重点，它在本仓库真实伤过人两次（见 47.4）。

## 47.2 第一步：按钮级权限 —— 只按权限码，不按角色

```typescript
// stores/auth.ts
const permissionSet = computed(() => new Set(profile.value?.permissions ?? []))

function can(permission: string): boolean {
  return permissionSet.value.has(permission)
}

function canAny(permissions: string[]): boolean {
  return permissions.some((p) => permissionSet.value.has(p))
}
```

页面里的用法：

```typescript
const auth = useAuthStore()

const canCreate = computed(() => auth.can(MetadataPermissions.Stu.Student.Create))
const canDelete = computed(() => auth.can(MetadataPermissions.Stu.Student.Delete))
const canExport = computed(() => auth.can(MetadataPermissions.Stu.Student.Export))
```

```vue
<el-button v-if="canCreate" type="primary" @click="openCreate">新增</el-button>
<el-button v-if="canDelete" type="danger" :disabled="selection.length === 0" @click="remove">
  删除选中（{{ selection.length }}）
</el-button>
```

三条约定：

1. **只判断权限码**，永远不写 `if (role === 'admin')` ——
   权限是元数据驱动的，角色到权限的映射完全在后端。前端自己推断必然与后端不一致；
2. **权限码用常量**（`MetadataPermissions`，来自共享包），不写字符串字面量 ——
   写错了不报错，只是按钮永远不显示；
3. **前端隐藏按钮只是体验优化，真正的拦截永远在后端**。
   所以"按钮隐藏了"不能作为安全依据（第 18 章的越权用例正是在测后端）。

## 47.3 第二步：页面骨架的最小实现

以学生列表为例，四个块各司其职，且**都是"降级可用"的**：

```typescript
async function load(): Promise<void> {
  loading.value = true
  try {
    const result = await studentApi.getList({
      schoolOrgId: query.schoolOrgId,
      keyword: query.keyword || undefined,
      studentStatusCode: query.studentStatusCode,
      gradeId: query.gradeId,
      classId: query.classId,
      skipCount: (page.value - 1) * query.maxResultCount,
      maxResultCount: query.maxResultCount,
      sorting: 'StudentNo ASC'
    })
    rows.value = result.items
    total.value = result.totalCount
  } finally {
    loading.value = false      // ★ finally，不是 then —— 出错时也要解除 loading
  }
}
```

`finally` 那一点很重要：写在 `then` 里的话，请求失败时 `loading` 会永远为 true，
页面看起来像"一直在加载"，用户只能刷新。

**学校下拉的降级**：

```typescript
async function loadSchools(): Promise<void> {
  try {
    const tree = await orgApi.getTree()
    schools.value = flattenSchools(tree)
  } catch {
    // 组织接口失败时不阻塞列表：用户仍可用关键字查询（受后端数据权限约束）
    schools.value = []
  }
}
```

**关键字与筛选条件的分工**：`keyword` 传 `undefined` 而不是空串 ——
后端把空串当成"要找关键字为空串的记录"，结果是空列表。
这是一个非常常见的坑（`SchoolSelect` 组件里专门做了归一化）。

## 47.4 ★ 别再手写码值：`useCodeOptions`

### 这个坑真实伤过人两次

| 场景 | 当时写错的代码 | 后果 |
|---|---|---|
| 学籍状态过滤 | `{ value: 'Studying', label: '在读' }` | 后端存的是码值 `01` → 拿 `'Studying'` 比对 **静默返回空列表**（HTTP 200） |
| 异动类型的"异动后状态" | 同样手写英文名 | 审批通过后**直接写进学生的学籍状态** → 主档被写坏，打印学籍卡时才发现 |

两次的共同点：**前端一套值、后端一套值，而且不报错**。类型检查、集成测试都拦不住。

### 解法：把码值来源收敛到一个组合式函数

```typescript
export function useCodeOptions(categoryCode: string): UseCodeOptionsReturn {
  const entry = entryOf(categoryCode)   // 模块级缓存，见下

  const options = computed<CodeOption[]>(() =>
    entry.items.value.map((i) => ({ value: i.code, label: i.name }))   // ← value 永远来自码表
  )

  async function load(): Promise<void> {
    if (entry.loaded.value) return

    // 并发去重：两个组件同时 load 只会发一次请求
    entry.pending ??= fetchItems().finally(() => { entry.pending = null })
    await entry.pending
  }

  function nameOf(code?: string | null): string | undefined {
    if (!code) return undefined
    return index.value.get(code)
  }

  return { options, loading: entry.loading, loaded: entry.loaded, error: entry.error, load, nameOf, refresh }
}
```

页面里就变成：

```typescript
const statusCodes = useCodeOptions(CodeCategories.StudentStatus)

onMounted(async () => {
  await Promise.all([loadSchools(), statusCodes.load()])
  await load()
})
```

```vue
<el-select v-model="query.studentStatusCode" placeholder="全部" clearable>
  <el-option v-for="o in statusCodes.options.value" :key="o.value" :label="o.label" :value="o.value" />
</el-select>
```

### 三个非显然的设计决定

**① 模块级缓存 + 并发去重，而不是 Pinia**

码表极低频变更（只有"微代码管理"页会改），但同一页面里常有多处要用
（统计页的"学籍状态"下拉 + 结果表里的状态翻译）。用模块级缓存最直接。

**② 失败不缓存（这条修掉了一个真问题）**

学生详情抽屉原来自己写了一套 `Promise.all + optionsLoaded` 缓存，
而 `optionsLoaded = true` **写在 catch 之后**：

```typescript
// ❌ 原来的写法：失败也标记"已载入"
try { ... } catch { return [] } 
optionsLoaded = true      // ← 一次网络抖动 → 六个下拉**整个会话都空着**
```

`useCodeOptions` 只在**成功**时置 `loaded`：

```typescript
try {
  entry.items.value = await codeApi.getItemsByCode(categoryCode)
  entry.loaded.value = true       // 失败时保持 false，下次还会重试
} catch (e) {
  entry.error.value = e instanceof Error ? e.message : '码表载入失败'
  entry.loaded.value = false
}
```

**③ 类别编码写成常量**

```typescript
export const CodeCategories = {
  StudentStatus: 'STUDENT_STATUS',
  Sex: 'SEX',                        // ⚠ 注意**不是** GENDER，类别编码就是 SEX
  ChangeApplyStatus: 'CHANGE_APPLY_STATUS',
  GuardianRelation: 'GUARDIAN_RELATION',
  // ...
} as const
```

编码拼错的表现是**接口 200 但返回空数组**（查一个不存在的类别），
下拉框静默变空 —— 排查时很难想到是编码拼错了。

## 47.5 第三步：大集合下拉必须虚拟滚动

`SchoolSelect.vue` 的注释记录了一组实测数据：

> 全省 6,789 所学校时，普通 `el-select` 打开一次就**多出 6,799 个 DOM 节点**、
> 总节点从 1,231 涨到 29,867，**主线程被卡住 100 秒以上** ——
> 表现是"对话框点不开、页面假死"，而接口、类型检查、集成测试**全是绿的**。

所以"选学校"统一用 `el-select-v2`（虚拟滚动，DOM 数与选项数无关）：

```vue
<el-select-v2 v-model="inner" :options="options" filterable :clearable="clearable" />
```

**为什么不做成"服务端搜索"**：可选范围本来就由数据范围限定，是**有限集合**，
本地 `filterable` 只是内存字符串匹配，反而比往返接口更快。

**年级/班级**同理（`GradeClassSelect.vue`），而且它多一层依赖链：

```
学校 → 学年 → 年级 → 班级
```

这三层依赖必须在组件内处理掉，否则每个页面都会重复犯同样的两个错：

1. 没选学校就去拉年级（接口要 `schoolOrgId`，请求会失败或拿到空）；
2. **换了学校不清空已选的年级** —— 界面上显示"一年级"，
   但那个 Id 属于上一所学校，查询条件会在别处生效，结果为空。

```typescript
watch(() => [props.schoolOrgId, effectiveYear.value] as const, () => void loadGrades(), { immediate: true })

async function loadGrades(): Promise<void> {
  gradesError.value = ''
  grades.value = []
  classes.value = []
  classId.value = undefined          // ← 清空下级选择

  const school = props.schoolOrgId
  const year = effectiveYear.value
  if (!school || !year) { gradeId.value = undefined; return }

  try {
    grades.value = await orgApi.getGrades(school, year)
  } catch (e) {
    gradesError.value = e instanceof Error ? e.message : '年级载入失败'   // 写进 placeholder
  }

  // 外部传进来的 gradeId 不在新列表里 → 它属于上一所学校，清掉
  if (gradeId.value && !grades.value.some((g) => g.id === gradeId.value)) gradeId.value = undefined
}
```

还有一个只有"重置"时才会暴露的细节：**只清 `v-model` 是不够的**，
选项列表还留在子组件里。所以组件必须 `defineExpose({ reset })`：

```typescript
function reset(): void {
  gradeId.value = undefined
  classId.value = undefined
  grades.value = []
  classes.value = []
}
```

值得抄进规约的两条：

1. **下拉框禁用字面量 value**：选项的 `value` 必须来自码表（`useCodeOptions`）或
   后端接口（如年级/班级/学校），不允许手写；
2. **上千条的集合一律用虚拟滚动下拉**（`el-select-v2`）。

## 47.7 本章要点

1. 按钮权限**只判断权限码**，不推断角色；权限码用共享包里的常量。
2. 前端隐藏按钮只是体验，**真正的拦截在后端**。
3. `loading` 要在 `finally` 里解除；辅助数据（学校/码表）拉取失败要**降级不阻塞**。
4. **绝不手写码值**：统一走 `useCodeOptions`，`value` 只能来自码表。
   它已经伤过人两次，而且两次都**不报错**。
5. 码表失败**不缓存**（原来的写法会让六个下拉整个会话都空着）。
6. 上千条的集合用 `el-select-v2`；学校/年级/班级各有封装组件，
   把依赖链与级联清空收在一处。
7. 组件的 `reset` 要连**选项列表**一起清，不只是 `v-model`。
