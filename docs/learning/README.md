## 一、这份文档想解决什么问题

大多数 ABP 教程只教你"跑起来模板"，然后你就卡在下面这些问题里：

- 业务 ORM 想用 **SqlSugar**，但 ABP 的仓储、工作单元、软删除、审计字段全是围绕 EF Core 设计的 —— 怎么共存？
- ABP 自带的身份/权限/审计模块用 EF Core，我的业务表用 SqlSugar，**同一个库、两种 ORM**，事务怎么办？
- **学籍号**要按学校并发取号，不能重号；
- 姓名里有**生僻字**（𰻞、𠮷），从数据库到打印全链路都要不出现方块；
- 照片要传到 **NAS**，NAS 会卡、会掉线，但**教师上传不能失败**；
- 每个省/市/县的**审批流程都不一样**，业务人员要能自己改流程，而不是改程序。

这份文档按**实际建库、建表、建接口的顺序**走一遍，每一章都包含：

| 每章的结构 | 说明 |
|---|---|
| **要解决的问题** | 先讲清楚不这么做会踩什么坑 |
| **动手步骤** | 可以直接照抄的命令与代码 |
| **验证方法** | 怎么确认这一步真的成了（而不是"看起来没错"） |
| **踩坑记录** | 我实际踩过的坑，以及为什么 |

## 二、前置知识与环境

### 2.1 你需要会什么

不需要精通，但需要**能看懂**：

- C# 与 .NET（会用 `async/await`、LINQ、依赖注入）
- 关系型数据库基础（表、索引、事务、外键）
- 命令行（PowerShell 或 bash 都可）
- 前端：HTML/CSS/JavaScript 基础（第五篇才用到）

### 2.2 你需要装什么

| 工具 | 版本 | 用途 |
|---|---|---|
| Windows 10/11（22H2+） | — | 宿主系统 |
| WSL2 + Ubuntu | 22.04 或 24.04 | 跑 Docker 容器（数据库/缓存/消息队列） |
| Docker Desktop（开启 WSL2 集成） | 最新版 | 容器运行时 |
| .NET SDK | **10.0** | 后端 |
| Node.js | 20 LTS 或更高 | 前端 |
| Visual Studio 2022/2026 | 17.12+ | 写后端（用 VS Code 也可以） |
| VS Code | 最新版 | 写前端 |
| Git | 最新版 | 版本管理 |

> **为什么数据库放在 WSL 的 Docker 里，而不是直接装 Windows 版？**
> 因为生产环境一定是 Linux + PostgreSQL。开发期就用同一个大版本、
> 同样的 `C.UTF-8` 排序规则，能提前暴露"Windows 上没事、Linux 上乱码/排序错"这类问题。
> 而且 Docker 里换版本、清库、加扩展都是一条命令的事。

### 2.3 关于本仓库里的 `.tools/` 目录

本仓库有一个 `.tools/` 目录，里面是**在受限沙箱里开发时的替代方案**
（自建 PostgreSQL、本地 NuGet 镜像代理、缓存重定向等）。

**你自己在正常开发机上学这套系统时，完全不需要它。**
凡是文档里出现 `.tools/` 的地方，都会额外给出"正常环境怎么做"。

## 四、用什么工具写（后端 VS、前端 VS Code）

按你的要求，这套项目**后端用 Visual Studio、前端用 VS Code**。具体怎么开：

### 4.1 后端：Visual Studio

```
文件 → 打开 → 项目/解决方案 → 选择仓库根目录的 Xjgl.sln
```

几个值得先做的设置：

| 设置 | 位置 | 为什么 |
|---|---|---|
| 启动项目设为 `Xjgl.HttpApi.Host` | 解决方案资源管理器右键 → 设为启动项目 | 它才是 Web 入口，`Xjgl.HttpApi` 只是类库 |
| 打开"错误列表"的**警告**级别 | 视图 → 错误列表 → 筛选 | 本项目的两个关键 bug 都是编译期警告指出来的（见第 08 章） |
| 设置 `appsettings.Development.json` 不被提交 | 属性 → 生成操作 | 里面会有你的本机连接串 |

调试 DbMigrator：右键 `Xjgl.DbMigrator` → 调试 → 启动新实例。
**建议第一次先把 DbMigrator 跑通再去调试 Host**，否则 Host 会因为表不存在而报一堆错。

### 4.2 前端：VS Code

```powershell
code <仓库根>\web
```

建议装这几个扩展（工作区里可以写进 `.vscode/extensions.json` 共享给团队）：

| 扩展 | 用途 |
|---|---|
| `Vue - Official`（原 Volar） | `.vue` 文件的语法与类型支持，**必须装**，不要装已废弃的 Vetur |
| `ESLint` | 代码检查 |
| `EditorConfig for VS Code` | 统一缩进与换行符 |
| `Error Lens` | 把错误直接显示在代码行尾（对 Vue 模板错误特别有用） |

**一个容易踩的点**：VS Code 要打开 `web` 目录（工作区根），
而**不是** `web/apps/pc`。因为依赖装在 `web/node_modules`（pnpm 工作区），
打开子目录会导致 TS 找不到类型定义，满屏红波浪线。

### 4.3 两边都打开也没问题

后端和前端是完全独立的两个工程，各开各的窗口即可。
联调时后端跑在 `http://localhost:44300`，前端 dev server 跑在 `http://127.0.0.1:5173`，
前端的 Vite 代理会把 `/api` 转发到后端（见第 44 章）。

## 六、几个贯穿全篇的约定

1. **命名**：解决方案前缀 `Xjgl`（"学籍管理"拼音首字母）。
2. **数据库表名**：业务表用 snake_case（`stu_student`、`sys_code_item`），
   ABP 框架表保持 ABP 默认命名（`AbpUsers` 等）—— 不强行统一，
   因为改框架表名会牵扯到 ABP 内部所有 SQL。
3. **代码注释写"为什么"**：本项目的注释不解释"这行在做什么"，
   只解释"为什么必须这么做、不这么做会怎样"。你读源码时会看到大量这类注释。
4. **命令**：Windows 下用 PowerShell；WSL 内的命令会单独标注 `# WSL`。

## 七、开始之前：先确认你认同这几个判断

这套系统里有几个**有争议的设计决定**，我先摊开说明。
如果你不认同，后面会越读越别扭：

| 决定 | 理由 | 代价 |
|---|---|---|
| 业务 ORM 用 SqlSugar，不用 EF Core | 批量导入（一次几万行）、复杂报表 SQL、CodeFirst 建表在 SqlSugar 上更顺手 | 与 ABP 的集成要靠自己写一层（第 07~09 章），比纯 EF Core 方案多写约 1500 行基础设施 |
| 审批流自研，不用 BPMN/Elsa | "同一层级只审一次"这种按组织维度去重合并的需求，通用引擎表达起来很别扭；业务人员也更接受"横向步骤条" | 要自己实现实例化与合并算法（第 32~33 章，约 400 行） |
| 菜单与路由存数据库，前端动态注册 | "模块管理"本身就是一个业务功能（管理员可增删模块、改路径、停用） | 前端第一次加载多一次接口调用；组件解析不到时要准备占位页 |
| 照片存 NAS，路径用学生 Id 而不是学籍号 | 学籍号写在 NAS 目录上等于把学生身份信息摊给运维看 | 由路径反推学生需要查库 |
| 年级/班级不进组织树 | 它们是**学年维度**的数据，每年重建一次；混进组织树会让树无限膨胀 | 数据范围判断要同时看组织树与学年 |
