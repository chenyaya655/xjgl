# 37 照片存储抽象：为什么要分主存储与降级存储

> 对应代码：`src/Xjgl.Domain/Photos/IPhotoStorage.cs`、
> `src/Xjgl.Domain/Photos/StuPhoto.cs`（`FileSystemPhotoStorage`）、
> `src/Xjgl.Domain/Photos/ResilientPhotoStorage.cs`、`PhotoPathRule.cs`
> 对应测试：`test/Xjgl.Domain.Tests/Photos/PhotoStorageTests.cs`、
> `Photos/ResilientPhotoStorageTests.cs`

## 37.1 要解决的问题

学生的照片放在 **NAS** 上（省厅统一采购的存储）。而 NAS 的特点是：

- **它是网络存储**：会卡、会掉线、会维护重启；
- **它的可用性低于 Web 应用**：Web 可能 99.9%，NAS 做不到；
- **但教师上传照片不能失败**：一个班 50 个孩子排队等着拍照，
  弹出"NAS 不可用，请稍后再试"等于让整个采集工作停摆。

所以需求是一句话：**存储不可用时，上传仍然要成功**。
这不可能靠"重试 NAS"实现，只能靠**先写别处**。

## 37.2 第一步：把"存储"抽象成接口

```csharp
public interface IPhotoStorage
{
    string Name { get; }

    /// <summary>写入；失败不抛异常，而是返回结果（调用方要能"降级"而不是"崩"）。</summary>
    Task<PhotoWriteResult> WriteAsync(
        string relativePath, Stream content, CancellationToken cancellationToken = default);

    Task<bool> DeleteAsync(string relativePath, CancellationToken cancellationToken = default);

    Task<bool> ProbeAsync(CancellationToken cancellationToken = default);
}

/// <summary>读能力单独一个接口 —— 因为"能读"与"能写"的角色不同（见下）。</summary>
public interface IPhotoBlobReader
{
    Task<Stream?> OpenReadAsync(string relativePath, CancellationToken cancellationToken = default);
}
```

**为什么读写分成两个接口**：`ResilientPhotoStorage`（写）需要"主 + 降级"两份，
而读的时候要**先主后降级依次尝试**。两者职责不同，混在一个接口里会让实现承担两套语义。

`PhotoWriteResult` 里有一个关键字段：

```csharp
public sealed record PhotoWriteResult(bool Success, string? Error, bool Degraded);
//                                                              ↑ 写到了降级区
```

`Degraded` 会一路传到数据库的 `stu_photo.status = FallbackPending`，
于是**后台补偿任务知道"这一张还在本地盘上，NAS 好了要搬过去"**。

## 37.3 第二步：路径规则（为什么用学生 Id 而不是学籍号）

```csharp
public static class PhotoPathRule
{
    // photo/{学校组织Id}/{学生Id}.jpg
    public static string Build(Guid schoolOrgId, Guid studentId, string fileName) => ...

    // photo/{学校组织Id}/thumb/{学生Id}.jpg
    public static string BuildThumbnail(Guid schoolOrgId, Guid studentId) => ...

    // 允许的扩展名（白名单，不是黑名单）
    public static bool IsAllowedExtension(string fileName) => ...
}
```

**为什么路径里不放学籍号**：NAS 目录会被运维、备份脚本、甚至别的系统看到。
学籍辅号是**学生身份标识**，把它摊在目录名上等于把"某个学生在这个学校"这件事
暴露给所有能访问 NAS 的人。学生 Id 是内部 GUID，反查需要查库（有权限控制）。

扩展名用**白名单**（`jpg/jpeg/png/bmp`）而不是黑名单：黑名单永远漏。

> 但白名单也**不够**：可执行文件改名成 `.jpg` 一样能过。
> 所以还有内容校验（第 38 章）—— **两道关卡解决的是不同问题，不能互相替代**。

## 37.4 第三步：文件系统实现的两个细节

```csharp
public class FileSystemPhotoStorage : IPhotoStorage, IPhotoBlobReader
{
    public FileSystemPhotoStorage(string name, string rootPath)
    {
        Name = name;
        _rootPath = Path.GetFullPath(rootPath);

        // ★ 这里**故意吞掉异常**
        TryEnsureRoot();
    }
}
```

**为什么构造函数要吞异常**：NAS 挂载点在应用启动时未必就绪（维护窗口、网络未通、
容器启动顺序）。此时如果让构造函数抛异常，**整个应用就起不来了** ——
而照片存储恰恰是"可以暂时不可用"的那部分。目录不存在时后续写入会失败，
进而被熔断器识别并走降级 —— 这才是期望的行为。

写入用"**先写临时文件再原子改名**"：

```csharp
var tempPath = targetPath + "." + Guid.NewGuid().ToString("N")[..8] + ".tmp";

await using (var file = File.Create(tempPath))
{
    await content.CopyToAsync(file, cancellationToken);
}

File.Move(tempPath, targetPath, overwrite: true);
```

为什么必须这样：直接 `File.Create(targetPath)` 后写内容，中间任何时刻
**另一个请求/后台任务都可能读到半截文件**（缩略图生成任务正是并发的读方）。
原子改名保证"要么是完整的旧文件，要么是完整的新文件"。

## 37.5 第四步：容错存储（主 + 降级）

```csharp
public class ResilientPhotoStorage : IPhotoStorage
{
    private readonly NasPhotoStorage _primary;          // NAS
    private readonly LocalFallbackPhotoStorage _fallback; // 本机磁盘
    private readonly PhotoCircuitBreaker _breaker;        // 熔断器（第 38 章）

    public async Task<PhotoWriteResult> WriteAsync(string relativePath, Stream content, ...)
    {
        // NAS 可用 → 写 NAS；失败或熔断打开 → 写本地降级区并标记 Degraded
        // 两者都失败 → 返回 Success=false（这才是真的失败）
    }
}
```

关键性质（每一条都有用例守）：

| 性质 | 为什么重要 |
|---|---|
| 主存储失败 **不抛异常**，而是返回 `Degraded` | 调用方（上传服务）要继续走完落库，不能崩 |
| 降级写入成功后，台账状态是 `FallbackPending` | 补偿任务据此知道"这一张要搬回去" |
| 读的时候**先主后降级** | NAS 恢复但补偿还没跑时，照片仍然读得到 |
| 两个都失败 → `Success=false` | 不能让"两处都没存下"被当成成功 |

## 37.6 怎么验证

```powershell
dotnet test test\Xjgl.Domain.Tests --filter "FullyQualifiedName~PhotoStorageTests"
dotnet test test\Xjgl.Domain.Tests --filter "FullyQualifiedName~ResilientPhotoStorageTests"
```

**测试里怎么模拟 NAS 故障**（本仓库的做法很值得学）：

```csharp
/// <summary>把「NAS」弄坏：删掉目录，在原地放一个同名文件，任何目录创建都会失败。</summary>
private void BreakNas()
{
    var root = _nasStorage.RootPath;
    if (Directory.Exists(root)) Directory.Delete(root, recursive: true);
    Directory.CreateDirectory(Path.GetDirectoryName(root)!);
    File.WriteAllText(root, "NAS 故障演练：这里故意放一个文件占位。");
}

private void RepairNas()
{
    var root = _nasStorage.RootPath;
    if (File.Exists(root)) File.Delete(root);
    Directory.CreateDirectory(root);
}
```

不 mock、不搭 NAS：把"NAS 根目录"指向测试输出目录下的一个本地目录，
需要故障时把它换成一个**同名文件** —— 于是"创建目录必然失败"，
写入失败、熔断、降级**全部真实发生**。这样能在毫秒级、可重复地演练完整故障链路，
而覆盖的是与生产**完全相同**的代码路径（同一套 DI 装配、同一个熔断器）。

## 37.7 本章要点

1. 存储抽象要分**写**（`IPhotoStorage`）与**读**（`IPhotoBlobReader`）两个接口，职责不同。
2. `PhotoWriteResult.Degraded` 是整条降级链路的信息载体，会一路传到台账状态。
3. 路径用**学生 GUID**，不用学籍号（避免把学生身份摊给运维看）。
4. 扩展名用白名单，且要明白它**不能替代内容校验**。
5. 存储构造函数要吞异常：NAS 未就绪不该让整个应用起不来。
6. 写入必须"临时文件 + 原子改名"，否则并发读会拿到半截文件。
7. 故障演练用"把根目录换成同名文件"，比 mock 更真实、比真 NAS 更可控。
