# 31 流程模板、节点与实例化算法（截断 + 合并）

> 对应代码：`src/Xjgl.Domain/Changes/ChangeTypeAndFlow.cs`、
> `src/Xjgl.Domain/Changes/ChangeFlowPlanner.cs`、
> `src/Xjgl.Application/Changes/ChangeTypeAppService.cs`
> 对应测试：`test/Xjgl.Domain.Tests/Changes/ChangeFlowPlannerTests.cs`

## 31.1 要解决的问题

第 29 章说明了"自研三阶段算法"的选择。本章把**数据模型**与**算法细节**写清楚：

- 模板与节点怎么存（以及为什么有"草稿/发布"两态）；
- 节点上的每个字段有什么用；
- 三阶段算法**逐行**怎么走（本章会给出可运行的心智模型）；
- 怎么让业务人员在改完流程后**立刻知道会发生什么**（流程预览）。

## 31.2 第一步：模板的两态（草稿 / 发布）

模板不是"改完即生效"，而是**草稿 → 发布**两态：

```csharp
public class StuChangeFlowTemplate : FullAuditedAggregateRoot<Guid>, IXjglBusinessEntity
{
    public Guid ChangeTypeId { get; set; }
    public string Name { get; set; } = default!;
    public int Version { get; set; }
    public bool IsPublished { get; set; }        // ← 只有已发布的才能用来提交申请
    public DateTime? PublishedTime { get; set; }
}
```

**为什么要两态**：业务人员改流程时可能改到一半（加了个节点还没配角色）。
如果改完即生效，那些**改到一半就提交的申请**会按半成品流程实例化 ——
而且申请人看不出异常（流程照样"跑起来了"）。两态把"编辑中"与"可受理"分开。

一条硬规则：**没有已发布流程的异动类型不允许提交申请**。

```csharp
// 提交申请时
var template = await GetPublishedTemplateAsync(apply.ChangeTypeId);
if (template == null || !template.IsPublished)
    throw new BusinessException(XjglDomainErrorCodes.ChangeFlowNotConfigured);
```

> 为什么这条要写得这么硬：没有它，用户提交后会得到一个**没有任何审核节点**的申请，
> 状态永远是"待审核"却谁都看不到待办 —— 一个卡死且无法解释的状态。
> 有专门的用例 `没有已发布的流程模板_提交被拒绝` 守这一点。

## 31.3 第二步：节点字段逐个说清

```csharp
public class StuChangeFlowNode : FullAuditedAggregateRoot<Guid>
{
    public Guid TemplateId { get; set; }
    public int Seq { get; set; }                       // 从 1 开始，决定先后
    public string NodeName { get; set; } = default!;   // "转入县区审核"
    public string OrgResolver { get; set; } = default!;// "TargetCounty" —— 相对描述！
    public string RoleCode { get; set; } = default!;   // 由哪种角色处理
    public string MergeStrategy { get; set; } = ChangeMergeStrategies.MergeToLast;
    public bool AllowReject { get; set; } = true;
    public int TimeoutDays { get; set; }
    public bool IsEnabled { get; set; } = true;
}
```

四个字段值得单独解释：

### `OrgResolver`：只能是预定义的解析器

取值来自 `ChangeOrgResolvers`（`TargetSchool` / `TargetCounty` / `TargetCity` /
`SourceSchool` / `SourceCounty` / `SourceCity`）。**不能填组织 Id** ——
理由见第 29 章：模板全省共用，写死组织换一个县就失效。

### `RoleCode`：决定"谁能看到这条待办"

待办列表的查询条件里有它。取值与 `APPROVE_LEVEL` 码表对齐
（校级/县区级/地市级/省厅级学籍管理员）—— 于是"县区管理员"登录后
只看得到属于县级节点的待办，**这比在查询里写一堆组织判断简单得多**。

### `MergeStrategy`：合并时保留哪个节点

| 策略 | 含义 |
|---|---|
| `MergeToLast` | 同组织的多个节点合并后，**保留序号最大**的那个（即"审到最后一步"） |
| `MergeToFirst` | 保留序号最小的 |

为什么默认 `MergeToLast`：转学里 ② 转入县区 与 ⑤ 转出县区 指向同一组织时，
业务语意是"县区这一级的审核在**流程靠后**的位置完成"（要等两校都确认完）。
用 `MergeToFirst` 会让县区审在转出校之前完成，与直觉相反。

### `TimeoutDays`：只做提示，不做定时器

超时的判断放在**查询时**（"已超出 N 天未处理"的标记），不做后台定时器。
理由：定时器要处理"节点已被别人处理"的竞态，而它的价值只是"提醒"。

## 31.4 第三步：算法逐行（`IChangeFlowPlanner.Plan`）

签名先看清楚 —— **纯函数**，数据库通过回调进来：

```csharp
FlowPlanResult Plan(
    IEnumerable<FlowNodeDefinition> nodes,
    Func<string, ResolvedOrg?> resolveOrg,   // 解析器名 → 组织（应用层查好）
    string maxApproveLevel);                 // 来自异动类型
```

### 阶段 ① 解析

```csharp
var resolved = new List<(FlowNodeDefinition Node, ResolvedOrg Org, string Level)>();

foreach (var node in nodes.Where(n => n.IsEnabled).OrderBy(n => n.Seq))
{
    var org = resolveOrg(node.OrgResolver);

    if (org == null)
    {
        // 解析不到（例如"转出学校"对休学而言不存在）→ 跳过，但要记录下来
        result.Warnings.Add($"节点「{node.Name}」（序号 {node.Seq}）无法解析组织，已跳过。");
        continue;
    }

    var level = ToApproveLevel(org.OrgType);   // School/County/City/Province
    resolved.Add((node, org, level));
}
```

**注意 `resolved == null` 不是错误**：休学没有"转入学校"，`TargetSchool` 解析不到是正常的。
所以这里用 warning 而不是异常 —— 这一点如果做错（抛异常），休学就永远提交不了。

### 阶段 ② 截断

```csharp
var maxLevelOrder = ApproveLevels.GetOrder(maxApproveLevel);

foreach (var (node, org, level) in resolved)
{
    if (ApproveLevels.GetOrder(level) > maxLevelOrder)
    {
        result.Warnings.Add($"节点「{node.Name}」超出审核终止级别「...」，已截断。");
        continue;
    }
    kept.Add((node, org, level));
}
```

`maxApproveLevel` 非法时**退回校级并告警**，而不是抛异常：

```csharp
if (maxLevelOrder <= 0)
{
    result.Warnings.Add($"审核终止级别「{maxApproveLevel}」不合法，已按校级处理。");
    maxLevelOrder = ApproveLevels.GetOrder(ApproveLevels.School);
}
```

理由：这是"配置里写了个不认识的值"，退回最保守的行为（审得最少）并告警，
比让整条链路不可用更合适。

### 阶段 ③ 合并（本章重点）

```csharp
// 按解析出的组织 Id 分组 —— 同一组织只保留一个待办
var groups = kept.GroupBy(x => x.Org.Id).ToList();

foreach (var group in groups)
{
    var members = group.OrderBy(x => x.Node.Seq).ToList();

    // 组内策略取「首个节点」的配置（同组节点应配置一致）
    var strategy = members[0].Node.MergeStrategy;

    // MergeToLast → 保留序号最大的；MergeToFirst → 保留最小的
    var survivor = strategy == ChangeMergeStrategies.MergeToFirst
        ? members.First()
        : members.Last();

    tasks.Add(new PlannedFlowTask
    {
        Seq = survivor.Node.Seq,
        Name = survivor.Node.Name,
        OrgId = group.Key,
        // MergedFromSeqs 记录"这一条代表了哪几个原始节点" —— 前端展示用
        MergedFromSeqs = members.Where(m => m != survivor).Select(m => m.Node.Seq).ToArray(),
        // ...
    });
}
```

`MergedFromSeqs` 是**必须有的**：界面上要能显示
"转入县区审核（已合并：转入县区、转出县区）"。
没有它，业务人员看到流程少了两步会以为配错了 —— 而实际上那正是他想要的合并。

### 存活节点的 `Seq` 保持不变

注意 `Seq = survivor.Node.Seq`，**不是重新编号成 1,2,3**。为什么：

- 申请单的 `CurrentSeq` 直接存这个值，"推进到下一个待办"就是找
  `Seq > current && Status == Pending` 里最小的；
- 重新编号会让"合并前是第 5 步"这个信息丢失，日志与界面上都难以追溯。

## 31.5 怎么验证（单测是主力）

这个算法**最适合单测**：纯函数、无数据库、用例可以覆盖组合情况。

```csharp
[Fact]
public void 同县区转学_县区与地市各合并一次()
{
    var plan = planner.Plan(nodes, resolver, ApproveLevels.City);

    // 原始 6 个节点 → 存活 4 个（②⑤ 合并、③⑥ 合并）
    plan.Tasks.Select(t => t.Seq).ShouldBe(new[] { 1, 4, 5, 6 });
    plan.Tasks.Single(t => t.Seq == 5).MergedFromSeqs.ShouldBe(new[] { 2 });
}
```

## 31.6 流程预览：让"改完立刻知道会发生什么"

这是本模块**最有价值的一个接口**（`POST /api/app/change-type/preview-flow`）：
给一组「目标学校 + 原学校」，直接返回**实际会走哪几步、每步审到哪一级、哪几步被合并了**。

```csharp
// 应用层：把组织查好，喂给纯函数，再把结果转成视图模型
public async Task<PreviewFlowResultDto> PreviewAsync(PreviewFlowInputDto input)
{
    var nodes = await LoadNodesAsync(input.ChangeTypeId);
    var type = await _types.GetAsync(input.ChangeTypeId);

    // 构造解析器 → 组织 的映射（这里是唯一碰数据库的地方）
    var targetSchool = await _orgs.GetAsync(input.TargetSchoolOrgId);
    var sourceSchool = input.SourceSchoolOrgId.HasValue
        ? await _orgs.GetAsync(input.SourceSchoolOrgId.Value) : null;

    ResolvedOrg? Resolve(string resolver) => resolver switch
    {
        ChangeOrgResolvers.TargetSchool => ToResolved(targetSchool),
        ChangeOrgResolvers.TargetCounty => ToResolved(await GetParentAsync(targetSchool, OrgTypes.County)),
        // ...
        _ => null
    };

    var plan = _planner.Plan(nodes, Resolve, type.MaxApproveLevel);

    return ToPreview(plan);   // 含 warnings
}
```

为什么它比"看流程模板"有用得多：**模板是输入，待办列表才是输出**，
而两者之间的转换（解析 + 截断 + 合并）才是会出错的地方。
让业务人员看到输出，等于把算法的正确性交给他日常验证。

## 31.7 本章要点

1. 模板必须**草稿/发布两态**；没发布就不许提交申请（否则会卡死在无人可审的状态）。
2. 节点只写**相对描述**（`OrgResolver`），不写组织 Id。
3. 解析不到组织时**跳过 + warning**，不是抛异常（休学没有转入学校是正常的）。
4. 合并按**组织 Id 分组**，默认保留序号最大的节点（`MergeToLast`）；
   必须记录 `MergedFromSeqs` 供界面展示。
5. 存活节点的 `Seq` **不重新编号** —— `CurrentSeq` 依赖它推进流程。
6. 把算法做成**纯函数 + 回调**，它就能被彻底单测；预览接口是它最好的验收手段。
