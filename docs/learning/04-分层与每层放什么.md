# 04 九个项目怎么分层，每一层放什么

> **对应阶段**：P0 ｜ **预计耗时**：1 小时 ｜ **产出**：一套不会随着代码变多而失控的分层约定

---

## 4.1 要解决的问题

分层最大的风险不是"分得不够细"，而是**"什么东西都往 Application 层塞"**。
半年后你会看到：

- 一个 3000 行的 `StudentAppService`，里面既有 DTO 转换、又有 SQL、又有业务规则；
- 同样的"判断学生能不能转学"的规则，在申请接口和审核接口里各写了一遍，还写得不一样；
- 想给"转学规则"写个单元测试，发现它依赖数据库、依赖当前登录用户，只能启动整个应用来测。

**分层的本质是"让变化点被隔离"**：业务规则变得最慢，放在最里层；
接口和框架变得最快，放在最外层。

---

## 4.2 每一层放什么（本项目实际的做法）

| 项目 | 放什么 | **不放什么** |
|---|---|---|
| `Xjgl.Domain.Shared` | 常量、错误码、枚举、跨端共享的校验规则（如学籍号格式、身份证校验、生僻字判断） | 实体、业务逻辑 |
| `Xjgl.Domain` | 实体（聚合根）、领域服务、**纯函数形式的业务算法**、跨对象的不变式 | 任何 ORM 引用、DTO、`IApplicationService` |
| `Xjgl.Application.Contracts` | DTO、应用服务接口、权限码常量 | 实现、数据库访问 |
| `Xjgl.Application` | 应用服务实现：编排（取数 → 规则校验 → 写库 → 返回 DTO） | 复杂的业务算法（应下沉到 Domain） |
| `Xjgl.EntityFrameworkCore` | ABP 框架表（`AbpUsers`/`AbpPermissionGrants`…）的 `DbContext`、仓储、迁移 | 业务表 |
| `Xjgl.SqlSugarCore` | SqlSugar 客户端工厂、映射约定、仓储实现、序列服务 | 业务规则 |
| `Xjgl.HttpApi` | 控制器（约定式 + 手写）、HTTP 层的模型绑定 | 业务逻辑 |
| `Xjgl.HttpApi.Host` | 启动装配：配置、鉴权、缓存、后台任务、Swagger | 业务逻辑 |
| `Xjgl.DbMigrator` | 迁移控制台入口 | — |

## 4.3 三条贯穿全项目的约定

### 约定 1：Domain 不引用任何 ORM

看这个项目里 `Xjgl.Domain` 的引用：

```powershell
dotnet list src\Xjgl.Domain\Xjgl.Domain.csproj reference
# 只有 Xjgl.Domain.Shared
```

**为什么值得这么较真？** 举个真实例子 —— 异动的流程实例化算法：

```csharp
// src/Xjgl.Domain/Changes/ChangeFlowPlanner.cs
public static class ChangeFlowPlanner
{
    /// <summary>
    /// 把流程模板实例化成实际的审核任务序列。
    /// 纯函数：输入模板 + 申请单 + 组织解析器，输出节点序列，不碰数据库。
    /// </summary>
    public static IReadOnlyList<PlannedNode> Plan(
        ChangeFlowTemplate template,
        ChangeApplyContext context,
        IChangeOrgResolver resolver)
    {
        // 1) 解析：把"转入学校所在县区"这类抽象描述解析成具体组织 Id
        // 2) 截断：按异动类型配置的最高审核级别砍掉多余的省级节点
        // 3) 合并：同一组织只保留一次审核 —— "同县区转学只审一次" 就是这么来的
        ...
    }
}
```

因为它是纯函数，所以：

- 14 个测试用例覆盖了跨市/同市/同县/本校/含省级等所有组合，**跑完只要几毫秒**；
- 不需要起数据库、不需要登录用户；
- 算法改错了会立刻红，而不是等 QA 点十遍界面才发现。

**如果这个算法写在 `ChangeFlowAppService` 里**，它会需要 `IXjglRepository<SysOrg>`、
需要当前用户、需要事务 —— 于是只能写成集成测试，跑一次 3 秒，
覆盖 5 种场景就是 15 秒，改一行代码等 15 秒，人就不愿意跑了。

### 约定 2：DTO 与实体严格分开，不跨越边界

- 实体（`StuStudent`）只在 `Domain` 与 `Application` 内部流动；
- 对外（HTTP）只暴露 DTO（`StudentListItemDto`）；
- **不要**为了省事把实体直接返回给前端：一旦实体加了个 `IdCardEncrypted` 字段，
  它就会悄悄出现在接口返回里 —— 这是学籍系统里最不能容忍的泄露。

本项目的做法：每个应用服务里都有一个显式的 `ToDto` 映射方法，
**刻意不用 AutoMapper 自动映射**（AutoMapper 只在框架层用）。
理由是自动映射会让"哪些字段被暴露了"变得不可见，
而学生信息里有身份证号、家庭住址、监护人电话，暴露面必须一眼可查。

### 约定 3：跨 ORM 的东西一律显式，不做魔法

ABP 的工作单元（UnitOfWork）是为 EF Core 设计的：
它在 `SaveChangesAsync` 时统一提交、统一发事件。

SqlSugar 是另一个 ORM，**它的变更不在 ABP 的工作单元里**。
所以本项目：

- 业务数据（SqlSugar）用**显式事务作用域** `ISqlSugarTransactionScope`；
- 框架数据（EF Core）走 ABP 的 `IUnitOfWork`；
- **两者目前不能共享同一个事务** —— 这是一个已知代价，第 09 章专门讲。

把它们混在一起"看起来能跑"，但在跨 ORM 的写操作里会出现
"一边回滚了、一边没回滚"的数据不一致，这是最难查的一类 bug。

## 4.4 一个请求走过的完整路径

用"新增学生"举例，看每一层各做什么：

```
① HTTP 层（Xjgl.HttpApi）
   POST /api/app/student
   → 约定式控制器自动生成，把 JSON 绑定成 CreateUpdateStudentDto
   → 触发 [Authorize(Stu.Student.Create)] 鉴权

② 应用层（Xjgl.Application/Students/StudentAppService.cs）
   public async Task<StudentDto> CreateAsync(CreateUpdateStudentDto input)
   {
       // 2.1 输入校验（跨端规则，调 Domain.Shared）
       if (!RareCharacterText.IsValidPersonName(input.Name, out var nameError))
           throw new BusinessException(XjglDomainErrorCodes.ValidationFailed)
               .WithData("reason", nameError);

       // 2.2 取数（通过 ORM 无关的仓储接口）
       var school = await EnsureSchoolAsync(input.SchoolOrgId);

       // 2.3 查重（身份证摘要）
       var idCardHash = ComputeIdCardHash(idCard);
       var duplicated = await _students.FindAsync(s => s.IdCardHash == idCardHash);
       if (duplicated != null) throw new BusinessException(...).WithData(...);

       // 2.4 取号（并发安全，见第 22 章）
       var studentNo = await _sequenceService.NextStudentNoAsync(school.Code);

       // 2.5 建实体（业务不变式在实体构造/领域方法里）
       var entity = new StuStudent(...);

       // 2.6 落库
       await _students.InsertAsync(entity, autoSave: true);

       // 2.7 返回 DTO（显式映射）
       return ToDto(entity, school);
   }

③ 领域层（Xjgl.Domain）
   StuStudent 的字段约束、StudentNumberRule 的拼装规则、
   RareCharacterText 的姓名校验规则 —— 全是纯逻辑

④ 基础设施层（Xjgl.SqlSugarCore）
   IXjglRepository<StuStudent> 的实现：
   拼 SQL、加软删除过滤、自动填 CreatorId/CreationTime
```

**关键点：业务规则（③）不知道数据库存在，应用层（②）不知道 SqlSugar 存在。**

## 4.5 验证方法

**① 依赖方向没被破坏**

```powershell
# Domain 只能引用 Domain.Shared
dotnet list src\Xjgl.Domain\Xjgl.Domain.csproj reference

# Application 只能引用 Domain 与 Application.Contracts
dotnet list src\Xjgl.Application\Xjgl.Application.csproj reference
```

**② 单元测试真的不碰数据库**

```powershell
dotnet test test\Xjgl.Domain.Tests
```

跑完之后**故意把数据库容器停掉**，再跑一次。如果还能全绿，
说明单元测试确实没有偷偷依赖数据库：

```powershell
docker compose -f deploy/docker-compose.dev.yml stop postgres
dotnet test test\Xjgl.Domain.Tests      # 期望：仍然全绿
docker compose -f deploy/docker-compose.dev.yml start postgres
```

**这个验证很有价值** —— 它证明业务规则真的可以脱离环境测试。

**③ Application 层没有偷偷引用 ORM 实现**

```powershell
Select-String -Path src\Xjgl.Application\**\*.cs -Pattern "using SqlSugar|using Microsoft.EntityFrameworkCore"
# 期望：没有匹配
```

（本项目目前唯一的例外是 `ISqlSugarTransactionScope` 的位置问题，
属于已知技术债，第 09 章会讲怎么收尾。）

## 4.6 踩坑记录

### 坑 1：把业务规则写在应用服务里

最常见的写法：

```csharp
// 反面教材：规则和编排混在一起
public async Task ApproveAsync(Guid taskId)
{
    var task = await _tasks.GetAsync(taskId);
    if (task.Seq != currentMaxSeq) throw new BusinessException("还有前置审核未完成");
    if (task.Status != "Pending") throw new BusinessException("该任务已处理");
    ...
}
```

这些判断是**业务不变式**，应该放在 `StuChangeFlowTask` 实体的方法里：

```csharp
// 正确做法：实体自己保证不变式
public void Approve(Guid operatorUserId, string opinion, DateTime now)
{
    if (Status != ChangeTaskStatuses.Pending)
        throw new BusinessException(XjglDomainErrorCodes.ChangeTaskAlreadyHandled);

    Status = ChangeTaskStatuses.Approved;
    ApproverUserId = operatorUserId;
    Opinion = opinion;
    ApprovedTime = now;
}
```

这样任何调用方（PC、H5、小程序、后台任务）都不可能绕过规则。

### 坑 2：DTO 直接复用实体

一开始为了省事，把 `StudentDto` 做成 `StuStudent` 的子类。
后来给实体加了 `IdCardEncrypted`（密文），结果它跟着出现在接口返回里。
**改掉之后，本项目所有 DTO 都是独立类 + 显式映射。**

### 坑 3：`RootNamespace` 不统一导致的"找不到类型"

如果各项目 `RootNamespace` 不同，写 `using Xjgl.Students;` 时 IDE 提示找不到，
而实际类型在 `Xjgl.Domain.Students` 下。这类问题在项目变多后会反复出现，
统一根命名空间可以一次性避免。

### 坑 4：把 SqlSugar 的 `ISugarQueryable` 当成 `IQueryable`

这是本项目最关键的一个技术事实：

> **SqlSugar 的 `ISugarQueryable<T>` 并不实现 `IQueryable<T>`。**

后果是：业务仓储**无法**继承 ABP 的 `RepositoryBase<T>`，
因为 ABP 的仓储抽象完全建立在 `IQueryable<T>` 之上（`GetQueryable()` 返回 `IQueryable<T>`）。

这就是为什么本项目在 `Xjgl.Domain/Data/IXjglRepository.cs` 里
自定义了一个 ORM 无关的仓储接口：

```csharp
public interface IXjglRepository<TEntity> : ITransientDependency
    where TEntity : class, IEntity, new()
{
    Task<TEntity?> FindAsync(Expression<Func<TEntity, bool>> predicate, ...);
    Task<List<TEntity>> GetPagedListAsync(
        Expression<Func<TEntity, bool>>? predicate,
        string? sorting,
        int skipCount,
        int maxResultCount,
        ...);
    Task<long> GetCountAsync(Expression<Func<TEntity, bool>>? predicate, ...);
    ...
}
```

**注意 `GetCountAsync` 的谓词是可空的** —— 这不是随便设计的。
早期版本它不可空，调用方在"不带过滤条件查询全部"时传了 `null`，
于是底层拼出了以 `WHERE` 结尾的残缺 SQL，PostgreSQL 报
`42601: syntax error at end of input`，接口 500。
而这个缺陷躲过了 138 个集成测试（因为测试都带了过滤条件），
最后是靠真实调用接口才暴露（见第 08 章）。
