# 26 学生子表：监护人 / 简历 / 奖励 / 资助 / 体质，以及删除时的级联

> 对应代码：`src/Xjgl.Application/Students/StudentProfileAppService.cs`、
> `src/Xjgl.Application/Students/StudentAppService.cs`（`DeleteAsync` 与 `CascadeSoftDeleteAsync`）、
> `src/Xjgl.Application/Students/StudentAccessGuard.cs`
> 对应测试：`test/Xjgl.Application.Tests/Students/StudentProfileTests.cs`

## 26.1 要解决的问题

一个学生档案下面挂着六张子表：监护人、学习简历、奖励、处分、资助、体质健康。

它们有三个**共同点**，也正是本章的全部难点：

1. **都是"一对多"且生命周期跟随主档** —— 学生删了，子表不该留下孤儿行；
2. **都是独立路由**（`/api/app/student-profile/...`），**不会自动继承主档的数据范围**；
3. **一张子表里有敏感信息**（监护人的身份证号、联系电话）。

第 2 点最危险：如果不额外校验，"外校账号拿到学生 Id 就能读到别人学校家长的身份证号"。
这不是理论风险 —— 本项目的子表接口最初就是靠第 18 章的守卫补上的。

## 26.2 第一步：先设计"孩子怎么找到父母"

每张子表都有一个 `StudentId` 外键，但**没有数据库级外键约束**（因为主表由另一套 ORM 建）。
所以"孤儿行"不会由数据库帮你拦住，必须在应用层处理。表的形状（以监护人为例）：

```csharp
public class StuGuardian : FullAuditedAggregateRoot<Guid>, IXjglBusinessEntity
{
    public Guid StudentId { get; set; }
    public int Seq { get; set; }              // 同一学生内的序号（用于排序）
    public string Name { get; set; }
    public string? RelationCode { get; set; } // 码值，不是中文字面量
    public string? IdCardEncrypted { get; set; }  // 加密存（第 23 章那套）
    public string? IdCardHash { get; set; }       // 摘要（查重用）
    public string? PhoneNumber { get; set; }
    public bool IsPrimary { get; set; }           // 第一监护人（同一学生唯一）
    // ...
}
```

两个刻意的设计：

- **`Seq` 而不是靠 `CreationTime` 排序**：同一批导入的子行创建时间可能相同，
  排序不稳定会让"第一监护人"在两次打开时顺序不同；
- **身份证号同样加密 + 摘要**：监护人身份证是敏感信息，与主档同一套规则
  （复用 `IIdCardProtector`），**不给第二套实现的机会**。

## 26.3 第二步：数据范围必须逐表校验（`IStudentAccessGuard`）

这是本模块**最容易漏**的一步。子表接口拿到的是 `studentId`（或子表行 `Id`），
而"这个学生我能不能看"是主档的判断逻辑。有两个做法：

```csharp
// ❌ 做法一：在每个子表方法里复制一遍范围判断
//   6 张表 × (读/写) ≈ 十几处，漏一处就是越权读家长身份证
private async Task EnsureInScopeAsync(StuStudent student) { /* 复制粘贴 */ }

// ✅ 做法二：抽成守卫，两处服务共用（本项目）
public interface IStudentAccessGuard
{
    Task EnsureInScopeAsync(StuStudent student);
    Task EnsureOrgInScopeAsync(SysOrg org, string message);
}
```

守卫的两个方向都要有：

- **读**：`GetGuardiansAsync(studentId)` 先取学生 → 校验范围；
- **写**：`UpdateGuardianAsync(guardianId, ...)` 要**由行反查学生**再校验 ——
  只校验"这行存不存在"就漏了越权。

```csharp
// 写路径：必须反查学生
var guardian = await _guardians.GetAsync(id);
await _guard.EnsureInScopeAsync(await _students.GetAsync(guardian.StudentId));
```

> **实测**：`StudentProfileTests` 里有两条专门守这个方向的用例
> （外校账号读子表被拒 / 外校账号改子表行同样被拒）。第二条尤其重要 ——
> 只挡读不挡写，等于允许把数据塞进别人的学校。

## 26.4 第三步：业务规则放哪一层

六张子表各自的规则不复杂，但要**放对位置**：

| 规则 | 放哪 | 为什么 |
|---|---|---|
| 第一监护人唯一（设新的把旧的降级） | 应用服务 | 需要读同表其它行，是业务规则 |
| 体检一学年一条 | 应用服务 | 需要按 (学生, 学年) 查重 |
| 简历的结束日期不能早于开始日期 | DTO 校验 / 应用服务 | 纯字段间关系 |
| 奖励/处分的日期不能晚于今天 | **不校验** | 业务上允许补录历史，也可能补录未来（预登记） |
| 身份证号"留空不覆盖" | 应用服务 | 见下 |

最后一条值得单独说：界面上监护人的身份证号**始终显示掩码**（`410102********1234`）。
用户不改它就直接保存时，提交上来的是**掩码字符串**而不是明文。
如果不特殊处理，就会把掩码当成新号码写进库 —— 而且看起来"保存成功"。

```csharp
// 留空/掩码 → 保留原值；只有真的传了新的完整号码才覆盖
if (IdCardValidator.TryNormalize(input.IdCardNumber, out var normalized, out _))
{
    entity.IdCardEncrypted = _idCards.Encrypt(normalized);
    entity.IdCardHash = _idCards.ComputeHash(normalized);
}
// 传的是空或掩码 → 什么都不做（保留原值）
```

## 26.5 第四步：删学生时把子表一起软删（**但留痕不删**）

这是本章最容易做错的一处，而且本仓库真实踩过。

```csharp
public async Task DeleteAsync(Guid id)
{
    var entity = await _students.GetAsync(id);
    await _guard.EnsureInScopeAsync(entity);

    // 留痕写在删除之前：删掉之后就再也拿不到姓名与学籍辅号了
    await _changeLogger.LogDeletedAsync(entity);

    await _students.DeleteAsync(entity, autoSave: true);

    await CascadeSoftDeleteAsync(entity.Id);   // ← 六张子表 + 照片
}
```

`CascadeSoftDeleteAsync` 的规则（写成注释放在代码里，因为"哪些删哪些不删"必须一眼可见）：

| 表 | 删？ | 理由 |
|---|---|---|
| 监护人 / 简历 / 奖励 / 处分 / 资助 / 体检 | ✅ 软删 | 与学生档案同生命周期；监护人表里有**加密身份证号与电话**，学生删了不该留 |
| 照片记录 | ✅ 软删 | 否则台账里会出现"查不到学生、却查得到他的照片" |
| NAS 上的图片文件 | ❌ 不删 | 存储有独立的补偿/对账机制；顺手删文件会让"删错了想恢复"变成不可逆 |
| **变更留痕** | ❌ **不删** | **它是这次删除唯一的凭证** —— 见下 |

### 为什么留痕不能删（本节教训）

我第一版把留痕也一起级联软删了，理由听起来很顺："学生都没了还留着流水干嘛"。
结果立刻打红了既有用例：

```
删除学生_记录删除流水并保留姓名与辅号
…
deleted.StudentName.ShouldBe("待删学生", "学生删掉之后，流水里仍要能看出这是谁");
```

主档已经查不到，**姓名与学籍辅号只存在于流水里**。把留痕跟着删掉，等于删完什么都不剩，
出了问题连"谁在什么时候删了谁"都答不上来。

> **结论：审计数据与业务数据的生命周期必须分开考虑**，
> 不能因为"都是子表"就一起处理。现在有用例同时钉住两个方向：
> 子表必须清空 **+** 留痕必须留下且**变多**（多了一条「删除」流水）。

### 级联删除最容易写错的地方

**少写 `StudentId` 条件**。那样一次删学生会把全库同表的行都软删掉，
而"只造一个学生"的用例**根本看不出来**。所以必须有隔离用例：

```csharp
[Fact]
public async Task 删除学生_只删该学生的子表_不动别人的()
{
    var victim = await CreateStudentAsync(school.Id, "被删学生");
    var bystander = await CreateStudentAsync(school.Id, "保留学生");

    await _profile.CreateGuardianAsync(victim.Id, ...);
    await _profile.CreateGuardianAsync(bystander.Id, ...);

    await _students.DeleteAsync(victim.Id);

    (await guardians.GetListAsync(g => g.StudentId == victim.Id)).ShouldBeEmpty();
    (await guardians.GetListAsync(g => g.StudentId == bystander.Id))
        .ShouldHaveSingleItem().Name.ShouldBe("保留家长");
}
```


## 26.7 本章要点

1. 子表**不继承**主档数据范围 —— 必须走 `IStudentAccessGuard`，且**写路径要反查学生**。
2. 敏感字段（监护人身份证）与主档用同一套加密/摘要实现，不要写第二套。
3. 掩码回传要当"未修改"处理，否则会把掩码写进库，而且**保存成功**。
4. 删学生要级联软删子表与照片记录，但**不动 NAS 文件、不动变更留痕**。
5. 级联删除必须有"只删该学生的"隔离用例 —— 少写 `StudentId` 条件时，
   单学生用例是发现不了的。
