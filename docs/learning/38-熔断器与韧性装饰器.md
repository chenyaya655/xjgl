# 38 从零写一个可测试的熔断器（以及舱壁、超时、降级装饰器）

> 对应代码：`src/Xjgl.Domain/Photos/PhotoCircuitBreaker.cs`、
> `src/Xjgl.Domain/Photos/ResilientPhotoStorage.cs`
> 对应测试：`test/Xjgl.Domain.Tests/Photos/PhotoCircuitBreakerTests.cs`

## 38.1 要解决的问题

NAS 挂掉之后，如果每个请求都"老老实实去试一次 NAS"，会发生两件坏事：

1. **每次上传都要等超时**（假设 10 秒）—— 500 张照片的批次要等 5000 秒；
2. **恢复瞬间被打垮**：NAS 刚活过来，积压的请求一起冲上去，又把它打死。

熔断器解决第一件：**连续失败到一定程度后，直接拒绝而不去试**。
但"直接拒绝"对上传来说不可接受（教师传不上去），所以必须是**降级**：
熔断期间直接写本地盘，不去碰 NAS。

本项目要的不是"接一个现成的 Polly"，而是**一个可以彻底测试的状态机**。
第 38 章把它的三个状态与边界条件写清楚。

## 38.2 三个状态与两个阈值

```
             失败率超阈值（且样本足够）
   ┌────────┐ ──────────────────────► ┌────────┐
   │ Closed │                          │  Open  │
   │ 正常放行 │ ◄────────────────────── │ 直接拒绝 │
   └────────┘   半开试探成功            └────────┘
        ▲                                   │
        │        OpenSeconds 到期            │
        │                                   ▼
        │                            ┌───────────┐
        └──────────────────────────── │ HalfOpen  │
              试探成功 → 回到 Closed    │ 放一个请求过去 │
              试探失败 → 回到 Open      └───────────┘
```

四个参数（都可配置，测试里调小到毫秒级）：

| 参数 | 含义 | 生产建议 |
|---|---|---|
| `MinimumSamples` | **样本足够才计算失败率**（避免"前 2 次都失败就熔断"） | 3~10 |
| `FailureRateThreshold` | 失败率阈值（0.5 = 一半失败就熔断） | 0.5 |
| `OpenSeconds` | 熔断持续多久后进入半开 | 30~60 秒 |
| `HalfOpenMaxAttempts` | 半开放几个请求试探 | 1 |

**为什么必须有 `MinimumSamples`**：没有它，应用刚启动时头两个请求失败
（比如 NAS 还在挂载）就会熔断，而"熔断"意味着接下来一段时间**碰都不碰 NAS** ——
于是本来只抖动 1 秒的问题被放大成 30 秒。

```csharp
public sealed class PhotoCircuitBreaker
{
    public CircuitState State { get; private set; } = CircuitState.Closed;
    public int ConsecutiveFailures { get; private set; }
    public int FailureCount { get; private set; }
    public int SuccessCount { get; private set; }

    /// <summary>是否允许这次请求真的去打后端。</summary>
    public bool ShouldAllow(DateTime now) { ... }

    public void RecordSuccess() { ... }
    public void RecordFailure(DateTime now) { ... }
}
```

## 38.3 关键设计：为什么时间要**传进来**

```csharp
// ❌ 内部读 DateTime.UtcNow → 测试只能真的 sleep(30 秒)
public void RecordFailure() { _openedAt = DateTime.UtcNow; }

// ✅ 时间由调用方传 → 测试推进"假时间"即可
public void RecordFailure(DateTime now) { _openedAt = now; }
```

这是**可测试性设计**里最有价值的一招：把"时间"变成参数，
故障恢复、状态迁移这类"需要等一段时间"的逻辑就能在**毫秒内**被完整验证。

```csharp
[Fact]
public void 熔断后经过OpenSeconds进入半开_试探成功则恢复()
{
    var breaker = new PhotoCircuitBreaker(minimumSamples: 3, failureRate: 0.5, openSeconds: 1);
    var now = new DateTime(2026, 1, 1, 0, 0, 0, DateTimeKind.Utc);

    for (var i = 0; i < 3; i++) { breaker.ShouldAllow(now); breaker.RecordFailure(now); }
    breaker.State.ShouldBe(CircuitState.Open);

    // 时间不够：仍然拒绝
    breaker.ShouldAllow(now.AddMilliseconds(500)).ShouldBeFalse();

    // 推过 OpenSeconds：进入半开，放行一个
    breaker.ShouldAllow(now.AddSeconds(2)).ShouldBeTrue();
    breaker.State.ShouldBe(CircuitState.HalfOpen);

    // 半开试探成功 → 回到 Closed
    breaker.RecordSuccess();
    breaker.State.ShouldBe(CircuitState.Closed);
}
```

> 注意这个用例**全程没有 `Thread.Sleep`** —— 它跑完只要几毫秒。
> 如果用内部时钟，同样的场景要等 1 秒以上（`OpenSeconds` 调小到 1 也只能这样），
> 而 `OpenSeconds` 在生产上是 30~60 秒。

## 38.4 半开状态的竞态（最容易做错的地方）

半开时"只放一个请求过去"，但如果多个线程同时到达呢？

```csharp
// ❌ 错误：多个线程都会看到 HalfOpen 然后全部放行
public bool ShouldAllow(DateTime now)
{
    if (State == CircuitState.Open && now >= _openedAt.AddSeconds(_openSeconds))
        State = CircuitState.HalfOpen;
    return State != CircuitState.Open;      // HalfOpen → true（所有请求都放行）
}

// ✅ 正确：半开期间只放一个，其余仍然拒绝
private bool _halfOpenProbeInFlight;

public bool ShouldAllow(DateTime now)
{
    lock (_gate)
    {
        if (State == CircuitState.Open)
        {
            if (now < _openedAt.AddSeconds(_openSeconds)) return false;   // 还在熔断期
            State = CircuitState.HalfOpen;
            _halfOpenProbeInFlight = false;
        }

        if (State == CircuitState.HalfOpen)
        {
            if (_halfOpenProbeInFlight) return false;   // 已经有一个在试探了
            _halfOpenProbeInFlight = true;
            return true;
        }

        return true;   // Closed
    }
}
```

不这么做的话，"恢复瞬间被打垮"这个问题会在**熔断器自己身上重演**：
NAS 刚活，积压的几百个请求同时进入半开全部放行。

## 38.5 舱壁与超时：另外两道闸门

熔断器管"后端整体是否可用"，另两个管"单个请求别拖死别人"：

```csharp
// 舱壁（Bulkhead）：最多 4 个并发写 NAS —— 与上传服务共用一个闸门
private readonly SemaphoreSlim _bulkhead = new(initialCount: bulkheadSize);

// 超时：单次写 NAS 最多 10 秒，超了就当失败（交给熔断器统计）
using var cts = CancellationTokenSource.CreateLinkedTokenSource(cancellationToken);
cts.CancelAfter(_timeout);
```

**为什么需要舱壁**：如果 NAS 变慢（不是挂掉，而是延迟从 10ms 变成 2 秒），
熔断器不会打开（因为请求最终都成功了），但**Web 的线程池会被慢慢占满**。
舱壁限制并发数，让"慢"不会蔓延成"整个应用没响应"。

> 这三个参数（`BulkheadSize` / `TimeoutSeconds` / 熔断三件套）
> 在 `appsettings.json` 里都有，测试里被调到很小以便在毫秒级观察故障链路。

## 38.6 一个容易忽略的细节：熔断期间探活**不**该做

`ResilientPhotoStorage` 里有一处注释值得抄下来：

```
// NAS 不可用时它会自动落本地降级区并标记 Degraded，
// 由补偿任务在 NAS 恢复后连同原图一起回放。
// 因此这里**不需要**先探活 NAS —— 探活是"把降级区的东西搬回 NAS"才需要的判断。
```

也就是说：写入路径**不要**先 `ProbeAsync()` 判断"NAS 活着吗"再决定写哪。
理由：

- 多一次网络往返（NAS 慢时它本身就要等超时）；
- **探活成功不代表写入成功**（磁盘满、权限问题），反过来也一样；
- 直接写、失败了降级，是最短的判断链，也最真实。

## 38.8 本章要点

1. 熔断的三个状态 + **`MinimumSamples`**（避免冷启动误熔断）。
2. **时间作为参数传进来**，故障恢复逻辑才能在毫秒级被验证。
3. 半开时**只放一个请求**，否则"恢复瞬间被打垮"会在熔断器内部重演。
4. 舱壁（限并发）与超时是熔断之外的另外两道闸门，解决"慢"而不是"挂"。
5. 写路径**不要先探活**：直接写、失败降级，判断链最短也最真实。
