# 27 导入导出中心：逐行容错与"一个都不能少"

> 对应代码：`src/Xjgl.Domain.Shared/Text/Csv.cs`、
> `src/Xjgl.Application/Students/StudentImportExportAppService.cs`
> 对应测试：`test/Xjgl.Domain.Tests/Text/CsvTests.cs`、
> `test/Xjgl.Application.Tests/Students/StudentImportExportTests.cs`

## 27.1 要解决的问题

开学季学校要把几百名学生一次性建籍。这条需求看着简单，但有四个必须做对的点：

| 问题 | 做错的后果 |
|---|---|
| 一行数据错了，整批要不要失败？ | 整批失败 → 老师要一行行找错，几百行数据反复重传 |
| 错误提示怎么写？ | 只说"导入失败"，等于让老师拿着几百行数据自己猜 |
| 导入要不要复用"手工录入"的校验？ | 不复用 → **导入成了绕过校验的后门**（身份证校验位、跨校查重、生僻字规则全失效） |
| 导出看到的数据和界面一致吗？ | 不一致 → "界面看不到、导出却拿得到"的越权，或者"界面筛了、导出是全量" |

## 27.2 第一步：先写一个纯函数的 CSV 读写（`Csv`）

导入导出的格式问题上，社区方案要么太重（引 Excel 库，还得处理 `.xlsx` 的样式），
要么太随意（`string.Split(',')`，遇到地址里的逗号就崩）。本项目**手写一个纯函数 CSV 工具**放在 `Domain.Shared`：

```csharp
public static class Csv
{
    public static List<string[]> Parse(string? text);                                  // 解析（RFC4180 引号规则 + 去 BOM）
    public static string Write(IEnumerable<IEnumerable<string?>> rows);                 // 生成
    public static string WriteForExcel(IEnumerable<IEnumerable<string?>> rows);         // 生成（带 UTF-8 BOM）
    public static Dictionary<string, int> BuildHeaderIndex(string[] header);            // 表头名 → 列下标
    public static string? Cell(string[] row, Dictionary<string, int> header, string columnName);
}
```

四个细节：

1. **带 BOM 的 `WriteForExcel`**：不带 BOM 的 UTF-8 CSV，用 Excel 打开就是乱码。
   这一条不做，用户第一反应就是"你这系统导出的文件坏了"。
2. **`Parse` 要去掉 BOM**：别人用 Excel 另存为 UTF-8 CSV 时同样会带 BOM —— 不去掉，第一列名就变成 `\uFEFF姓名`，按名字取列全部失败。
3. **按表头名取列，不按列序**：Excel 里插一列、调一下顺序太常见了。
4. **RFC4180 引号规则**：地址里的逗号、换行、双引号都要能正确往返。

单元测试（14 个用例）覆盖：引号内逗号/换行/转义引号、空字段、BOM、行尾差异（`\r\n` / `\n`）、
缺列时不抛异常而是返回 null。

## 27.3 第二步：接口设计

```csharp
public interface IStudentImportExportAppService : IApplicationService
{
    string GetImportTemplate();                              // 模板（含表头 + 一行示例）
    List<ImportColumnDto> GetColumns();                      // 列说明（前端做字段提示）
    Task<ImportStudentsResultDto> ImportAsync(ImportStudentsDto input);
    Task<string> GetExportAsync(StudentQueryDto input);      // 导出 CSV 文本
}
```

导入结果的 DTO 是**逐行**的：

```csharp
public class ImportStudentsResultDto
{
    public int Total { get; set; }
    public int Succeeded { get; set; }
    public int Failed { get; set; }
    public List<ImportRowErrorDto> Errors { get; set; } = new();   // 第几行 + 原因
    public string Message { get; set; } = default!;                 // "共 2 条：全部导入成功。"
}
```

**必须把每一行的失败原因带回前端**：只告诉用户"导入失败"等于让他拿着几百行数据自己找问题。
实测的错误提示长这样（这是真实运行输出）：

```
第 2 行 端到端导入甲：身份证号的出生日期段不合法
第 3 行 端到端导入乙：身份证号校验位不正确
```

## 27.4 第三步：导入必须复用 `CreateAsync`

这是整个模块**最重要的一条**：

```csharp
// 导入的核心是一个循环：逐行组装 DTO → 调 IStudentAppService.CreateAsync → 收集失败原因。
// **复用 CreateAsync 是刻意的**：导入必须与手工录入走完全相同的校验
// （身份证校验位、跨校查重、生僻字姓名规则、学籍辅号生成、数据范围），
// 否则"导入进来的数据"就成了绕过校验的后门。
```

于是导入自动获得了这些能力（**不用写一行额外代码**）：

- 身份证号校验位 + 15 位老号补齐；
- 跨校查重（同一身份证号在建籍时被拦住）；
- 生僻字姓名规则（不能含数字、长度按码点算）；
- 学籍辅号按校并发取号（第 22 章）；
- 数据范围（老师没法把学生导进自己看不见的学校）；
- 变更留痕（第 20 章：导入建的档同样产生建档流水）。

唯一的代价是性能：逐行串行调用比批量插入慢。这是**刻意的取舍**——
"导入的数据和手工录入的数据一样可靠"比"导入快 3 倍"重要得多。
数据量真正大时，正确的做法是"后台任务 + 分批 + 进度轮询"（见技术债），而不是绕过校验直接写库。

## 27.5 第四步：导出复用列表查询

```csharp
// 复用列表查询：它已经带了数据范围约束与码值翻译，
// 导出不能另起一套查询 —— 否则很容易出现"界面看不到、导出却能拿到"
var page = await _students.GetListAsync(BuildQuery(skip));
```

导出还有两个必须处理的限制：

### ① ABP 对单次 `MaxResultCount` 有硬上限（默认 1000）

```csharp
/// **ABP 对单次请求的 MaxResultCount 有硬上限（默认 1000）**，
/// 传更大的值会被方法参数校验直接拒掉（AbpValidationException）——
/// 因此导出不能"一次要 5000 条"，只能分页累积。
private const int ExportPageSize = 1000;
private const int ExportRowLimit = 5000;
```

这个坑我实际踩过：`MaxResultCount = 5000` 直接抛 `AbpValidationException`。

### ② 导出必须打掩码

导出的 CSV 会被转发、打印、放在共享盘上。因此导出里的身份证号是
`410102********4311`（复用 `MaskedIdCard`），而不是明文。

## 27.6 验证方法

### ① 单元测试（CSV 纯函数，14 个）

不需要数据库，直接测边界：引号、换行、BOM、缺列。

### ② 集成测试（11 个）

| 用例 | 断言 |
|---|---|
| 模板 | 有表头 + 一行示例，列数与列说明一致 |
| 正常导入 | `Total=2 / Succeeded=2`，列表里确实查得到 |
| 混入非法身份证 | `Succeeded=0 / Failed=2`，**每行都有可读原因** |
| 重复身份证号 | 第二行被查重拦住，提示含"已存在" |
| 学校标识码不存在 | 该行失败，其余行照常成功 |
| 导出 | 含表头、含数据、**身份证已掩码**、带 BOM |
| 导出受数据范围约束 | 外校账号导出拿不到别人的学生 |

### ③ 端到端验证（真实 HTTP）

本项目这一轮验证时真的跑了一遍导入导出，并**故意混入非法数据**看错误是否可读：

```bash
# 导入（合法 + 非法混排）→ 期望 200，且 errors 里能逐行说明原因
curl -X POST .../api/app/student-import-export/import -d '{"content":"..."}'
```

一个副产品：验证时我先用"随机数 + 字母 X"拼身份证号，结果**两行全被拒**，
提示分别是"出生日期段不合法"与"校验位不正确" —— 这不是 bug，反而是校验在工作的证据。
后来改成"算法生成校验位"才导入成功。

## 27.7 踩坑记录（这一章踩的坑最多）

| 现象 | 根因 | 教训 |
|---|---|---|
| **导出接口返回 405** | 方法名 `ExportAsync` **不以 `Get` 开头**，ABP 的自动 API 约定把它注册成了 **POST**，而前端是带查询串 GET 下载 | ABP 按方法名前缀决定 HTTP 动词；**进程内测试直接调方法，永远发现不了路由问题**。改名 `GetExportAsync` 后路由才是 `GET .../export`。这条催生了 `tools/audit-routes.mjs`（见下） |
| 前端调用路由写错却没人发现 | 同类问题还有第二处：照片批量删除 `DeleteManyAsync` → `DELETE /many`，前端却发 POST | 修完一处后做了一次**全量核对**（106 次前端调用 vs 真实 swagger），才发现第二处 |
| "0 项不匹配"是假绿灯 | 核对脚本第一版的正则匹配不了嵌套泛型（`http.get<PagedResult<T>>(...)`），把 20 次调用静默跳过 | **假绿灯比没有检查更危险**：现在脚本里有"解析数量必须等于文件里出现次数"的交叉断言 |
| 导出超 1000 条报 `AbpValidationException` | ABP 的 `MaxResultCount` 上限 | 分页累积；把上限写进常量与注释，别让下一个人再踩 |
| Excel 打开导出文件是乱码 | 没有 UTF-8 BOM | `WriteForExcel` 专门负责这件事 |
| 用 GBK 另存的 CSV 导入失败 | 前端用 `File.text()` 按 UTF-8 解码，GBK 字节变成替换字符 → 表头匹配失败 | 目前的提示是"导入文件缺少必需列"，用户看不出真正原因是编码（已记入技术债：应探测编码并明确提示） |

### 关于 `tools/audit-routes.mjs`

它的存在理由就是上面那个 405：

```
从 swagger.json 取真实路由与动词 → 逐个核对 web/packages/api/src/index.ts 里每一次调用
```

CI 里会跑。它守住的是一类**进程内测试根本覆盖不到**的问题：前后端"契约"层面的不一致。

## 27.8 真进度百分比（债 23）

后台化的直接后果是：用户点完按钮之后**什么都看不到**。批次 C 那会儿界面上只有
"排队中… / 正在生成…"两句文案，还有任务表里恒等于 0（或终值）的 `Processed`。

### 三种做法，只有一种是诚实的

| 做法 | 为什么不这么干 |
|---|---|
| 按**已用时间**估算百分比 | 任务比预期慢时显示"90%"卡十分钟，比预期快时突然跳完。**它会在最需要它的时候稳定骗人** |
| 不管什么种类都编一个百分比 | 同上，只是编得更随意 |
| **只报"真的产出到第几条"** | 有些种类结构上给不出中间进度 —— 那就**如实**没有百分比（界面显示"正在生成…"），而不是补一个数字 |

### 哪些种类有真百分比

| 有真百分比（分片产出） | 为什么 |
|---|---|
| `StudentCsv` / `ChangeApplyCsv` / `ChangeAuditCsv` / `UserCsv` / `UserProvisionCsv` | 分页累积（每页 1000，ABP 硬上限），每页之后上报一次 |
| `StudentRosterPdf` | 同样分页取数，每页之后上报一次 |
| `PhotoZip` | 逐张读文件写进压缩包，每处理一张报一次 |

| **没有**（如实显示"正在生成…"） | 结构原因 |
|---|---|
| `OrganizationCsv` | 一次 `GetSortedListAsync` 取全量 → 当场 `Csv.WriteForExcel` 一次成形，中间没有"产出到第几条"这个概念 |
| `CodeCsv` | 同上；而且它连一条"总数已知"的取数语句都没有 —— 条数是按类别逐个累加出来的，累加完也就写完了 |
| `StudentCardPdf` | 产物是**一张**卡片，`Total` 恒为 1，报"已处理 1 / 共 1"只是收尾时补一句废话 |

⚠ 照片打包还有一段**没有**进度：`LoadRowsAsync` 持续翻页直到取够 `MaxCount`
或数据耗尽，那一段在"台账几万条、可导出的只有几百张"时反而是最慢的。
它给不出分母（此刻连总共要打包多少张都不确定），所以如实显示"正在生成…"。

### 分母是"本次真的会写出去的行数"，不是"符合条件的总数"

这一条踩过：`StudentCsv` 会被 `MaxRows` 截断，拿"符合条件总数"当分母时，
截断场景下"已处理"**永远追不上**总数，界面上永远差最后几个百分点 ——
看起来就像卡住了，而任务其实早就产出完了。

所以每种都取 `min(总数, 该种类的上限)`。这样两条不变式天然成立：
`Processed <= Total`，且跑完时 `Processed == RowCount`。

### 节流：为什么不每行写一次库

10 万行 = 100 页 = 100 次 `UPDATE sys_export_task`，而它们与**生成本身**抢的
正是同一条数据库连接。结果是"加进度"这个纯展示功能反而拖慢了它要服务的那个操作。
照片打包更极端：逐张上报，500 张就是 500 次 UPDATE。

`ThrottledExportProgressSink` 的规则是**两个条件都满足才写**：

- 距上次落库 ≥ **2 秒**（前端轮询是 1.5 秒，比它更快就是纯浪费）；
- 又处理了 ≥ **1000 条**（与分页生成器本来的批次单位一致）。

例外是**第一次上报立刻写**：用户点了导出，界面上要尽快出现"已处理 1000 / 共 N"，
否则最前面那段（可能正是最慢的第一次查询）一直显示"正在生成…"，看起来就像没在跑。

节流状态放在**进程内**、没有加库表字段：判断"该不该写"只需要"上次写到哪儿、
什么时候写的"，落到库里只会多一次读 + 一次迁移 + 多实例竞争，换来的信息量为零。
代价说清楚：进程重启后节流窗口重来一次，表现为重启后第一次上报总会落库。

### 只写两列，不整行覆盖

进度每秒可能写一次，若用"查出实体、改两个字段、整行写回"，任务表就变成
"谁最后写谁赢"—— 用户这期间点的"取消"会被静默抹掉。
所以加了 `IXjglRepository.UpdateColumnsAsync`（只更新指定列，
走原生参数化 UPDATE，列名从属性名转蛇形）。

> 这一条上踩过两个坑，都记在实现里：**表名必须问 SqlSugar**
> （`SysExportTask` 没有 `[SugarTable]`，表名靠全局的 `UseSnakeCaseTableName`
> 配置转出来的；自己回落到类名会拼出 `sysexporttask` → `42P01`，
> 而进度上报把异常吞掉只记警告，表现成"进度永远不动"）；
> 以及 `SqlSugar.SqlParameter` 这个类型**不存在**，要用 `SugarParameter`。

### 前端：文案只能有一处实现

八个导出入口 + 任务中心对话框共用 `describeExportProgress`
（`web/packages/api/src/progress.ts`）。抽出来的主要理由不是"少写代码"，
而是**复制品对漏改免疫**：八份复制里必然有两份被忘掉，而那两处不报错、不变红，
只是永远显示旧文案。

它最关键的分支是**回退**：`total == 0` 或 `processed == 0` 时**绝不显示百分比**。
后端的 `Total` 在组织/微代码那几种里结构上就是 0，照算会得到 `Infinity`/`NaN`，
显示成「已处理 0 / 0（0%）」—— 一条**永远不动的进度条**，
用户看到它只会得出"卡死了"，然后关掉重来。

百分比一律**向下取整**：99.6% 显示 100% 会让用户以为好了、去点下载，
而那时产物还没落盘。

### 测试怎么证明进度是真的

⚠ **只看"任务最终成功"证明不了任何事**：`ExportTaskWorker` 收尾时有一行
`task.Processed = result.RowCount`，所以哪怕生成器一次都不上报，终值也是对的。

所以 `StudentCsvExportProgressTests` 分三层：

1. **记录用 sink**（确定性地）断言"每页之后各报一次"、"中途的值小于总数"、
   "最后一次等于实际行数"；
2. **真实 sink + 真实库**断言第一页之后确实落库了、且列级更新没把别的列抹掉；
3. **节流单独一组**：第一次立刻写、差 5 条且间隔未到时不写、攒够一批要写、
   只差几条时隔够了也要写（否则照片打包的进度会一直不动）。

> 还有一个测试侧的取舍值得记：要覆盖"跨页"就得超过一页的数据，
> 而生产页大小是 1000 —— 于是把**页大小做成可配置**
> （`Xjgl:Export:StudentCsvPageSize`、`Xjgl:Print:RosterPageSize`，
> 生产默认仍是 1000），测试里设成 5，7 条数据就走完同一个循环体。
> 这与 `Xjgl:Photo:ExportPageSize` 是同一条取舍。
