# 12 元数据驱动的权限（二）：动态权限定义

> **对应阶段**：P1 ｜ **预计耗时**：2 小时 ｜ **产出**：`[Authorize("Stu.Student.Create")]` 里的权限码能在运行期从数据库定义出来

---

## 12.1 要解决的问题（本章是全项目最"拧"的一处）

第 11 章把权限做成了数据库里的数据。紧接着就是一个硬矛盾：

| 事实 | 后果 |
|---|---|
| ABP 的 `PermissionDefinitionProvider.Define()` 是**同步**方法 | 里面不能用 `await`，不能查数据库 |
| 它在**应用启动时执行一次** | 启动时数据库里有什么，就定义了什么 |
| 而权限数据在数据库里 | 启动时要去读库 —— 但同步方法里不能异步读库 |

**如果直接查库会怎样**：SqlSugar 提供同步 API（`.ToList()`），
看似可以在 `Define()` 里同步查库。但那样做很危险：

- `PermissionDefinitionProvider` 在 **DI 容器构建期**就被调用，
  此时数据库连接、配置、日志可能都还没就绪；
- 一旦数据库连不上，`Define()` 抛异常 → **整个应用起不来**；
- 而"数据库暂时不可用"是完全可能发生的（第 10 章那个 Redis/MQ 的坑就是同类）。

**本项目的解法：两层缓存 + 失败降级。**

```
启动期                                    运行期
  │                                        │
PermissionDefinitionProvider          MyProfileAppService
  │  同步取快照                            │  同步取快照
  ▼                                        ▼
IModuleMetadataCache.GetSnapshot()  ← 同一个进程内缓存
  │
  ├─ 首次访问：从数据库加载（同步 API）
  ├─ 之后：直接返回内存快照
  └─ 读取失败：返回 Empty 快照（不抛异常）
```

**关键设计：读取失败返回空快照而不是抛异常。**
空快照意味着"这次启动没有业务权限定义" —— 应用能起来，
管理员登录后看不到业务菜单（第 06 章坑 2 说的就是这个现象）。
相比之下"应用起不来"严重得多。

## 12.2 动手步骤

### 步骤 1：快照的数据结构

```csharp
// src/Xjgl.Domain.Shared/Metadata/ModuleMetadataSnapshot.cs（放在 Shared 层）
public sealed class ModuleMetadataSnapshot

    public static readonly ModuleMetadataSnapshot Empty = new();
```

### 步骤 2：缓存接口与实现

```csharp
// Domain.Shared — 接口
public interface IModuleMetadataCache
{
    /// <summary>获取快照（首次访问时从数据库加载并缓存）。读取失败时返回空快照而不抛异常。</summary>
    ModuleMetadataSnapshot GetSnapshot();

    /// <summary>失效缓存，下次访问重新加载。</summary>
    void Invalidate();
}
```

```csharp
// src/Xjgl.SqlSugarCore/Metadata/SqlSugarModuleMetadataCache.cs — 实现（单例）
public class SqlSugarModuleMetadataCache : IModuleMetadataCache, ISingletonDependency
{
    private readonly ISqlSugarClientFactory _factory;      // ★ 注入工厂，不注入客户端
    private readonly ILogger<SqlSugarModuleMetadataCache> _logger;

    private ModuleMetadataSnapshot? _snapshot;
    private readonly object _sync = new();

    public ModuleMetadataSnapshot GetSnapshot()
    {
        if (_snapshot != null)
        {
            return _snapshot;          // 快路径：无锁返回
        }

        lock (_sync)
        {
            if (_snapshot != null)
            {
                return _snapshot;
            }

            try
            {
                // 同步查库：用一次性客户端，不占用请求作用域的连接
                using var client = _factory.Create();
                _snapshot = Load(client);
            }
            catch (Exception ex)
            {
                // ★ 读取失败不抛异常：让应用能起来，权限问题人工排查
                _logger.LogError(ex, "加载模块元数据失败，本次启动将没有业务权限定义。");
                _snapshot = ModuleMetadataSnapshot.Empty;
            }

            return _snapshot;
        }
    }

    public void Invalidate()
    {
        lock (_sync)
        {
            _snapshot = null;
        }
    }
}
```

**两个细节值得注意：**

1. **注入工厂而不是客户端**：这个类是**单例**，如果注入 Scoped 的 `ISqlSugarClientAccessor`
   就是 captive dependency（第 07 章的坑）。工厂是单例，可以从它临时 `Create()` 一个客户端。
2. **双检锁 + 快路径**：`GetSnapshot()` 在每次权限校验时都会被调用（高频），
   快路径必须无锁。

### 步骤 3：动态权限定义提供器

```csharp
// src/Xjgl.Application.Contracts/Permissions/DynamicPermissionDefinitionProvider.cs
public class DynamicPermissionDefinitionProvider : PermissionDefinitionProvider
{
    private readonly IModuleMetadataCache _cache;

    public DynamicPermissionDefinitionProvider(IModuleMetadataCache cache)
    {
        _cache = cache;
    }

    public override void Define(IPermissionDefinitionContext context)
    {
        var snapshot = _cache.GetSnapshot();

        if (snapshot.IsEmpty)
        {
            // 数据库还没建表/连不上：不定义任何业务权限，应用照常启动。
            return;
        }

        foreach (var subsystem in snapshot.Subsystems.OrderBy(s => s.Sort))
        {
            // 子系统不是权限，只是一个分组，因此这里用模块作为权限组
            foreach (var module in subsystem.Modules.OrderBy(m => m.Sort))
            {
                var group = context.AddGroup(
                    module.PermissionName,                 // 组名 = 模块权限名，如 "Stu.Student"
                    LocalizableString.Create<XjglResource>(module.Name));

                // 模块级权限（能否进入这个页面）
                var modulePermission = group.AddPermission(module.PermissionName);

                // 操作级权限（页面内的按钮）
                foreach (var action in module.Actions.OrderBy(a => a.Sort))
                {
                    var actionPermission = group.AddPermission(
                        action.PermissionName,
                        LocalizableString.Create<XjglResource>(action.Name));

                    // 声明父子关系：授了模块权限不等于授了操作权限，
                    // 但界面上会呈现为树形，便于批量勾选
                    actionPermission.AddChild(action.PermissionName);
                }
            }
        }
    }
}
```

注册（在 `Application.Contracts` 模块里）：

```csharp
Configure<AbpPermissionOptions>(options =>
{
    options.DefinitionProviders.Add<DynamicPermissionDefinitionProvider>();
});
```

### 步骤 5：当前用户的权限与菜单（真正被前端调用的地方）

`MyProfileAppService` **不走 ABP 的权限定义管理器**，而是直接从快照枚举 + 逐个问权限检查器：

```csharp
public async Task<MyProfileDto> GetAsync()
{
    var userId = CurrentUser.Id!.Value;
    var user = await _userManager.FindByIdAsync(userId.ToString())!;
    var roles = await _userManager.GetRolesAsync(user);

    var snapshot = _metadataCache.GetSnapshot();
    var permissionSet = await ResolvePermissionsAsync(snapshot);

    return new MyProfileDto
    {
        UserId = userId,
        UserName = user.UserName!,
        RealName = user.Name,
        Roles = roles.ToList(),
        Permissions = permissionSet.ToList(),        // 前端按这个控制按钮显隐
        Menus = BuildMenus(snapshot, permissionSet)  // 前端按这个注册路由
    };
}

/// <summary>逐个权限码问 ABP：授过没有。</summary>
private async Task<HashSet<string>> ResolvePermissionsAsync(ModuleMetadataSnapshot snapshot)
{
    var granted = new HashSet<string>(StringComparer.Ordinal);

    foreach (var permissionName in snapshot.AllPermissionNames)
    {
        if (await _permissionChecker.IsGrantedAsync(permissionName))
        {
            granted.Add(permissionName);
        }
    }

    return granted;
}
```

**为什么值得这样做**：ABP 自带的 `IPermissionAppService.GetAllPermissionsAsync()`
返回的是"已定义的权限" —— 但它的分组结构是给"权限配置页"用的，
不适合直接驱动菜单。这里自己构建 `MenuGroupDto`，
把"有权限才返回"这件事在服务端就做完 —— **前端拿不到没权限的菜单，也就无从渲染**。

## 12.3 验证方法

**① 权限定义真的生效**

```powershell
$token = (登录拿令牌)
$perm = curl.exe -s "http://localhost:44300/api/permission-management/permissions?providerName=R&providerKey=admin" -H "Authorization: Bearer $token"
```

返回里应该能看到 `Stu.Student.Create`、`Pho.Photo.Compensate` 等业务权限。

**② `/api/app/my-profile` 返回菜单与权限**

```powershell
curl.exe -s "http://localhost:44300/api/app/my-profile" -H "Authorization: Bearer $token"
```

期望：

```json
{
  "userName": "admin",
  "roles": ["admin"],
  "permissions": ["Sys.Module.Query", "Stu.Student.Create", "... 共 123 个"],
  "menus": [
    { "code": "Sys", "name": "系统管理", "children": [
        { "code": "Module", "name": "模块管理", "path": "/system/module",
          "component": "system/module/index", "actions": ["Sys.Module.Query", "..."] }
    ]}
  ]
}
```

**重点核对 `path` 与 `component`** —— 这两个字段直接决定前端能不能找到页面（第 46 章）。

**③ 停用模块后菜单消失**

```powershell
# 1) 把"照片管理"停用
curl.exe -s -X PUT "http://localhost:44300/api/app/module/<id>" -H "Authorization: Bearer $token" `
  -H "Content-Type: application/json" -d '{"subsystemId":"...","code":"Photo","name":"照片管理","isEnabled":false}'

# 2) 重新拉 profile：menus 里不该再有 Pho
curl.exe -s "http://localhost:44300/api/app/my-profile" -H "Authorization: Bearer $token"
```

**④ 权限校验真的拦得住**

```powershell

curl.exe -s -X POST "http://localhost:44300/api/photos/upload" -H "Authorization: Bearer $otherUserToken"
# 期望：403
```

## 12.4 踩坑记录

### 坑 1：全新数据库首次启动，admin 没有任何业务权限

见第 06 章坑 2 的完整复盘。一句话：**框架的授权发生在业务权限定义之前**，
必须在元数据种子写完后显式补授一次 admin。

### 坑 2：新增模块后必须重启才能用 `[Authorize]`

**这是当前实现的一个真实限制**，必须讲清楚：

- `_metadataCache.Invalidate()` 让**菜单**立刻生效
  （因为 `MyProfileAppService` 是每次请求重新读快照）；
- 但 `[Authorize("新模块.操作")]` 用的**权限定义**是启动时构建的，
  **新增的权限码在重启前不被认识** —— 表现为"接口对所有角色都返回 403"。

`MetadataPermissions.cs` 里的注释就是在提醒这件事：

> **新增业务模块时，权限码必须同时出现在这里和种子数据里**，
> 否则 `[Authorize]` 会引用一个不存在的权限（表现为所有人都被拒绝）。

**更好的做法**（P1 收尾要做）：ABP 10 提供**动态权限定义存储**
（`IDynamicPermissionDefinitionStore`，数据落在 `AbpPermissions` 表 ——
本项目的 EF 迁移里已经建好了这张表）。
把"运行期新增的模块权限"写进这个 store，就不需要重启。
改造点集中在 `ModuleAppService` 的写方法里：建完模块后顺手调
`IDynamicPermissionDefinitionStore.CreateAsync(...)`。

### 坑 3：在 `Define()` 里直接查库导致应用起不来

前面讲过。**规则：`Define()` 里只能拿已经准备好的内存数据。**

### 坑 4：忘了 `Invalidate()`，出现"要重启才生效"

菜单不刷新是最常见的投诉。排查方法：看 `ModuleAppService` 里每个写方法是不是都以
`_metadataCache.Invalidate()` 结尾。本项目在 10 处写方法里都加了 ——
**新增写方法时容易漏**。

更稳的做法是把它做到仓储的事件里（模块/操作变更即失效），
但那样会把缓存耦合进仓储。当前选择"显式调用 + 靠 review 保证"。

### 坑 5：`AllPermissionNames` 忘了包含模块级权限

如果只把操作权限放进 `AllPermissionNames`，
"只授了模块权限、没授任何操作权限"的用户会看不到菜单 ——
而模块权限本身就是"能看到这个页面"的意思。

本项目 `AllPermissionNames` 同时包含**模块权限名**与**操作权限名**。

## 12.5 本章产出

| 项 | 值 |
|---|---|
| 矛盾 | `Define()` 同步 + 启动执行一次 ↔ 权限在数据库里 |
| 解法 | 进程内快照缓存（同步读 + 首次加载 + 失败降级为空）+ 变更时显式失效 |
| 权限校验 | `[Authorize("Stu.Student.Create")]` 直接用元数据里定义的权限码 |
| 菜单驱动 | `MyProfileAppService` 自己构建菜单树，只返回有权限的 |
| 已知限制 | 新增模块的权限定义需**重启**才被 `[Authorize]` 认识；改进路径是 `IDynamicPermissionDefinitionStore` |
