# 48 照片批量上传的交互设计，与一个"只有浏览器能看见"的编码缺陷

> 对应代码：`web/apps/pc/src/views/photo/list/index.vue`、
> `web/apps/pc/src/views/student/list/index.vue`（导入）、
> `web/apps/pc/src/utils/csvEncoding.ts`
> 对应测试：`web/apps/pc/src/utils/csvEncoding.test.ts`（11 条）、
> `web/e2e/specs/03-photo.spec.ts`

## 48.1 要解决的问题

照片采集是**教师日常最重的操作**：一个班 50 个孩子，照片在手机/相机里，
文件名往往是乱的（`IMG_0001.jpg`）。所以交互设计要解决两个问题：

1. **文件名与学生怎么对上**（这是最容易张冠李戴的地方）；
2. **失败要逐条说清楚**（50 个文件里挂了 3 个，用户需要知道是哪 3 个）。

而 CSV 导入还有一个**只在浏览器里才会暴露**的编码问题 —— 那是本章最重要的一节。

## 48.2 第一步：上传交互的三个决定

### 决定一：**先匹配再上传**，而不是"传完再说"

```typescript
interface UploadRow {
  file: File
  studentNo: string      // 文件名去掉扩展名后当作学籍辅号
  studentId?: string
  studentName?: string
  matched: boolean
  note?: string
}
```

界面上的流程是：选文件 → **显示匹配结果表**（哪张对上了哪个学生）→
用户确认后再点"上传 N 张"。

**为什么这一步不能省**：照片装错人是**很难发现**的错误 ——
它不会报错，只会让某个孩子的档案里挂着别人的照片，可能到毕业才发现。
让人在匹配结果表上看一眼，代价是几秒钟。

### 决定二：匹配用"一次拉名单 + 兜底逐个查"

```typescript
// 先一次性拉「缺照片名单」在本校范围内建索引（绝大多数上传都是补齐缺照片的学生）
const missing = await photoApi.getMissingList({ schoolOrgId: uploadSchoolId.value, maxResultCount: 500 })
const index = new Map<string, MissingPhotoStudent>()
for (const student of missing.items) if (student.studentNo) index.set(student.studentNo, student)

// 未命中的再按学籍辅号逐个精确查（可能是"替换已有照片"）
for (const row of uploadRows.value.filter((r) => !r.matched && r.studentNo)) {
  if (!/^\d{10,20}$/.test(row.studentNo)) { row.note = '文件名不是学籍辅号'; continue }
  const found = await studentApi.getList({ schoolOrgId: uploadSchoolId.value, keyword: row.studentNo, maxResultCount: 5 })
  const exact = found.items.find((s) => s.studentNo === row.studentNo)
  // ...
}
```

这样 50 个文件通常只需要 **1 次**请求，而不是 50 次。

正则 `^\d{10,20}$` 提前挡掉"文件名明显不是辅号"的情况，
避免为 `IMG_0001` 这种名字去查库。

### 决定三：上传结果逐条展示

后端返回 `PhotoUploadItemResultDto`（第 39 章），前端照实展示：

```vue
<el-tag :type="!resultOf(row.studentId)!.success ? 'danger'
              : resultOf(row.studentId)!.degraded ? 'warning' : 'success'">
  {{ resultOf(row.studentId)!.success
       ? (resultOf(row.studentId)!.degraded ? '已暂存（待补传）'
          : resultOf(row.studentId)!.skipped ? '秒传（内容未变）' : '上传成功')
       : '失败' }}
</el-tag>
```

**四个状态都不能合并**：

| 状态 | 含义 | 为什么不能混 |
|---|---|---|
| 上传成功 | 已写 NAS | — |
| **已暂存（待补传）** | NAS 不可用，写到了本地盘 | 说成"成功"会让运维以为不用管 |
| **秒传（内容未变）** | 哈希一致，没重复写存储 | 用户会疑惑"我传了 50 张怎么只写了 2 张" |
| 失败 | 带原因 | 需要用户处理 |

## 48.3 第二步：缩略图的显示（为什么必须走 Blob）

照片接口要求 Bearer 令牌，而**浏览器发图片请求不会带 `Authorization` 头**。
所以不能写 `<img :src="/api/photos/.../thumbnail">` —— 那必然 401，
而表现是"表格里一片空白"（`<img>` 加载失败不会有任何提示）。

正确做法：用 axios 取回 Blob，再 `createObjectURL` 交给 `<img>`：

```typescript
async function loadThumbnails(rows: PhotoDto[]): Promise<void> {
  const wanted = rows.filter((r) => r.status === 'Normal' || r.status === 'FallbackPending')

  // ★ 换页时先释放上一页的对象 URL
  Object.values(thumbUrls.value).forEach((url) => URL.revokeObjectURL(url))
  thumbUrls.value = {}

  const next: Record<string, string> = {}

  await Promise.all(wanted.map(async (row) => {
    try {
      const blob = await photoApi.getThumbnail(row.studentId)
      next[row.studentId] = URL.createObjectURL(blob)
    } catch {
      // 单张取不到不影响整页（例如照片文件已从存储里消失）
    }
  }))

  thumbUrls.value = next
}
```

**`revokeObjectURL` 不能漏**：不释放的话，翻十几页就会一直占着几十 MB 内存。
这是"每页只泄漏一点"的典型，只有长时间使用才会暴露。

## 48.4 ★ 第三步：CSV 导入的编码问题（一个只有浏览器能看见的缺陷）

### 症状

教师用 Excel "另存为 CSV" 导出名单，然后在系统里导入，得到的提示是：

> 导入文件缺少必需列：姓名、性别…

于是他会反复检查列名、重排列顺序、甚至重装 Office。而**真正的原因是编码**：
Excel 的"另存为 CSV"默认用**本机编码**（简体中文 Windows 上是 GBK），
而导入接口只接受 UTF-8。

### 为什么不能"用 `File.text()` 读一下就行"

```typescript
// ❌ 原来的写法
const content = await file.text()      // ← 按 UTF-8 解码，GBK 文件会变成一串 U+FFFD
importResult.value = await studentImportApi.import(content)
```

`File.text()` 按 UTF-8 解码，GBK 的中文变成替换字符 `�`，
于是**表头"姓名"变成"��"** → 后端报"缺少必需列"。
用户看到的提示与真正原因毫无关系。

### 解法：先按**字节**探测编码

```typescript
// utils/csvEncoding.ts
export function probeCsvEncoding(buffer: ArrayBuffer): CsvEncodingProbe {
  const bytes = new Uint8Array(buffer)
  if (bytes.length === 0) return { ok: true, detected: '空文件', text: '' }

  if (startsWith(bytes, UTF8_BOM)) {
    // 剥掉 BOM：留着它会让第一列列名匹配不上（表现为「缺少必需列：姓名」）
    const body = bytes.subarray(UTF8_BOM.length)
    return { ok: true, detected: 'UTF-8（带 BOM）', text: new TextDecoder('utf-8').decode(body) }
  }

  if (startsWith(bytes, UTF16_LE_BOM) || startsWith(bytes, UTF16_BE_BOM)) {
    return { ok: false, detected: 'UTF-16 LE/BE', reason: '...请改用「CSV UTF-8（逗号分隔）」另存...' }
  }

  const check = validateUtf8(bytes)
  if (check.valid) return { ok: true, detected: 'UTF-8（无 BOM）', text: new TextDecoder('utf-8').decode(bytes) }

  const gbk = looksLikeGbk(bytes)
  return { ok: false, detected: gbk ? 'GBK / GB18030（本地编码）' : '未知的非 UTF-8 编码', reason: '...' }
}
```

### 为什么自己写 UTF-8 校验，而不用 `TextDecoder`

```typescript
// ❌ 能用，但报错信息没有定位能力
new TextDecoder('utf-8', { fatal: true })   // "The encoded data was not valid for encoding utf-8"

// ✅ 自己走一遍状态机，顺便能报"第 N 个字节不合法"
function validateUtf8(bytes: Uint8Array): { valid: boolean; badIndex: number } { /* RFC 3629 */ }
```

自己实现还带来一个额外能力：**识别 GBK**。GBK 的双字节首字节落在 `0x81~0xFE`，
与 UTF-8 的续字节规则冲突，所以很容易区分：

```typescript
function looksLikeGbk(bytes: Uint8Array): boolean {
  let gbkPairs = 0
  for (let i = 0; i < bytes.length; i += 1) {
    const b = bytes[i]
    if (b >= 0x81 && b <= 0xfe) {
      const next = bytes[i + 1]
      // GBK 第二字节：0x40~0xFE（去掉 0x7F）
      if (next !== undefined && next >= 0x40 && next <= 0xfe && next !== 0x7f) { gbkPairs += 1; i += 1 }
    }
  }
  return gbkPairs >= 2
}
```

于是界面能给出**可执行**的建议，而不是一句"导入失败"：

> 文件不是 UTF-8 编码（判定：GBK/GB18030，第 1 个字节处不合法）。
> Excel 的「另存为 CSV」默认使用本机编码，中文会变成乱码…
> 请在 Excel 里选择「CSV UTF-8（逗号分隔）」另存后再导入。

### 为什么"自动转码"是错的选择

把 GBK 自动转成 UTF-8 需要完整的 GBK 码表（几百 KB + 引一个库）。
更重要的是：**猜错编码比明确拒绝更糟** —— 猜错会静默产生**错误的姓名**入库，
而姓名错了要发现时已经打印过学籍卡了。明确要求 UTF-8 是一次性成本，
且模板本身带 BOM，用 Excel 打开再保存仍是 UTF-8。

### 11 条单元测试守住它

```powershell
cd web
pnpm test:unit
```

覆盖：纯 ASCII / UTF-8 无 BOM / UTF-8 带 BOM（**断言 BOM 被剥掉**）/
空文件 / GBK 被拒 / UTF-16 被拒 / 截断序列 / 过长编码（`0xC0 0x80`）/
代理区码点 / 高位首字节 / **4 字节生僻字正常放行**。

最后一条尤其重要：`𠮷`（`F0 A0 AE B7`）是 4 字节序列里最容易被"过长编码"规则误伤的一类 ——
而本系统专门为生僻字做了整条链路（第 24、25 章），导入当然不能挡它。

> **为什么用 `node --test` 而不是引 vitest**：被测代码是**纯函数、零依赖、零 DOM**，
> 为一个百来行的工具引一整套测试运行器 + 变换器不划算。
> Node 22.7+ 能直接跑 TypeScript（仅类型擦除），配上内置的 `node:test` 就够用，
> 且**新增依赖为零** —— 这也是它能进 CI 而不会成为维护负担的原因。
>
> 代价要在 tsconfig 里开 `allowImportingTsExtensions`：Node 的 ESM 解析**不补后缀**，
> 所以测试里必须写 `import ... from './csvEncoding.ts'`。

端到端里"缩略图能渲染出来"那条值得单独说：它**轮询 `naturalWidth > 0`**，
而不是断言 `<img>` 存在。因为 `<img>` 存在但加载失败是很常见的形态
（401、404、Blob 没建好），而 `naturalWidth` 才能证明**图真的解出来了**。

```typescript
await expect
  .poll(async () => img.evaluate((el) => (el as HTMLImageElement).naturalWidth))
  .toBeGreaterThan(0)
```

## 48.6 本章要点

1. 照片上传**先匹配再上传**，让人确认对应关系（装错人很难发现）。
2. 匹配策略：一次拉缺照片名单建索引 + 未命中逐个精确查（50 个文件 1 次请求）。
3. 四个结果状态（成功/已暂存/秒传/失败）**不能合并展示**。
4. 缩略图必须走 **Blob + `createObjectURL`**，并记得 `revokeObjectURL`。
5. CSV 导入必须先**按字节探测编码**：`File.text()` 会把 GBK 变成乱码，
   然后报出与真正原因无关的"缺少必需列"。
6. **自己实现 UTF-8 校验**（能报第几个字节不合法 + 能识别 GBK），
   给出可执行的建议；"自动转码"是错的（猜错会静默写坏姓名）。
7. 纯函数单测用 `node --test` 即可，零新增依赖；记得开 `allowImportingTsExtensions`。
