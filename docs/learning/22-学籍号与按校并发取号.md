# 22 学籍号与按校并发取号：为什么不用 GUID，也不用 count+1

> 对应代码：`src/Xjgl.Domain.Shared/Students/StudentNumberRule.cs`、
> `src/Xjgl.Domain/Sequences/SysSequence.cs`、
> `src/Xjgl.SqlSugarCore/Sequences/SqlSugarSequenceService.cs`、
> `src/Xjgl.Application/Students/StudentAppService.cs` 的 `GenerateStudentNoAsync`
> 对应测试：`test/Xjgl.Domain.Tests/Students/StudentNumberRuleTests.cs`、
> `test/Xjgl.Application.Tests/Sequences/SequenceServiceTests.cs`

## 22.1 要解决的问题

学籍辅号（省级/校级学籍号）必须满足四个条件：

1. **全局唯一** —— 重号意味着两个学生的档案混在一起，是最严重的数据事故；
2. **可读、可排序** —— 老师要能一眼看出"这是哪个学校的几号学生"；
3. **按学校自增** —— 每所学校从 1 开始，互不干扰；
4. **并发安全** —— 开学季几十所学校同时批量导入，不能发出重复号。

先把三个"看起来能用"的方案排除掉：

| 方案 | 为什么不行 |
|---|---|
| GUID / 雪花 Id | 唯一且并发安全，但**不可读**：老师要拿它核对纸质材料，"3f2a9c1e-…" 没法用 |
| `SELECT count(*) + 1` | 并发下必然重号（两个事务读到同一个 count）；软删除后还会**回收旧号**，把已发出去的号再发一次 |
| 每所学校建一个 PostgreSQL `SEQUENCE` | 并发安全，但要在运行期 `CREATE SEQUENCE`（DDL），每加一所学校就要建一个对象；备份恢复、权限、迁移都会变得难缠 |

本项目用的是**号段表 + 建议锁**：一张 `sys_sequence` 表存所有号段，按名字区分。

## 22.2 第一步：把学籍号规则做成可配置的纯函数

`StudentNumberRule`（放在 `Domain.Shared`，前后端都能用）：

```csharp
/// 默认规则：{SchoolCode:10}{Seq:6} —— 共 16 位
public const string DefaultTemplate = "{SchoolCode:10}{Seq:6}";
```

- `SchoolCode`：**学校标识码**（教育事业统计的机构标识码），10 位，其前 6 位就是行政区划码，
  所以天然满足"行政区划 + 学校代码"的编码习惯；
- `Seq`：按学校维度**永久自增**的流水号，6 位 ⇒ 单校容量 100 万。

唯一性推导很简单：**学校标识码全国唯一 × 校内流水唯一 ⇒ 全局唯一**。

规则解析成"段"的列表，于是"改规则"变成改一个设置项 `Xjgl.StudentNumberRule`，不改代码：

```csharp
var template = await _settingProvider.GetOrNullAsync(XjglSettings.StudentNumberRule);

if (!StudentNumberRule.TryParse(template, out var rule, out _) || rule == null)
{
    rule = StudentNumberRule.Default;   // 配置坏了也别让建籍失败
}
```

> **注意区分两个"学籍号"**：全国学籍号（`G` + 身份证号，19 位）由全国系统分配，
> 本系统**只存储不生成**（`StuStudent.NationalStudentNo`）；本规则的产物是省级/校级**学籍辅号**。

## 22.3 第二步：号段表

```csharp
/// 通用取号器（号段表）。用途：学籍辅号、异动申请单号、导入批次号…
/// 为什么不追求连续：并发取号必须避免锁竞争，允许跳号；
/// 唯一性由数据库行锁保证，不依赖应用层。
public class SysSequence : FullAuditedAggregateRoot<Guid>, IXjglBusinessEntity
{
    public string Name { get; set; } = default!;   // 号段名称，如 STU_NO:{学校标识码}
    public long CurrentValue { get; set; }          // 已取到的最大号
    public int Length { get; set; }                 // 仅供展示与预警（接近 999999 时提示扩容）
}
```

学籍号的号段名是 `STU_NO:{学校标识码}` —— **按学校分段**正是"每校从 1 开始"的实现方式。

## 22.4 第三步：取号实现（整个功能的核心）

`SqlSugarSequenceService.NextRange` 用三步完成"按需建行 + 自增取值"，全在一个事务里：

```csharp
var ownsTransaction = !client.Ado.IsAnyTran();

if (ownsTransaction)
{
    client.Ado.BeginTran();
}

// 1) 号段名建议锁（事务结束自动释放）：同名的并发调用在这里被串行化
client.Ado.SqlQuery<object>(
    "SELECT pg_advisory_xact_lock(hashtext(@Name))",
    new { Name = name });

// 2) 号段行不存在则插入
client.Ado.ExecuteCommand(
    "INSERT INTO sys_sequence (id, name, current_value, length, is_deleted, creation_time, concurrency_stamp) " +
    "SELECT @Id, @Name, 0, @Length, false, now(), @Stamp " +
    "WHERE NOT EXISTS (SELECT 1 FROM sys_sequence WHERE name = @Name AND is_deleted = false)",
    new { Id = Guid.NewGuid(), Name = name, Length = length, Stamp = Guid.NewGuid().ToString("N") });

// 3) 原子自增并返回新值
var rows = client.Ado.SqlQuery<long>(
    "UPDATE sys_sequence SET current_value = current_value + @Count " +
    "WHERE name = @Name AND is_deleted = false " +
    "RETURNING current_value",
    new { Name = name, Count = count });
```

四个细节都不是可选的：

| 细节 | 为什么 |
|---|---|
| `pg_advisory_xact_lock(hashtext(name))` | **事务级**建议锁：同名串行、不同名（不同学校）互不阻塞，且事务结束自动释放，不会出现"锁没释放"的僵尸状态 |
| `INSERT ... WHERE NOT EXISTS` | 号段行按需创建，第一所学校第一次建籍时自动出现，不需要预置数据 |
| `UPDATE ... RETURNING` | 一次往返完成"加值 + 读取"，不需要再查一次（少一次竞态机会） |
| **显式带上 `concurrency_stamp`** | ABP 实体的该列是 `NOT NULL`，但**原生 SQL 不走审计拦截器**，不会自动补 —— 漏了就是一条 `null value in column "concurrency_stamp" violates not-null constraint` |

### 事务归属：外部有事务时不要自己提交

```csharp
var ownsTransaction = !client.Ado.IsAnyTran();
```

如果调用方（比如批量导入）已经开了一个事务，取号就必须**加入**它，而不是自己 `Commit`——
否则会把调用方的事务提前提交掉，后面任何一步失败都无法回滚。

### 允许跳号

事务回滚时已取出的号会作废（比如取号后校验失败）。这**符合学籍号的业务预期**：
唯一即可，不要求连续。如果强求连续，就必须用更重的锁（表锁），并发性能会显著下降。

## 22.5 第四步：调用处

```csharp
private async Task<string> GenerateStudentNoAsync(SysOrg school)
{
    var template = await _settingProvider.GetOrNullAsync(XjglSettings.StudentNumberRule);
    if (!StudentNumberRule.TryParse(template, out var rule, out _) || rule == null)
    {
        rule = StudentNumberRule.Default;
    }

    var sequence = _sequenceService.NextValue($"STU_NO:{school.Code}", length: 6);

    try
    {
        return rule.Format(school.Code, sequence);
    }
    catch (InvalidOperationException ex)
    {
        // 例如流水号超过 6 位（单校超过 100 万学生）—— 这是配置/数据问题，必须明确报出来
        throw new BusinessException(XjglDomainErrorCodes.StudentNumberGenerateFailed)
            .WithData("reason", ex.Message);
    }
}
```

注意流水号**超长时报错而不是截断**：截断会直接造成重号。

## 22.6 验证方法

### ① 单元测试钉住规则本身

| 用例 | 期望 |
|---|---|
| 默认模板 | `TotalLength == 16` |
| `{SchoolCode:10}{Seq:6}` 格式化 | `4101020001` + `1` → `4101020001000001` |
| 支持固定文字 | 如 `41-{Seq:6}` 这类模板能正确解析 |
| 非法模板 | `TryParse` 返回 false 并给出原因 |

### ② 并发取号必须真的并发测

```csharp
// 并行取 100 个号，断言"没有重号、且都 > 0"
var results = await Task.WhenAll(Enumerable.Range(0, 100)
    .Select(_ => Task.Run(() => _sequenceService.NextValue(segmentName))));

results.Distinct().Count().ShouldBe(results.Length);
```

这条用例是**唯一能证明取号正确**的方式：单线程顺序取号，任何实现都不会重号。

### ③ 端到端验证

```bash
# 同一所学校连建 3 个学生，辅号应当是连续的（中间没有别人取号时）
# 期望：4101020001000001 / 4101020001000002 / 4101020001000003
```

## 22.7 踩坑记录

| 现象 | 根因 | 教训 |
|---|---|---|
| `null value in column "concurrency_stamp" violates not-null constraint` | 原生 SQL 插入不经过 ABP 的审计/并发戳拦截器 | 用原生 SQL 写 ABP 实体表时，审计列、软删列、并发戳都要自己补 |
| 取号把调用方的事务提前提交 | 没有判断"我是否拥有这个事务" | 任何会开事务的基础设施服务，都要先判断事务归属（`IsAnyTran()`） |
| 想用 `count(*) + 1` 图省事 | 并发重号 + 软删后回收旧号 | 号段必须**单调递增**，绝不回收 |
| 流水号溢出后截断 | "反正 100 万够用" | 溢出必须报错：截断等于重号，而重号是最严重的数据事故 |
