# 15 年级与班级：为什么它们不在组织树里

> **对应阶段**：P1 ｜ **预计耗时**：1.5 小时 ｜ **产出**：一套"稳定组织 + 学年维度"的两层建模

---

## 15.1 要解决的问题

初学者设计学籍系统时最常见的错误是把年级班级也挂进组织树：

```
某小学
 ├ 一年级
 │  ├ 一班
 │  └ 二班
 └ 二年级
```

**第一年看起来很好，第三年就崩了。** 因为每年 9 月：

- 一年级变成二年级，二年级变成三年级……如果节点是"年级"，
  要么改节点的名字（那历史数据全乱），要么每年新建一套（树无限膨胀）；
- 毕业班的节点永远留着（挂着一批已毕业学生），树的叶子会越来越多；
- "数据范围"判断变得极其复杂：某个老师能看"三年级的全部班级"，
  而"三年级"每年指向的不是同一批人。

**根因**：年级班级是**学年维度的数据**，组织树是**组织结构**。
前者每年重建，后者几年才动一次。把它们混在一起，就是把"会变的"和"不常变的"绑死了。

---

## 15.2 两层建模

```
第一层：组织结构（稳定，几年才动一次）
   省厅 → 市局 → 县局 → 学校          sys_org

第二层：学年维度（每年重建，随学年滚动）
   学校 + 学年 → 年级 → 班级           sys_grade / sys_class
```

于是：

| 问题 | 用哪一层回答 |
|---|---|
| "这个学生属于哪个学校？" | `stu_student.school_org_id` → 第一层 |
| "这个老师的账号能看哪些学生？" | 第一层（组织树 + 数据范围） |
| "本学年三年级的班级有哪些？" | 第二层（`school_org_id` + `academic_year`） |
| "三年前三年级的学生现在在哪？" | 第二层的历史学年数据 + 学生自己的 `academic_year` |

**关键点：数据范围只看第一层。** 学校内部的年级班级划分不影响"能看哪些学校的数据"，
这样权限判断永远简单。

## 15.3 实体设计

```csharp
public class SysGrade : FullAuditedAggregateRoot<Guid>, IXjglBusinessEntity
{
    public Guid SchoolOrgId { get; set; }             // 属于哪个学校

    /// <summary>学年，如 "2025-2026"。年级是学年维度的数据，必须带学年。</summary>
    public string AcademicYear { get; set; } = default!;

    /// <summary>年级编码，如 1 / 2 / 3（或 G1/G2）。同一学校同一学年内唯一。</summary>
    public string GradeCode { get; set; } = default!;

    public string GradeName { get; set; } = default!; // 如 "三年级"

    public int Sort { get; set; }
    public bool IsEnabled { get; set; }
    public string? Remark { get; set; }
}

public class SysClass : FullAuditedAggregateRoot<Guid>, IXjglBusinessEntity
{
    public Guid SchoolOrgId { get; set; }
    public Guid GradeId { get; set; }                 // 属于哪个年级
    public string AcademicYear { get; set; } = default!;

    public string ClassCode { get; set; } = default!;
    public string ClassName { get; set; } = default!;  // 如 "三（1）班"
    public int Sort { get; set; }
    public bool IsEnabled { get; set; }
}
```

**冗余 `AcademicYear` 到班级上**是有意的：按学年查班级（"本学年所有班级"）是高频操作，
不用先 join 年级。代价是插入时要保证与年级的学年一致 —— 在应用服务里校验。

## 15.4 应用服务

```csharp
public interface IGradeClassAppService : IApplicationService
{
    Task<List<GradeDto>> GetGradesAsync(Guid schoolOrgId, string? academicYear = null);
    Task<GradeDto> CreateGradeAsync(CreateUpdateGradeDto input);
    Task<GradeDto> UpdateGradeAsync(Guid id, CreateUpdateGradeDto input);
    Task DeleteGradeAsync(Guid id);

    Task<List<ClassDto>> GetClassesAsync(Guid gradeId);
    Task<ClassDto> CreateClassAsync(CreateUpdateClassDto input);
    // ...
}
```

路由（ABP 约定式）：`GET /api/app/grade-class/grades/{schoolOrgId}`。

### 三条业务规则

| 规则 | 为什么 |
|---|---|
| 同一学校 + 同一学年内，年级编码唯一 | 否则"三年级"会出现两个 |
| 班级的学年必须与所属年级一致 | 冗余字段的一致性由应用层保证 |
| 年级下还有班级时不允许删除 | 与组织树同样的守卫思路 |

## 15.5 升级与毕业：本学年结束后怎么滚动

这是两层建模之后**必然要面对**的问题：9 月开学时，全校学生要"升一级"。

**本项目的现状：这个功能还没做**（在方案文档里列为 P2 收尾项）。它的设计要点是：

1. **不能直接改学生的年级** —— 那会把上一学年的历史数据改掉；
2. 正确做法是**批次任务**：`预演（生成变更清单）→ 执行（写新学年记录）→ 可回滚`；
3. 同时处理三类人：正常升级、毕业（状态改为"毕业"）、留级/休学复学。

**为什么先不做也不影响使用**：学年滚动每年只发生一次，
且完全可以由开学前的一次数据初始化完成；而把它做错的代价（历史数据被改写）很高，
所以值得单独设计、单独测试。**这属于"知道该怎么做、但排在后面"的功能，
而不是"没想到"。**

## 15.6 验证方法

**① 学年维度隔离**

```powershell
# 在同一个学校下，为两个学年各建一个"三年级"
POST /api/app/grade-class/grade { "schoolOrgId":"...", "academicYear":"2024-2025", "gradeCode":"3", "gradeName":"三年级" }
POST /api/app/grade-class/grade { "schoolOrgId":"...", "academicYear":"2025-2026", "gradeCode":"3", "gradeName":"三年级" }
# 期望：两条都能建成功（学年不同）

GET /api/app/grade-class/grades/<schoolOrgId>?academicYear=2025-2026
# 期望：只返回新学年的那一批
```

**② 建班与守卫**

```powershell
POST /api/app/grade-class/class { "gradeId":"...", ... }
DELETE /api/app/grade-class/grade/<有班级的年级 id>
# 期望：拒绝
```

## 15.7 踩坑记录

### 坑 1：班级名重复（"一班"）

不同年级都有"一班"，如果只按 `ClassName` 判重会误判。
**判重必须带维度**：`SchoolOrgId + AcademicYear + GradeId + ClassCode`。

### 坑 2：把年级塞进组织树

见 15.1 的分析。**判断标准**：
如果一个东西"每学年都会重建"，它就属于第二层。

### 坑 3：学生表上的 `AcademicYear` 与年级的学年不一致

学生主表自己有 `AcademicYear`（第 21 章），年级也有。
如果两者不一致（例如学生转学后学年没更新），会出现"学生在 2025-2026 学年，
却挂在 2024-2025 的三年级下"这种脏数据。

**处理**：学生新增/异动时校验两者一致；这也是学生子表与异动模块要一起考虑的点。

### 坑 4：以为"升级"就是改个数

升级涉及历史数据、毕业状态、留级、复学等多种情况，
一次操作的错误会影响一整个年级的学生。**必须做成可预演、可回滚的批次任务。**
