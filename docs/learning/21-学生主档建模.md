# 21 学生主档建模：字段从哪来，为什么这么切

> 对应代码：`src/Xjgl.Domain/Students/StuStudent.cs`、
> `src/Xjgl.Application.Contracts/Students/StudentDtos.cs`、
> `src/Xjgl.Application/Students/StudentAppService.cs`
> 对应测试：`test/Xjgl.Application.Tests/Students/StudentAppServiceTests.cs`

## 21.1 要解决的问题

学生主档是这套系统里**字段最多、牵涉面最广**的一张表。动手之前先回答四个问题：

| 问题 | 本项目的答案 |
|---|---|
| 字段从哪来？ | 按《教育管理信息 普通中小学校管理信息》的**学生基本数据集**组织，不自己拍脑袋定字段 |
| 码值怎么存？ | 一律存**码值**（`01` / `1`），中文名由后端查微代码翻译 —— 绝不存 `"在读"` |
| 身份证号怎么存？ | **双字段**：`IdCardEncrypted`（AES 密文）+ `IdCardHash`（HMAC 摘要，用于唯一索引与查重） |
| 姓名里的生僻字怎么办？ | 全链路按 **Unicode 码点**处理，并有独立的字体链路（见第 24~25 章） |

## 21.2 第一步：把字段分组

`StuStudent` 的字段按用途分成六组，**组与组之间没有耦合**，读代码时一眼能看出"这个字段管什么"：

```csharp
public class StuStudent : FullAuditedAggregateRoot<Guid>, IXjglBusinessEntity
{
    // ---- 标识 ----    NationalStudentNo（全国学籍号）、StudentNo（学籍辅号）、ClassStudentNo、Name、FormerName、Pinyin
    // ---- 身份 ----    GenderCode、BirthDate、IdCardTypeCode、IdCardEncrypted、IdCardHash、NationCode、
    //                   CountryCode、PoliticalCode、NativePlace、BirthPlace、HouseholdNatureCode、HouseholdAddress
    // ---- 联系 ----    HomeAddress、CurrentAddress、PhoneNumber、PostalCode、Email
    // ---- 就学 ----    SchoolOrgId、SchoolPathCode、AcademicYear、GradeId、ClassId、EnrollDate、
    //                   EnrollTypeCode、StudyModeCode、SchoolLengthCode、StudentStatusCode
    // ---- 学生属性 ---- IsMigrantChild、MigrantTypeCode、IsLeftBehindChild、LeftBehindTypeCode、
    //                   IsPoor、IsDisabled、DisabilityCode、HealthCode
    // ---- 其它 ----    PhotoPath、SourceSystem、ExternalKey、Remark
}
```

三条约定：

1. **所有码值字段都以 `Code` 结尾**（`GenderCode`、`NationCode`…）。
   看到 `Code` 就知道"这个值要去微代码表里翻译"，不会误当文本用。
2. **学籍状态有常量类**（`StudentStatuses`），并提供 `IsInSchool(status)` 这样的**语义方法** ——
   统计在校生时不写 `status == "01" || status == "03" || status == "05"`，而是 `IsInSchool(s.StudentStatusCode)`。
3. **`SchoolPathCode` 是冗余字段**（学生的学校物化路径）。它不是"设计冗余"，而是**性能与安全**都要：
   数据范围过滤靠它做一次前缀比较（第 18 章），比每次 join 组织表便宜得多。

## 21.3 第二步：让"有没有照片"只有一个判据

```csharp
/// <summary>照片相对路径（存 NAS 上的路径，不存二进制）。</summary>
public string? PhotoPath { get; set; }
```

约定：**`stu_student.PhotoPath` 是"有没有照片"的唯一判据**，而不是"`stu_photo` 里有没有行"。
原因：缺照片名单要分页，而"没有行"这种判据在 SQL 里要写 `NOT EXISTS`，分页与计数都很别扭；
`PhotoPath IS NULL` 则是最普通的条件（见第 43 章）。

## 21.4 第三步：DTO 分两层

不要把实体直接当接口返回。本项目分两个 DTO，各自有明确用途：

| DTO | 用途 | 内容 |
|---|---|---|
| `StudentListItemDto` | 列表页 | 只放列表需要的字段（辅号、姓名、性别、年龄、学校/年级/班级名、状态名、**掩码身份证**、是否有照片） |
| `StudentDto : StudentListItemDto` | 详情页 | 继承列表项 + 其余字段 |

注意 `StudentDto` **继承** `StudentListItemDto`。这样做的好处是：前端"从列表点进详情"时字段是包含关系，
不会出现"列表里有、详情里没有"这种让人意外的缺口。

### 两个绝对不能出现在列表里的东西

```csharp
/// <summary>脱敏后的身份证号（保留前 6 后 4）。</summary>
public string? MaskedIdCard { get; set; }
```

- **身份证号明文**永远不出接口（只有掩码）；
- **实体本身**永远不出接口（否则 `IdCardEncrypted` 会被序列化出去）。

## 21.5 第四步：创建与更新分开处理

```csharp
public async Task<StudentDto> CreateAsync(CreateUpdateStudentDto input) { ... }

public async Task<StudentDto> UpdateAsync(Guid id, CreateUpdateStudentDto input)
{
    // 原学校与目标学校都必须在自己范围内（防止把学生"改"到自己看不到的学校）
    await _guard.EnsureInScopeAsync(entity);

    var school = await EnsureSchoolAsync(input.SchoolOrgId);
    await _guard.EnsureOrgInScopeAsync(school, "该学校不在您的数据范围内，不能把学生转到该校");

    // 身份证号变了才需要查重（没变就不用白查一次）
    if (!string.Equals(entity.IdCardHash, idCardHash, StringComparison.Ordinal))
    {
        var duplicated = await _students.FindAsync(s => s.IdCardHash == idCardHash && s.Id != id);
        if (duplicated != null) { throw new BusinessException(XjglDomainErrorCodes.DuplicateIdCard)... }
    }
    ...
}
```

更新时有两条容易漏的规则：

1. **改学校要查两次范围**：原学校（学生现在在哪）+ 目标学校（要转到哪）。只查一个方向，
   就能把学生"改"到自己看不到的学校里去。
2. **身份证号变了才查重**：否则每次保存都要多一次全表查重。

## 21.6 第五步：表名与列名怎么来的

领域层**不引用任何 ORM**，实体上也没有任何 SqlSugar 特性。表名靠约定推导：

```
StuStudent  → stu_student
SysOrg      → sys_org
SysCodeItem → sys_code_item
```

推导规则集中在 `Xjgl.SqlSugarCore`（`EntityNameService` + `SqlSugarClientFactory`）。
好处是：换 ORM 只改集成层；领域模型可以纯粹地表达业务。

建表由 `DbMigrator` 调 SqlSugar CodeFirst 完成（第 06 章），
`IXjglBusinessEntity` 是"这张表由 SqlSugar 建"的标记接口：

```csharp
public class StuStudent : FullAuditedAggregateRoot<Guid>, IXjglBusinessEntity
```

`FullAuditedAggregateRoot<Guid>` 带来四样东西，建表时会自动落成列：

| 基类提供 | 列 |
|---|---|
| 审计 | `creation_time` / `creator_id` / `last_modification_time` / `last_modifier_id` |
| 软删除 | `is_deleted` / `deleter_id` / `deletion_time` |
| 并发戳 | `concurrency_stamp` |
| 主键 | `id`（Guid） |

> ⚠ 这些列是 **NOT NULL**（`concurrency_stamp` 尤其容易被忽略）。
> 一旦你用原生 SQL 插入数据，审计拦截器不会介入，必须自己补上（第 22 章有个真实例子）。

```bash
dotnet run --project src/Xjgl.DbMigrator

# 2) 用 psql 看列（业务表是 snake_case）
#    期望看到 id / student_no / name / id_card_encrypted / id_card_hash / school_path_code / is_deleted ...
```

集成测试（`StudentAppServiceTests`）覆盖的关键点：

| 用例 | 断言 |
|---|---|
| 新增学生 | 自动生成 **16 位**学籍辅号，且等于"学校标识码(10) + 流水号(6)" |
| 重复身份证号 | 抛 `DuplicateIdCard`，并把**已存在的学生姓名与辅号**带回提示 |
| 列表返回 | `MaskedIdCard` 形如 `410102********0011`，**不含明文** |
| 改学校 | 目标学校不在范围内 → `UserNotInDataScope` |

## 21.8 踩坑记录

| 现象 | 根因 | 教训 |
|---|---|---|
| 学生列表里"身份证号""照片"两列**一直是空的** | 前端类型里写的是 `idCardMasked` / `photoPath`，后端返回的是 `maskedIdCard` / `hasPhoto` | 前后端字段名不一致**不会报错**，只会显示空白。清单页要跟接口对一遍（本项目后来加了 `tools/audit-routes.mjs`，虽然它查的是路由不是字段，但思路一致：**契约要机器核对**） |
| 列表接口不带筛选条件时报 500 | 可选过滤条件拼出 `WHERE` 结尾的残缺 SQL（第 08 章的 `Where(null)` 坑） | 所有集成测试都带了筛选条件 → 没测过的输入组合就是没覆盖 |
| 属性名与中文名混淆 | 有人想直接把 `"在读"` 存进 `StudentStatusCode` | 存码值、翻译在后端；前端下拉框也别手写英文/中文值（本项目真的踩过：`Studying` 写进状态导致过滤永远返回空） |
