# 44 前端工程结构：为什么用 pnpm 工作区，以及共享包怎么划

> 对应代码：`web/package.json`、`web/pnpm-workspace.yaml`、
> `web/packages/api/src/`、`web/apps/pc/src/api/index.ts`
> 相关文档：`web/README.md`

## 44.1 要解决的问题

本系统有**三个前端**（PC / H5 / 未来的微信小程序），它们要访问**同一套后端接口**。
于是第一个决定就是：接口层要不要共享？

先看"不共享"会怎样。`types.ts` 有 700 多行类型定义（`StudentListItem`、`ChangeApply`、
`PhotoDto`…）。如果三端各存一份：

- 后端改一个字段名 → 必须记得改三处；
- 忘了改的那一端**不会编译报错**（后端返回的 JSON 里没有那个字段而已），
  表现是界面上显示空白或 `undefined`；
- 而"空白"几乎无法定位：类型检查是绿的、接口是 200、日志里没有异常。

这类缺陷正是"共享一份"能根除的。所以本仓库的结论是：
**API 层抽成工作区包 `@xjgl/api`，三端共用**。

## 44.2 工作区布局

```
web/
├─ pnpm-workspace.yaml
├─ package.json                 ← 根脚本（dev / build / test:e2e / test:unit / typecheck）
├─ packages/
│  └─ api/                      ← @xjgl/api：请求封装 + 类型 + 权限码 + 端点表
└─ apps/
   ├─ pc/                       ← @xjgl/pc：Vue3 + Element Plus（5173）
   └─ h5/                       ← @xjgl/h5：移动端（5174，hash 路由）
```

`pnpm-workspace.yaml` 决定哪些目录是工作区成员：

```yaml
packages:
  - 'apps/*'
  - 'packages/*'
```

依赖通过 `workspace:*` 引用：

```jsonc
// apps/pc/package.json
"dependencies": {
  "@xjgl/api": "workspace:*",     // ← 始终指向工作区内的源码，不是发布版
  ...
}
```

> **`workspace:*` 的好处**：改 `packages/api` 的源码**立刻**在 PC/H5 生效，
> 不需要 build、不需要 link、不会出现"两份副本版本不一致"。
> 代价是**发布时**要处理（本项目不发布，所以是纯收益）。

## 44.3 共享包里放什么：四条判据

不是"能共享就共享"。放进 `@xjgl/api` 的东西必须满足"三端语义完全一致"：

| 放进共享包 | 不放进共享包 |
|---|---|
| 请求封装（axios 实例、拦截器、令牌续期） | 页面组件（PC 用 Element Plus，H5 用移动端组件） |
| 后端 DTO 的 TypeScript 类型 | 路由表（PC 是元数据驱动，H5 是固定三页签） |
| 权限码常量（`MetadataPermissions`） | UI 状态（哪个抽屉打开着） |
| 接口路径表（`ENDPOINTS`） | 业务页面的默认筛选值 |
| 领域常量（`StudentStatDimensions` 等） | 格式化函数（各端展示习惯不同） |

判断标准一句话：**"如果在这里改了，另外两端是不是必须跟着改？"** 是则共享。

### 权限码必须共享的一个真实理由

`MetadataPermissions` 是"与后端 `MetadataPermissions` 一一对应"的字符串常量。
它在三端各存一份的话，后端加一个权限时必然出现"改了 PC 忘了 H5" ——
而症状是**那个按钮永远不显示，且不报任何错**。

```typescript
// packages/api/src/permissions.ts
export const MetadataPermissions = {
  Stu: { Student: { Query: 'Stu.Student.Query', /* ... */ } },
  Chg: { Apply: { Create: 'Chg.Apply.Create' /* ... */ } },
  Rpt: { Student: { Query: 'Rpt.Student.Query' } },   // 统计与列表是两套权限
} as const
```

文件头还写了一条维护约定：**后端改权限时请顺手搜这里**。

## 44.4 兼容壳：为什么 `apps/pc/src/api/index.ts` 只有一行

```typescript
// apps/pc/src/api/index.ts
export * from '@xjgl/api'
```

明明可以直接 `import { studentApi } from '@xjgl/api'`，为什么要留这个壳？

理由很实际：抽包之前 PC 端已经有**十几处** `import ... from '@/api'`。
一次性改十几处导入路径的风险（改漏、改错、IDE 重构失误）**大于**收益。
保留同名薄壳，业务代码**一行都不用改**，而 `/api` 这个别名在业务代码里读起来也更自然。

同样的壳还有 `apps/pc/src/constants/permissions.ts`、
`apps/pc/src/api/http.ts`（路由层要用 `setUnauthorizedHandler`）。

> 这是一个通用的迁移套路：**先抽包、再留壳、最后按需清理**。
> 直接"一刀切改所有导入"是这类重构里最常见的自伤方式。

## 44.5 三个容易踩的坑

### 1. VS Code 必须打开 `web` 目录，不能打开 `apps/pc`

依赖装在 `web/node_modules`（pnpm 工作区提升）。打开子目录会导致
TypeScript 找不到类型定义，**满屏红波浪线**，而 `pnpm typecheck` 却是绿的。

### 2. `pnpm` 不在 PATH 里时要走 corepack

Node 20+ 自带 corepack，`web/package.json` 里用 `packageManager` 把版本钉死，
因此**不需要全局安装 pnpm**：

```bash
corepack enable          # 之后 pnpm 就在 PATH 上了
corepack pnpm@9.15.0 install   # 或者一行显式指定版本，连 enable 都不用
```

如果所在环境的 PATH 不允许写入、或者你不想动全局 PATH（笔者的开发环境就属于这种），
可以把 shims 装到工作目录下的一个子目录里，再按需加进 PATH：

```powershell
corepack enable --install-directory .\.tools\corepack\shims
$env:PATH = "$PWD\.tools\corepack\shims;" + $env:PATH

pnpm --filter @xjgl/pc typecheck
```

### 3. `vite build` 在受限沙箱下会 `spawn EPERM`

esbuild 通过命名管道起服务进程，而受限沙箱禁止命名管道。
**这不是代码问题** —— 类型检查（`vue-tsc`）在受限环境下仍然可用，
构建需要放宽沙箱。识别方法：报错里是 `Error: spawn EPERM`
而不是任何业务错误。

## 44.6 根脚本：把常用命令收在一处

```jsonc
// web/package.json
"scripts": {
  "dev": "pnpm --filter @xjgl/pc dev",
  "dev:h5": "pnpm --filter @xjgl/h5 dev",
  "build": "pnpm --filter @xjgl/pc build",
  "typecheck": "pnpm -r typecheck",          // ← 递归，三端都查
  "test:unit": "pnpm --filter @xjgl/pc test:unit",
  "test:e2e": "playwright test --config e2e/playwright.config.ts"
}
```

`pnpm -r typecheck` 是关键：它保证**改了共享包之后三端都还在编译**。
只查 PC 的话，H5 里因为共享包改动而坏掉的地方不会被发现。

## 44.7 怎么验证

```powershell
cd web

# 三端类型检查（含共享包）
pnpm typecheck

# 前端单元测试（纯函数，用 node --test）
pnpm test:unit

# 端到端（PC + H5 两个 project）
$env:E2E_API_URL = 'http://127.0.0.1:44300'
pnpm test:e2e
```

## 44.8 本章要点

1. 三端共用 API 层：**改一个字段名不会漏改某一端**，这是共享的唯一理由。
2. 判断标准：「在这里改了，另外两端是否必须跟着改？」是则放进共享包。
3. 权限码必须共享 —— 漏一端的症状是"按钮永远不显示且不报错"。
4. 迁移时**留兼容壳**（`export * from '@xjgl/api'`），不要一刀切改导入。
5. VS Code 打开工作区根（`web`），不是子应用目录。
6. 受限沙箱下 `vite build` 会 `spawn EPERM`，而类型检查仍可用。
