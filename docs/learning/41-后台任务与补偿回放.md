> 对应代码：`src/Xjgl.Domain/Exporting/SysExportTask.cs`、
> `src/Xjgl.Application/Exporting/`、
> `src/Xjgl.HttpApi.Host/Exporting/ExportTaskWorker.cs`、

> 对应测试：`test/Xjgl.Application.Tests/Students/StudentImportExportTests.cs`、

## 41.1 要解决的问题

有几类操作**不能放在 HTTP 请求里做**：

| 操作 | 为什么不能同步 |
|---|---|
| 生成 500 人花名册 PDF | 渲染是 CPU 活，几十秒；浏览器会先超时 |
| 打包 1000 张照片 zip | 读大量文件 + 压缩；zip 全在内存里 |
| 生成缩略图 | 每张都要解码 + 缩放，是 CPU 活 |
| 把降级照片搬回 NAS | 依赖外部存储可用性，不能拖住上传 |

本项目的统一解法是**"任务式"**（对用户可见的产出）+ **"后台 worker"**（用户不可见的补齐）。
本章把这两条路讲清楚，重点是**那些"静默出错"的地方**。

## 41.2 第一步：用户可见的产出 → `sys_export_task`

统一的任务表（一份就够，不为每种导出建表）：

```csharp
public class SysExportTask : FullAuditedAggregateRoot<Guid>, IXjglBusinessEntity
{
    public string Kind { get; set; } = default!;        // 见 ExportTaskKinds
    public string Status { get; set; } = default!;      // Queued/Running/Succeeded/Failed/Canceled/Expired
    public string ParametersJson { get; set; } = default!;  // ← 条件快照

    public Guid RequestedByUserId { get; set; }
    public string? RequestedByName { get; set; }
    public string? RequestedByRoles { get; set; }       // ← 数据范围的依据

    public string? FileName { get; set; }
    public string? ContentType { get; set; }
    public string? RelativeArtifactPath { get; set; }
    public long FileSize { get; set; }

    public int Total { get; set; }                      // 符合条件的一共几条
    public int RowCount { get; set; }                   // 实际写进产出物的几条
    public bool IsTruncated { get; set; }               // 是否少人
    public string? Message { get; set; }
    public string? FailureReason { get; set; }

    public DateTime? ExpiresTime { get; set; }
}
```

三个字段是**安全和可解释性的核心**：

### `ParametersJson`：条件快照，而不是"再查一次"

任务入队时把查询条件序列化存下来。worker 执行时**用快照**，不重新解析请求。
理由：用户点了导出之后又去改了筛选条件，任务不该跟着变。

### `RequestedByRoles` / `RequestedByUserId`：worker 怎么知道"以谁的身份执行"

worker 里**没有当前用户**（没有 HTTP 请求上下文）。而数据范围必须按**发起人**算 ——
否则省厅的导出任务和县级的导出任务会产出同样多的数据。

所以入队时把用户 Id 与角色存下来，worker 执行时**重建身份**：

```csharp
// worker 里
using var scope = _scopeFactory.CreateScope();
var runner = scope.ServiceProvider.GetRequiredService<IExportTaskRunner>();
await runner.RunAsync(task);
```

> **为什么这很重要**：本仓库有一条实测证据 —— 县级账号提交的花名册 `total=10`，
// 而省厅账号提交同样的花名册 `total=40`。**证明 worker 确实以发起人的数据范围执行**。
> 如果 worker 用"无身份"执行，两者都会变成全量 —— 那是越权导出。

### `Total` / `RowCount` / `IsTruncated`：**少人必须说出来**

这是本模块最重要的一条产品规则。原来的实现只回"打了几行"，不回"一共有几行"，
于是超出 `MaxRows` 时少人在产出物里**没有任何痕迹**。

现在三个字段都如实落库，并且 message 写明差多少：

```
实际导出 5 行 / 共 10 行，已达导出上限（5 行未导出）
```

前端配合 `describeTruncation(task)` 用 `ElMessage.warning` **强制展示**
（而不是只弹一个绿色成功）：

```typescript
export function describeTruncation(task: ExportTask): string | null {
  if (!task.isTruncated) return null

  const missing = Math.max(0, task.total - task.rowCount)

  return `${task.kindName}已生成，但**只包含 ${task.rowCount} 条（共 ${task.total} 条，少 ${missing} 条）**。${task.message ?? ''}`
}
```

**为什么后端如实算了、前端还必须强制展示**：名单类产出少人是最不能接受的失败方式。
后端"如实交代"如果被前端变成一个绿色提示，那份如实就白做了。

## 41.3 第二步：worker 的四个必须有的性质

```csharp
public class ExportTaskWorker : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        // ① 首次延迟 + 固定间隔轮询（不是队列推送）
        await Task.Delay(initialDelay, stoppingToken);

        while (!stoppingToken.IsCancellationRequested)
        {
            try
            {
                await ProcessOnceAsync(stoppingToken);
            }
            catch (OperationCanceledException) when (stoppingToken.IsCancellationRequested)
            {
                // 正常停机
            }
            catch (Exception ex)
            {
                // ② ★ 绝不能把异常抛出去：BackgroundService 的异常会让**整个主机停机**
                _logger.LogError(ex, "[导出任务] 本轮执行异常，将在下个周期重试。");
            }

            await Task.Delay(interval, stoppingToken);
        }
    }
}
```

| 性质 | 不这么做的后果 |
|---|---|
| **吞掉所有异常** | .NET 6+ 里 `BackgroundService` 漏出的异常会**默认停掉整个主机** |
| 轮询间隔 ≥ 5 秒 | 空转查询把数据库打满 |
| 单轮限量（`LIMIT 5`） | 积压 1000 个任务时一次性全捞进内存 |
| 单调时间用 `IClock` | 过期清理逻辑偏一个时区 |

第三条在 SQL 里能直接看到：

```sql
SELECT ... FROM sys_export_task
WHERE NOT is_deleted AND status = @Status0
ORDER BY creation_time ASC LIMIT 5 OFFSET 0
```

## 41.4 第三步：产物存储与"下载只能本人"

产物写在服务端，文件名是**服务端生成的 GUID**（防猜测 + 防路径穿越）：

```csharp
// 产物路径 = {taskId:N}.{ext}
```

下载接口校验两件事：

```csharp
// ① 任务必须属于当前用户
if (task.RequestedByUserId != CurrentUser.Id) throw new EntityNotFoundException(...);
//                                                       ↑ 404 而不是 403

// ② 产物必须还在（保留期过了就被清理）
if (!File.Exists(path)) throw new EntityNotFoundException(...);
```

**为什么用 `EntityNotFoundException`（404）而不是 403**：
"这个任务存在但你不能下"与"没这个任务"在语义上都该对未授权者返回 404 ——
403 会泄露"确实存在这样一个任务"。这也是 ABP 里要特别注意的一点
（第 08 章的坑：`BusinessException` 被映射成 403，不是 404）。

实测记录（本项目）：跨用户下载**两个方向都测**，都是 404。

## 41.5 第四步：用户不可见的补齐 —— 缩略图

缩略图生成有两条路径**共用同一个服务**（这是刻意的）：

- 刚上传、还没有缩略图的；
- 功能上线前的老照片，从来没有缩略图。

它们在数据上是**同一种状态**（`thumbnail_path` 为空），所以只需要一条扫描逻辑：

```csharp
var pending = await _photos.GetPagedListAsync(
    p => p.ThumbnailPath == null
         && p.RelativePath != null
         && (p.Status == PhotoStatuses.Normal || p.Status == PhotoStatuses.FallbackPending)
         && (schoolOrgId == null || p.SchoolOrgId == schoolOrgId),
    "UploadedTime DESC",   // ★ 新的优先，见下
    0, maxCount, cancellationToken);
```

### ★ 扫描方向：这条队列有一个会**永久堵住**的失效模式

原图读不到的记录（存储被清理、文件被手工删过）**状态不变**，
于是**每一轮都会被重新扫到**。实测数据（本机测试库）：

| 指标 | 实测 |
|---|---|
| 缺缩略图且状态正常 | **415 条** |
| 单轮上限 | 200 |
| 其中原图文件实际存在 | 7 个 |

于是 415 条陈年坏数据**永久占据队列前 200 位**，新上传的照片**永远轮不上** ——
而后台任务每轮都在跑、日志里也不报错。表现是"新上传的照片一直没有缩略图"。

修复：

1. **扫描方向改为"新的优先"**（`UploadedTime DESC`）—— 刚上传的下一轮就拿到缩略图，
   坏数据只是永远排在队尾（它们本来也生成不出来）；
2. 新增可选参数 `Guid? schoolOrgId`（只补某校）—— 给运维一个"就修这一所"的入口，
   同时让依赖它的测试**确定**。

> **未根治**：真正的修法是给"已确认原图缺失"的记录打标记并移出队列，
> 那需要先与业务确认能否自动标记。

### 为什么缩略图的**生成**必须移出上传请求

这是"债 18"：原来在上传请求内同步生成（解码 + 缩放），
一次 500 张的批次，CPU 开销会实打实地拖长请求。
现在上传只做"探测尺寸"（也是解码，但只读头部），生成交给 worker。

注意上传响应里因此**不该有** `thumbnailPath`：

```csharp
result.ThumbnailPath.ShouldBeNull("缩略图生成已移出上传请求");
```

端到端测试里有一条断言**写反过**（断言 `thumbnailPath` 为真），
它之所以"偶尔通过"是因为后台任务碰巧跑过 —— 那测的是"运气"，不是契约。

## 41.6 第五步：补偿回放（降级照片搬回 NAS）

```csharp
public class PhotoCompensationWorker : BackgroundService
{
    // 每 5 分钟一次：把 FallbackPending 的照片回放到 NAS
    // 主存储仍不可用时**立即中止（不空转）**，返回 Aborted = true
}
```

两个设计点：

1. **先探活再做**（与写入路径相反）：补偿是"把降级区的东西搬回 NAS"，
   需要先确认 NAS 真的可写 —— 否则每张都会失败一次，白跑一轮；
2. **NAS 不可用时立即中止**，不是"逐个试完"：`Aborted = true` 让调用方知道
   "不是没有待补偿的，而是现在做不了"。

缩略图也要跟着回放：降级期间生成的缩略图落在本地降级区，
补偿时连同原图一起搬回主存储（有用例
`降级上传_缩略图补齐落在本地降级区_补偿后回放到主存储` 守它）。

## 41.8 本章要点

1. 重活统一"任务式"：入队 → worker 执行 → 轮询 → 下载；条件用**快照**。
2. worker 没有当前用户，所以入队时要**存发起人 Id 与角色**，执行时重建身份 ——
   否则会越权导出（本项目实测：县级 total=10、省厅 total=40）。
3. `Total`/`RowCount`/`IsTruncated` 三个字段让"少人"可见；**前端必须强制展示**。
4. worker 必须**吞掉所有异常**（否则会停掉整个主机）、限量、用 `IClock`。
5. 下载只允许本人，用 **404** 而不是 403（不泄露"任务存在"）。
6. 缩略图队列要**新的优先**，否则会被"原图读不到"的陈年记录永久堵死。
7. 补偿回放要先探活主存储、不可用时**立即中止**（不空转）。
