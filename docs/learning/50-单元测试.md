# 50 单元测试：哪些代码值得测，哪些不值得

> 对应代码：`test/Xjgl.Domain.Tests/`（177 条）、`web/apps/pc/src/utils/csvEncoding.test.ts`
> 相关文档：第 51 章（集成测试）、第 52 章（端到端）

## 50.1 要解决的问题

"要不要给这段代码写单测"是个每天都在做的判断，而两种极端都错：

- **什么都测**：给 DTO 的 getter 写测试、给三层透传的 Service 写测试 ——
  测试量巨大，但**从没拦住过一个真缺陷**（它们只会在重构时一起改红）；
- **只测"核心算法"就完事**：漏掉"纯函数但极其容易算错"的那类代码
  （码点长度、CSV 编码探测、状态机）—— 而那些恰是最需要测的。

本章给出一条可操作的判据，并用本项目的实际分布说明它怎么落地。

## 50.2 判据：三个问题，全是"是"才值得测

> **① 它有分支吗？② 它的正确性从代码上看不出来吗？③ 它出错的代价大于写测试的成本吗？**

逐条解释：

| 问题 | 反例（不值得测） | 正例（值得测） |
|---|---|---|
| 有分支吗 | DTO 的属性赋值 | 熔断器的三状态迁移 |
| 正确性显而易见吗 | `Name = input.Name` | 按**码点**算长度（`Length` 是错的） |
| 出错代价大吗 | 只影响一条日志的格式 | 写坏学生主档 / 少打一个人 |

按这条判据，本项目的单元测试（`Xjgl.Domain.Tests`，177 条）集中在**五类**：

| 类别 | 例子 | 条数占比 |
|---|---|---|
| **纯算法**（有分支、易算错） | 流程实例化的截断与合并、令牌桶补充、生僻字码点处理 | 最多 |
| **状态机** | 熔断器、图片处理结果判定 | 多 |
| **校验规则** | 身份证校验位、CSV 编码探测、姓名合法性 | 多 |
| **序列化 / 格式** | CSV 转义、生僻字截断 | 少 |
| **公式** | 学籍辅号规则解析与格式化 | 少 |

**故意不测的**：DTO、`ToDto()` 映射（由集成测试覆盖"字段真的传到了"）、
Controller（由端到端覆盖）。

## 50.3 例一：为什么熔断器值得测（状态机 + 时间）

熔断器是典型的"必须有单测"：它有 3 个状态、2 个阈值、1 个时间窗口，
人工很难构造"熔断后 30 秒"的场景。

关键在于**把时间做成参数**（第 38 章详述）：

```csharp
public bool ShouldAllow(DateTime now) { ... }
public void RecordFailure(DateTime now) { ... }
```

于是故障恢复能**在毫秒内**验证：

```csharp
[Fact]
public void 熔断后经过OpenSeconds进入半开_试探成功则恢复()
{
    var breaker = new PhotoCircuitBreaker(minimumSamples: 3, failureRate: 0.5, openSeconds: 1);
    var now = new DateTime(2026, 1, 1, 0, 0, 0, DateTimeKind.Utc);

    for (var i = 0; i < 3; i++) { breaker.ShouldAllow(now); breaker.RecordFailure(now); }
    breaker.State.ShouldBe(CircuitState.Open);

    breaker.ShouldAllow(now.AddMilliseconds(500)).ShouldBeFalse();
    breaker.ShouldAllow(now.AddSeconds(2)).ShouldBeTrue();     // 半开
    breaker.RecordSuccess();
    breaker.State.ShouldBe(CircuitState.Closed);
}
```

> **全程没有 `Thread.Sleep`** —— 这个用例跑完只要几毫秒。
> 如果用内部时钟（`DateTime.UtcNow`），同样的场景要真等 1 秒以上，
> 而 `OpenSeconds` 在生产上是 30~60 秒。

**这条经验可以推广**：任何"需要等一段时间"的逻辑，
第一步就是**把时间变成参数**。

## 50.4 例二：为什么流程算法值得测（纯函数 + 组合多）

`ChangeFlowPlanner.Plan(nodes, resolveOrg, maxApproveLevel)` 是纯函数
（数据库通过回调进来），所以测试极其轻：

```csharp
[Fact]
public void 同县区转学_县区与地市各合并一次()
{
    var plan = planner.Plan(nodes, resolver, ApproveLevels.City);

    plan.Tasks.Select(t => t.Seq).ShouldBe(new[] { 1, 4, 5, 6 });
    plan.Tasks.Single(t => t.Seq == 5).MergedFromSeqs.ShouldBe(new[] { 2 });
}
```

而它**值得**测的理由是：截断 + 合并的组合情况很多
（同县/同市/跨市 × 终止级别 4 种），
而这些组合在界面上**看起来都"跑起来了"** —— 只有断言待办的 `Seq` 才能发现合并错了。

**这里有一条可迁移的设计教训**：让算法**只依赖纯函数 + 回调**，
它就能被彻底单测；反之如果它自己查数据库，测试就得起一个数据库。

## 50.5 例三：为什么前端也会有单测（零依赖的做法）

前端大部分代码不值得单测（组件渲染由端到端覆盖），
但**纯函数工具**值得 —— 本项目的例子是 `csvEncoding.ts`（第 48 章）。

做法是**零新增依赖**：Node 22.7+ 能直接跑 TypeScript（仅类型擦除），
配内置的 `node:test`：

```jsonc
// apps/pc/package.json
"scripts": {
  "test:unit": "node --test \"src/**/*.test.ts\""
}
```

```typescript
import assert from 'node:assert/strict'
import { test } from 'node:test'

import { probeCsvEncoding } from './csvEncoding.ts'

test('4 字节 UTF-8（生僻字 U+20BB7 𠮷）正常放行', () => {
  const probe = probeCsvEncoding(buf([0xf0, 0xa0, 0xae, 0xb7]))

  assert.equal(probe.ok, true, '生僻字必须能导入 —— 本系统专门为它做了整条链路')
  assert.equal(probe.text.codePointAt(0), 0x20bb7)
})
```

**tradeoff 要写清楚**：需要在 `tsconfig.json` 开 `allowImportingTsExtensions`
（Node 的 ESM 解析不补后缀，所以 import 必须带 `.ts`）。

> **判断标准**：为一个百来行的纯函数引一整套测试运行器 + 变换器**不划算**；
> 而"零新增依赖"的 `node --test` 让它能进 CI 而不会成为维护负担。

## 50.6 反例：不要写的三类单测

### 反例一：给"魔法数字"写断言

```csharp
// ❌ 这个数字由图像库的编码器决定，随版本变化（实测某版本是 616，不是 512）
photo.FileSize.ShouldBe(512);

// ✅ 断言"I/O 两端的值相等" —— 这才是有意义的不变量
photo.FileSize.ShouldBe(content.Length, "台账里的文件大小必须等于实际写入的字节数");
```

**它变红时的报错**（"应为 512、实际 616"）看起来像"业务把大小算错了"，
**排查方向会被完全带偏**。这是本仓库真实修过的一处。

### 反例二：只断言"没抛异常"

```csharp
// ❌ 这什么也没证明 —— 把它删掉、或者让它什么都不做，测试照样绿
await tx.ExecuteAsync(async () => { await repo.InsertAsync(entity); });
// 测试结束
```

对比第 33 章那条**真正有用**的写法：中途抛异常 → 断言前面的写**查不到**。

### 反例三：断言"当前是坏的"却不说明原因

```csharp
// ⚠ 这种断言本身没错，但必须写清"为什么故意断言失败态"以及"什么时候该改"
expect(page.url(), '若这里不再是登录页，说明 SSO 已打通 —— 请把本用例改成"拿到授权码"')
  .toMatch(/\/login/)
```

本项目在 SSO 那处**刻意**留了这样一条用例：把"未打通"变成可执行的记录，
并在真打通后**变红**提醒改断言。**不写理由的"坏态断言"会在半年后被当成 bug 删掉。**

## 50.7 怎么跑

```powershell
# 后端领域单测（177 条，3~4 秒）
dotnet test test\Xjgl.Domain.Tests --nologo

# 只跑某一类
dotnet test test\Xjgl.Domain.Tests --filter "FullyQualifiedName~PhotoCircuitBreakerTests"

# 前端纯函数单测（11 条，0.2 秒）
cd web
pnpm test:unit
```

## 50.8 本章要点

1. 判据三条：**有分支 + 正确性不显然 + 出错代价大**，全满足才值得写单测。
2. 单测集中在：纯算法、状态机、校验规则、格式化；**不测** DTO 与透传。
3. 让算法只依赖**纯函数 + 回调**，它就能被彻底单测。
4. **把时间做成参数**，"需要等一段时间"的逻辑才能在毫秒内验证。
5. 前端纯函数单测用 `node --test`（零新增依赖），记得开 `allowImportingTsExtensions`。
6. 不要写魔法数字断言；不要只断言"没抛异常"；"坏态断言"必须写清理由与何时该改。
