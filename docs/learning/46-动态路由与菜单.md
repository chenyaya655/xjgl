# 46 元数据驱动的动态路由与菜单（含一个"菜单点进去 404"的真缺陷）

> 对应代码：`web/apps/pc/src/router/index.ts`、`web/apps/pc/src/layout/MainLayout.vue`、
> `src/Xjgl.Application/Metadata/MyProfileAppService.cs`
> 对应测试：`web/e2e/specs/04-modules.spec.ts`、`06-report.spec.ts`

## 46.1 要解决的问题

本系统的"模块管理"是一个**业务功能**：管理员可以新增模块、改路径、改图标、启停模块。
如果路由写死在前端，管理员在界面上改的东西就不会生效 ——
"模块管理"这个功能就退化成摆设。

所以路由必须**由后端元数据驱动**。本章讲清楚这条链路，以及它带来的一个
**只在跨子系统同 code 时出现**的真缺陷（本仓库踩过，且排查了很久）。

## 46.2 第一步：登录后拉一次拿到"我能看什么"

```typescript
// stores/auth.ts
async function loadProfile(): Promise<void> {
  loading.value = true
  try {
    profile.value = await profileApi.get()   // GET /api/app/my-profile
  } finally {
    loading.value = false
  }
}
```

这个接口一次返回：用户身份 + 组织 + 角色 + **权限码集合** + **可见菜单树**。
三个关键点：

- **后端只返回你有权限的菜单**，所以"菜单 = 路由 + 权限"天然一致；
- `permissionSet` 用 `Set` 而不是数组：按钮级判断是高频操作（每次渲染都可能调）；
- 前端**不做角色推断**（不写 `if (role === 'admin')`）—— 权限是元数据驱动的，
  角色与权限的对应关系完全在后端。前端一旦自己推断，就会在管理员改授权后与后端不一致，
  表现是"按钮看得见、点了报 403"。

```typescript
function can(permission: string): boolean {
  return permissionSet.value.has(permission)
}
```

## 46.3 第二步：把菜单树变成路由表

```typescript
/** 视图组件集合。Vite 在构建期静态分析 glob，因此路径必须是字面量。 */
const viewModules = import.meta.glob('../views/**/*.vue')

function resolveView(component?: string | null) {
  if (!component) return () => import('@/views/Placeholder.vue')

  const normalized = component.replace(/^\/+|\/+$/g, '')
  const candidates = [`../views/${normalized}.vue`, `../views/${normalized}/index.vue`]

  for (const candidate of candidates) {
    if (viewModules[candidate]) return viewModules[candidate]
  }

  // ★ 解析不到时**不抛错**，而是回落到占位页
  return () => import('@/views/Placeholder.vue')
}
```

**为什么解析不到要回落而不是报错**：模块是运行期数据，管理员完全可能
"先建好模块、等开发补页面"。此时让用户看到一个"该模块尚未实现"的页面，
远好过一个白屏或报错。

## 46.4 ★ 真缺陷：路由名跨子系统冲突，导致"菜单点进去 404"

这是本仓库一个**排查了很久**的缺陷，值得完整讲。

### 症状

`Rpt`（统计报表）子系统下新增了两个模块，菜单里能看到「学生统计」，
但点进去是 **404**。而「异动统计」（同一个子系统、同样的配置形状）却正常。

### 排查过程（五个被证伪的假设）

| 假设 | 怎么证伪的 |
|---|---|
| 视图文件不存在 | `Get-ChildItem` 确认 `views/report/student/index.vue` 在 |
| Vite 的 glob 没收集到 | 直接请求 `/src/router/index.ts`，看到该键**在** glob 结果里 |
| 后端菜单没返回它 | 抓 `my-profile` 响应体，该菜单项**在**里面 |
| 路由路径写错了 | 后端返回的 `path` 就是 `/report/student` |
| 是不是 catch-all 抢先匹配 | 不是，其它同形状的路由都正常 |

最后在注册循环里加了一行日志，**立刻看到真正的原因**：

```
DIAG-ROUTE item=Student path=/student/list     route=/student/list     name=Student already=false
DIAG-ROUTE item=Student path=/report/student   route=/report/student   name=Student already=true   ← 被跳过！
```

### 根因

```typescript
// ❌ 用 item.code 当路由名
function toRoute(item: MenuItem, groupName: string, groupCode: string) {
  return {
    path: item.path,
    name: item.code,          // ← "学生管理"的 code 是 Student，"学生统计"的 code 也是 Student
    component: resolveView(item.component),
  }
}

export function registerDynamicRoutes(menus) {
  for (const group of menus) {
    for (const item of group.children) {
      const route = toRoute(item, group.name, group.code)
      if (!route || registered.has(String(route.name))) continue   // ← 第二个被静默跳过
      router.addRoute('layout', route)
      registered.add(String(route.name))
    }
  }
}
```

**`code` 只在同一个子系统内唯一**（后端是 `(subsystem_id, code)` 唯一索引），
跨子系统重名**完全正常**：

```
Stu 子系统有模块 code=Student → /student/list
Rpt 子系统也有模块 code=Student → /report/student   ← 同一个路由名
```

去重集合 `registered` 按路由名判断，于是第二个被跳过。

### 为什么这个缺陷特别难发现

- **接口、类型检查、路由核对脚本全是绿的** —— 问题不在接口，在路由注册；
- 它只影响"**跨子系统同 code**"的那一个模块，同一子系统内完全看不出来；
- 27 条既有端到端用例全绿也拦不住它（没有一条覆盖报表页）。

### 修复：路由名前缀子系统 code

```typescript
return {
  path: item.path,
  /**
   * 路由名必须**全局唯一**：vue-router 的 addRoute 遇到重名时会覆盖先前那一条，
   * 而 getRoutes() 里不会告诉你少了谁。
   *
   * code 只在同一子系统内唯一，所以缀上子系统 code（如 Rpt:Student）。
   * 子系统 code 本身是主键级唯一的，拼出来的名字必然全局唯一。
   */
  name: `${groupCode}:${item.code}`,
  component: resolveView(item.component),
  meta: { title: item.name, code: item.code, /* ... */ },
}
```

**这个缺陷的教训比修复本身更有价值**：

1. **"我以为的根因"被证伪了五次**，最后一次才是对的 —— 排查要穷尽假设，
   而不是抓住第一个像的原因；
2. **不要用"业务编码"当技术标识符**。业务编码的作用域（子系统内唯一）
   与技术约束（路由名要全局唯一）不匹配，就必须显式转换；
3. **加一行日志比读十遍代码有效**。前面五个假设都是"读代码推出来的"。

## 46.5 第三步：注册之后要能"重新解析当前路径"

```typescript
if (restored) {
  // 路由表变了，重新解析当前目标。
  // ⚠ 必须用 fullPath 字符串，不能写 { ...to, replace: true }
  return { path: to.fullPath, replace: true }
}
```

为什么不能用 `{ ...to, replace: true }`：`to` 是**已解析**的路由对象，
里面带着 `name: 'not-found'`（此刻它匹配的是 catch-all），
而 vue-router 里 **name 优先于 path** —— 会被导航回 404 页。
表现是"刷新业务页面永远停在页面不存在"。这个坑是端到端测试抓出来的。

## 46.6 菜单渲染与图标

菜单里 `<el-menu-item :index="item.path">` 的 `index` 就是路由路径，
配合 `router` 属性由 Element Plus 负责跳转。

图标名来自后端元数据（`sys_module.icon`，如 `User` / `OfficeBuilding`），
是**运行期字符串**，没法直接当组件用。`AppIcon.vue` 按需查表：

```vue
<script setup lang="ts">
const registry = ElementPlusIcons as unknown as Record<string, Component>

const resolved = computed<Component>(() => {
  const name = props.name?.trim()
  // 未识别的名字回落到默认图标而不是报错 —— 新增模块时忘了配图标名，界面不该白屏
  return (name && registry[name]) || ElementPlusIcons.Menu
})
</script>
```

**为什么不把几百个图标全部 `app.component()` 注册成全局组件**：
那样会让每个图标都成为 Vue 的全局解析目标，模板编译期无法 tree-shake。

## 46.7 怎么验证

```powershell
cd web
$env:E2E_API_URL = 'http://127.0.0.1:44300'

# 每个模块都能打开（参数化冒烟）
pnpm test:e2e --grep "各模块冒烟"

# 统计页（正是上面那个缺陷所在的页面）
pnpm test:e2e --grep "统计报表"
```

`04-modules.spec.ts` 的做法值得抄：它**遍历后端返回的菜单**逐个打开，
断言"渲染出内容而不是 404 页"。这正是能拦住本缺陷的形态：

```typescript
for (const path of menuPaths) {
  test(`${label} 页面能打开并渲染出内容`, async ({ page }) => {
    await page.goto(path)
    // 404 页有固定文案；它同样是 200，所以不能只看状态码
    await expect(page.getByText('页面不存在或您没有访问权限')).toHaveCount(0)
  })
}
```

> 注意最后那条注释：**catch-all 404 页返回的也是 200**，
> 所以"页面能打开"不能靠状态码判断，必须看**内容**。
> 这也是为什么本仓库的端到端用例里到处在断言"404 文案不存在"。

## 46.8 本章要点

1. 路由由后端元数据驱动，"模块管理"才成为一个真业务功能。
2. `resolveView` 解析不到要**回落占位页**，不要抛错（管理员可能先建模块后补页面）。
3. **不要用业务 code 当路由名**：它只在子系统内唯一，而路由名要全局唯一。
   用 `${groupCode}:${item.code}` 这类显式转换。
4. 排查"页面 404"时，**加一行日志看注册循环**比读代码快得多。
5. 动态注册后重定向要用 `fullPath` **字符串**（name 优先于 path）。
6. **catch-all 404 页也返回 200**，所以"页面能打开"必须断言内容。
7. 图标按需查表 + 回落默认图标，不做全局注册。
