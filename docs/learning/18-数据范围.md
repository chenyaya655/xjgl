# 18 数据范围：能看哪些数据，与"能不能看"是两件事

> 对应代码：`src/Xjgl.Domain/Organizations/UserDataScope.cs`、`UserDataScopeProvider.cs`，
> 使用处：`src/Xjgl.Application/Students/StudentAppService.cs`、`Photos/PhotoAppService.cs`、
> `Students/StudentAccessGuard.cs`
> 对应测试：`test/Xjgl.Domain.Tests/Organizations/UserDataScopeTests.cs`、
> `test/Xjgl.Application.Tests/DataScope/DataScopeTests.cs`

## 18.1 要解决的问题

第 11~12 章做好了权限：`Stu.Student.Query` 决定"**能不能**查学生"。
但**权限回答不了"能查哪些学生"**。没有数据范围时，系统的真实状态是：

> 任何登录用户只要在查询里传一个别的县的组织 Id，就能把那个县的学生全查出来。

这不是假设，是本项目实现数据范围**之前**的真实状态。它的危险之处在于：
从代码上看一切都对 —— 接口有 `[Authorize]`、权限码校验通过、参数格式合法。
**权限点是对的，是"数据"漏了。**

所以数据范围要回答两个不同的问题：

| 问题 | 典型场景 | 判据 |
|---|---|---|
| 这条**实体**我能不能看？ | 直接打开某个学生详情 / 照片 | 实体上冗余的物化路径（`SchoolPathCode`）与我的范围比较 |
| 我**请求的这个组织子树**能不能查？ | 列表页筛选"某县" | 请求的组织路径与我的范围**有交集** |

## 18.2 第一步：把范围写成纯值对象

别看数据范围牵扯数据库，**判断逻辑本身一行数据库代码都不该有**。
因为"前缀比较"这种逻辑最容易写错方向，而只有把它做成纯函数，才能用穷尽式单元测试把边界钉死。

`src/Xjgl.Domain/Organizations/UserDataScope.cs` 的核心就三件事：

```csharp
public sealed class UserDataScope
{
    public string Scope { get; }              // All / OrgAndChildren / OrgOnly / SelfOnly / Custom
    public Guid? OrgId { get; }
    public string? OrgPathCode { get; }       // 物化路径，如 41.4101.410102.410102001
    public bool IsSuperAdmin { get; }

    public bool IsUnrestricted => IsSuperAdmin || Scope == DataScopes.All;   // 全省
    public bool IsEmpty        => !IsUnrestricted && string.IsNullOrWhiteSpace(OrgPathCode);

    /// 某个实体（学生、照片）是否在范围内：比较实体上冗余的路径
    public bool AllowsEntityPath(string? entityPathCode) { ... }

    /// 客户端请求的组织子树是否与我的范围有交集
    public bool AllowsRequestedOrgPath(string? requestedOrgPathCode) { ... }
}
```

### 两个方向的比较

`AllowsEntityPath` 是单向的：实体的路径必须**等于**我的路径，或者以 `我的路径 + "."` 开头。

```csharp
private bool IsSelfOrDescendant(string pathCode)
    => string.Equals(pathCode, OrgPathCode, StringComparison.Ordinal)
       || pathCode.StartsWith(OrgPathCode + ".", StringComparison.Ordinal);
```

`AllowsRequestedOrgPath` 却是**双向**的，这一点必须理解清楚：

```csharp
//   1) 请求的是我或我的后代 → 请求 ⊆ 我；
//   2) 请求的是我的**上级** → 我 ⊆ 请求。
//      这一条不能少：县区管理员想看"本市范围"的统计时会传市 Id，
//      若判为无交集，正常的按上级筛选就直接失效了。
return IsSelfOrDescendant(requestedOrgPathCode)
       || OrgPathCode!.StartsWith(requestedOrgPathCode + ".", StringComparison.Ordinal);
```

**"请求上级也算有交集"安全吗？** 安全，前提是**实体层仍然叠加范围约束**：
允许请求只是让"筛选条件"通过，最终返回的数据依旧被 `AllowsEntityPath` 裁到"我的子树"内。
这也是本项目的写法约定：**范围校验分两层，缺一层就漏**。

### 默认安全：无组织 = 什么都看不到

```csharp
/// 什么都看不到（未关联组织且非超管）
public bool IsEmpty => !IsUnrestricted && string.IsNullOrWhiteSpace(OrgPathCode);
```

这是整个设计里**唯一不能搞错的方向**。反过来（没有组织就默认全都能看）在开发期很方便，
上线就是"任何一个没有配组织的账号都能看全省"。

## 18.3 第二步：从"当前用户"解析出范围

`UserDataScopeProvider` 的职责是：当前用户 → 预置记录 → 所属组织 → 范围。

| 用户的组织 | 范围 |
|---|---|
| 省厅（Province） | 全部数据 |
| 地市 / 县区 / 学校 | 本级及下级 |
| 未关联组织 + 内置 `admin` 角色 | 全部数据（**超管旁路**） |
| 未关联组织 + 非 admin | 什么都看不到 |

两个实现细节值得抄：

**① 注册为 Scoped，并且自己缓存结果**（同一个请求里多个查询只解析一次，避免一次列表请求查好几遍组织）：

```csharp
public class UserDataScopeProvider : IUserDataScopeProvider, IScopedDependency
{
    private UserDataScope? _cached;

    public async Task<UserDataScope> GetAsync() => _cached ??= await ResolveAsync();
```

**② 超管旁路必须有**：内置 `admin` 账号没有关联组织（它不是某一个学校的人）。
若不旁路，系统管理员登录后看不到任何数据、也无法排查问题；集成测试也没法用 admin 覆盖全量场景。

## 18.4 第三步：在查询里怎么用

### 列表：先判请求组织，再拼谓词

```csharp
var scope = await _dataScopeProvider.GetAsync();

// 未关联组织且非超管：**返回空，而不是报错**。
// 列表接口报错会把"这个人没有数据权限"变成界面上的一个红条，
// 而正确的产品行为是他本来就看不到任何数据（空列表）。
if (scope.IsEmpty)
{
    return new PagedResultDto<StudentListItemDto>(0, new List<StudentListItemDto>());
}

// 请求的组织必须在数据范围内：不在范围内**直接返回空**，不去查库。
if (input.SchoolOrgId.HasValue)
{
    var requestedOrg = await _orgs.FindAsync(input.SchoolOrgId.Value);

    if (requestedOrg == null || !scope.AllowsRequestedOrgPath(requestedOrg.PathCode))
    {
        return new PagedResultDto<StudentListItemDto>(0, new List<StudentListItemDto>());
    }
}
```

### SqlSugar 的坑：不能用"恒假谓词"短路

我最初的写法是"范围为空时拼一个 `s => false` 让数据库返回空"，结果 **SqlSugar 直接抛异常**——
它无法把常量假表达式翻译成 SQL。同理，谓词里写三元表达式会被翻译成 `SqlFunc.IIF` 并报
`argument do not support`。

因此本项目的约定是：**空结果的判断放在调用方，谓词构造只负责拼条件**；
真的需要在谓词里表达"永远不匹配"时，用一个**不可能出现的路径前缀**当哨兵：

```csharp
/// 用来表达"这个范围不可能匹配任何路径"的哨兵前缀
private const string ImpossiblePathPrefix = "\u0001";
```

### 单条实体：明确抛异常，而不是返回空

```csharp
public async Task EnsureInScopeAsync(StuStudent student, CancellationToken ct = default)
{
    var scope = await _dataScopeProvider.GetAsync();

    // 越权访问明确抛异常而不是返回空：调用方需要区分
    // 「这条数据存在但你看不到」与「这条数据不存在」
    if (!scope.AllowsEntityPath(student.SchoolPathCode))
    {
        throw new BusinessException(XjglDomainErrorCodes.UserNotInDataScope)
            .WithData("reason", "该学生不在您的数据范围内");
    }
}
```

### 子表接口是独立路由，必须自己校验

学生详情下有六张子表（监护人 / 简历 / 奖励 / 处分 / 资助 / 体检），照片、变更留痕也是独立接口。
**它们不会自动继承主档接口的过滤条件** —— 少校验一处，就是"能看学生却看不到、但能直接读家长身份证号"。

所以这段判断被上提成了 `StudentAccessGuard`（`src/Xjgl.Application/Students/StudentAccessGuard.cs`），
凡是学生相关的接口都先过它：

```csharp
// 子表是独立路由，不会自动继承主档的过滤条件 ——
// 放在某个应用服务的私有方法里，子表接口就只能复制一份，迟早漏一处
await _guard.GetInScopeAsync(studentId);
```

## 18.5 验证方法

### ① 单元测试把边界钉死（不需要数据库）

| 用例 | 期望 |
|---|---|
| 省厅（All） | 任意路径都放行 |
| 县区（OrgAndChildren） | 本县、本县学校放行；**邻县、市本级、省厅不放行** |
| 学校（OrgAndChildren） | 本校放行；同县另一所学校不放行 |
| OrgOnly | 只有自己放行，下级不放行 |
| 未关联组织 | 一律不放行（`IsEmpty`） |
| 超管 | 一律放行 |
| `AllowsRequestedOrgPath`：请求上级 | 放行（否则按上级筛选失效） |
| `AllowsRequestedOrgPath`：请求邻县 | 拒绝 |

### ② 集成测试按身份验证，但**每次换身份必须新开 DI 作用域**

这是本项目最值得记住的一条测试教训：

> `ICurrentUser` 是 **Scoped** 的，并且会缓存用户 Id 与角色。
> 集成测试里整个测试类共用根作用域，如果在同一个作用域里换身份，
> 第二次之后 `ICurrentUser` 仍然返回第一次的值 —— 表现是"所有身份都像第一个身份"，
> 越权断言全部失效。**本类最初 8 个用例全挂就是这个原因。**

因此"以某个身份做某事"必须这样写（见 `DataScopeTests`）：

```csharp
private async Task<T> InScopeAsAsync<T>(
    Guid userId, string userName, string[] roles, Func<IServiceProvider, Task<T>> action)
{
    _principal.SetUser(userId, userName, roles);   // 换 principal

    using var scope = ServiceProvider.CreateScope();   // 必须新开作用域

    return await action(scope.ServiceProvider);
}
```

另外集成测试要**串行执行**（`test/Xjgl.Application.Tests/xunit.runner.json` 里
`parallelizeTestCollections: false`、`parallelizeAssembly: false`），
否则并行跑的测试类会互相覆盖那个共享的 principal。

## 18.6 踩坑记录

| 现象 | 根因 | 教训 |
|---|---|---|
| 越权用例全部通过（其实是假通过） | 同一 DI 作用域里换身份，`ICurrentUser` 缓存了第一个身份 | 涉及"当前用户"的集成测试必须新开作用域；断言要能区分身份（比如每人查到的条数不同） |
| `s => false` 直接抛异常 | SqlSugar 翻译不了常量假表达式 | 空结果在调用方短路；谓词里需要"永不匹配"时用哨兵前缀 |
| "请求上级"被误判为越权 | `AllowsRequestedOrgPath` 的双向包含**写反了方向** | 单元测试专门有一条钉住它：`requested.StartsWith(my + ".")` 与 `my.StartsWith(requested + ".")` 是两件事 |
| 一个县区账号查到了全省 | 只有权限、没有数据范围 | 权限与范围正交，必须分别实现；"默认安全"（无组织 = 看不到）比"默认方便"重要 |
| 照片/子表接口能越权读到 | 复用了主档的权限但忘了范围校验 | 独立路由必须自己校验；把判断上提成共享守卫，而不是每个服务各写一遍 |

## 18.7 还没做的部分（诚实记录）

- **`sys_role_data_scope` 按角色配置范围**：目前范围完全由"用户所属组织的层级"推导。
  它覆盖"上级能看下级"这个主流场景，但表达不了例外（例如"某市局只看本市、不看他下属县"）。
- **仅本人（SelfOnly）**：值对象已支持，但没有配置入口（需要角色级配置表）。
- **自定义组织集合（Custom）**：当前退化为"本级及下级"—— 宁可收紧，也不要在配置表落地前
  出现比设计更宽的可见性。
