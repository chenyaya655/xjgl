# 34 审核、驳回与撤销审核：状态机与并发

> 对应代码：`src/Xjgl.Application/Changes/ChangeFlowAppService.cs`、
> `src/Xjgl.Domain/Changes/ChangeApply.cs`（`ChangeApplyStatus` / `ChangeTaskStatus`）
> 对应测试：`test/Xjgl.Application.Tests/Changes/ChangeFlowAppServiceTests.cs`

## 34.1 要解决的问题

流程跑起来之后，用户真正会做的事只有四个：**通过、驳回、撤回申请、撤销审核**。
看起来简单，但每一个都要回答"**当前状态下允许吗**"，
而漏判的后果是数据进入一个**没人能解释的状态**。

本章把两张状态表与四个动作讲清楚，重点在**那些容易漏的约束**。

## 34.2 两张状态表

**申请单状态**（`ChangeApplyStatus`）：

| 状态 | 含义 | 终态？ |
|---|---|---|
| `Draft` | 草稿（当前实现不产生，为将来留） | 否 |
| `Submitted` | 待审核（刚提交） | 否 |
| `InProgress` | 审核中（已有人通过，还有人没审） | 否 |
| `Approved` | 已通过（业务联动已生效） | 否（可撤销） |
| `Rejected` | 已驳回 | **是** |
| `Withdrawn` | 已撤回（申请人自己撤） | **是** |
| `Archived` | 已归档 | 是 |

**流程任务状态**（`ChangeTaskStatus`）：

| 状态 | 含义 |
|---|---|
| `Pending` | 待处理（会出现在待办列表） |
| `Approved` | 已通过 |
| `Rejected` | 已驳回 |
| `Skipped` | **已跳过**（驳回后把后续节点统一置成它） |
| `Merged` | 已合并（被同组织的另一个节点代表） |
| `Revoked` | 已撤销（撤销审核时退回待处理） |

`Skipped` 的存在理由值得单独说：驳回即终止流程，但**后续未处理的节点还在表里**。
不把它们标记掉，详情页会出现"申请单已驳回，却还挂着两个待处理节点" ——
用户会以为还要有人继续审，而这些节点永远不会再被处理。

```csharp
private async Task SkipPendingTasksAsync(Guid applyId, int afterSeq)
{
    var pending = await _tasks.GetListAsync(t =>
        t.ApplyId == applyId && t.Seq > afterSeq && t.Status == ChangeTaskStatus.Pending);

    foreach (var task in pending) task.Status = ChangeTaskStatus.Skipped;

    if (pending.Count > 0) await _tasks.UpdateManyAsync(pending, autoSave: true);
}
```

## 34.3 四个动作的约束（一张表看完）

| 动作 | 允许的前提 | 漏判的后果 |
|---|---|---|
| **通过** | 申请单在进行中；当前节点确实轮到我 | 越级审批、重复审批 |
| **驳回** | 同"通过"；且该节点 `AllowReject` | 驳回了不允许驳回的节点 |
| **撤回申请** | 只有**申请人自己**、且**还没有人审过** | 审到一半被申请人抽走 |
| **撤销审核** | 申请单是 `Approved`；且**后续节点都未处理** | 后面有人基于"已通过"做过动作却被回滚 |

### 动作一：通过（推进到下一步）

```csharp
var (apply, current, tasks) = await LoadCurrentTaskAsync(input.ApplyId);

current.Status = ChangeTaskStatus.Approved;
current.HandledByUserId = CurrentUser.Id;
current.HandledByName = CurrentUser.UserName;
current.HandledTime = now;
current.Opinion = input.Opinion;

await _tasks.UpdateAsync(current, autoSave: true);
await WriteLogAsync(apply.Id, current.Id, current.Seq, ChangeFlowActions.Approve, ...);

// 找下一个待处理节点
var next = tasks
    .Where(t => t.Seq > current.Seq && t.Status == ChangeTaskStatus.Pending)
    .OrderBy(t => t.Seq)
    .FirstOrDefault();

if (next == null)
{
    // 最后一个节点 → 流程完成 + 业务联动
    apply.Status = ChangeApplyStatus.Approved;
    apply.CurrentSeq = null;
    apply.FinalApprovedTime = now;
    await _applies.UpdateAsync(apply, autoSave: true);

    await ApplyStudentChangesAsync(apply);          // 第 32 章
    await WriteLogAsync(..., ChangeFlowActions.Archive, "全部节点审核通过，学籍变更已生效");
}
else
{
    apply.Status = ChangeApplyStatus.InProgress;
    apply.CurrentSeq = next.Seq;
    await _applies.UpdateAsync(apply, autoSave: true);
}
```

`LoadCurrentTaskAsync` 里有两个必须做的判断（**不是可选的健壮性，是业务约束**）：

```csharp
private async Task<(StuChangeApply, StuChangeFlowTask, List<StuChangeFlowTask>)>
    LoadCurrentTaskAsync(Guid applyId)
{
    var apply = await _applies.GetAsync(applyId);

    // ① 申请单必须还在流程中
    if (apply.Status is ChangeApplyStatus.Rejected or ChangeApplyStatus.Withdrawn
        or ChangeApplyStatus.Approved)
    {
        throw new BusinessException(XjglDomainErrorCodes.ChangeApplyNotInFlow)
            .WithData("reason", $"申请单当前状态是「{...}」，不能继续审核。");
    }

    // ② 当前节点必须存在，且必须是「待处理」—— 否则说明有人已经处理过了
    var current = (await _tasks.GetListAsync(t =>
            t.ApplyId == applyId && t.Seq == apply.CurrentSeq))
        .SingleOrDefault();

    if (current == null || current.Status != ChangeTaskStatus.Pending)
    {
        throw new BusinessException(XjglDomainErrorCodes.ChangeTaskNotPending)
            .WithData("reason", "该节点已被处理，请刷新后重试。");
    }

    // ...
}
```

> **为什么 `ChangeTaskNotPending` 这条很重要**：两个审核员同时打开同一条待办、
> 都点"通过"时，第一个人处理完之后 `Status` 已经是 `Approved`。
> 没有这条判断，第二个人的操作会把"当前节点"再通过一次 —— 流程**跳过一个节点**，
> 而且申请单的 `CurrentSeq` 会指向不该在的位置。
> 这是"并发下静默跳步"，界面上完全看不出来。

### 动作二：驳回

除了状态改成 `Rejected` 并把后续节点 `Skipped`，还有两点：

```csharp
// ① 该节点是否允许驳回（模板上的 AllowReject）
if (!current.AllowReject)
    throw new BusinessException(XjglDomainErrorCodes.ChangeRejectNotAllowed);

// ② 驳回必须写意见 —— 否则学校不知道要补什么材料，会反复打电话
//    （前端也强制必填，这里是后端的兜底）
```

驳回**不改学生档案**（有专门用例 `驳回后申请单结束_学生学籍不变`）——
因为只有"全部通过"才触发业务联动。

### 动作三：撤回申请（申请人自己撤）

约束是两条：

```csharp
if (apply.CreatedByUserId != CurrentUser.Id) throw ...;      // 只能撤自己的
if (apply.Status != ChangeApplyStatus.Submitted) throw ...;   // 只能撤"还没人审过"的
```

第二条是关键：一旦有人审过（`InProgress`），就不能由申请人单方面撤回 ——
否则别人的审核动作被静默作废。

### 动作四：撤销审核（最复杂的一个）

```csharp
public async Task<ChangeApplyDto> RevokeApprovalAsync(ChangeAuditActionDto input)
{
    var apply = await _applies.GetAsync(input.ApplyId);

    // ① 只有「已通过」的能撤销
    if (apply.Status != ChangeApplyStatus.Approved) throw ...;

    // ② 后续节点都已处理时不允许撤销
    //    语义：后面已经有人基于"已通过"做了动作，不能再整体回滚
    var laterHandled = await _tasks.GetCountAsync(t =>
        t.ApplyId == apply.Id &&
        t.Status == ChangeTaskStatus.Approved &&
        t.Seq > /* 被撤销的那个节点 */ ...);

    if (laterHandled > 0)
        throw new BusinessException(XjglDomainErrorCodes.ChangeRevokeNotAllowed);

    // ③ 把被撤销的节点退回「待处理」，申请单回到进行中
    // ④ 回滚学生档案（用快照，见第 32 章）
    await RevertStudentChangesAsync(apply);
    // ⑤ 留痕：回滚本身也是重要变更
}
```

## 34.4 待办列表：为什么它"只返回轮到我的"

待办列表（`/todo-list`）的查询条件不是"所有待我审的"，而是**"当前轮到我审的"**：

```csharp
// 我的待办：apply.CurrentSeq 指向的任务，且角色与我匹配、且组织在我的数据范围内
var tasks = await _tasks.GetListAsync(t => t.Status == ChangeTaskStatus.Pending);
// 再按 apply.CurrentSeq == task.Seq 过滤 → 只有"当前节点"会出现在待办里
```

这样设计的效果：**同一个申请单在任一时刻，只有一个角色能看到它的待办**。
审核员打开页面看到的就是"现在轮到我了"，不需要理解流程走到哪。

角色匹配用 `RoleCode`（第 31 章），数据范围用组织路径（第 18 章）——
两者叠加，于是"甲县的县区管理员"只看得到甲县相关且属于县区级的待办。

## 34.6 本章要点

1. **两张状态表**（申请单 / 流程任务）都要维护，`Skipped` 是驳回后清理后续节点用的。
2. 审核前必须判断"申请单还在流程中" **且** "当前节点仍是待处理" ——
   后者是防并发重复审批、防**静默跳步**的关键。
3. 驳回要校验 `AllowReject` 且强制写意见；驳回**不动学生档案**。
4. 撤回申请只能由申请人本人、且只在"还没人审过"时。
5. 撤销审核只在 `Approved` 且"后续节点都未处理"时允许；回滚要用**快照**并留痕。
6. 待办列表的口径是"**当前轮到我**"，靠 `CurrentSeq` + `RoleCode` + 数据范围三者叠加。
