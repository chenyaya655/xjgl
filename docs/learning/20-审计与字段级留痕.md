# 20 审计与字段级留痕：谁在什么时候把学籍状态改了

> 对应代码：`src/Xjgl.Domain/Students/StuChangeLog.cs`、
> `src/Xjgl.Application/Students/StudentChangeLogger.cs`、
> `src/Xjgl.Application/Students/StudentChangeLogAppService.cs`
> 对应测试：`test/Xjgl.Application.Tests/Students/StudentChangeLogTests.cs`

## 20.1 要解决的问题

学籍档案是要被审计的。家长来问：

> "我孩子的学籍状态什么时候被改成转出的？谁改的？为什么改？"

系统必须答得出来。只记"某人某时改过这条学生记录"是**没有价值**的 ——
真正要回答的是"**改了哪个字段、从什么值变成什么值**"。所以留痕必须是**字段级**的。

另外三件事必须一开始就定清楚：

| 问题 | 决定 |
|---|---|
| 身份证号要不要写进日志？ | **不写明文**。审计要的是"被谁改过"，不是把全校身份证号再抄一份到日志表里（那等于多开一个泄露面） |
| 学生被删除了怎么办？ | **删除本身也是一次需要留痕的变更**，而且删完还要能查（留痕存在的意义就是这个场景） |
| 一次修改动了两个字段算几条？ | 两条，但共享一个 `BatchId`，界面才能显示成"一次修改中的两处变动" |

## 20.2 第一步：设计留痕表

`src/Xjgl.Domain/Students/StuChangeLog.cs`（表名 `stu_change_log`）：

| 字段 | 用途 |
|---|---|
| `StudentId` / `StudentNo` / `StudentName` | 留痕要能独立回答"这是谁"，所以**冗余**姓名与辅号（学生删掉后仍要能查） |
| `SchoolPathCode` | 学生当时所在学校的物化路径（**为数据范围过滤而冗余**，见 20.5） |
| `BatchId` | 一次操作内多行共享 |
| `Action` | Create / Update / Delete / Change / Import |
| `FieldName` / `FieldLabel` | 字段名与**中文名**（存中文名是为了将来改了属性名也不影响历史可读性） |
| `OldValue` / `NewValue` | 值（已经是人能读的文本） |
| `Reason` | 变更原因（异动审批写入时会带申请单号） |
| `OperatorId` / `OperatorName` / `OccurredAt` | 谁、什么时候 |
| `Source` | 手工录入 / 批量导入 / 学籍异动 |

## 20.3 第二步：快照 + 比对（而不是"记录输入里带了哪些字段"）

`StudentChangeLogger` 的用法是一对：**改之前先取快照**，改完再把快照交给它比对。

```csharp
// 先取快照再改：留痕用的是"前后比对"，只写真正变化的字段
var before = _changeLogger.Snapshot(entity);

ApplyInput(entity, input, idCard, idCardHash, school);

await _students.UpdateAsync(entity, autoSave: true);

await _changeLogger.LogUpdatedAsync(entity, before);
```

为什么不用"记录输入 DTO 里带了哪些字段"？因为那样会漏掉**由业务逻辑推导出来的变化**
（例如按学校生成的辅号、按异动类型写入的状态），而审计恰恰要能回答"这条记录的哪个字段变了"。

### 快照项里为什么要有 CompareKey

```csharp
public sealed record StudentFieldSnapshot(string Name, string Label, string? Value, string? CompareKey);
```

身份证号是个特例：它是 **AES 密文，每次加密结果都不同**（随机 IV），
直接比密文会把"没改"误判成"改了"。因此比较用 **HMAC 摘要**，展示用摘要前缀：

```csharp
// 身份证号：比较用摘要（密文每次加密都不同），展示用摘要前缀（不把明文抄进日志表）
F(nameof(StuStudent.IdCardHash), "身份证号", null, student.IdCardHash),
```

### 码值要翻译成人话

```csharp
case nameof(StuStudent.StudentStatusCode) when statusNames.Count > 0:
    return Translate(statusNames, value!);   // → "休学（02）"
```

`在读（01）` 这种写法兼顾了"给人看"与"可追溯"。
另外**只为变化了的字段去查码表**：平时一次修改也就动一两个字段，没必要每次都查一圈。

### 删除要写在删除之前

```csharp
// 留痕写在删除之前：删掉之后就再也拿不到姓名与学籍辅号了
await _changeLogger.LogDeletedAsync(entity);

await _students.DeleteAsync(entity, autoSave: true);
```

## 20.4 第三步：挂在哪些地方

| 写入点 | 动作 | 说明 |
|---|---|---|
| `StudentAppService.CreateAsync` | Create | 建档（谁在什么时候建的、学籍辅号是什么） |
| `StudentAppService.UpdateAsync` | Update | 字段级 diff |
| `StudentAppService.DeleteAsync` | Delete | 删档留痕（删除前写） |
| `ChangeFlowAppService` 审批通过 | Change | 来源写"学籍异动"，原因带申请单号 |
| `ChangeFlowAppService` 撤销审核 | Change | 学籍回滚同样要留痕 |

异动那一处值得单独说：异动流程自己的 `stu_change_flow_log` 记的是"**审批动作**"
（谁点了通过、意见是什么），而 `stu_change_log` 记的是"**学籍字段发生了什么变化**"。
两者互补，不能只留一个。

## 20.5 第四步：查询与数据范围

留痕表里带着学生姓名与身份证摘要，越权读到同样是泄露。
查询按学生的做法用**物化路径前缀**过滤（这正是表上冗余 `SchoolPathCode` 的原因）：

```csharp
// 按学生 Id 反查会拼出巨大的 IN 条件；存下路径就能像学生表一样用前缀比较过滤
var inScope = scope.IsUnrestricted
              || (hasScopePath && l.SchoolPathCode == scopePathCode)
              || (hasScopeChildPrefix && l.SchoolPathCode != null
                  && l.SchoolPathCode.StartsWith(scopeChildPrefix!));
```

### 学生已经被删除时怎么办

这是**本功能存在的理由**，因此不能因为"查不到学生"就报 404：

```csharp
var student = await _students.FindAsync(studentId);

if (student != null)
{
    // 学生还在：按学生当前的数据范围判断（他的历史记录可能属于已转出的学校）
    await _guard.EnsureInScopeAsync(student);
}
else if (!rows.Any(r => scope.AllowsEntityPath(r.SchoolPathCode)))
{
    // 学生已被删除：退回校验流水上的学校路径，且只要有一条在范围内就放行
    throw new BusinessException(XjglDomainErrorCodes.UserNotInDataScope)
        .WithData("reason", "该学生已删除，其学籍变更流水不在您的数据范围内");
}
```

这个分支是**被自己写的用例逼出来的** —— 见踩坑记录。

## 20.6 验证方法

集成测试（`StudentChangeLogTests`，9 个用例里的关键几条）：

| 用例 | 断言 |
|---|---|
| 新增学生 | 1 条 Create，`NewValue` 含姓名与**学籍辅号**，`OperatorName` 为当前用户 |
| 只改电话与状态 | **恰好 2 条** Update（姓名/学年没变就不写），旧值 `13800000000` → 新值 `13900001111`，状态 `在读（01）` → `休学（02）` |
| 保存时什么都没改 | 0 条 Update（否则流水会被"空保存"淹没） |
| 更换身份证号 | `NewValue` 以"摘要"开头，且**响应里搜不到明文**，新旧摘要不同 |
| 删除学生 | 1 条 Delete，`OldValue` 含姓名与辅号 |
| 外校账号读留痕 | 抛 `UserNotInDataScope` |
| 全局查询 | 只返回本范围内的流水（范围外学生的流水一条都不出现） |

## 20.7 踩坑记录

| 现象 | 根因 | 教训 |
|---|---|---|
| "删除后仍能追溯"的用例直接报 `EntityNotFoundException` | 第一版先调 `StudentAccessGuard.GetInScopeAsync(studentId)`，它按 Id 加载学生 —— 学生被软删后查不到 | 复用现成的守卫很自然，但"守卫的前提是对象存在"与"留痕的前提是对象可能不存在"直接冲突。**写完功能要按"这个功能被发明出来的那个场景"验一遍**，而不是验"常规路径能跑通" |
| 密文比较导致"没改也报改了" | AES 每次加密结果不同（随机 IV） | 比较用 HMAC 摘要，展示用掩码；把"用于比较的值"与"用于展示的值"分开 |
| 日志表里出现身份证明文 | 直接把 `IdCardEncrypted` 解密后写进去 | 留痕里只存摘要前缀；明文一旦落进日志表，删除成本远高于当初不写 |
| 一次修改产生两条互不相关的记录 | 没有批次概念 | 加 `BatchId`，界面才能合并成"一次修改的 N 处变动" |
| 清理脚本/统计算进了已删学生的流水 | 留痕不随学生级联删除（这是**故意的**） | 这是设计而非缺陷，但要在文档里写清楚（见方案文档技术债第 17 条） |

## 20.8 与"字段级留痕"相关的取舍

- **不做"修改前后整行快照"**：那样查起来要自己 diff，且无法按字段检索（"查所有改过学籍状态的记录"）。
- **不做"触发器"式的数据库审计**：审计需要业务语义（哪个字段叫"学籍状态"、码值 `02` 是什么意思），
  数据库触发器给不出这些；而且跨 ORM（EF Core + SqlSugar）时触发器更难维护。
- **留痕接口只读**：能被改的审计日志等于没有审计。
