# 49 H5 与微信小程序：能共享什么、必须分开什么

> 对应代码：`web/apps/h5/`（`vite.config.ts`、`src/router/index.ts`、`src/views/`）、
> `web/e2e/specs/h5-smoke.spec.ts`、`web/e2e/playwright.config.ts`
> 相关文档：第 44 章（工作区结构）、第 45 章（令牌续期）

## 49.1 要解决的问题

教师真正采集照片的场景是**在教室里用手机**，所以 H5 不是"PC 的缩小版"，
它有自己的取舍。本章讲三件事：

1. H5 与 PC **共享什么、必须分开什么**（这是最容易做错的判断）；
2. H5 的三个**移动端特有**的决定（端口、hash 路由、构建目标）；
3. 小程序：为什么**只留口子不实现**。

## 49.2 能共享什么：只有 API 层

先看结论，再看理由：

| 共享 ✅ | 分开 ❌ |
|---|---|
| `@xjgl/api`（请求封装、类型、权限码、端点表） | 路由表 |
| 后端 DTO 的 TypeScript 类型 | 页面组件 |
| 权限码常量 | 布局与导航 |
| 令牌续期的整套逻辑 | UI 状态与交互 |

**为什么路由表必须分开**：PC 是**元数据驱动**的动态路由（第 46 章，
管理员能在"模块管理"里增删模块）；H5 是**固定三个页签**。两者不是"同一张表的不同渲染"，
而是两种不同的产品形态。

**为什么页面组件必须分开**：PC 用 Element Plus 的桌面组件（`el-table`、`el-drawer`），
H5 需要触屏友好的形态。硬套同一套组件的结果是"手机上表格要左右拖、按钮太小点不中"。

```typescript
// apps/h5/src/router/index.ts —— 固定三页签，不做元数据驱动
const routes: RouteRecordRaw[] = [
  { path: '/login', component: () => import('@/views/login/index.vue'), meta: { anonymous: true } },
  {
    path: '/',
    component: () => import('@/layout/TabBar.vue'),
    redirect: '/todo',
    children: [
      { path: 'todo',   name: 'todo',   component: () => import('@/views/todo/index.vue'),   meta: { title: '待办' } },
      { path: 'photo',  name: 'photo',  component: () => import('@/views/photo/index.vue'),  meta: { title: '拍照上传' } },
      { path: 'mine',   name: 'mine',   component: () => import('@/views/mine/index.vue'),   meta: { title: '我的' } }
    ]
  },
  // H5 只有三个页签，其它路径一律回到待办 —— 比给一个 404 页更符合移动端习惯
  { path: '/:pathMatch(.*)*', redirect: '/todo' }
]
```

注意最后那条 catch-all：**移动端不做 404 页，直接回首页**。
手机用户看到"页面不存在"只会困惑，而他的意图几乎总是"打开应用"。

## 49.3 H5 的三个移动端特有决定

### 决定一：端口 5174（与 PC 分开）

```typescript
// apps/h5/vite.config.ts
server: {
  port: 5174,
  host: '127.0.0.1',
  proxy: {
    '/api':     { target: apiTarget, changeOrigin: true },
    '/connect': { target: apiTarget, changeOrigin: true }
  }
}
```

后端的 `CorsOrigins` 本来就配了 5173/5174，所以**两边可以同时跑**，
不需要为了调试移动端而关掉 PC。

### 决定二：`base: './'`（相对路径）+ **hash 路由**

政务系统的 H5 经常挂在**子路径**下（如 `https://xxx.gov.cn/xjgl/h5/`）。
两个配套决定：

```typescript
export default defineConfig({
  base: './',                              // ← 绝对路径 /assets/... 在子路径下会 404
})

// router
export const router = createRouter({
  history: createWebHashHistory(),          // ← .../h5/#/todo
  routes
})
```

**为什么必须是 hash 模式**：history 模式要求 nginx 把 `/xjgl/h5/*` 全部 rewrite 到
`index.html` —— 而现场部署往往不归我们管。漏配一条 rewrite 的表现是
"能打开首页，一刷新就 404"。hash 模式**完全不依赖服务端配置**。
代价是 URL 里多个 `#`，对内部办公系统可以接受。

> 这条有专门的端到端用例守：
> `hash 路由下刷新页面不会 404（这正是选 hash 模式的原因）` ——
> 登录 → 切到"我的" → `page.reload()` → 必须还在"我的"页。

### 决定三：构建目标 `es2015`

```typescript
build: {
  target: 'es2015',    // ← 教师的手机型号很杂，仍有 Android 7/8 的老机器
  rollupOptions: {
    output: {
      manualChunks: { vue: [...], element: [...] }   // 切分以利用长期缓存
    }
  }
}
```

默认的 `esnext` 目标会让老 WebView **直接白屏** —— 而这类问题
**在开发机上永远看不到**（开发机是新版 Chrome）。

`manualChunks` 的理由在移动端更明显：不切分时整个应用是一个 1.4MB 的 `index.js`，
在农村 4G 上首屏要等好几秒；切分后 vue 与 element-plus 可以长期缓存，
业务代码改动只让用户重下几十 KB。

> ⚠ 注释里也诚实写了：这**没有**解决首屏体积本身（完整 Element Plus 约 1MB）。
> 真要压下去得改成按需引入（`unplugin-vue-components`），那会动构建链，留作后续优化。

## 49.4 H5 的端到端测试：为什么必须是独立项目

`playwright.config.ts` 里两个项目**互相 `testIgnore`**：

```typescript
projects: [
  {
    name: 'chromium',
    testIgnore: /h5-.*\.spec\.ts$/,                 // PC 项目不跑 H5 的用例
    use: { ...devices['Desktop Chrome'], baseURL: WEB_URL }
  },
  {
    name: 'h5',
    testMatch: /h5-.*\.spec\.ts$/,                  // H5 项目只跑 H5 的用例
    use: { ...devices['Pixel 5'], baseURL: H5_URL } // 移动视口 + 触屏 + 移动 UA
  }
]
```

而且要**多起一个 webServer**（H5 是另一个 Vite 应用）：

```typescript
webServer: [
  { /* 后端 Host */ },
  { command: 'pnpm --filter @xjgl/pc dev', url: WEB_URL, ... },
  { command: 'pnpm --filter @xjgl/h5 dev', url: H5_URL, ... }  // ← 缺这条会"连接被拒绝"
]
```

**为什么不能"在 PC 项目里顺便跑一下 H5"**：登录页字段都不同
（PC 是"请输入用户名"，H5 是"用户名 / 手机号"），
拿 PC 的 spec 去跑必然全红，而那种红只会制造噪音。

### H5 用例里最有价值的一条断言：横向溢出探针

移动端最典型的布局缺陷是"某个元素比屏幕宽"，表现是页面能左右拖动、右侧内容被裁掉。
**桌面宽度下永远不会出现**，所以只能在移动视口里断言：

```typescript
const overflow = await page.evaluate(
  () => document.documentElement.scrollWidth - document.documentElement.clientWidth
)

expect(overflow, `「${label}」页在 ${page.viewportSize()?.width}px 宽下有横向溢出`).toBeLessThanOrEqual(1)
```

这条断言成本极低（一行 `evaluate`），却能拦住一整类只在手机上出现的问题。

## 49.5 微信小程序：为什么只留口子不实现

本项目的 `SsoConstants` 里已经预留了小程序登录的授权类型常量：

```csharp
/// <summary>
/// 微信小程序的令牌端点授权类型。
///
/// 【为什么现在只留常量不实现】
/// 小程序拿不到浏览器会话，它走的是「wx.login 拿 code → 后端换 openid → 换令牌」，
/// 与本系统现在的密码模式/授权码模式都不同。
/// </summary>
public const string WeChatMiniProgramGrantType = "urn:wechat:miniprogram";
```

**为什么这个口子值得留**：`OpenIddictDataSeedContributor` 的授权类型处理
有一个 `default` 分支，会为**自定义授权类型**自动补上
`Permissions.Prefixes.GrantType + "{值}"`。所以将来接小程序时只需要：

1. 在 DbMigrator 的 appsettings 里加一个客户端，`GrantTypes` 写这个值；
2. 实现一个对应的令牌端点处理器。

**不需要改种子框架**。这是"把扩展点预留在数据/协议层"而不是
"预留一个空方法"的典型做法 —— 后者往往会因为假设不对而全部重写。

不实现的原因很实际：小程序需要**企业主体认证 + 审核**，
而且它的用户群（教师）与本系统现有的激活流程（第 17 章）重叠，
在需求明确之前实现等于替业务方做决定。

## 49.6 怎么验证

```powershell
cd web
$env:E2E_API_URL = 'http://127.0.0.1:44300'

# 只跑 H5 项目（会自动拉起 5174 的 dev server）
pnpm test:e2e --project=h5

# 两个项目都跑（PC + H5，共 46 条）
pnpm test:e2e
```

手工看一眼移动端形态（比断言更直观）：

```powershell
pnpm dev:h5
# 浏览器打开 http://127.0.0.1:5174/ ，F12 切到手机模拟视图
```

## 49.7 本章要点

1. 三端只共享 **API 层**（请求封装 / 类型 / 权限码 / 端点表）；路由与页面必须分开。
2. H5 用 **hash 路由 + `base: './'`**：子路径部署下"刷新即 404"与"资源 404"都不依赖服务端配置。
3. 构建目标降到 **`es2015`**：老安卓 WebView 白屏只在真机上暴露。
4. H5 的端到端必须是**独立 Playwright 项目**（移动视口）+ **独立 webServer**；
   两个项目互相 `testIgnore`。
5. **横向溢出探针**是移动端性价比最高的断言。
6. 小程序只留**协议层扩展点**（授权类型常量），不实现；
   将来只需加客户端配置 + 一个令牌处理器。
